# B13 + B14: location and geofences, summaries and live KPI tiles

## Summary

B13 gives records a place on the map. `@hykr/db` adds a PostGIS `geography` point column
(`geoPoint`), its GiST index (`geoIndex`) and an address column (`addressColumn`); PostGIS is
enabled by an idempotent SQL hook. Points travel as `GeoPoint = { lat, lng }`. The list grammar
gains a `geo` field type with `near` (within a radius, `ST_DWithin`) and `within` (a bounding
box), and a geo field in `sortable` sorts by distance to its `near` point, with keyset cursors.
`withinMeters(conn, at, center, radiusM)` is the geofence check a command runs in its `load`
(PostGIS, the same spheroid as `near`). The app gets `features/location`: the device's position
with its accuracy, the device geocoder, and `<LocationField>`. The sample's meetings keep an
address and a point, list "near me" sorted by distance, and take people's check-ins only within
the module's radius.

B14 gives every entity a summary: counts, sums, averages, minimums and maximums, grouped by up
to two fields (dates by day, week, month, quarter or year in the business's time zone), under
exactly the list's scope and filters, and never over a field the reader cannot see.
`GET /api/<plural>/summary`, `api.entity(spec).summary(q)`, `useEntitySummary`, an agent tool
`summarize-<plural>`, a view source `by: 'summary'`, and `kpi.row` tiles computed from a summary
(`of`) instead of numbers the assistant typed, so a saved page recomputes them for whoever opens
it. The sample's orders screen shows order totals by status and by month this way.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | A point is stored in a PostGIS `geography` column through a drizzle `customType` (`geoPoint(name)` in `@hykr/db`). Plain `geography`, not `geography(Point,4326)`: drizzle-kit 0.31 quotes a custom type with a modifier as one identifier, which Postgres refuses, so the table does not narrow the column to points; every write goes through `pointSql` (a point, SRID 4326) and a read throws on anything else. Written as `ST_SetSRID(ST_MakePoint(lng, lat), 4326)::geography`, read from the driver's hex EWKB into `{ lat, lng }`. The JSON shape is `GeoPoint` (`@hykr/contracts`, WGS84 degrees, lat −90..90, lng −180..180). Because the column already reads and writes `{ lat, lng }`, no entity plugin is needed: lists, gets, events and audit carry the object. | Plan B13 ("Geography custom type + GiST index"); gap map (drizzle 0.45 has no geography type). |
| 2 | `geoIndex(name, column)` is a GiST index (`index(name).using('gist', column)`); `near` and `within` are written so it can be used (`ST_DWithin`, `ST_Intersects` on geography). | Plan B13. |
| 3 | PostGIS is enabled by `framework/db/sql/pre/10-postgis.sql`, a `DO` block that creates the extension only when `pg_extension` lacks it, so a database where an administrator installed it needs no privilege. Where it is missing and the role may not create it, the migrate fails with Postgres's own message. `init.sql` keeps creating it for Compose. | Plan ("Extensions … go in the sql/pre hooks"); gap map risk (CREATE EXTENSION needs a superuser). Fail closed. |
| 4 | Every drizzle config that sees `public` or `app` sets `extensionsFilters: ['postgis']` (framework, application, fixture), so drizzle-kit never treats `spatial_ref_sys` as a table to manage. | Gap map B13. |
| 5 | List field type `geo` (contracts `framework/geo.ts`, SQL in core `query/geo.ts`): operators `near: { lat, lng, radiusM }` (0 < radiusM ≤ 20,000 km) and `within: { south, west, north, east }` (south ≤ north, west ≤ east; a box across the antimeridian is refused). No `eq`. Query string forms `location[near]=12.97,77.59,500` and `location[within]=12.9,77.5,13.1,77.7`; JSON forms are objects. `toQueryString` now JSON-encodes an object operator value, which the `geo` type also reads. | Plan B13 ("near/within list filters"); F3 decision 29 (object values). |
| 6 | A `geo` field in `sortable` sorts by distance to the point of its `near` filter (`sort=location`, `-location` for farthest first); without a `near` filter it is a 400 `sort_needs_near`. The keyset cursor keeps the row's point and compares distances computed by PostGIS on both sides, so pages never skip or repeat; rows without a point sort last. `ListFieldSql` gains an optional `order` hook for this, usable by any added type. | Plan B13 ("distance sort"). |
| 7 | `withinMeters(conn, at, center, radiusM)` → `{ inside, distanceM }` and `metersBetween(conn, a, b)` (`@hykr/core`) measure with PostGIS on the WGS84 spheroid, like `near`. A command runs them in `load` (which has the transaction) and decides in `authorize`. `distanceMeters(a, b)` (contracts, haversine) is for clients to show a distance, never to decide. | Gap map ("a withinMeters helper for command load/authorize"). |
| 8 | Addresses: `Address` (`line1`, optional `line2`, `locality`, `region`, `postalCode`, `country` as ISO 3166-1 alpha-2) and `addressText(a)` in contracts; `addressColumn(name)` (jsonb) in `@hykr/db`. A record keeps its coordinates beside it in a `geoPoint` column, so the point is indexed and filterable. No server-side geocoding (it would need an outside provider): the app geocodes on the device. | Gap ("addresses with coordinates"); task rule (no stubs beyond the named interfaces). |
| 9 | App `features/location`: `currentLocation({ accuracy })` asks for foreground permission and returns `{ point, accuracyM }`; `addressOf(point)` and `pointOf(address)` use the device's geocoder (null on the web, where Expo has none); `useCurrentLocation()`; `<LocationField>` with "Use my location", the address it finds, and clearing. The sample app adds the `expo-location` config plugin and its permission text in `app.json`. | Plan B13 ("app/features/location"); F6 decision 26. |
| 10 | A device's position and accuracy are what the person sends: the framework does not trust or correct them. The sample refuses a fix less precise than its radius, and keeps each check-in's point, distance and accuracy as evidence. GPS spoofing stays possible and is logged as a limit. | Gap map risk ("GPS spoofing makes a geofence weak evidence"). Fail closed on imprecise fixes. |
| 11 | Summary grammar (`@hykr/contracts`, `framework/summary.ts`): the list's filters and `q`, `groupBy` (at most 2; a date field needs a bucket, `createdAt:month`), `sum`, `avg`, `min`, `max` (lists of fields, at most 6 measures), `sort` (`count`, `key`, `<fn>:<field>`; `-` for descending; default key ascending, nulls last), `limit` on groups (default 50, max 200). The count is always there. `summaryInputSchema` (JSON) and `summaryQuerySchema` (query string, comma lists). | Plan B14 ("group-by, sum, count"); gap map ("a ListConfig aggregate declaration"). |
| 12 | What a field can do in a summary comes from its list field type (`ListFieldType.summary`): `enum`, `id`, `boolean` and `text` group by value, `date` groups by bucket, `number` and `money` are measured. A field must be filterable to be summarized: the list config is the declaration, so no spec changes. A type a feature adds opts in with its own `summary`. | Default: no new config to keep in step; the list config already lists the indexed, public fields. |
| 13 | Result: `{ groups, totals, more }`; a bucket is `{ key, count, sum?, avg?, min?, max? }`. Number measures are numbers (an average a float). Money measures are `Money`: the record's currency joins every key, and `totals` has one bucket per currency, so amounts in two currencies are never added. A money average is rounded half up to whole minor units. No rows: one zero bucket in `totals`, measures null. `more` says groups were cut at `limit`. | B3B5 decision 2 (one currency per record); fail closed on mixed currencies. |
| 14 | Dates bucket in the business's time zone (tenant `timeZone`). Keys are text: `2026-11-06` (day), the Monday of the week (ISO), `2026-11`, `2026-Q4`, `2026`. | Gap map B3 risk (periods in the tenant's zone). |
| 15 | Scope: a summary covers exactly the rows its list would: the business, the reader's grants, every plugin's `scope`, then the filters. It takes that WHERE from the entity's own `repo.list`, run against a connection that records the query instead of sending it. `define-entity.ts` is a hot file this unit is not listed for (F3 → B19 → B12); the recorder fails closed (500) if the list's query shape ever changes. | Plan hot-file table; gap map risk ("Under 'own' grants, dashboards come out per person"). |
| 16 | Field hiding: every field a summary names (filters, groups, measures, the search columns when `q` is given, the currency field for money) must be in the reader's projection of a record. The check reads one record of the reader's scope **without the filters** through `toRead` (plugins' `project`, read projectors, and A4's field-policy plugin once it lands, which removes hidden fields in `project`), so a refusal is not an oracle on hidden values. A hidden field is a 403 `{ rule: 'field_hidden' }`, before any number is computed. No record in reach: zeros, which reveal nothing. Projection is assumed to depend on the reader, not on the record. This branch was first built on A4 and also checked A4's declared policy and its plugins' `query` hook; feat/platform-gaps then backed A4 out, so those two checks wait for A4 (Deferred). | Plan B14 ("respects field policy"); gap map risk (a sum of a hidden margin). Fail closed. |
| 17 | `GET /api/<plural>/summary` follows the list's `expose`: `internal` has no route, `human` is people only, an agent on a non-`all` list is refused `humans_only`. It is declared before `GET /:id`, so `summary` is never read as an id. No catalog route change: the only route it overlaps is the same entity's `/:id`. | Plan B14. |
| 18 | The agent's `summarize-<plural>` tool exists for every entity whose list is exposed to the agent (`entityToolIds` adds it, so ids are checked for collisions). Its input is strict, with `groupBy` and the measures as enums of the allowed fields; its description says it counts and totals and is not a written summary. When the result fits in four tiles it shows a `kpi.row` with `of` (computed again on the client), so its numbers are never the model's. `kpi.row` gains the `inline` surface for this: before, it was canvas, text and speech only, so a tool's tiles were dropped in the chat. | Plan B14 ("a summarize tool"); gap map risk ("Agent-supplied kpi.row numbers can be hallucinated"). |
| 19 | `kpi.row` takes `items` (numbers the assistant already has) or `of: { entity, query, labels? }`: a summary of an entity (by plural), computed with the reader's own session wherever the row is shown: the chat, a saved page, WhatsApp text and speech. Tiles are the groups (label the key, value the first measure, else the count; at most four) or, without `groupBy`, the count and each measure. `labels` renames a tile by its key or measure (`open`, `count`, `sum:total`). On the server the registry checks `of` against that entity's summary grammar; a saved page keeps the query, never the numbers. | Plan B14 ("kpi.row from aggregate queries"); gap map ("an optional source on kpi.row so saved pages recompute"). |
| 20 | Views get two hooks in `defineView`: `check(props, ctx)` (more checks than the props schema, with the registry's entities) and `load(props, io)` (data a view fetches for itself when the server puts it into words; `kpi.row` resolves `of` with it). | 21 | A view source may be `by: 'summary'`: the client fills `props[into]` with the entity's summary for the view's query (checked against the summary grammar), and the server does the same to put it into words. | Plan B14 ("aggregate sources in define-view/validate"). |

## Assumptions to review

- **Check-in radius.** The sample allows check-in within 200 m of the meeting's point, and only
  with a fix at least as precise. Which radius do sites need, and should it be per site, per
  business (a setting) or per record?
- **Accuracy.** A fix less precise than the radius is refused rather than accepted with a
  warning. Is that too strict for weak signal indoors?
- **Location as personal data.** Check-ins keep the person's point. Retention, consent text and
  erasure of check-ins belong to B18 (privacy); nothing deletes them yet. Is a privacy notice in
  the app enough for the pilot?
- **Continuous tracking.** Only point-in-time check-ins exist. Is tracking during a visit wanted?
- **No server geocoding.** Addresses are typed or found by the phone's geocoder; the server
  never calls a geocoding service. Is a server geocoder (and which provider) needed?
- **PostGIS on managed Postgres.** The hook needs PostGIS installed, or a role that may create
  it. Will production run on a provider that offers PostGIS?
- **Projection per reader.** The field-hiding check assumes a projector hides a field from a
  reader on every record alike (A4's field policy does: it goes by capability). A projector that
  hides a field on some records only would let a summary over that field through. Is any such
  rule planned?
- **Filters on hidden places.** Until A4 lands, nothing refuses a list filter on a field a
  projector hides, so someone who cannot see a record's point could still find it with
  `location[near]`. A4's field-policy `query` hook refuses filters on hidden fields for every type,
  `geo` included. Is a place sensitive enough to hide before then?
- **kpi.row in the chat.** `kpi.row` now shows inline in the app's chat (it was canvas, text and
  speech only), so the summarize tool's tiles appear under the answer. Is that the wanted look?
- **One summary tool per entity.** Every entity whose list the assistant may call gets a
  `summarize-<plural>` tool. With many entities, should the assistant get one generic tool, or
  per-module tools (A1)?
- **Groups and buckets.** At most two group fields and 200 groups; weeks start on Monday (ISO);
  months, quarters and years are calendar ones in the business's time zone. Are fiscal quarters
  (from `fyStartMonth`) wanted?
- **Summaries over filterable fields only.** A field is summarized only if it is filterable.
  Should a spec be able to allow or forbid summaries separately?
- **Staff see their own.** Under `own` grants a staff member's summary covers only their rows,
  like their lists. Should owners give staff business-wide numbers without their rows?

  also refuse fields A4's declared policy hides (exact for every record, and with no record in
  reach) and run every entity plugin's `query` hook with the summary as a list query naming the
  grouped and measured fields. The branch had both before feat/platform-gaps backed A4 out:

  ```ts
  const policyHidden = new Set(hiddenFields(fieldPolicyOf(spec), p));

  if (declared) throw refuse(declared);
  const asList: ListQuery = { filters: q.filters, q: q.q, limit: 1, count: false,
    sort: named.map((field) => ({ field, dir: 'asc' })) };
  for (const x of def.plugins()) x.query?.(asList, p, { spec, table: def.table });
  ```
