# V13: words acceptance found: a lookup shown as the answer, meters named by their label, one alert per crossing

## Summary

The acceptance run on the merged branch found three low-severity defects. All three are words
people read.

- **A lookup was shown as the answer.** A staff member asked on WhatsApp for an order over the
  limit. The reply read "I've asked the team for approval: Save a new order ... Nothing changes
  until they decide." and then "No orders.". The orders script looks before it writes
  (`list-orders` with the title, then `save-order`), and every view a turn's calls returned was
  shown. The root is the framework, not the sample's script. Any script, and any live model,
  that reads before it writes shows the list it read. The fixture's "delete <task>" showed it
  too, and so did the sample's meeting close and every `list-*` before an update. The rule now:
  a read whose view comes before a write in the same turn is a lookup, and no channel shows it.
  WhatsApp words nothing of it, the app hides its view, and the saved thread keeps none. A read
  with no write after it is the answer, and shows.
- **A meter limit's refusal named the internal meter.** The 402 body and `GET /api/credits` read
  "This business has used 2 of its 1 calls of tool_calls this period". A refusal now names the
  meter as people call it, in the reader's language: "Assistant actions: this period's limit is
  reached" (hi: "असिस्टेंट के काम: इस अवधि की सीमा पूरी हो गई"). A module's meter declares its
  `label` (Labels). The framework's meters use its own phrases (`credits.meter.*`, which the
  credits screen already used).
- **One use past a limit sent "low" together with "limit reached".** One use crossed both levels
  of a cap (a limit of 1, a long voice session). It stored both levels and sent both events: the
  sample's "Voice minutes: 3000% of the limit used" alert beside the pause. Now only the pause is
  said. The alert's row is still stored, so "low" is not said after the pause either.

V11 (gap/V11, merging first) changes the same feature. It stops a limit that pauses nothing (the
`messages` limit with no paused kind) from raising a level or reporting a refusal (`limitStops`
in `assess` and `limitRefusal`, `MeterDef.pausesSome`). It changes neither the words of a reason
nor how many events one crossing sends. So none of the three was fixed there, and this unit
builds on it. `git merge-tree --write-tree gap/V13 gap/V11` merges with no conflict.

## Decisions

| # | Decision | Source |

| 1 | The lookup is fixed in the framework, not in the orders script. It is the framework's rendering, and a script cannot ask for a call's view to be left out. | 2 | **The rule** (`lookupsIn` in `@hykr/contracts`, chat.ts). A call is a lookup when three things hold: its output shows a view (a present of kind `inline` or `text`), it is not a write, and a later call in the same turn is a write. A write is known by its result's shape (`wroteIn`): `done` with a `value`; `needs_approval` with an `approval`; or a resumed run's decision (`approved`, `rejected`, `expired`, `failed`) with an `approval`. A read's record can carry a `status` of its own (an order is `approved`, a job `done`), so the status alone does not decide. | Default (the result shapes are `WriteResult` and `decisionOutcome`). |

## Assumptions to review

- **Lookups are found by their place, not their purpose.** A read before a write is taken to be
  how the assistant found what to write. "Show order 12 and submit it" now shows only the
  submit. Is that right, or should a read the person asked for by name survive a later write?
- **A refused write leaves the lookup shown** (decision 9). Hiding it would need tools to mark
  a refusal as a write's (the HTTP method on `ApiError`). Is that worth it?
- **No numbers in a limit's reason** (decision 11). The status and the screen carry the
  quantities. Should the reason say "(2 of 1)" in the meter's display unit?
- **An agent's 402 is in English.** An agent's call carries no language, so the guard cannot
  word it for the person. The turn's own sentence (`EndWhenPaused`) is in the turn's language.
- **No alert after the pause is lifted by a higher limit** (decision 16).

## The same class, searched

- Every script that reads before it writes. In the framework: `fake/scripts/states.ts`
  (`list-<plural>` before a transition), `agents.ts`, `pages.ts`, `comments.ts`, `documents.ts`
  and `jobs.ts`. In the sample: todos (done, delete), meetings (close, move, invite,
  follow-up), orders (save, transition, revise, PDF, send) and briefs. In the fixture: delete.
  All of these are covered by decision 4, with no change to any script.
- Every place a turn's tool results become what a channel shows: `summarize` and `partsOf` in
  `chat.service.ts`, `partsOf` in `resume/parts.ts` (a second copy, fixed too), `toRenderTurn`
  (reads `toolCalls`), `ToolPart` (the app), and the voice worker's parts (the app's
  `ToolPart`).
- Every refusal reason the credits word: the limit, the budget, the operator's pause and the
  unreadable settings (`unavailable`), each a phrase in three languages now.
- Everywhere a meter reaches people: the 402 reason, `GET /api/credits` (`paused`,
  `meters[].refusal`, `meters[].label`), the operator's status, the credits screen and the
  sample's alerts (the event's `label`). The back office's operator usage report still lists
  `m.meter` (see Leads).
- Every announcement of a level: `announce` is the only place that sends one, both on use
  (`record`) and on reconcile (plan, top-up, sweep).

## Leads checked

- **The orders script.** It is the framework (decision 1). The script's own wording ("I've
  asked the team ...") was right.
- **Golden WhatsApp conversations and eval cases.** None asserts a lookup's view. 02's "add"
  writes without looking, and 04 deletes through the API. The evals score tools and replies,
  not views. None changed. The golden conversations skip in a worktree (`WHALOC_TEST_URL`
  unreachable), so they were read, not run.
- **An asked-for list on WhatsApp repeats its rows.** "list orders" with one order says the
  order in the reply and again in the view's words. With none, "You have no orders." is followed
  by "No orders.". The orders script writes the rows out when it is not spoken. This is a
  different class (a reply that repeats its view, not a lookup) and is left as a lead for the
  sample.
- **The operator's usage report** (`framework/back-office/src/screens/OperatorScreen.tsx`) lists
  meters by name (`tool_calls 12`). It is an operator's view of the platform report, which
  carries no label. Left as a lead.

## API sketch

```ts
// @hykr/contracts (chat.ts)
wroteIn(output: unknown): boolean            // a write's result: done, waiting, decided
lookupsIn(outputs: readonly unknown[]): Set<number>   // reads with a view before a write

// @hykr/api (credits)
defineMeter({ name: 'report_pages', unit: 'page',
  label: { en: 'Report pages', hi: 'रिपोर्ट पेज', te: 'రిపోర్ట్ పేజీలు' } });
meterLabel(meter, lang): string;  meterLabels(meter): Labels;
refusalFor(a, meter, variant?, lang = 'en'); limitRefusal(a, meter, lang = 'en');
turnRefusal(a, lang = 'en');
metering()?.check({ tenantId, meter, variant?, lang? });

// HTTP
GET /api/credits?lang=hi                     // meters[].label, paused.reason in Hindi
GET /api/credits/operator/:tenantId?lang=te

// contracts: MeterStatus.label: string; CreditsThresholdRow.label?: Labels
// api-client: api.credits.status(lang?)
```

## Test plan

Each test below failed on the code before its fix. The new tests are in new files, apart from
V11's.

- `framework/api/test/framework/lookups.test.ts` (no database): `wroteIn` knows a done, parked
  or decided write from a read's record whatever its `status`. `lookupsIn` takes a read with a
  view before a done, parked or decided write. It leaves a lone read, two reads, a read after the
  write, a write's own view, a canvas and a read before a refusal. It failed first, because the
  functions did not exist.
- `framework/api/test/framework/lookups.e2e.test.ts` (fixture). "delete Buy milk" in words:
  `list-tasks` has no `present`, `toRenderTurn(...).views` is empty, and the saved part has no

  keeps the list. It failed first: `list-tasks` carried its `present`.
