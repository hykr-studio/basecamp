# F2: application modules, app side

## Summary

The Expo app is composed from **app modules**, the app-side half of an application module.
`defineAppModule({ name, nav, suggestions, bind, hrefFor, webmcp, plugins })` declares one;
`<AppShell app modules plugins catalog registry config />` merges them, checks every merge for
collisions at startup (a collision throws), binds each module's components, and gives framework
features **plugin slots**: a provider wrapper, an on-signed-in effect, extra routes (public or
not), destinations and a nav filter. `bindView` and `bindScreen` throw on a duplicate name.
Records link to their screen through one merged `hrefFor`. The `Register` declaration types the
app's hooks from one catalog or from several modules' entity maps.

The sample app (`application/mobile`) is split into `src/modules/{meetings,notes,todos}/`, with
thin route files under `src/app/<module>/`. URLs are unchanged. The home screen (Today) stays the
application's own. The back office is not changed.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | `defineAppModule({ name, order?, nav?, suggestions?, bind?, hrefFor?, webmcp?, plugins? })` in `@hykr/app` (`framework/app/src/framework/app-domain.ts`). It checks the name and the nav prefix, and records the module so the shell can refuse objects that were not made with it. | Plan, "Module system" (F2) and the F2 row. `order` and `plugins` are defaults: see 5 and 11. |
| 2 | `AppShell` takes `app` (the application's own settings: `title`, `tagline`, `home`, and the `nav`, `suggestions` and `webmcp` of its own screens), `modules`, `plugins`, `catalog`, `registry` and `config`. The variant that took raw `domain` and `views` is removed. The application builds `catalog` and `registry` itself, so the shell does not depend on how `createCatalog` merges modules. | Plan "Compat: break freely". The task notes: coordinate with F1 only through aggregate exports. F1 owns `createCatalog` and `createUiRegistry`. |
| 3 | The home screen and anything that combines several modules belong to the application (`app.nav`, `app.suggestions`, `src/home/`), not to a module. | Gap map MOD-app, risk "the home screen ... must stay owned by the application". |
| 4 | Merge order of destinations and suggestions: the application's, then the modules', then the plugins', then the framework's (Pages). | Default. It keeps today's order (Today first, Pages last). |
| 5 | Modules are ordered by `order` (default 0), then by their position in `modules`. When `modules` is an object (a namespace import of the barrel), they are first sorted by key, because bundlers do not agree on the key order of a namespace. | Default. The barrel `application/mobile/src/modules/index.ts` is one line per module (`merge=union` in `.gitattributes`), so the list cannot be one array. |
| 6 | One validation pass when the shell installs, each failure a thrown error naming both sides: module names unique, lower case (`/^[a-z][a-z0-9-]*$/`) and not `pages`; a module's destinations under `/<name>`; nav hrefs unique; suggestion texts unique; each `hrefFor` record type claimed once and known to the catalog; each WebMCP screen claimed once, with entities known to the catalog; plugin names unique; plugin routes well formed, unique, and not under a module's or the framework's prefix; every module made with `defineAppModule`. | Plan "Duplicate bindView and bindScreen calls throw"; gap map MOD cross-cutting ("silent overwrite is the dominant failure mode"). Fail closed. |
| 7 | A module's routes live under its own prefix, `src/app/<name>/` and `/<name>/...`, so two modules never claim one URL. | Plan "thin route files under `src/app/<module>/`"; gap map MOD-app risk on route groups both claiming `/`. |
| 8 | `bindView` and `bindScreen` throw when a name is already bound. The message names who bound it (`bindingAs(owner, fn)`; the shell binds as `framework` and as each module's name). `clearBindings()` empties both maps; the shell calls it before binding again (Fast Refresh). After binding, a bound view or screen that is not in the registry throws too: the assistant could never show it. | Plan. The registry check is a default (a view left out of `uiDomain` fails at startup instead of silently). |
| 9 | `hrefFor` is a record per module, keyed by record type (the audited entity name): `{ meeting: (id) => '/meetings/' + id }`. The framework adds `page`. `hrefFor(type, id)` from `@hykr/app` reads the merged map. `AssistantActivity` uses it; its `hrefFor` prop is removed. | Plan "a merged `hrefFor`"; gap map MOD-app extension point. A record, rather than a function per module, makes a collision detectable. |
| 10 | `webmcp` is declarative only: `{ [screen]: { reads: EntityName[] } }`, keyed by the screen's `useScreenContext` name. `webMcpFor(screen)` returns the merged entry and its module. Registering tools with `navigator.modelContext` is A2's. `WebMcpScreen` is an open interface, so A2 can add keys (actions later). | PRD Platform & AI 7.1, "WebMCP: read-only tools per screen behind feature detection". Gap A2 (`A2←F2`). |
| 11 | Plugins (`AppPlugin`) are how framework features plug into the shell. They come from `AppShell plugins` and from modules' `plugins`. Slots: `Provider`, `onSignedIn`, `routes`, `nav`, `useNav`. | Task notes: "plugin slots (provider wrapper, on-signed-in effect, extra routes, nav filter)". Plan "plugin slots for provider, route and nav filter". |
| 12 | `Provider` wraps everything under the shell's own providers (data, toasts, language, assistant), signed in or not. The first plugin is outermost. | Default. A9 (push) and A2 (WebMCP) need data and the assistant context; B9's public screens need the providers too. |
| 13 | `onSignedIn(user)` runs once per signed-in person, after the shell mounts. Its cleanup runs at sign-out, when the person changes, and when the shell installs again (before the new plugins sign in). A throw or a rejected promise is logged with the plugin's name, never thrown into the app, and the other plugins still run. `SignedIn` (in `framework/plugins.ts`) runs them: the shell renders it, keyed by installation, as the one child of `ChatRuntime`, with the shell inside it, so the two always mount and unmount together. Fix round 1: they were two siblings with the same key, so a new installation replaced the effects without unmounting them (their cleanups never ran) and React logged a duplicate-key error on every render. | Default. A push registration that fails must not take the app down. It decides no access, so logging does not weaken a rule. |
| 14 | `routes` are screens at paths no route file claims (`/approvals/:id`). The application's `+not-found.tsx` serves them: `NotFoundScreen` renders the matching plugin route before saying "not found". Paths are fixed segments and `:params`. A route marked `public` also renders when nobody is signed in, alone, without the navigation or the thread. Everything else still needs a session. | Default. Expo Router builds routes from files only, so a library cannot add a route file. B9 (public route gate) and A1 (`/approvals/:id` app route) build on it. Fail closed: public only when the route says so, and the API still decides what it may load. |
| 15 | `useNav(items)` is a hook (it may read feature flags or roles through React Query). Filters run in plugin order. A filter may hide or reorder destinations, never add one: items it returns that were not given to it are dropped. Destinations are added only through `nav`, where they are checked for collisions. Each merged destination carries `module` (or none for the application's and framework's), so a filter can hide a whole module. | Default. A11 (per-studio flags gating nav, failing closed) and A4 (roles). PRD Overview: "Modules and agents ship behind per-studio feature flags that fail closed". |
| 16 | The shell installs again only when `app`, `catalog`, `registry`, or the members of `modules` or `plugins` change (the lists are compared item by item, so an inline array does not reinstall on every render). A new installation remounts the shell and its sign-in effects (one keyed `SignedIn` around the shell, see 13), so plugin hooks never change order inside one mounted shell. | Default (React's rules of hooks; Fast Refresh). |
| 17 | `Register` stays the one typing seam. It takes `{ catalog: typeof catalog }` as before, or `{ modules: typeof modules }`: a list of isomorphic module specs (`ModuleSpec`), whose entity maps are intersected (`MergedEntities`). `CatalogOf<R>` does the resolution. The sample registers its catalog until F1's module specs land. | Plan "typed `Register` over the merged catalog"; gap map MOD-app. The `modules` form does not depend on how F1 types `createCatalog(...modules)`. |
| 18 | Sample layout: `src/modules/<m>/index.ts` (the module and the components other code may use), `routes.tsx` (the route components), `views.tsx` (view components), `screens/`, `components/`. `src/modules/index.ts` lists the modules, one line each. `src/app/<m>/...` are one-line re-exports. Today lives in `src/home/Today.tsx`. `src/app.ts` holds the application's settings and `src/catalog.ts` the catalog, the registry and the `Register` declaration. | Plan Decisions, "Modules": app side `application/mobile/src/modules/<name>/`, thin route files under `src/app/<module>/`. |
| 19 | A module reaches another module only through that module's `index.ts`. Meetings uses the notes and to-do rows (meetings → notes, todos, the same direction as the server's close-meeting). The to-do row links to its meeting through `hrefFor('meeting', id)` and reads it by entity name, so to-dos import nothing from meetings. | Plan "Boundaries": a module imports another only through its public entry, with no cycles. |
| 20 | App module names equal the server modules' names (`meetings`, `notes`, `todos`). The app imports the domain only through the aggregate entries `@application/domain/contracts` and `@application/domain/views`. | Task notes (coordinate with F1 through aggregate exports). Plan "Demo". |
| 21 | The back office is not changed. It is not domain-aware. | Gap map MOD-app ("no change is needed unless modules want staff screens"); task notes ("only if trivial"). |
| 22 | Tests for the app side run in `@hykr/app` with Vitest, on the parts that need no React Native: composition, validation, route matching and the plugin glue. A second tsconfig (`tsconfig.test.json`) typechecks the tests, including type-level checks of `Register`. `@hykr/ui-registry` tests the binding rules. `SignedIn` is rendered by React's real reconciler (`react-dom/client`, a dev dependency at the workspace's pinned 19.2.3) into a bare container object, because the repo has no DOM library and its components render no elements. `@types/react-dom` is not added: it re-keys the peers of most React packages in the lockfile, so the test types the two calls it uses. | Default. `@hykr/app` had no unit tests; the fixture app (`framework/api/test/fixture`) is server-only. The render test is from fix round 1 (no test rendered the shell's signed-in tree). |

## Assumptions to review

- **One URL prefix per module.** A module's destinations must sit under `/<name>`. Should one
  module own several top-level prefixes (a `win` module with `/leads` and `/quotes`), or should
  such a module be split?
- **Home and dashboards.** The application owns the home screen and any screen that combines
  modules. Who owns studio dashboards that mix modules (a Morning Brief): the application, or a
  dedicated module that depends on the others?
- **Public routes.** A `public` plugin route renders signed out, without the shell; signed in,
  it renders inside the shell. Should a signed-in member opening a share link see it bare, as a
  homeowner would?
- **Nav filters hide only.** A filter can hide or reorder destinations, never add one. Is that
  enough for feature flags and roles, or must a flag also add a destination?
- **Plugin failures are quiet.** An `onSignedIn` error is logged, not shown. Should a failing
  plugin (push registration, offline sync) tell the person?
- **WebMCP key.** WebMCP tools are declared per screen context name (`useScreenContext({ screen })`).
  Is the screen context name the right key, or should tools hang off route paths?
- **Module order.** Destinations follow `order`, then the modules' list. Is a number enough, or
  should the application list its modules' order in one place?
- **Back office.** It stays framework-only. Do modules need staff screens there?
- **Cross-module rows.** The meetings screen uses the notes and to-dos rows. Is that coupling
  acceptable, or should a module offer views only through the registry?

## API sketch

```ts
// @hykr/app
type NavItem = { href: string; label: string; icon: IconName; match: (path: string) => boolean;
  readonly module?: string }                                     // set by the merge
type Suggestion = { text: string; what: string; readonly module?: string }
interface WebMcpScreen { reads: readonly EntityName[] }          // open: A2 adds keys

interface AppSettings {                                          // the application's own
  title: string; tagline: string; home?: { href: string; label: string };
  nav?: readonly NavItem[]; suggestions?: readonly Suggestion[];
  webmcp?: Readonly<Record<string, WebMcpScreen>>;
}

interface AppModule {
  name: string;                                                  // 'meetings': routes under /meetings
  order?: number;                                                // nav position, default 0
  nav?: readonly NavItem[];                                      // hrefs under /<name>
  suggestions?: readonly Suggestion[];
  bind?: () => void;                                             // bindView / bindScreen
  hrefFor?: Readonly<Record<string, (id: string) => string>>;    // by record type: { meeting: … }
  webmcp?: Readonly<Record<string, WebMcpScreen>>;               // by screen context name
  plugins?: readonly AppPlugin[];
}
defineAppModule(m: AppModule): AppModule

interface AppPlugin {
  name: string;
  Provider?: ComponentType<{ children: ReactNode }>;
  onSignedIn?: (user: SessionUser) => void | (() => void) | Promise<unknown>;
  routes?: readonly AppRoute[];
  nav?: readonly NavItem[];
  useNav?: (items: readonly NavItem[]) => readonly NavItem[];    // a hook; hide or reorder only
}
interface AppRoute {
  path: string;                                                  // '/approvals/:id'
  screen: ComponentType<{ params: Readonly<Record<string, string>> }>;
  public?: boolean;                                              // also signed out, without the shell
}

type AppShellProps = { app: AppSettings; modules: readonly AppModule[] | Readonly<Record<string, AppModule>>;
  plugins?: readonly AppPlugin[]; catalog: Catalog; registry: Registry; config?: Partial<AppConfig> }

// Composition (run by AppShell; exported for tests and for code that runs without the shell)
composeApp({ app, modules, plugins?, catalog }): ComposedApp     // validates; throws on a collision
interface ComposedApp { title; tagline; home?; modules: readonly AppModule[]; nav: readonly NavItem[];
  suggestions: readonly Suggestion[]; plugins: readonly AppPlugin[];
  routes: readonly (AppRoute & { plugin: string })[];
  hrefFor(type: string, id: string): string | undefined;
  webMcpFor(screen: string): (WebMcpScreen & { module?: string }) | undefined }
matchRoute(routes, path): { route, params } | undefined
FRAMEWORK_NAV: readonly NavItem[]                                // Pages

// Plugin glue (pure; AppShell uses them)
wrapProviders(plugins, children): ReactNode
runSignedIn(plugins, user): () => void                           // the cleanup
<SignedIn key={generation} user plugins>{shell}</SignedIn>        // runSignedIn while mounted
filterNav(items, filtered): NavItem[]                            // keeps only given items

// Runtime readers
getApp(): ComposedApp;  hrefFor(type, id): string | undefined;  webMcpFor(screen)
getRuntime(): { catalog; registry; app: ComposedApp }; getCatalog(); getRegistry()

// Typing
interface Register {}                                            // { catalog } or { modules }
type CatalogOf<R>; type MergedEntities<M extends readonly { entities }[]>; type RegisteredCatalog = CatalogOf<Register>

// @hykr/ui-registry/react
bindView(view, component) / bindScreen(screen, component)        // throw on a duplicate name
bindingAs<T>(owner: string, fn: () => T): T                      // who binds, for messages
clearBindings(): void
boundViews(): string[]; boundScreens(): string[]
```

Removed: `AppDomain`, `defineAppDomain`, `getAppDomain`, `AssistantActivity`'s `hrefFor` prop,
and `AppShell`'s `domain` / `views` props.

How a framework feature plugs in (A2, A9, A11, B9, B12):

```ts
// framework/app/src/features/push/plugin.ts
export const pushPlugin: AppPlugin = {
  name: 'push',
  onSignedIn: (user) => { void registerToken(user); },
};
// the application: <AppShell ... plugins={[pushPlugin]} />
```

How an application adds a module:

```ts
// application/mobile/src/modules/orders/index.ts
export const orders = defineAppModule({
  name: 'orders',
  nav: [{ href: '/orders', label: 'Orders', icon: 'file-text', match: (p) => p.startsWith('/orders') }],
  suggestions: [{ text: 'new order', what: 'starts an order' }],
  bind: () => { bindView(OrderListView, OrderListComponent); },
  hrefFor: { order: (id) => `/orders/${id}` },
  webmcp: { orders: { reads: ['orders'] } },
});
// application/mobile/src/modules/index.ts: export { orders } from './orders';
// application/mobile/src/app/orders/index.tsx: export { OrdersRoute as default } from '@/modules/orders/routes';
```

## Test plan

- `framework/app/src/framework/compose-app.test.ts` (Vitest), with fixture modules built in the
  test: merge order (app, modules by `order` then list, plugins, framework); a namespace object
  sorted by key; `module` stamped on destinations and suggestions; each collision throws (module
  name, nav href, suggestion, `hrefFor` type, WebMCP screen, plugin name, route path) and each
  bad declaration throws (nav outside the prefix, reserved name, unknown record type or entity,
  route under a module prefix, an object not made with `defineAppModule`); merged `hrefFor`
  (a module's, the framework's `page`, unknown types); `webMcpFor`; `matchRoute` (params,
  trailing slash, encoded segments, no match on a different length).
- `framework/app/src/framework/plugins.test.ts`: `wrapProviders` nests in plugin order;
  `runSignedIn` runs every plugin, logs a throw and a rejection without stopping the others, and
  runs cleanups in reverse; `filterNav` hides, reorders and drops additions.
- `framework/app/src/framework/signed-in.test.ts`: the shell's signed-in tree
  (`<ChatRuntime><SignedIn key={generation}><Shell/></SignedIn></ChatRuntime>`) rendered with
  react-dom: sign-in runs once per installation, after the shell mounts, and not on a re-render;
  a new installation runs the old cleanups, then unmounts and remounts the shell, then signs in
  again; sign-out and a change of person run the cleanups; React logs nothing. The same test on
  the old tree (two siblings with one key) fails on the missing cleanup and the duplicate-key error.
- `framework/app/src/framework/register.test.ts`: type-level checks, run by `tsc -p
  tsconfig.test.json` in `typecheck`: `CatalogOf<{ catalog }>` is that catalog; `CatalogOf<{
  modules }>` has every module's entities plus the platform's; an empty Register is the general
  catalog.
- `framework/ui-registry/src/react.test.ts`: a duplicate `bindView` or `bindScreen` throws and
  names both owners; `clearBindings` allows binding again; `boundViews` / `boundScreens` list them.
- The sample: `pnpm turbo run build typecheck --filter=@application/mobile...` (the web export
  bundles every route), `pnpm lint`, `pnpm lint:deps`. The API and fixture tests are unchanged
  and must stay green.
- Done once by hand, not in CI (before fix round 1; production bundle, so React's development
  warnings were silent): the web export (`expo export --platform web`) rendered in headless
  Chrome against a fake API, with a temporary plugin in `_layout.tsx`. The nav was in merge order
  with the nav filter applied, the provider wrapped the app, `onSignedIn` ran once, the assistant's
  activity linked a meeting through `hrefFor`, the plugin route rendered inside the shell, and the
  public route rendered signed out. An unknown signed-out path showed sign-in.
- No e2e tests: F2 adds no access path. Everything it shows still loads through the API, which
  applies tenancy, field hiding and approvals.

## Deferred

- **A dependency-cruiser rule for app modules.** F1 owns `.dependency-cruiser.cjs`. Proposed rule
  for the integrator:
  `{ name: 'app-modules-through-index', severity: 'error', from: { path: '^application/mobile/src/modules/([^/]+)/' }, to: { path: '^application/mobile/src/modules/([^/]+)/.+', pathNot: ['^application/mobile/src/modules/$1/', '^application/mobile/src/modules/[^/]+/index\\.tsx?$'] } }`,
  plus `src/app/**` importing only `src/modules/*/routes` and `src/home/**`.
- **Checking app modules against server modules** (an app module whose name no server module
  has). It needs F1's module ids in the catalog.
- **Registering WebMCP tools** (A2), **feature-flag and role nav filters** (A11, A4), **public
  route behaviour for share links** (B9), **offline providers** (B12) and **push registration**
  (A9). Each uses a slot above.
- **`basecamp module add`** scaffolding the app half (F1 owns the CLI). It should write
  `src/modules/<name>/index.ts`, one line in `src/modules/index.ts` and `src/app/<name>/index.tsx`.
- **Back-office modules.** Not needed while the back office is framework-only.
