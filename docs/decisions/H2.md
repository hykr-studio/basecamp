# H2: writers for a business's settings sections

## Summary

The gaps added settings sections that hold what the boundary rule moved out of the framework
(approval thresholds, levels and band approvers, currency and financial year, business hours,
SLA durations, memory recall, share-link lifetimes, inbound media, unknown senders, how long an
invitation lasts), but only some sections had a writer (features, branding, wording, domains,
models, credits, privacy, roles, support). A business could change the others only with SQL. H2
adds one mechanism for all of them, plus a writer for the base settings the calendars depend on:

- A section opts in where it is declared: `defineSettingsSection(key, schema, { editable })`
  (`editable: true` is `settings.manage`; `{ capability }` names another). The framework's
  approvals, money, businessHours, sla, memory, shares, files and parties need `settings.manage`;
  `members` (A4's `inviteDays`, read by member and party invitations) needs `members.manage`.
  Sections with their own writer (credits, models, privacy, roles, support, branding, wording)
  do not opt in, so their own checks cannot be bypassed.
- `PATCH /api/settings/sections/:section { value }` (command `settings.section`): a JSON merge
  patch (RFC 7396) of the stored section, through `runWrite`: validated by the section's schema,
  unknown keys refused, checked for meaning (`settingsChecks`), authorized by the section's
  capability, audited with the section before and after, and announced (`settings.changed`) so
  the process drops its cached copy.
- The same writer covers the base settings' editable part as the pseudo-section `general`
  (`PATCH /api/settings/sections/general`): `timeZone` (a zone the runtime knows), `quietHours`,
  `replyTime` and `marketingPerWeek`.
- `GET /api/settings/sections` and `GET /api/settings/sections/:section` read them, for the
  people who may change them.
- `settingsChecks` (contributions, `defineSettingsCheck`) check what a schema cannot: the
  framework's own check a band approver's capability and person, a level's name, an SLA's name,
  overlapping open hours, band order, a currency the runtime knows, share lifetimes. An
  application adds checks for its own sections the same way.
- Typed `@hykr/api-client` methods: `settings.sections()`, `settings.section(key)` and
  `settings.updateSection(key, patch)`, typed by the section (`EditableSettingsKey`,
  `SettingsPatch<EditableSettingsValue<K>>`).
- The back office's Settings screen edits every section the person may change as JSON and sends
  the merge patch of what changed (`patchBetween`). The sample's orders test sets its business's
  money settings through the writer.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | One generic writer for every opted-in section, not one command per section: a section added later (by the framework or an application) becomes editable by declaring `editable`, with no new route, spec or client method. | Gap list (H2 notes: "PATCH /api/settings/:section, or one command per section"); plan "mechanisms only". |
| 2 | The route is `/api/settings/sections/:section`, not `/api/settings/:section`: `/api/settings/branding`, `/api/settings/wording` and `/api/settings/domains` already exist, and a parameter route beside them would depend on registration order. | Default: no route ambiguity. |
| 3 | Opt-in, fail closed: a section is editable here only when its declaration says `editable`. Unknown sections and sections that keep their own writer answer 404 `not_found` (the list route shows which exist). Credits are the platform operator's and models, privacy, roles and support have their own checks; a generic write would bypass them. `members` had no writer at all (only `roles` is written by `/api/members`), so it opts in (decision 18). | Security default (a business must not raise its own credit allowance). |
| 4 | A write is a JSON merge patch (RFC 7396) of the stored section: an object merges key by key, `null` removes a key (its default applies again), anything else (arrays included) replaces. So a business sets one threshold, one SLA or one weekday without resending the others, and `{ key: null }` restores a default. | Default: a standard, predictable patch; matches the existing `null` clears convention of `PATCH /api/settings/branding`. |
| 5 | What is stored is what the business set (the merged patch), not the parsed section with defaults filled in, so a default the application or the framework changes later still reaches a business that never set it. The answer is the parsed section (defaults applied). | Default: defaults stay the application's. |
| 6 | Validation, all 400 `settings_invalid` with `problems` (one line per problem, by dotted path): the merged section must parse with the section's schema; a key the schema does not know (anywhere in the patch) is refused rather than dropped; then every `settingsChecks` entry for the section runs in the write's transaction. A stored section that no longer parses must be repaired by the same patch (its problems are listed). | Gap list ("refuse unknown or invalid values"). |
| 7 | The framework's checks: **approvals** (a level override names a declared level; a band approver's capability is declared; a named approver is a member of this business with a team role, not a customer, never a person elsewhere; a band after one without `upTo`, or after a larger one in the same currency, is unreachable; at most 50 bands per key); **money** (a currency `Intl` knows; bands ascending within a currency); **businessHours** (intervals of a day do not overlap; holidays are not repeated); **sla** (every name in `within` and `off` is an SLA a served entity declares); **shares** (`defaultDays` within `maxDays`, `sessionHours` within `maxDays`). memory, files and parties need only their schemas. | Gap list examples ("a band approver capability that does not exist", "a calendar that does not parse"); A5 `decidersFor` (named approvers must be members); B6 `addBusinessTime` (overlaps would count twice). |
| 8 | Who: each section's capability, `settings.manage` (owners and admins) for every framework section. A person only (the assistant gets 403 `people_only`; the specs are `expose: 'human'`, no tools), signed in (`session`), or the system principal (server code). A staff member gets 403 `needs_settings_manage`, audited as `denied`. | A11 decision 7 (the assistant does not change a business's setup); PRD Platform&AI 7.3 ("studios accept tier defaults; few will loosen tier 2": the owner decides). |
| 9 | Base settings are written by the same command as the pseudo-section `general` (`PATCH /api/settings/sections/general`; no section may be called `general`), for `timeZone`, `quietHours`, `replyTime` and `marketingPerWeek`; they stay top-level keys of the stored settings. `grievanceContact` and `privacyUrl` stay with the privacy team's writer (`PATCH /api/privacy/settings`), `features` with `PUT /api/features/:key`. A time zone must be one `Intl.DateTimeFormat` accepts: an unknown zone would make every SLA clock in business hours throw. The base schema itself stays lenient on read (stored settings keep parsing). | Gap list (B6 business hours and B3 fiscal-year boundaries depend on the base settings); F4 decision (TenantSettings defaults). |
| 10 | Each write locks the business's row (`for update`), changes only its own top-level keys (`jsonb_set`, or `||` and `-` for the base keys), and audits `{ [section]: before }` / `{ [section]: after }` as stored. `settings.changed` (with the section) is stored in the outbox and published after commit, and this process drops its cached copy at once; others within their 10 s TTL. Approvals and SLAs read settings in the write's own transaction, so a new threshold or duration applies on the very next write in every process. | A11 decision 7; existing `SettingsChanged` handler. |
| 11 | A section write can be parked like any write: an application that wants a second person to agree to, say, a loosened level declares a level rule on `settings.section`. The value is checked when the write is loaded, so a refused value is refused at once rather than parked, and again when an approval's replay loads it, so a replay finds problems that arose meanwhile. Someone who may not change the section is refused (and audited) without the checks running, so a refusal says nothing about the business's team. | CLAUDE.md "one write path"; A5 level rules. |
| 12 | Reads are for the people who may write: `GET /api/settings/sections` lists the editable sections the person may change, each with its value (defaults applied) or, when its stored value no longer parses, `value: null` and its problems; `GET /api/settings/sections/:section` one of them (403 without its capability, 404 for one not editable). `general` is read the same way (settings.manage). | Default: fail closed; what members need of a section reaches them through its own feature (`/api/money`, `/api/sla`, the approval cards). |
| 13 | At start, every editable section's capability must be declared, and every settings check must name an editable section or `general`; otherwise the API does not start. | Fail closed: a typo would leave a section that nobody can change, or a check that never runs. |
| 14 | Cross-business: there is no business id in these routes; a write always changes the principal's own business. Naming another business with `x-tenant-id` is refused (403 `not_a_member`) by the resolver before anything runs (F4); naming another business's person as a band approver is 400, the same answer as for a person who does not exist. | CLAUDE.md "Not yours is a 404"; F4 resolver. |
| 15 | The body is `{ value }`, not the patch itself: a command's body is the input's shape without path parameters, and a bare body would have its unknown keys stripped by the route's DTO before the writer could refuse them. | `commandController` (core). |
| 16 | The back office edits each section as JSON (as it edits agents' triggers), sending only what changed, so a key taken out goes back to its default and an untouched default is never stored. A change a level rule makes wait shows "Waiting for approval". | Default: the smallest screen that makes every section editable without SQL. |
| 17 | `BusinessHours`' interval refinement no longer throws on a time that is no time of day ('25:00'): the time's own issue reports it (it was a 500). | Found by the tests. |
| 18 | `members` (`inviteDays`, how long a member's or a party's invitation can be accepted) opts in with `editable: { capability: 'members.manage' }`, not `settings.manage`: who may invite decides how long an invitation lasts, and a business that gives `members.manage` to another role gives this with it. A refusal is 403 `needs_members_manage`. Its schema bounds it (an integer, 1 to 90 days), so it has no settings check. Support access never holds `members.manage` (`FRAMEWORK_WITHHELD`), so support cannot lengthen invitations either. | Review finding (A4 registered the section with no writer); A4 decision 23 (`members.manage` invites). |

## Assumptions to review

- **Who edits which section.** Every framework section but `members` is `settings.manage`
  (owners and admins); `members` is `members.manage` (owners and admins by default, and any role
  a business gives it). Should approval thresholds and approvers need the owner alone, or a
  second person's approval (a level rule on `settings.section` does this today, per
  application)? Should the invitation lifetime need `settings.manage` as well?
- **Loosening approvals.** A settings manager can set `parks: false` on a level that allows it
  (`tenantMayLoosen`), lengthen undo windows and expiries, and change who approves which band.
  Should loosening a level, or naming oneself as a band's approver, need another person?
- **Base defaults.** The base settings' defaults (time zone, quiet hours, reply time, one
  marketing message a week) are F4's, unchanged here. Should a new business be asked for its time
  zone at sign-up instead?
- **Cache across processes.** Other API processes keep a business's cached settings for up to
  10 s after a change (approvals and SLA clocks read them fresh). Is 10 s acceptable for quiet
  hours, branding and the model policy, or should `settings.changed` be broadcast?
- **Reading settings.** Only the people who may change a section read it here. Should members
  see the business hours and SLA durations (for countdowns), and customers the reply time?

## API sketch

```ts
// contracts: a section opts in
export const SlaSection = defineSettingsSection('sla', SlaSettings, { editable: true });
defineSettingsSection('fixtureClaims', schema, { editable: { capability: 'fixture.claims.setup' } });

// api: a check the schema cannot make (contributes.settingsChecks)
defineSettingsCheck({
  name: 'fixture.claims', section: 'fixtureClaims',
  check: (value, { tx, tenantId, principal, catalog }) => [/* problems */],
});

// HTTP
GET   /api/settings/sections               → [{ key, capability, value, problems }]
GET   /api/settings/sections/:section      → { key, capability, value, problems }
PATCH /api/settings/sections/:section      { value: <merge patch> } → { status: 'done', value: { key, value } }
PATCH /api/settings/sections/general       { value: { timeZone?, quietHours?, replyTime?, marketingPerWeek? } } (null: default)

// client
api.settings.updateSection('approvals', { thresholds: { 'payments.limit': { minor: 50_000, currency: 'EUR' } } });
api.settings.updateSection('sla', { within: { 'orders.decision': '36h' }, off: [] });
api.settings.updateSection('general', { timeZone: 'Europe/Berlin' });
```

## Test plan

- `framework/api/test/framework/settings-sections.e2e.test.ts` on the fixture's `claims` module
  (`fixture/src/features/settings/claims.ts`: a claim with states, an SLA counted in business
  hours and one in all hours, two approval levels, a level rule reading a threshold and a band,
  and the module's own editable section with its own check):
  - an owner patches approvals, money, businessHours, sla, memory, shares, files and parties;
  - `members`: read with `members.manage`; staff get 403 `needs_members_manage`; 91 days is
    400; an admin sets 14 days and the next invitation expires 14 days after it was made; `null`
    restores the default;
    the answer has defaults applied, the stored value is what was sent, the audit holds before
    and after, `settings.changed` is stored;
  - merge semantics: one key added beside another, `null` restores the default;
  - refused: an unknown section (404), a section with its own writer (404), an unknown key, a
    value the schema refuses, a band capability nobody declares, a band approver of another
    business, a level nobody declares, an SLA nobody declares, overlapping hours, a time zone
    that does not exist (all 400 `settings_invalid`);
  - staff get 403 `needs_settings_manage`, audited `denied`; the assistant gets 403;
    another business's person with `x-tenant-id` gets 403 and changes nothing; each business's
    write leaves the other's settings as they were;
  - a new threshold takes effect on the next write (a claim that ran now waits);
    a new band approver decides the next parked claim;
  - a new SLA duration and new business hours set the next timer's due time, `off` starts none;
  - general settings: time zone, quiet hours, reply time, read back through `/api/me`'s cache;
  - the module's own section with its own capability and check.
- `framework/api/test/framework/settings-sections.test.ts`: the merge patch (no prototype
  reached), unknown keys at any depth, `patchBetween`, `general`, the pure checks.
- `application/api/test/domain/orders.e2e.test.ts` sets the sample business's money through the
  writer.

## Deferred

- Forms per section: the back office edits JSON; neither app has a screen for these sections.
- A settings write is not undoable (no undo window applies to `settings.*` unless an
  application's level gives one).
- Cross-process cache drop is per process (other processes within the 10 s TTL).
