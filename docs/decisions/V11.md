# V11: events, credits, words and auth, what the reviews left

## Summary

The reviews of V5 (credits), V6 (retries, events, egress), V7 (words and channels) and V9 (auth
routes, OAuth pages, verified domains) approved those units and left findings. This unit fixes
the defects among them, the same-class sites, two hazards in `framework/core/src/write/approvals.ts`
(an approver who left the business, and a replay that no longer validates), and the doc
corrections and missing tests the reviewers named.

- **Auth.** `TRUST_PROXY` sets Express's `trust proxy` when the API starts, so behind a balancer
  each client has its own rate-limit bucket; every route sees the caller's address as Express
  does (a client's own `x-hykr-client-address` is replaced everywhere); the OAuth sign-in page
  carries the language to the consent page only, never to a client's `redirect_uri`.
- **Events and retries.** A subscriber whose filter throws misses that event alone; a repeated
  credentials update answers the first answer after the connection is gone; the routes that keep
  their own reply (back-office reply, file presign and discard, job cancel, calendar `complete`)
  run one at a time per caller and key, under a claim row that holds no pooled connection; a
  notification whose filter throws misses that event alone.
- **Credits.** A meter reports only a refusal that happens, and a limit that stops nothing raises
  no level; the operator's plan is checked as it will be stored; the credits screen says a
  turn-refusing limit once.
- **Approvals.** A named approver who left the team, and a requester outside it, give way to the
  holders of `approvals.decide`; a replay that no longer validates ends as failed, once; the
  replay's transaction waits for no second connection.
- **Words.** What became of a request reads in English, Hindi and Telugu; no rule reason or help
  text says whose approval it is.

## Assumptions to review

- **The approver-left fallback is not announced.** The holders of `approvals.decide` can decide
  a request whose named approver left, and see it in their Approvals list, but nobody sends them
  the `approval.request` notice. Should leaving the team (or a demotion) re-send pending requests
  that named that person?
- **Who decides after the approver left is fixed.** It is always `approvals.decide`, not the
  band's next approver or the capability a later band names. An application that wants another
  fallback has no setting for it.
- **A 400, 410 or 422 on replay closes the request as failed.** A command that answers 400 for a
  reason that could pass later (none known today) would now end its request instead of leaving it
  for another try.
- **The claim's limits are fixed.** A request waits up to 30 s for another with its key, then
  answers 409 `idempotency_in_progress`; a claim older than 2 min is taken over. A route's work
  that runs longer than 2 min (a storage call has no timeout of its own) can be taken over by a
  retry and run twice, as before V11; a crashed holder makes retries wait up to 2 min, each
  answering 409 after 30 s. Neither is a setting.
- **A waiter polls.** Each try is one short statement on a pooled connection (every 10 ms to
  200 ms). Many retries of one slow request cost a little database work, never a held connection.
- **`TRUST_PROXY=true` takes the leftmost forwarded address.** It is right only behind a balancer
  that overwrites `X-Forwarded-For`; one that appends to it (nginx's
  `$proxy_add_x_forwarded_for`, most cloud balancers) lets a client choose the address its rate
  limits count. The guide and `.env.example` say to prefer a hop count or the balancer's
  addresses. Nothing checks the setting against the deployment.
- **A filter that throws is not retried for its subscriber or its notification.** The event is
  relayed to the others and marked relayed; the subscriber (or notification) that missed it never
  gets it, even once its filter is fixed. Only the log (and, for a subscriber, the `error` column)
  says so.
- **A requester off the team never decides their own request**, even where a rule says
  `by: 'requester'` (decision 1). An application that wants a contact to approve their own
  assistant's request has no way to say so.
- **A limit that stops nothing is silent.** A `messages` limit with no kind in `pauseMessages`
  raises no alert at all (decision 11), and an empty `pauseMessages` is the neutral default (A3
  decision 5), so a deployment or business that sets a `messages` limit and nothing else hears
  nothing as it nears the number. A3 decision 9 now says so.

## API sketch

```ts
// @hykr/core: a route that keeps its own reply runs one request at a time per (caller, key).
// A claim row, no held connection; 409 idempotency_in_progress after CLAIM_WAIT_MS.
return oneAtATime(this.db, { principal: p, idempotencyKey }, async () => {
  const repeat = await findRepeat(this.db, ctx, op, request);
  if (repeat) return repeat.result;
  // ... the work, once ...
  await saveReply(this.db, ctx, op, request, { status: 'done', value });
  return value;
});

// @hykr/core: whether this person decides, with the named approver's standing looked up.
mayDecide(row, p, { approverGone });

// @hykr/api: an event feed may keep who missed a relayed event.
const feed: EventFeed = { name, pending, relayed, failed, skipped: async (items, { prefix }, ctx) => {} };

// @hykr/api (credits): a meter that pauses only some uses says whether a plan pauses any.
defineMeter({ name: 'messages', unit: 'message', pausable, pausesSome: (plan) => plan.pauseMessages.length > 0 });
```

## Suggestions that did not hold, and what was not done

- **`unchangedSince` by version or fingerprint (V6, optional hardening).** Not done. A repeat
  re-reads a secret only when the row's `updated_at` equals the stored reply's to the
  millisecond; a collision needs another admin's change in that same millisecond, and the
  repeat is by the same caller with the same key. A version column is a schema change for a
  very small risk; recorded here and in Deferred.
- **ApprovalCard: reword the reason for the requester.** Taken as "leave it out" instead
  (decision 15): rows parked before this change keep their words, which no rewording on the
  server reaches.
- **A file presign that looks up the record before its repeat (same class as the connection
  update).** Holds as it is: a repeated presign signs a new upload URL, so the caller must
  still be allowed (decision 5).
- **The doc route for V5's alertAt.** The code route was taken instead (decision 12).
