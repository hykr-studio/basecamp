# V11: events, credits, words and auth, what the reviews left

## Summary

The reviews of V5 (credits), V6 (retries, events, egress), V7 (words and channels) and V9 (auth
routes, OAuth pages, verified domains) approved those units and left findings. This unit fixes
the defects among them, the same-class sites, two hazards in `framework/core/src/write/approvals.ts`
(an approver who left the business, and a replay that no longer validates), and the doc
corrections and missing tests the reviewers named.

Work in progress: the sections below are filled in as each fix lands.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | **A named approver who left gives way to the business.** By default, when a request's named approver (`approverUserId`: an amount band's person, a rule's `{ userId }`, or the requester deciding their own) is no longer on the business's team, the holders of `approvals.decide` decide it, never the requester. "On the team" is the rule a request parks under: a membership in the business with a role no outsider is given, among the roles the business has (`teamRoles(rolesOfBusiness(settings))`). So a person who left, and one who holds only a contact's or participant's roles now, have both left; back on the team, the request is theirs alone again. | Brief (V9's approver-left case, "record this as a decision"); V9 Deferred; default (the park-time rule, applied again at decide time). |
| 2 | The rule is one fact read in two places. `decidable` (lists, `get`, `decide`) gains an arm for holders of `approvals.decide` over rows whose named approver has no team membership (`NOT EXISTS` on `app.memberships` with `roles && <team roles>`), and the named approver's own arm now needs that membership too. `mayDecide(row, p, { approverGone })` and the card's `decider` (`{ by: 'capability', capability: 'approvals.decide' }`) take the same fact, which `ApprovalService` looks up for the rows it returns (`goneApprovers`, one query). `keepOwn` (WhatsApp) still calls `mayDecide` without it: a request it renders has just parked, when its named approver is on the team by construction. | Advisor (the sync `mayDecide` feeds `canDecide` and the 403 `own_request`); default. |
| 3 | **A replay that no longer validates ends as failed.** `runWrite` validates first (`op.input.parse`), which throws a `ZodError`, not an `HttpException`, so a stored input that lost a required field (an erasure's scrubbing, V3's hazard) answered 500 and stayed pending until it expired. `decide` now closes it as `failed` with "What was asked is no longer complete (<paths>)". A replay refused with 400, 410 or 422 also ends as failed (it would be refused again), joining 401, 403, 404 and 409; a 5xx or a 429 still leaves it pending. | Brief (V3's replay hazard: "have decide close a replay that fails validation as failed"). |
| 4 | **A filter that throws withholds the event from its own subscriber only.** `route` no longer throws when a subscriber's `when` does: it leaves that subscriber out and routes the event to the rest. The row is relayed (`relayed_at`), and which subscriber missed it, with why, is logged and kept in the row's `error` column (`failed_at` stays null). `EventFeed` gains an optional `skipped(items, { prefix }, ctx)` (the outbox feed writes `error`), and `RelayOutcome` a `skipped` list; `relayed` and `failed` keep their signatures, so a feed of an application's own keeps working. A row the envelope refuses still fails alone, as V6 decided. No schema change: `error` exists since V6. | V6's review (suggestion taken: skip only the subscriber, record the failure in the error column); advisor (a public extension point gains an optional method, not a new signature). |
| 5 | **A repeated credentials update answers the first answer, even once the connection is gone.** `updateConnection` with credentials looks for the repeat (`findRepeat` with the same op and the keyed tag of the body) before it reads the row, checks the connector and seals, as `createConnection` does. Same-class sites checked: every other route that works before its `runWrite` (endpoint create and rotate, calendar complete, job cancel, file discard, the back-office reply) already looks first; calendar disconnect's `leftovers` does not 404. A file presign checks the record before its repeat on purpose: its repeat signs a new upload URL, so the caller must still be allowed. | V6's review (suggestion taken). |
| 6 | **Routes that keep their own reply run one at a time per key.** `oneAtATime(db, ctx, work)` (`@hykr/core`, beside `findRepeat` and `saveReply`) runs `work` in a transaction holding `pg_advisory_xact_lock` on (principal, key); `work` looks for the repeat and saves its reply on that connection. A second request sent while the first still runs (the common retry: a client that timed out) waits, then answers the first reply. Used by the back-office reply, a file's presign and discard, a job's cancel and a calendar sign-in's `complete`: two at the same moment now send one WhatsApp message, make one pending file, audit one discard and one cancel (both answer 200, not 409 `already_finished`), and exchange Google's code once (both answer 201, not 400 `calendar_sign_in_invalid`). Without a key nothing changes. | V6's review (suggestion taken: the lock, re-checking `findRepeat` under it). |
| 7 | The route lock is keyed `idempotency.route:<principal>:<key>`, not `runWrite`'s `idempotency:…`: calendar `complete` calls `runWrite` with the same key on another connection, which would wait for the outer lock for ever. The file presign and discard do their writes on the lock's own connection; the others write on their own connections while the lock's transaction waits, so each such request holds one more connection while it runs (bounded by the pool's 30 s connection timeout). | Advisor (deadlock on the same key); default. |
| 8 | **`TRUST_PROXY`, a deployment setting read when the API starts.** `configureHttp(nest)` (`framework/api/src/infra/http.ts`), called by `startApi` and by the tests' `boot`, sets Express's `trust proxy` from it before any route is mounted: unset, empty, `false`, `off`, `no` or `0` trust nothing (today's behaviour, the default); `true`, `on` or `yes` trust every proxy; a whole number is that many hops; anything else is Express's comma list (addresses, subnets, `loopback`, `linklocal`, `uniquelocal`). The string is turned into a number or a boolean first, since Express would read `'1'` as an address. It is read in the function, not in `config.ts`'s constant, so a test sets it before it boots. Documented in guide section 4, section 14 ("The IP behind a proxy") and `.env.example`, with `THROTTLE` beside it. | V9's review (follow-up taken: a config `startApi` applies); brief. |
| 9 | **The caller's address is the API's on every route.** The same setup stamps `x-hykr-client-address` with `req.ip` on every request (deleted when there is none), so a client's own value never reaches a route or a server-side `auth.api` call made with the request's headers; `authMiddleware` stamps it again for an app that mounts Better Auth without `configureHttp`. This replaces "strip it everywhere": a stamp also gives such a call the right address instead of falling back to the client's `x-forwarded-for`. No route outside `/api/auth` reads the header today (checked by grep), so the fixture gains a test-only echo route (`GET /api/fixture-echo`) to observe it. | V9's review (suggestion taken, a global middleware in `startApi`); advisor (an echo route to fail first). |
