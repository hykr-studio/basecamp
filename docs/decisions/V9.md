# V9: auth routes, OAuth pages and verified domains hold the same rules as the API

## Summary

A fix unit from the live validation (`VALIDATION.md`, root cause 9, the MCP half; C6-1, an event
agent running on an older event, is another unit's). Better Auth answers `/api/auth/*` before any
Nest guard, and the OAuth pages read less than they promise. Four confirmed defects:

- **C6-2.** `x-channel` was parsed and enforced only in `PrincipalGuard`. On `/api/auth`, a
  session sending `x-channel: webmcp` could rename the person or consent to an outside client, and
  `x-channel: whatsapp` was not even refused. Now the same rules run in front of Better Auth's
  handler: a channel a session may not name is 400 `bad_channel`, and a read-only channel reaches
  nothing there (403 `read_only_channel`).
- **C6-3.** The OAuth pages read only `Accept-Language`. Now `?lang` (one of the application's
  languages) wins, whether the client put it in its authorization request (signed) or it was
  added to the page's address afterwards (the page then posts only the signed part back).
- **C6-4.** The consent screen could not narrow a module from change to read: it offered only the
  literal scopes asked for, and Better Auth refuses any other. Now an authorization request that
  asks to change a module also asks to read it, and the screen shows one choice per module: not
  allowed, read, or change.
- **C6-5.** `/mcp` told a client whose token was revoked, expired or unknown that "a bearer token
  is needed". It now says the token is invalid, expired or revoked.

The critic's leads were checked with tests on the fixture app; what held is fixed, the rest is
recorded below with how it was checked.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | The channel rules for `/api/auth` run in an Express middleware handed to the Nest Better Auth module (`AuthModule.forRoot({ middleware })`), so they apply to HTTP requests on the mount and never to the server's own `auth.api.*` calls (the guard's `getSession`, an OTP sign-in made by a share route). A Better Auth `hooks.before` would run for both. | Validation (C6-2 fix sketch); default. |
| 2 | Two helpers in `@hykr/contracts` (`channel-rules.ts`), `sessionChannelRefusal` and `readOnlyChannelRefusal`, decide both places: `PrincipalGuard` and the auth middleware give the same bodies (`bad_channel`, `read_only_channel`). | Default: one rule, one place. |
| 3 | On `/api/auth`, a read-only channel reaches nothing, GET included. No Better Auth route reads a record, and several GETs change something: `GET /oauth2/authorize` mints a code under a remembered consent, `verify-email` and the social callbacks sign in. The WebMCP tools never call it. | Default: fail closed; checked with a remembered consent. |
| 4 | The OAuth pages' language: `lang` in the query when it is one of the application's declared languages (`languages().of`), else the first `Accept-Language` entry, else English. The framework keeps no list. | A1 decision 15; validation fix sketch. |
| 5 | A `lang` added to a page's address after the signature is allowed. The pages verify only the signed part (the parameters Better Auth lists in `ba_param`, as its own `buildSignedOAuthQuery` keeps), and post that part back as `oauth_query` instead of `location.search`. The sign-in page carries such a `lang` on to the consent page. | Validation (C6-3, both cases). |
| 6 | A request to change a module also asks to read it. A `before` hook on `/oauth2/authorize` (`mcpScopeReads`) adds `<m>:read` next to each `<m>:write` in `scope` (the query, or the body of a POST), so the provider's literal check (`Scope not originally requested`) accepts a read-only consent. The read is added only where the client's registered scopes allow it, or the provider would refuse the whole request (`invalid_scope`). A dynamic registration holds every scope whatever it asks (Better Auth 1.7.7 stores them all), so no registration hook is needed; a client the server registers itself may hold fewer. `mcpNativeClients` now returns only the field it changes, so two hooks on one route merge. | Validation (C6-4 fix sketch); default. |
| 7 | The consent screen shows one row per module asked for, with radio choices: Not allowed, Read, and Change when change was asked. The most the client asked is chosen first. It posts `<m>:read`, or `<m>:read <m>:write`, per allowed module, plus `offline_access` if kept. New phrase `mcp.consent.none` in en, hi and te. | A1 decision 15 ("read/write choices; the person may narrow them"). |
| 8 | A stored consent that holds only `<m>:write` (given before the change) no longer covers the expanded request, so the person is asked once more. | Consequence of 6; accepted. |
| 9 | `/mcp`'s 401 body says which case it is: `A bearer token is needed` with none, `The access token is invalid, expired or revoked` with one it does not accept. The `WWW-Authenticate` challenge is unchanged. | Validation (C6-5 fix sketch). |
| 10 | Better Auth's own rate limits (3 sign-ins, sign-ups, password or email changes per 10 s per address; 100 per 10 s elsewhere) are counted in Redis, shared by every API process like the API's throttle, instead of each process's memory. They apply in production, and whenever `THROTTLE=on`, never with `THROTTLE=off`, decided per request. They key on the address Express sees (`req.ip`, which honours `trust proxy`), which `authMiddleware` hands Better Auth in a header of its own (`x-hykr-client-address`, a client's value always replaced): Better Auth's default reads one `x-forwarded-for` entry and otherwise puts every caller in one bucket, which with shared counters would let anyone lock everyone out of signing in. `x-forwarded-for` stays the fallback for the server's own `auth.api` calls (the address a session records). V11: the address is stamped on every request, not only on `/api/auth` (`configureHttp`), so a client's own value is replaced on every route, and `TRUST_PROXY` sets `trust proxy` at start. | Lead L10 (held for `/api/auth`); default. |

| L5: a verified domain trusted for credentialed CORS | Does not hold cross-site. | `auth-routes.e2e`: the session cookie is `HttpOnly; SameSite=Lax` with no `Domain` (asserted, so a change to `None` fails), so a browser sends it on no fetch from another site whatever CORS allows; a verified domain gets `Access-Control-Allow-Origin` and `-Credentials` for anyone's request, by design (A11). MCP per client: the existing `mcp.e2e` throttling test (121st call 429). The public form and share-link guest routes are Nest routes under the same `CallerThrottlerGuard` (by address), checked by reading. |

## Assumptions to review

- **A verified domain on the API's own registrable domain** (a business given `shop.<platform>`)
  would be same-site, and the Lax cookie would then reach it. Verification needs control of the
  domain's DNS, so this needs the platform to hand out its own subdomains. No tenant binding is
  built.
- **Both throttles key on `req.ip`.** Behind a load balancer without Express's `trust proxy`,
  that is the balancer's address, so every caller shares one bucket (3 sign-ins per 10 s for the
  deployment). Section 14 already says the framework does not set `trust proxy`; a deployment
  behind a proxy must.

## The same class, searched

- **Routes that skip `PrincipalGuard`.** Of the controllers marked `@AllowAnonymous()` or
  `@OptionalAuth()`, all but five pair it with `PrincipalGuard`, `OperatorGuard`, `ChatTurnGuard`
  or `HumanOnlyGuard`. The five: `/mcp` (a bearer token only; its tools call the API, which
  applies the rules), the OAuth pages (GET only, and they only show), the file blob route (a
  signed URL is the right), the WhatsApp webhook (HMAC) and the share guest routes (the link's
  token, never a session). None reads a session's `x-channel`. `OperatorGuard` refuses any
  channel but `app` and any agent key (`humans_only`). Better Auth's mount was the one place a
  session acted with the header unread: fixed (decision 1).
- **Language from a request.** `Accept-Language` is read only in `features/mcp/pages.controller.ts`
  (fixed); nothing in `framework/core`, `application/api` or the domain reads it.

## API sketch

```ts
// @hykr/contracts (channel-rules.ts)
CHANNEL_READS: readonly string[]; // ['GET', 'HEAD']
sessionChannelRefusal(named?: string): ChannelRefusal | undefined; // 400 bad_channel
readOnlyChannelRefusal(channel?: Channel, method: string, { readsToo? }): ChannelRefusal | undefined;
interface ChannelRefusal { status: 400 | 403; body: { error; rule?; reason } }

// @hykr/api
authMiddleware(req, res, next); // infra/auth.ts, AuthModule.forRoot({ middleware })
throttleStorage(); authRateLimit(); // infra/throttle.ts: one Redis storage for both throttles
withReads(scope, allowed?): string; mcpScopeReads: AuthPlugin; // features/mcp/oauth.ts
ConsentChoice; consentPage(lang, v, choices, oauthQuery); signInPage(lang, app, oauthQuery, carry?)
```

## Test plan

- A session naming `whatsapp` on `update-user` is 400 `bad_channel`, the body `/api/tasks` gives;
  the name is unchanged (C6-2).
- With `x-channel: webmcp`: `update-user`, `change-email`, `change-password`, `revoke-sessions`,
  `delete-user`, `oauth2/consent` (signed query), `GET oauth2/authorize`, `get-session` and
  `sign-out` are 403 `read_only_channel`; nothing changes, no consent row, still signed in; without
  the header `update-user` works (C6-2, L4 d).
- L4 a to c, L5 and L10 as in the table above.

`framework/api/test/framework/mcp.e2e.test.ts`:

- The consent screen shows one radio row per module, the most asked chosen (C6-4).
- A request for `tasks:write offline_access` is signed as `tasks:read tasks:write offline_access`;
  consenting `tasks:read` through `/api/auth/oauth2/consent` gives a `tasks:read` token: GET 200,
  POST 403 `out_of_scope`; asking for `tasks:write` again shows the screen, `tasks:read` does not
  (C6-4).
- A request naming no scope offers reading alone for every module; a client whose registered
  scopes hold only `tasks:write` still authorizes, with Change alone (C6-4).
- `lang=hi` in the authorization request: sign-in and consent in Hindi; `&lang=te` added to the
  consent or sign-in page's address: Telugu, the page posts back exactly the signed query and
  sign-in carries `te` on; a second `lang` against a signed one, or any added parameter that
  repeats a signed one (`&scope=`), is 400, while one of a new name (`&foo=1`) is ignored (200,
  and the posted query is the signed part alone: corrected by V11); an undeclared `lang` falls
  back to `Accept-Language` (C6-3).
- No token: "A bearer token is needed"; an unknown or revoked one: `invalid_token`, "The access
  token is invalid, expired or revoked" (C6-5).
- L6 (demotion), L13 (paused write), L19 (redirects) as in the table above.

Run against the sources before the fix (`aae893d7`, rebuilt), 11 of the 39 tests in the two
files fail: the 401 descriptions (two), the consent screen's rows, narrowing, no scope, the
write-only client, the pages' language, the session's channel, the webmcp channel and the rate
limits. The credentials test fails only on the name the webmcp test had changed (`Hijacked`):
each of its 401s passes there too, which is how L4 a to c was shown not to hold. The rest are the
leads that did not hold, passing before and after.

## Deferred

- **A named approver who leaves after a request parked naming them.** They can no longer reach
  it, and `decidable` lets nobody else decide a row with an `approverUserId`, so it waits until
  the sweeper expires it. A fix lets the holders of `approvals.decide` decide it once its named
  approver is no longer on the team (a join on `app.memberships` in `decidable` and
  `mayDecide`), in `framework/core/src/write/approvals.ts`, which other units also change. Guide
  section 14 ("Approval levels") says so. Done by V11 (decisions 1 and 2).
- **`trust proxy`.** Setting Express's `trust proxy` for a deployment behind a balancer remains
  the deployment's (section 14, "The IP behind a proxy"); both throttles then count per client.
  V11 adds the setting for it: `TRUST_PROXY`, applied by `startApi` (guide section 4).
- **Tests not written** for the lead parts checked by reading: a live run token on `/api/auth`
  (L4), a `callbackURL` over HTTP (Better Auth skips the check under test, L5), a share link, a
  calendar feed and an agent run after a demotion (L6, same resolver call as the MCP test), and
  hammering the guest routes with `THROTTLE=on` (L10, same guard as the MCP throttling test).
- **A `lang` both signed and added again** is refused (400): an added parameter may not shadow a
  signed one.
