# B1: files and media

## Summary

Records can carry files. An entity declares which of its fields hold files (the `files` trait,
with an accept list, a size cap and a count per field) and gives them the `FileRef` type: a file
id, or a list of them (`fileRefs(max)`). People upload in three steps: `POST /api/files` (presign,
for one entity's file field), a `PUT` of the bytes straight to object storage, then
`POST /api/files/:id/confirm`. The file becomes part of a record when a write puts its id in a
file field; that write goes through `runWrite` like any other, with its rules, approvals and
audit. From then on the file is reached only through the record that holds it: whoever can read
that record, and still sees that field, gets a short-lived download URL (`GET /api/files/:id`);
everyone else gets 404.

Storage sits behind one driver interface: S3-compatible (MinIO in development, any S3 in
production, its bucket created at startup when missing) and a local driver, in memory (tests and
CI) or in a folder, whose signed URLs the API serves itself. Images are checked against their
bytes and their size in pixels is kept. Audio files can be transcribed (the channel's
speech-to-text). A photo, document or video that arrives on WhatsApp is stored by an inbound hook
and named to the assistant's turn, so the assistant can put it on a record. "Delete my data"
erases what a person sent, and a sweeper removes abandoned uploads and files a record let go of.

In the app, `<FileField>` picks from the photo library, the camera or the file picker and
uploads; `<FileThumbs>` shows a record's files. The sample's `notes` module keeps up to ten photos
on a note, and its scripted model puts a photo sent on WhatsApp on a new note.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | A file field holds file **ids** (`FileRef` is a uuid; `fileRefs(max)` a list of them), not copies of the file's metadata. Metadata and URLs come from `/api/files`. A record round-trips unchanged (a client sends back what it read), nothing on the record can drift from the stored file, and the assistant passes ids like any other reference. | Plan B1 row ("`FileRef` field type"); default: ids are what the read path can check synchronously, and URLs must be fresh anyway. |
| 2 | Which fields hold files, and what each accepts, is declared on the spec: `traits: { files: { photos: { accept: ['image/*'], maxBytes, max } } }`. When the API or the worker starts, `FilesService` checks every served entity with the trait: each field is in the read schema and in the create or update schema, the table has a column with that key, `max` and `maxBytes` are positive whole numbers. A mistake stops the start. | Plan ("Traits … a feature declares its key on `EntityTraits`"); fail closed. |
| 3 | Columns: `fileColumn(name)` (text, nullable) and `fileColumns(name)` (text[], default empty) from `@hykr/db`. The column's key is the field's name. | Default: matches how other columns are declared; text[] reads back as `string[]`. |
| 4 | Upload is presign → PUT → confirm. The presigned PUT signs `content-type` and `content-length`, so the store refuses any other type or size (checked against MinIO: a wrong type or length is a 403 `SignatureDoesNotMatch`). Confirm reads the object's head and first 64 KiB: the size must match, and a declared JPEG, PNG, GIF, WebP, HEIC/HEIF, AVIF or PDF must start like one, or the object is deleted and confirm answers 422 (`size_mismatch`, `content_mismatch`); the file stays pending and can be uploaded again until it expires (409 `upload_expired`). Nothing uploaded: 409 `not_uploaded`. Multipart through the API is not built: bytes never pass through it for S3. | Gap map B1 risks ("Multer multipart on the same app may conflict. Presigned direct-to-bucket upload avoids this"); plan ("presign → confirm → get"). |
| 5 | A presign names what the file is for: `{ entity, field, id? }` (the entity's name). The field's `accept` (415 `type_not_accepted`) and size cap (413 `too_large`, with `maxBytes`) apply before anything is stored; with `id`, the person must reach the record (404 otherwise) and be allowed to update it now (`def.decide(p, 'update', row, {})`: a refusal is 403 with its rule, a park is allowed since the write will park); without `id` they must be allowed to create one. An unknown entity or field is 400 `unknown_file_field`. | Plan ("scoped through the owning row"); fail closed. |
| 6 | Uploading (presign, confirm, discard) is for people: `HumanOnlyGuard` (the assistant gets 403). Reading (`GET /api/files/:id`, `GET /api/files?ids=`) and transcribing are open to the assistant too, through the same reach; the assistant never gets a download URL. The assistant attaches files it was given (WhatsApp) through the records' own create and update tools. | Default: least privilege for agents; "the assistant is a user" still holds for reads and attaching. |
| 7 | **Who reaches a file.** Same business, always (the query is scoped by tenant). An attached file: the owning record must be reachable by the principal (the entity's scoped `repo.find`, so its access, grants and plugins' scopes apply), an agent needs the entity's `get` exposed to it, and the record **as projected for that principal** (`def.toRead(row, p)`) must still list the file in that field. So a hidden field (field policy, a read projector) hides its files too. An unattached file (uploaded, not yet on a record): only whoever uploaded it (the same person, the same WhatsApp contact, or a person whose linked number sent it). A detached or erased file: nobody. Anything else is 404, never 403. `GET /api/files?ids=` leaves out what the caller does not reach. File metadata passes the read projectors as resource type `file`. | Plan ("scoped through the owning row"), gap map ("never by guessable object key"), task ("hidden fields stay hidden", "another tenant gets 404"). |
| 8 | **Attaching is the record's write.** A write hook (`files`, `afterRun`, in the write's transaction) makes each touched record's file fields match its row: the ids now in the field are compared with the files the database holds as attached there (not with `before`, so commands that omit it work too). Every new id must be a ready file of this business that is either on no record and uploaded by the same subject, or one this very field let go of (a detached file can come back until it is swept: an undo); its type and size must fit the field, and the field's count cap holds. Then it is claimed (`resource_type`, `resource_id`, `field`), the rows locked `FOR UPDATE`. Ids that left the field, and every file of a deleted record, are let go (`detached`). Any failure refuses the whole write as `deny('file_unavailable')`: rolled back, audited as denied, 403. One answer for missing, foreign, pending, taken and unfit files, so it says nothing about other businesses. | Plan B1 row; F3 write hooks ("Throwing rolls the whole write back"). |
| 9 | A CRUD write that parks (an approval) has its new file ids checked at park time (same rules, nothing claimed), so an approval never carries a file the requester could not attach. They are claimed when the approved write replays (as the requester, so the uploader check holds). A command's file fields are checked through its `touched` rows; a command that leaves a changed record out of `touched` leaves its new ids unclaimed, and unclaimed files are reachable only by their uploader (fails closed). A parked command's input is not checked until it runs. | Task ("parked writes are audited"); F3 rule ("Every record you change goes into `touched`"). |
| 10 | One file belongs to one record field. Copying a file to a second record is not built; neither is moving it to another field. | Default: one owner keeps access simple to reason about. |
| 11 | Download URLs are presigned GETs, valid `FILES_URL_TTL_S` (300 s by default), with the stored type and a `Content-Disposition`: `inline` only for raster images, audio, video and PDF; `attachment` for everything else (SVG and HTML included). The file name is sent as an ASCII fallback and as UTF-8 (`filename*`). The local driver's blob route adds `X-Content-Type-Options: nosniff`, a sandboxing `Content-Security-Policy` and `Cache-Control: private`. | Default: stored-XSS defence, since the local driver serves from the API's origin. |
| 12 | `accept` matches `type/*` or exact types. A family (and `*/*`) never matches `image/svg+xml`: SVG must be named. Without `accept`, any type is accepted (still served as an attachment unless safe inline). Sizes: a field's `maxBytes`, capped by `FILES_MAX_BYTES` (25 MiB by default). | Gap map owner question ("Max file size, allowed types"); default. |
| 13 | Drivers: `STORAGE_DRIVER=s3` (MinIO in development, any S3-compatible store elsewhere), `fs` (a folder, `STORAGE_DIR`), `memory` (one process; tests and CI). Production refuses to start with `memory`; `fs` needs `STORAGE_DIR`, `s3` needs its keys. Unset means `memory`, with a warning. Both Vitest configs and CI set `memory`. `application/.env.example` sets `s3` with the local MinIO, because the API and the worker are two processes and memory is per process. | Task ("an in-memory/fs fake (CI uses the fake: STORAGE_DRIVER=memory)"); gap map risk ("CI services are only postgres, redis and mailpit"). |
| 14 | S3: `S3_ENDPOINT` is what the server calls, `S3_PUBLIC_ENDPOINT` what presigned URLs name (a phone on the LAN cannot reach `localhost:9000`), default the same. Path-style addressing whenever an endpoint is set. Checksums only when required (`requestChecksumCalculation: 'WHEN_REQUIRED'`), so presigned PUTs from browsers and phones work. Object keys are `t/<tenant>/<file id>`, made by the server (the id is generated before the insert), never from user input. | Gap map risk ("internal and public endpoints must be configured separately"); probed against the local MinIO. |
| 15 | The bucket is created at startup when it is missing (API and worker, `HeadBucket` then `CreateBucket`). A store that is down logs an error and does not stop the start; file routes answer 503 `storage_unavailable` until it is back, and the next call tries again. CORS is not configured: MinIO allows any origin by default; a production bucket needs a CORS rule for the app's origins. | Task ("Create the MinIO bucket at startup if missing"). |
| 16 | The local driver's URLs are relative (`/api/files/blob/<token>`), signed with HMAC-SHA256 over the grant (key, method, type, size for a PUT, disposition for a GET, expiry), with `STORAGE_SECRET` (derived from `BETTER_AUTH_SECRET` when unset). The route needs no session (the token is the right, as with a presigned S3 URL); a PUT must send the signed type and exactly the signed size. `@hykr/api-client` resolves a relative URL against its base. The route reads the raw body itself (Better Auth's parser takes only JSON and forms; a JSON file's raw bytes are kept by its `rawBody` option). | Default: the API's public address is not in its config, and tests run on a random port. |
| 17 | Images: confirm reads the type and, for JPEG, PNG, GIF and WebP, the width and height. No thumbnails, no re-encoding and no EXIF stripping on the server (there is no image library in `@hykr/api`). The app's picker re-encodes photos at 0.8 quality, which keeps them small on a phone's network. `sha256` is kept for files the server stores itself (it has the bytes); uploads have none (reading back a 25 MiB object to hash it was not worth it). | Gap map ("sharp 0.35.4 comes only through @livekit/agents in framework/voice-worker"); owner question kept. |
| 18 | **Voice.** An audio file can be transcribed: `POST /api/files/:id/transcribe` (and the assistant's `transcribe-file` tool) runs the WhatsApp channel's speech-to-text (Sarvam, or the `FAKE-STT:` notes in tests), keeps the words and their language on the file, and returns them; a second call returns the kept words. Not audio: 422 `not_audio`. A WhatsApp voice note is still turned into words and not stored, as before: the inbound processor transcribes it before any inbound hook runs, and that file is not this unit's to change. The files service takes speech-to-text through a `SPEECH` token, so `@hykr/api`'s entry never loads the channel's configuration. | Gap ("image/voice handling"); PRD Build 7.1 ("DPR by voice: Voice note → Sarvam transcript"); plan hot-file table (`inbound.processor.ts`: F5 → A5 → B7). |
| 19 | **WhatsApp media.** An inbound hook (`files`, a Nest provider that registers itself) stores each image, document or video a person sends: it downloads it through the adapter (the business number scopes the lookup), stores it as a ready file of that contact (and of their account, when the number is linked), marks the `channel.messages` row as `media` with `{ fileId }`, audits `file.received`, and adds one line to the turn: the file's name, type, size and id, and that its id goes in a record's file field. A document keeps its own file name (`filename` is now parsed into `InboundMessage`); others are named `whatsapp-<date>.<ext>`. The assistant then attaches it with the entity's create or update tool. A business turns this off with `files.keepInboundMedia` (a settings section, on by default). A file over the size cap, or one the download fails for, is not kept; the caption still reaches the turn. | Gap ("WhatsApp media kept on records"); F5 decision 24 and the F0 `InboundHook` comment ("store a photo's media"). |
| 20 | The assistant's tools: `get-file` (name, type, size, the record it is on, its kept words; no URL) and `transcribe-file`. Both call the HTTP API as the agent, so the same reach applies; a refusal is answered by the scripted model's engine ("I couldn't do that: No such file."). The scripted model's `files` set (order 300) answers "what does file <id> say", "what is file <id>", and a message that is only a file ("Which record should it go on?"). | Task ("add scripted-model scripts for new tools"). |
| 21 | **Erasure.** The `files` erasure contributor marks every file the subject sent (a contact: what came from that number; a person: what they uploaded, WhatsApp files of their linked number included) as erased in the erasure's transaction (its name and words are cleared at once) and counts them; the sweeper deletes their objects afterwards, so a rolled-back erasure deletes nothing. A record that held such a file keeps the id; the file answers 404. The export contributor lists the subject's files (kind `files`: id, name, type, size, source, status, words, when, the record it is on). | F5 decision 25; gap map ("erasure would need to cover objects"). |
| 22 | The sweeper (`files.sweep`, every 10 minutes) deletes, rows first and then objects: pending uploads older than a day, ready files never put on a record and files let go of after `FILES_DETACHED_GRACE_H` (168 hours), and erased files at once. Rows go first (locked, `SKIP LOCKED`) with a `file.swept` audit row each, so a file put back on its record meanwhile is never half deleted; an object whose delete fails is only logged. | Default: a grace period lets a removed file come back (an undo) before it is gone. |
| 23 | Abuse limits: at most `FILES_MAX_PENDING` (50) unconfirmed uploads per person in a day (429 `too_many_uploads`). Malware scanning and per-business quotas are not built. | Gap map owner questions; default. |
| 24 | Audit: `file.upload`, `file.confirm`, `file.discard`, `file.received` (WhatsApp) or `file.stored` (other server files), `file.transcribe`, `file.attach`, `file.detach` and `file.swept` rows (resource type `file`), besides the owning record's own write rows. Uploads are framework infrastructure written by the files service with its own audit rows, as the channel's tables are; the business write (attaching) goes through `runWrite`. `auditCtx` is now exported from `@hykr/core` so features audit like the write path. | CLAUDE.md rule 1 (one write path for records); default for infrastructure tables. |
| 25 | Server code stores files too: `FilesService.storeBytes({ tenantId, uploader, name, mime, bytes })` (`@hykr/api`) gives a ready file on no record. `uploader: { kind: 'server' }` makes a file only a system principal of that business can attach, for documents (B2), job results (B11) and import reports (B20). `bytesOf(row)` and `urlFor(row)` read and sign it. | Plan DAG (`B2←B1`, `B11←B1`, `B20←B1`). |
| 26 | The app: `<FileField label entity field recordId value onChange />` (`@hykr/app`) reads the field's policy from the catalog, shows its files (thumbnails for raster images), adds from the photo library, the camera (not on web) or the file picker (`expo-image-picker`, `expo-document-picker`) as `accept` allows, uploads each pick at once, and removes; the record keeps the ids when the form is saved. `<FileThumbs ids />` shows a record's files, each opening its URL. `useFiles(ids)` refetches every 4 minutes, before URLs expire. The mobile app adds the `expo-image-picker` config plugin with its permission strings (no microphone). Outbound media on WhatsApp (sending a document) is B2's. | Plan ("pickers in the app"); F6 decision 26 ("Expo config plugins … B1"). |
| 27 | `/api/files` is reserved for the framework (`reserveRoutes('files')`, loaded with `@hykr/api`'s entry), and the table `app.files` is the framework's. | CLAUDE.md ("A framework feature with its own `/api/<x>` routes calls `reserveRoutes`"). |
| 28 | The sample: `notes` keeps up to ten images of 10 MB (`photos`), shown in the editor (`FileField`), the detail screen, the card and the list (a count). Its scripted model's `note-with-photos` script turns a WhatsApp photo captioned "note <title>" into a new note with that photo; its rules tell a real model the same. | Task ("Sample demo: notes: photo attachments"). |

## Assumptions to review

| Topic | What we chose | Question for the product owner |
|---|---|---|
| Production store | Any S3-compatible store, configured per deployment; MinIO in development | Which store and region in production (S3 ap-south-1, R2, self-hosted MinIO)? Must files stay in India? |
| Sizes and types | Per field (`accept`, `maxBytes`); deployment cap 25 MiB; SVG only when named | What is the largest file, and which types are allowed (photos, PDFs, CAD drawings, videos)? |
| Thumbnails and EXIF | Originals only on the server; the app re-encodes picked photos at 0.8 quality; no EXIF (GPS) stripping | Should photos be resized, and their location data removed, on upload? |
| WhatsApp media | Kept by default; a business can turn it off; the assistant puts it on a record | Should photos and documents sent on WhatsApp be kept? Should anything be attached without the assistant (for example to the conversation)? |
| WhatsApp voice notes | Transcript only, as before; the audio is not kept | Should voice-note audio be kept with the record, or only its words? |
| Erasure | Everything a person or contact sent is erased; records keep a dangling id | Should "delete my data" remove the files people sent from business records (it does), and should staff see that a file was erased? For staff accounts, should their uploads to business records stay? |
| Attaching another person's upload | Only the uploader can attach a file on no record | Should staff be able to attach a file a customer sent on WhatsApp to a business record themselves? |
| Retention | Removed or never-used files are deleted 7 days later | How long should a removed file be recoverable? |
| Quotas and scanning | None | Is there a storage quota per business? Is malware scanning required for files from outside parties? |

## API sketch

```ts
// @hykr/contracts
interface EntityTraits { files?: Record<string, FileFieldPolicy> }
interface FileFieldPolicy { accept?: readonly string[]; maxBytes?: number; max?: number }
FileRef                       // z.uuid(), described for the model
fileRefs(max = 20)            // z.array(FileRef).max(max)
fileFieldsOf(spec): [field, FileFieldPolicy][]
acceptsMime(policy, mime): boolean;  fileIdsIn(value): string[];  baseMime(mime)
FileInfo                      // { id, name, mime, size, status, source, width, height, transcript,
                              //   transcriptLang, attachedTo: { entity, id, field } | null, createdAt,
                              //   url?, urlExpiresAt? }
PresignFileInput              // { name, mime, size, for: { entity, field, id? } }
PresignFileResult             // { file: FileInfo, upload: { url, method: 'PUT', headers, expiresAt } }
TenantSettingsSections.files  // { keepInboundMedia: boolean }  (default true)

// @hykr/db
files                         // app.files
fileColumn(name), fileColumns(name)

// HTTP (framework/api/src/features/files)
POST   /api/files                  presign (people)                          201
POST   /api/files/:id/confirm      (people)                                  200
GET    /api/files/:id              metadata + download URL, through the record
GET    /api/files?ids=a,b          the ones the caller reaches               { items }
DELETE /api/files/:id              an upload on no record, by its uploader   204
POST   /api/files/:id/transcribe   an audio file's words                     200
PUT|GET /api/files/blob/:token     the local driver's signed URLs (no session)

// @hykr/api
FilesService (storeBytes, bytesOf, urlFor, get, getMany, sweep), STORAGE, StorageDriver,
StorageUnavailable, SPEECH, filesConfig, fileLine
filesFeature: writeHooks [files], erasureContributors [files], exportContributors [files],
              queues [files.sweep], schedules [files.sweep], toolContributions [files:
              get-file, transcribe-file], inbound hook 'files' (a provider)

// @hykr/api-client
api.files.presign(input) / confirm(id) / get(id) / getMany(ids) / remove(id) / transcribe(id)
api.files.upload(body: Blob | ArrayBuffer | Uint8Array, { name, mime, for }): Promise<FileInfo>

// @hykr/app
useFiles(ids), useFileUpload(), fileFieldPolicy(entity, field), pickPhotos(), pickDocuments(),
<FileField label entity field recordId value onChange multiple? hint? />, <FileThumbs ids onRemove? />
```

Env: `STORAGE_DRIVER`, `STORAGE_DIR`, `STORAGE_SECRET`, `S3_ENDPOINT`, `S3_PUBLIC_ENDPOINT`,
`S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `FILES_MAX_BYTES`,
`FILES_URL_TTL_S`, `FILES_UPLOAD_TTL_S`, `FILES_DETACHED_GRACE_H`, `FILES_MAX_PENDING`.

## Deferred

- Thumbnails, re-encoding and EXIF stripping on the server (no image library in `@hykr/api`).
- Keeping WhatsApp voice-note audio (needs `inbound.processor.ts`, owned by F5 → A5 → B7).
- Sending media on WhatsApp and attachments by email (B2).
- A file on two records, moving a file between fields, versioned files of a record (a later
  "documents" feature can build on file fields).
- In-app audio recording (needs `expo-audio`, not installed); the app picks audio files instead.
- Per-business quotas (A3) and malware scanning.
- Objects of a deleted business, and files of rows deleted outside the write path (a cascade):
  their rows go with the business, or stay attached; the objects stay in the bucket.
- Multipart uploads for files over 5 GiB.
- A parked command's file ids are checked only when it runs.
- Pinning the MinIO image in compose (it is `:latest` from Chainguard; no tag was verified here).
