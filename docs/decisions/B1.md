# B1: files and media

## Summary

Records can carry files. An entity declares which of its fields hold files (the `files` trait,
with an accept list, a size cap and a count per field) and gives them the `FileRef` type: a file
id, or a list of them. People upload in three steps: `POST /api/files` (presign, for one entity's
file field), a `PUT` of the bytes straight to object storage, then `POST /api/files/:id/confirm`.
The file becomes part of a record when a write puts its id in a file field; that write goes
through `runWrite` like any other, with its rules, approvals and audit. From then on the file is
reached only through the record that owns it: whoever can read that record, and still sees that
field, gets a short-lived download URL (`GET /api/files/:id`); everyone else gets 404.

Storage sits behind one driver interface: S3-compatible (MinIO in development, any S3 in
production, its bucket created at startup when missing) and a local driver, in memory (tests and
CI) or on disk, whose signed URLs the API serves itself. Images are checked against their bytes
and their size in pixels is kept. Audio files can be transcribed (the existing speech-to-text). A
photo, document or video that arrives on WhatsApp is stored by an inbound hook and named to the
assistant's turn, so the assistant can put it on a record. "Delete my data" erases what a person
sent, and a sweeper removes abandoned uploads and files a record let go of.

The sample's `notes` module keeps photos on a note.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | A file field holds file **ids** (`FileRef` is a uuid; `fileRefs(max)` a list of them), not copies of the file's metadata. Metadata and URLs come from `/api/files`. A record round-trips unchanged (a client sends back what it read), nothing on the record can drift from the stored file, and the assistant passes ids like any other reference. | Plan B1 row ("`FileRef` field type"); default: ids are what the read path can check synchronously, and URLs must be fresh anyway. |
| 2 | Which fields hold files, and what each accepts, is declared on the spec: `traits: { files: { photos: { accept: ['image/*'], maxBytes, max } } }`. At startup the files feature checks every served entity with the trait: each field is in the read schema and in the create or update schema, and the table has a column with that key. A mistake stops the start. | Plan ("Traits … a feature declares its key on `EntityTraits`"); fail closed. |
| 3 | Columns: `fileColumn(name)` (text, nullable) and `fileColumns(name)` (text[], default empty) from `@hykr/db`. The column's key is the field's name. | Default: matches how other columns are declared; text[] reads back as `string[]`. |
| 4 | Upload is presign → PUT → confirm. The presigned PUT signs `content-type` and `content-length`, so the store refuses any other type or size (checked against MinIO). Confirm reads the object's head and first bytes: the size must match, and a declared image or PDF must start with that type's magic bytes, or the object is deleted and confirm answers 422. Multipart through the API is not built: the API keeps its own body parsing (Better Auth parses JSON only), and bytes never pass through it for S3. | Gap map B1 risks ("Multer multipart on the same app may conflict. Presigned direct-to-bucket upload avoids this"); plan ("presign → confirm → get"). |
| 5 | A presign names what the file is for: `{ entity, field, id? }`. The field's accept list and size cap apply before anything is stored; with `id`, the person must be able to update that record now (`def.decide`), without it they must be able to create one. Refusals are 403 with the rule (`no_access`, …), an unknown entity or field is 400. | Plan ("scoped through the owning row"); fail closed. |
| 6 | Upload routes (presign, confirm, discard, transcribe) are for people: `HumanOnlyGuard`. The assistant has no bytes to send; it attaches files it was given (WhatsApp) and reads their metadata. Reads (`GET /api/files/:id`, `GET /api/files?ids=`) accept agents too. | Default: least privilege for agents; "the assistant is a user" still holds for reads and attaching. |
| 7 | **Who reaches a file.** Same business, always. An attached file: the owning record must be reachable by the principal (the entity's scoped `repo.find`, so its access, grants and plugins' scopes apply), an agent needs the entity's `get` exposed, and the record **as projected for that principal** (`def.toRead(row, p)`) must still list the file in that field. So a hidden field (field policy, a read projector) hides its files too. An unattached file (uploaded, not yet on a record): only whoever uploaded it (same user, or same WhatsApp contact). A detached or erased file: nobody. Anything else is 404, never 403. | Plan ("scoped through the owning row"), gap map ("never by guessable object key"), task ("hidden fields stay hidden", "another tenant gets 404"). |
| 8 | **Attaching is the record's write.** A write hook (`files`, `afterRun`, in the write's transaction) compares each touched record's file fields before and after. Every new id must be a ready file of this business that is either unattached and uploaded by the same subject, or already this record's in this field (a detached one can come back until it is swept); its type and size must fit the field, and the field's count cap holds. Then it is claimed (`resource_type`, `resource_id`, `field`). Ids that left the field, and every file of a deleted record, are detached. Any failure refuses the whole write as `deny('file_unavailable')`: rolled back, audited as denied, 403. One answer for missing, foreign, pending and taken files, so it says nothing about other businesses. | Plan B1 row; F3 write hooks ("Throwing rolls the whole write back"). |
| 9 | A write that parks (an approval) has its new file ids checked at park time (same rules, nothing claimed), so an approval never carries a file the requester could not attach. They are claimed when the approved write replays. A command's file fields are checked through its `touched` rows; a command that leaves a changed record out of `touched` leaves its new ids unclaimed, and unclaimed files are visible only to their uploader (fails closed). | Task ("parked writes are audited"); F3 rule ("Every record you change goes into `touched`"). |
| 10 | One file belongs to one record field. Copying a file to a second record is not built. | Default: one owner keeps access simple to reason about. |
| 11 | Download URLs are presigned GETs, valid `FILES_URL_TTL_S` (300 s by default), with the stored type and a `Content-Disposition`: `inline` only for raster images, audio, video and PDF; `attachment` for everything else (SVG and HTML included). The local driver's blob route adds `X-Content-Type-Options: nosniff` and a sandboxing `Content-Security-Policy`. URLs are never given to the assistant's tools. | Default: stored-XSS defence, since the local driver serves from the API's origin. |
| 12 | `accept` matches `type/*` or exact types. `image/*` does not match `image/svg+xml`: SVG must be named. Without `accept`, any type is accepted (still served as an attachment unless safe inline). Sizes: a field's `maxBytes`, capped by `FILES_MAX_BYTES` (25 MiB by default). | Gap map owner question ("Max file size, allowed types"); default. |
| 13 | Drivers: `STORAGE_DRIVER=s3` (MinIO in development, any S3-compatible store elsewhere), `fs` (a folder, `STORAGE_DIR`), `memory` (one process; tests and CI). Production refuses to start without `s3` or `fs`. Unset elsewhere means `memory`, with a warning. Both Vitest configs and CI force `memory`. | Task ("an in-memory/fs fake (CI uses the fake: STORAGE_DRIVER=memory)"); gap map risk ("CI services are only postgres, redis and mailpit"). |
| 14 | S3: `S3_ENDPOINT` is what the server calls, `S3_PUBLIC_ENDPOINT` what presigned URLs name (a phone on the LAN cannot reach `localhost:9000`), default the same. Path-style addressing whenever an endpoint is set. Checksums only when required (`requestChecksumCalculation: 'WHEN_REQUIRED'`), so presigned PUTs from browsers and phones work. Object keys are `t/<tenant>/<file id>`, never from user input. | Gap map risk ("internal and public endpoints must be configured separately"); probed against the local MinIO. |
| 15 | The bucket is created at startup when it is missing (API and worker, `HeadBucket` then `CreateBucket`). A store that is down logs an error and does not stop the start; file routes answer 503 `storage_unavailable` until it is back, and the next call tries again. CORS is not configured: MinIO allows any origin by default; a production bucket needs a CORS rule for the app's origins (documented). | Task ("Create the MinIO bucket at startup if missing"). |
| 16 | The local driver's URLs are relative (`/api/files/blob/<token>`), signed with HMAC-SHA256 over the key, method, type, size cap and expiry, with `STORAGE_SECRET` (derived from `BETTER_AUTH_SECRET` when unset). `@hykr/api-client` resolves a relative URL against its base. | Default: the API's public address is not in its config, and tests run on a random port. |
| 17 | Images: confirm checks the magic bytes of JPEG, PNG, GIF, WebP, HEIC/HEIF and PDF against the declared type, and keeps the width and height of the first four. No thumbnails, no re-encoding and no EXIF stripping (there is no image library in `@hykr/api`): the app shows the original, sized down. | Gap map ("sharp 0.35.4 comes only through @livekit/agents in framework/voice-worker"); owner question kept. |
| 18 | **Voice.** An audio file can be transcribed: `POST /api/files/:id/transcribe` (and the assistant's `transcribe-file` tool) runs the WhatsApp channel's speech-to-text (Sarvam, or the `FAKE-STT:` notes in tests), keeps the words and their language on the file, and returns them; a second call returns the kept words. A WhatsApp voice note is still turned into words and not stored, as before: the inbound processor transcribes it before any inbound hook runs, and that file is not this unit's to change. | Gap ("image/voice handling"); PRD Build 7.1 ("DPR by voice: Voice note → Sarvam transcript"); plan hot-file table (`inbound.processor.ts`: F5 → A5 → B7). |
| 19 | **WhatsApp media.** An inbound hook (`files`) stores each image, document or video a person sends: it downloads it through the adapter (the business number scopes the lookup), stores it as a ready file uploaded by that contact (and their account, when the number is linked), marks the `channel.messages` row as `media` with the file id, audits `file.received`, and adds one line to the turn: the file's id, name, type and size, and that its id goes in a record's file field. The assistant then attaches it with the entity's update or create tool. A business can turn this off (`files.keepInboundMedia`, on by default). A file over the size cap, or one the download fails for, is not kept; the caption still reaches the turn. | Gap ("WhatsApp media kept on records"); F5 decision 24 and the F0 `InboundHook` comment ("store a photo's media"). |
| 20 | The assistant's tools: `get-file` (name, type, size, the record it is on, its kept words; no URL) and `transcribe-file`. Both call the HTTP API as the agent, so the same reach applies. The scripted model's `files` set answers "what does file <id> say" and acknowledges a message that is only a file. | Task ("add scripted-model scripts for new tools"). |
| 21 | **Erasure.** The `files` erasure contributor marks every file the subject sent (a contact: what came from that number; a person: what they uploaded) as erased, in the erasure's transaction, and counts them; the sweeper deletes their objects afterwards, so a rolled-back erasure deletes nothing. A record that held such a file keeps the id; the file answers 404. The export contributor lists the subject's files (kind `files`: id, name, type, size, when, the record it is on). | F5 decision 25; gap map ("erasure would need to cover objects"). |
| 22 | The sweeper (`files.sweep`, every 10 minutes): deletes pending uploads older than a day, detached files after `FILES_DETACHED_GRACE_H` (168 hours), and erased files, objects first. | Default: a grace period lets a removed file come back (an undo) before it is gone. |
| 23 | Abuse limits: at most `FILES_MAX_PENDING` (50) unconfirmed uploads per person in a day (429 `too_many_uploads`). Malware scanning and per-business quotas are not built. | Gap map owner questions; default. |
| 24 | Audit: `file.upload`, `file.confirm`, `file.discard`, `file.received`, `file.transcribe`, `file.attach` and `file.detach` rows (resource type `file`), besides the owning record's own write rows. Uploads are framework infrastructure written by the files service with its own audit rows, as the channel's tables are; the business write (attaching) goes through `runWrite`. | CLAUDE.md rule 1 (one write path for records); default for infrastructure tables. |
| 25 | Server code stores files too: `FilesService.store({ tenantId, uploader, name, mime, bytes })` gives a ready, unattached file, for documents (B2), job results (B11) and import reports (B20). | Plan DAG (`B2←B1`, `B11←B1`, `B20←B1`). |
| 26 | The app: `<FileField>` (`@hykr/app`) shows a file field's files (thumbnails for images), adds from the photo library, the camera or the file picker (`expo-image-picker`, `expo-document-picker`), uploads with `useFileUpload`, and removes. `useFiles(ids)` fetches metadata and fresh URLs through the record's reach. The mobile app adds the `expo-image-picker` config plugin with its permission strings. Outbound media on WhatsApp (sending a document) is B2's. | Plan ("pickers in the app"); F6 decision 26 ("Expo config plugins … B1"). |
| 27 | `/api/files` is reserved for the framework (`reserveRoutes('files')`), and the table `app.files` is the framework's. | CLAUDE.md ("A framework feature with its own `/api/<x>` routes calls `reserveRoutes`"). |

## Assumptions to review

| Topic | What we chose | Question for the product owner |
|---|---|---|
| Production store | Any S3-compatible store, configured per deployment; MinIO in development | Which store and region in production (S3 ap-south-1, R2, self-hosted MinIO)? Must files stay in India? |
| Sizes and types | Per field (`accept`, `maxBytes`); deployment cap 25 MiB; SVG only when named | What is the largest file, and which types are allowed (photos, PDFs, CAD drawings, videos)? |
| Thumbnails and EXIF | Originals only; no resizing, no EXIF (GPS) stripping | Should photos be resized, and their location data removed, on upload? |
| WhatsApp media | Kept by default; a business can turn it off; the assistant puts it on a record | Should photos and documents sent on WhatsApp be kept? Should anything be attached without the assistant (for example to the conversation)? |
| WhatsApp voice notes | Transcript only, as before; the audio is not kept | Should voice-note audio be kept with the record, or only its words? |
| Erasure | What a person sent is erased; records keep a dangling id | Should "delete my data" also remove the files people sent from business records (it does), and should staff see that a file was erased? |
| Attaching another person's upload | Only the uploader can attach an unattached file | Should staff be able to attach a file a customer sent on WhatsApp to a business record themselves? |
| Retention | Removed files are deleted 7 days later | How long should a removed file be recoverable? |
| Quotas and scanning | None | Is there a storage quota per business? Is malware scanning required for files from outside parties? |

## API sketch

```ts
// @hykr/contracts
interface EntityTraits { files?: Record<string, FileFieldPolicy> }
interface FileFieldPolicy { accept?: readonly string[]; maxBytes?: number; max?: number }
FileRef                       // z.uuid(), described for the model
fileRefs(max = 20)            // z.array(FileRef).max(max)
fileFieldsOf(spec): [field, FileFieldPolicy][]
acceptsMime(policy, mime): boolean;  fileIdsIn(value): string[]
FileInfo                      // { id, name, mime, size, status, width, height, transcript, transcriptLang,
                              //   source, attachedTo: { entity, id, field } | null, createdAt, url?, urlExpiresAt? }
PresignFileInput              // { name, mime, size, for: { entity, field, id? } }
PresignFileResult             // { file: FileInfo, upload: { url, method: 'PUT', headers, expiresAt } }
TenantSettingsSections.files  // { keepInboundMedia: boolean }  (default true)

// @hykr/db
files                         // app.files
fileColumn(name), fileColumns(name)

// HTTP (framework/api/src/features/files)
POST   /api/files                  presign (people)
POST   /api/files/:id/confirm      (people)
GET    /api/files/:id              metadata + download URL, through the owning record
GET    /api/files?ids=a,b          the ones the caller reaches
DELETE /api/files/:id              an unattached file, by its uploader (people)
POST   /api/files/:id/transcribe   an audio file's words (people)
PUT|GET /api/files/blob/:token     the local driver's signed URLs (no session; the token is the right)

// @hykr/api
STORAGE, type StorageDriver, FilesService (store, read, urlFor)
filesFeature: entityPlugins [files], writeHooks [files], erasureContributors [files],
              exportContributors [files], queues [files.sweep], schedules [files.sweep],
              toolContributions [files: get-file, transcribe-file], inbound hook 'files' (a provider)

// @hykr/api-client
api.files.presign(input) / confirm(id) / get(id) / getMany(ids) / remove(id) / transcribe(id)
api.files.upload(body: Blob | Uint8Array, { name, mime, for }): Promise<FileInfo>

// @hykr/app
useFiles(ids), useFileUpload(), <FileField value onChange entity field label multiple />
```

Env: `STORAGE_DRIVER`, `STORAGE_DIR`, `STORAGE_SECRET`, `S3_ENDPOINT`, `S3_PUBLIC_ENDPOINT`,
`S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `FILES_MAX_BYTES`,
`FILES_URL_TTL_S`, `FILES_UPLOAD_TTL_S`, `FILES_DETACHED_GRACE_H`, `FILES_MAX_PENDING`.

## Test plan

- `framework/contracts/src/framework/files.test.ts` (unit): `accept` matching (`image/*` is not SVG), ids from a value, a spec's file fields.
- `framework/api/src/features/files/sniff.test.ts` (unit): magic bytes and dimensions of JPEG, PNG, GIF, WebP; a mismatch.
- `framework/api/src/features/files/storage/local.test.ts` (unit): signed tokens (expiry, tampering, method), the memory and fs drivers.
- `framework/api/src/features/files/storage/s3.test.ts` (integration, skipped when MinIO is not reachable): bucket created when missing, presigned PUT refuses a wrong size or type, head, ranged read, GET URL, delete.
- `framework/api/test/framework/files.e2e.test.ts` (fixture `features/files`, a `cards` module with a photo field, an attachments list and a field hidden from staff):
  - presign → PUT → confirm → attach on create → `GET /api/files/:id` with a URL that serves the bytes;
  - another business: 404 on get, confirm, discard and in `?ids=`; its file id refused on attach (`file_unavailable`, audited as denied);
  - a field hidden from staff: its file is 404 for staff, visible to the owner;
  - an unattached file: only its uploader sees it; a colleague with the record's reach cannot attach it;
  - presign refusals: unknown field (400), wrong type, too large (413), no write reach (403), agents (403);
  - confirm refusals: size or magic bytes wrong (422), nothing uploaded (409);
  - a parked agent write with a file: approval and park audited, nothing claimed; approved: claimed;
  - removing a file from a record detaches it (404 afterwards); deleting the record detaches all; the sweeper deletes detached and stale pending files;
  - transcription of an audio file (fake STT), kept on the file; the `get-file`/`transcribe-file` tools through the scripted model;
  - WhatsApp: a photo is stored for the contact, the message row becomes `media`, the turn names it and the scripted model attaches it to a record; the setting off keeps nothing; "delete my data" erases it (audited count) and the sweeper removes its object.
- `application/api/test/domain/note-photos.e2e.test.ts`: a note with photos, a stranger's 404, a parked agent write.
- Unchanged and green: the delivery e2e (its stand-in Cloud API has no media, so the files hook fails quietly and is skipped).

## Deferred

- Thumbnails, re-encoding and EXIF stripping (no image library in `@hykr/api`).
- Keeping WhatsApp voice-note audio (needs `inbound.processor.ts`, owned by F5 → A5 → B7).
- Sending media on WhatsApp and attachments by email (B2).
- A file on two records; versioned files of a record (a later "documents" feature can build on file fields).
- In-app audio recording (needs `expo-audio`, not installed); the app picks audio files instead.
- Per-business quotas (A3) and malware scanning.
- Orphan detection for records deleted outside the write path (a cascade): their files stay attached until erased.
- Multipart uploads for files over 5 GiB.
