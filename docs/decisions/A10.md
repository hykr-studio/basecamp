# A10: model gateway and per-business model policy

## Summary

The assistant's models come from a **deployment registry** of OpenAI-compatible providers, set in
the environment (`MODEL_PROVIDERS`: base URL, key, region, models and their prices). In development,
`OPENROUTER_API_KEY` adds OpenRouter as one more provider of the same kind. The registry is closed:
a model nobody configured cannot run, and Mastra's model-router strings (which read any
`*_API_KEY`) are no longer used. The framework names no model and no provider of its own.

Each business has a **model policy**, the `models` settings section: the models it allows, the chat
and embedding models it uses, and the regions its providers must be in. Every turn's model is
chosen after the turn hooks (a hook may ask for one) and checked against the registry and the
policy. A model that is unknown, not allowed or in the wrong region refuses the turn; nothing falls
back to another model or provider. The agent resolves its model per turn from the request context,
the prompt-injection guardrail uses the same model, and `agentVersion` (id + model + prompt hash)
names the turn's model on every audit row. Embeddings (for A8) and prices (for A3) go through the
same registry and policy.

`GET /api/models` says what a business may use. `PUT /api/models/policy` sets the policy through
`runWrite` (audited, idempotent, parkable by a write hook), for people with `models.manage`.

The sample application's part is configuration: `application/.env.example` keeps OpenRouter for
development and shows an in-country gateway (`MODEL_PROVIDERS`, region `in`, prices in INR minor
units) for production.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | The registry is read from `MODEL_PROVIDERS`, a JSON array of providers: `{ id, baseUrl, apiKeyEnv? \| apiKey?, headers?, region?, models: [{ id, kind?, label?, price? }] }`. A model's ref is `<provider id>/<model id>` (the model id may contain `/`). Each provider is built with `@ai-sdk/openai-compatible` (`createOpenAICompatible`, `includeUsage: true`), so any OpenAI-compatible gateway works: one in-country for production, OpenRouter for development. | Gap A10 ("OpenAI-compatible provider configured per deployment (base URL, key, models, prices)"); plan note ("MODEL_PROVIDERS or similar env"); F6 added `@ai-sdk/openai-compatible` 3.0.63 for this. |
| 2 | `apiKeyEnv` names the variable that holds the key, so the key stays in the deployment's secret store and out of the JSON; `apiKey` inline is accepted too (not both). A provider with neither sends no `Authorization` (a gateway inside a private network). A named variable that is empty is warned about at startup; the provider's calls then fail (no fallback). | Default. |
| 3 | Malformed `MODEL_PROVIDERS` (bad JSON, a field of the wrong type, a duplicate provider id or model ref, the reserved provider id `fake`) stops the API and the worker at startup (`ModelPolicyService.onModuleInit`) with every problem listed (`ModelConfigError`). | Default, fail fast: a residency setting that is silently ignored is worse than a failed deploy. |
| 4 | The registry is closed: only configured providers and the models they list. A turn hook or a policy naming any other model is refused. | Gap map risk ("Silently falling back to OpenRouter outside India would break residency. The policy must fail closed"). |
| 5 | OpenRouter stays for development: with `OPENROUTER_API_KEY` set and no provider `openrouter` in `MODEL_PROVIDERS`, the registry adds `openrouter` (`https://openrouter.ai/api/v1`, `OPENROUTER_BASE_URL` overrides) with the models named by `AGENT_MODEL` and `EMBEDDING_MODEL` (when they start with `openrouter/`) and `OPENROUTER_MODELS` (comma-separated chat model ids). It has no region and no prices. To price it, declare it in `MODEL_PROVIDERS` like any provider. | Gap A10 ("OpenRouter stays for development"). |
| 6 | The deployment's defaults: `AGENT_MODEL` for chat and `EMBEDDING_MODEL` for embeddings; without them, the first listed model of that kind. A default that is not in the registry is logged at startup and every turn answers 503 `model_not_configured` naming it, before any turn hook runs, as the old key check did. The framework's built-in model id (`openrouter/openai/gpt-6-luna`) is gone; it lives in `application/.env.example`. | Default; boundary rule (no product configuration in `framework/`). |
| 7 | A price is `{ currency, inputPerMillion, outputPerMillion? }` (`ModelPrice` in `@hykr/contracts`): the cost to the deployment, in the currency's **minor units** per million tokens, with an ISO 4217 currency. Rates may be fractional (a gateway charges fractions of a minor unit per token). `costOf(ref, usage)` returns whole minor units, rounded up per call. An unpriced model has no cost (`undefined`); A3 decides what that means for credits. | Gap map risk ("A price table per model is needed for credits (A3)"); boundary rule (money is minor units plus an ISO currency; no currency in the framework). Rounding up: caps trigger early rather than late. |
| 8 | The business's policy is the settings section `models` (`contracts/src/settings/models.ts`): `{ allowed: ref[], chat?: ref, embedding?: ref, regions: string[] }`, every field defaulted. | Gap A10 ("per-tenant model policy (allowed models, fails closed)"); plan (`settings/models.ts`); gap map ("A TenantSettings.modelPolicy field (allowed models, region, fallback)"). |
| 9 | A business with an empty `allowed` list may use the deployment's default of each kind only, never another registered model. With a list, it may use exactly those. With `regions`, a model's provider must declare one of them (a provider without a region matches none). No business (no `tenantId`) gets the empty policy. | Default, fail closed (see Assumptions). |
| 10 | A turn's model: the first one a turn hook asks for, else the business's `chat`, else the deployment's default. It must be registered as a chat model (503 `model_not_configured` / `model_unknown`), allowed by the business and in its regions (403 `model_not_allowed`). Settings that do not parse refuse the turn (503 `model_policy_invalid`). No fallback. All refusals are `{ error: 'turn_refused', rule, reason }`, nothing saved. | Gap A10; F5 decision 15 ("the first hook that names a model wins") and 16 (the key check becomes a hook, generalized here). |
| 11 | The check lives in `gateTurn` (`modules/chat/turn-hooks.ts`), through a `ModelGate` slot that the `models` feature's `ModelPolicyService` fills in `onModuleInit` (`setModelGate`). `ready()` (is the deployment's default chat model configured) runs before the turn hooks, so a misconfigured deployment spends no credits or recall; `choose()` runs after them, so a hook's model is checked too. If the slot is empty (the feature did not load), every turn is refused (503). F5's `model-key` hook is removed. `ChatService` (F5's hot file) is unchanged: the chosen ref reaches the agent through `shape.model`, which `applyShape` already puts in the request context. | Plan hot-file table (`chat.service.ts`: F5 only, later gaps use TurnHooks); developer guide 5.10 ("A turn hook that needs DI is a Nest provider that registers itself in `onModuleInit`"). A plain turn hook cannot see the other hooks' answers, so it could not check a hook's model. |
| 12 | `TurnInfo.model` is set once the model is chosen, so `after` hooks see which model ran (A3 prices the usage with `costOf(turn.model, outcome.usage)`). `before` hooks run before it is chosen and see it unset. | Default; needed by A3. |
| 13 | The agent resolves its model per turn (`turnModel` / `modelFor`): the request context's `model`, built through the registry. A turn for a business (`tenantId` in the request context) without a `model` throws `ModelNotChosen`: only a turn the policy chose a model for can reach one. Studio and the evals (no business) use the deployment's default. | Plan note ("dynamic resolver through F5 requestContext"); fail closed for later callers (A6 agent runs, A7 resumes). |
| 14 | `agentVersion(instructions, model)` is computed per request: `assistant@<the turn's model ref>#<prompt hash>`. The tools' API client stamps it on every call (`x-agent-version`, read from the tool's request context), so two businesses on different models leave different versions in the audit trail. | PRD tab 1, 7.2 ("agent version = ID + model + prompt hash"); F5 Deferred ("Per-turn agentVersion when a hook picks the model (A10)"). |
| 15 | The prompt-injection guardrail (`GUARDRAILS=on`) is built per turn (Mastra's dynamic `inputProcessors`) with the turn's model, so the person's text never reaches a model the business does not allow. | Gap map extension point ("The same policy applied to the guardrail detector, embeddings (A8) and any LLM scorers"). |
| 16 | Embeddings go through the same registry and policy: `ModelPolicyService.embeddingFor(tenantId)` returns `{ ref, model }` (an AI SDK embedding model) for the business's `embedding`, else the deployment's default, checked like a chat model, or throws `ModelRefused`. | Plan A8 ("Embeddings go through A10"); gap map extension point. |
| 17 | No scorer uses a model today (all are code scorers), so there is nothing else to route. A future LLM scorer takes its model from `modelFor`. | Read from `framework/agents/src/scorers.ts`. |
| 18 | In fake mode (`MODEL_MODE=fake`) the scripted model answers every turn, as before. The registry also holds the in-process provider `fake`: `fake/scripted` (chat) and `fake/embedding` (a deterministic word-hashing embedding, so memory recall can be tested offline). They are fake mode's defaults and every policy allows them (nothing leaves the process). A model a hook or the business names is checked exactly as in live mode, so the policy is testable with the scripted model. `agentVersion` names `fake/scripted`, the model that answered. `AGENT_MODEL` is ignored in fake mode. | Plan note ("Fake model unaffected"); MODEL_MODE=fake in every test. |
| 19 | The agent decides fake or live per turn (`MODEL_MODE` read on each call), not once per process, so a test can run turns against a real OpenAI-compatible server after booting in fake mode. | Default; needed by the live e2e tests (decision 25). |
| 20 | `GET /api/models` (people only, any member): the business's policy, the chat and embedding model a turn would use (or the refusal's rule and reason; `embedding` is null when the deployment has no embedding model), and the deployment's models with `allowed` for this business. A model's `price` is shown only to `models.manage`. Settings that do not parse: 503 `model_policy_invalid`. | Default. Prices are the deployment's cost, not something every member needs. |
| 21 | `PUT /api/models/policy` replaces the policy. People only, signed in (`session` assurance), with the capability `models.manage` (owner and admin by default, contributed by the feature). It goes through `runWrite` as the operation `models.policy.set` on the resource `tenant`: one `tenant.update` audit row with the policy before and after, plus the command's row; a refusal is audited as `denied`; an idempotency key replays; a write hook may park it, and the approval replays it (`registerOp`). Unknown body keys are refused. It writes only the `models` key of the stored settings (`jsonb_set`, the row locked), from the stored row as it is, so an owner can repair settings that do not parse. | Gap map owner question ("Who sets the policy: the platform operator (B19) or each studio?"): default is the business's owner or admin, within what the deployment offers; CLAUDE.md rule 1 (one write path). |
| 22 | A policy is checked before it is saved (400 `invalid_policy` with every problem): every allowed ref is registered and in the regions; a `chat` or `embedding` it names is registered, of the right kind and allowed; and the chat model it would use (its own, else the deployment's default) is allowed, since otherwise every turn would be refused. An embedding model it does not name is not checked: embeddings are refused when asked for, and turns still run. It is checked again when it runs; an approval replayed after the deployment changed fails (409, the approval is closed as failed). | Default, fail closed; usability (a policy that refuses every turn is a mistake, a business without memory recall may be deliberate). |
| 23 | Changing the policy emits the named event `models.policy.changed` (`{ id, models }`, stored in the outbox). The API process that wrote it forgets its cached settings at once (`TenantConfigService.invalidate`); other processes see it when their copy expires (`tenantConfigTtlMs`, 10 s). | Default; the F4 cache. |
| 24 | There is no fallback model list. If the chosen model's provider fails, the turn fails (Mastra retries the same model). | Gap map ("Allowed fallback outside India, and with whose consent?"): none until the owner decides. |
| 25 | Speech (Sarvam STT and TTS in the voice worker, WhatsApp transcription) is outside the model policy. It is configured per deployment as before. | Gap map owner question ("Do embeddings and STT/TTS fall under the same policy?"): embeddings yes, speech deferred. |
| 26 | `basecamp eval --live --model <ref>` runs the evals on one registered model (it sets `AGENT_MODEL` for that run; `--model` without `--live` is refused), so each model can be checked before a business allows it. | Gap map risk ("Tool-calling quality varies a lot on in-India and open-weight models. Evals (basecamp eval --live) are needed per allowed model"). |
| 27 | The e2e tests run a stub OpenAI-compatible server in the test process (chat completions, whole and streamed, with tool calls and usage; embeddings) and point `MODEL_PROVIDERS` at it, so the gateway path (base URL, key header, model id, tool loop, usage, audit version, guardrail, embeddings) is tested end to end without a network. | Default. |
| 28 | `@hykr/api`'s index exports `ModelPolicyService`, `ModelRefused`, `ModelPolicyChanged` and `SET_MODEL_POLICY`, and reserves the route segment `models`. Nothing on that import path reads the environment (the controller takes the database from `CORE_OPTIONS`, not `infra/db`), because tests set variables after importing the index. | Index rule ("Nothing exported here reads the environment when it loads"); found when the WhatsApp suites failed. |

## Assumptions to review

- **No policy means the defaults only.** A business that never set a policy may use the deployment's
  default chat and embedding models, nothing else. Should a business without a policy instead get
  every model the deployment offers?
- **The business sets its own policy.** Owners and admins (`models.manage`) choose among the
  deployment's models. Should residency be set only by the platform operator (B19), or be a plan
  option the business cannot change?
- **A hook's model the business does not allow refuses the turn.** It is not replaced by the
  business's default. Is a refusal right, or should the policy quietly use the business's own
  model instead?
- **No fallback, ever.** A provider outage fails the turn. Is a fallback to another provider (in the
  same region, or anywhere with the business's consent) wanted?
- **Residency is per business (`regions`) and per deployment (which providers it configures).**
  Should a production deployment refuse to start with a provider outside a required region?
- **Speech is not under the policy.** Should STT and TTS providers be chosen per business too?
- **Prices are the deployment's cost** in minor units per million tokens, rounded up per call. Is
  per-call rounding acceptable for credits (A3), or should cost be summed exactly and rounded once?
- **Only `models.manage` sees prices.** Should every member see what a model costs?
- **An unnamed embedding model is not checked on save.** A policy whose `allowed` leaves out the
  default embedding model saves, and memory recall is then refused for that business. Should saving
  warn or refuse instead?
- **Which in-country provider, and its region name.** The sample's `.env.example` uses a placeholder
  gateway URL and region `in`. Which provider and which region names does production use?
- **The scripted model stands in for every model in fake mode.** Tests and demos never reach a
  gateway unless a test points `MODEL_PROVIDERS` at a stub and switches to live mode.

## API sketch

```ts
// Environment (per deployment)
MODEL_PROVIDERS='[{"id":"gw","baseUrl":"https://llm.example.net/v1","apiKeyEnv":"GW_API_KEY",
  "region":"south","models":[{"id":"large","label":"Large","price":{"currency":"XXX",
  "inputPerMillion":20,"outputPerMillion":80}},{"id":"embed","kind":"embedding"}]}]'
AGENT_MODEL=gw/large          // default chat model (else the first chat model listed)
EMBEDDING_MODEL=gw/embed      // default embedding model (else the first embedding model)
OPENROUTER_API_KEY=…          // development: adds provider "openrouter"
OPENROUTER_MODELS=a/b,c/d     // more OpenRouter chat models (optional)

// @hykr/contracts (settings/models.ts)
ModelRef, ModelRegion, ModelKind ('chat' | 'embedding'), ModelPrice
ModelPolicyFields             // zod object: { allowed, chat?, embedding?, regions }
ModelPolicy                   // the section's schema (key 'models'), defaults for everything
ModelsSettings                // defineSettingsSection('models', ModelPolicy)
ModelsCapability              // CapabilityDef 'models.manage' (owner, admin)
ModelsOverview, ModelInfo, ModelUse   // GET /api/models

// @hykr/agents
modelRegistry(env = process.env): ModelRegistry   // cached until a variable it reads changes
interface ModelRegistry {
  providers: readonly ProviderEntry[];   // never keys
  models: readonly ModelEntry[];         // { ref, provider, id, kind, label?, region?, price? }
  defaults: { chat?: string; embedding?: string };
  problems: readonly string[];           // warnings: unregistered default, empty key variable
  get(ref): ModelEntry | undefined;
  languageModel(ref): LanguageModel;     // throws UnknownModel
  embeddingModel(ref): EmbeddingModel;   // throws UnknownModel
}
chooseModel(registry, policy, { kind, requested? }): ModelChoice | ModelRefusal
allows(registry, policy, entry): boolean
policyProblems(registry, policy): string[]
priceOf(ref), costOf(ref, usage): Money | undefined
turnModel({ requestContext }): string             // the turn's ref; throws ModelNotChosen
modelFor({ requestContext }): LanguageModel
agentVersion(instructions, model): string
ModelConfigError, UnknownModel, ModelNotChosen, embedText (the fake embedding)

// @hykr/api
TurnInfo.model?: string                  // set once chosen; after hooks see it
interface ModelGate { ready(turn): TurnRefusal | null; choose(turn, requested?) }
class ModelPolicyService implements ModelGate {
  policyOf(tenantId): Promise<ModelPolicy>
  chatFor(tenantId, requested?): Promise<ModelChoice | ModelRefusal>
  embeddingFor(tenantId): Promise<{ ref; model }>   // throws ModelRefused
  overview(p): Promise<ModelsOverview>
}
GET  /api/models          → ModelsOverview
PUT  /api/models/policy   ModelPolicy → WriteResult (status done | needs_approval)
event models.policy.changed  { id: tenantId, models }

// CLI
basecamp eval --live --model <provider>/<model>
```

Refusal rules: `model_not_configured` (503), `model_unknown` (503), `model_policy_invalid` (503),
`model_not_allowed` (403), all as `{ error: 'turn_refused', rule, reason }`.

## Test plan

- Unit (`framework/agents/src/models/models.test.ts`, 20 tests): parsing `MODEL_PROVIDERS` (unset,
  valid, bad JSON, bad fields, duplicate ids and refs, reserved `fake`, bad prices), OpenRouter in
  development and when declared, defaults, `apiKeyEnv` warnings, the registry building models through
  the OpenAI-compatible provider and refusing others, rebuilding when the environment changes,
  `costOf` rounding, `chooseModel` (default, the business's model, a requested one, unknown, wrong
  kind, not allowed, region, deployment default missing, fake models), `policyProblems`,
  `turnModel` (chosen, a business turn without one, no business, fake mode), `agentVersion` per model,
  the fake embedding's determinism.
- E2E (`framework/api/test/framework/models.e2e.test.ts`, 26 tests, fixture
  `framework/api/test/fixture/src/features/models/`: a stub gateway, a hook that asks for a model, a
  write hook that parks a policy allowing `stub/big`, a `turn-model` tool and its script):
  - `GET /api/models`: defaults and `allowed` per model; an owner sees prices, a staff member does
    not; the assistant gets 403.
  - `PUT /api/models/policy`: an owner sets it, audited (`tenant.update` before/after and the
    command); another business is unaffected and cannot be reached (`x-tenant-id` of a business you
    are not in is 403, for GET and PUT); a staff member gets 403, audited as denied; the assistant
    gets 403; unknown refs, a `chat` outside `allowed`, a region mismatch, a wrong kind and an unknown
    key get 400; an idempotency key replays (and conflicts on another body); the fixture's write hook
    parks one, the park is audited, approving applies it.
  - Chat with the scripted model: the business's `chat` reaches the agent and the `after` hooks; a
    hook's allowed model runs; a model outside the regions or not allowed refuses the turn (403), an
    unknown one 503; a business without a policy runs on the default only; the audit row names
    `fake/scripted`; settings that do not parse refuse turns and the overview (503) and PUT repairs
    them.
  - Live through the stub gateway: the request carries the key and the provider's model id; the tool
    loop creates a task; usage reaches the `after` hooks; the audit row's `agentVersion` names the
    business's model, and changes when the policy changes; the streamed endpoint works the same
    (`stream_options.include_usage`); a business without a policy uses `AGENT_MODEL` only; a business
    in another region reaches that provider with its key; the guardrail calls only the business's
    model; embeddings go to the business's embedding model and a disallowed one is refused; a default
    the deployment does not configure refuses every turn before any hook runs.
- Updated: the runtime e2e (F5) hook asks for a registered model (`fake/scripted`) and its second
  hook's unregistered model loses; the old key-check test now covers "no model configured"; the
  identity e2e lists `models.manage` for owners.

## Deferred

- A settings screen for the policy in the app or back office (the PRD's AI setup step). The API is
  there.
- Operator-set or plan-level policies (B19), and a deployment-wide region lock.
- Fallback models and providers.
- Speech providers under the policy.
- Cached-input and per-request prices; prices for OpenRouter's implicit provider.
- Running `basecamp eval --live` automatically for every model a business allows.
- Other processes learning of a policy change at once (they wait for the settings cache to expire).
