# B21: connectors that sign in (OAuth), and one webhook URL per provider

Asked for by Interioring (18 Nov 2026): a studio connects its Facebook page once, and the leads
from its Facebook and Instagram ad forms arrive as briefs with their source (SAL-09).

## Summary

A business can now connect a service by signing in, not only by pasting its credentials.

- **The declaration.** A connector declares `oauth`: its authorize, token, revoke and API URLs,
  their hosts, the scopes it needs, PKCE, refresh, and the environment prefix of the deployment's
  client. Hooks cover what providers do differently: a long-lived exchange, scopes the token
  answer does not list, the accounts a grant reaches, a pick step, a non-standard revoke, and a
  provider's own word for an expired token.
- **The flow.** Start, an anonymous callback and complete, for a person with
  `integrations.manage` in their business, with the same protections as the calendar's sign-in
  (B17, 36 and 37), made generic and owned by the business.
- **The tokens.** They are sealed, refreshed before they end, revoked when the connection goes,
  and the connection is marked `needs_reauth` (audited, its managers told) when the provider
  stops taking them. Every call to the provider goes through the egress guard, to the
  connector's hosts only.
- **One URL for a provider.** `/webhooks/<connector>` is verified once with the app's secret, and
  each event goes to the one connection holding the account it names.
- **meta-leads.** The first connector on it: Facebook and Instagram lead ads, in
  `@hykr/connectors/meta-leads`. The sample's briefs module turns each lead into a brief.

The package makes no network call on its own: every helper takes an `OAuthHttp` the server builds. | Request; B10 decision 3 (the package holds no policy). |

| 4 | The client comes from the environment: `<clientFrom>_ID` and `_SECRET`. Without them the connector is listed `available: false` and start answers 503 `oauth_unavailable`; the server still boots. | Request; B17 26. |
| 5 | Start is `POST /api/integrations/connections/oauth/start { connector, returnTo, connectionId?, label? }`, needing `integrations.manage`, a person (`members_only`) and a business (`no_business`), never the assistant (`HumanOnlyGuard`). It makes a PKCE S256 pair and a state: `os` plus 32 random bytes, kept as its SHA-256 in `app.integration_oauth_states`, with the verifier sealed under `oauth:<tenant>:<user>:<id>`, for 10 minutes. The row is a nonce, written outside `runWrite`, as the calendar's is. | Request; B17 36. |
| 6 | The callback is `GET /api/integrations/oauth/callback`, anonymous, and exchanges nothing. It redirects to the address stored with the state: `INTEGRATIONS_RETURN_URL` (default `<APP_URL>/integrations`) or `INTEGRATIONS_APP_RETURN_URL`, the deployment's, never the request's. It passes on `code` and `state`, or `error`: `oauth_refused` for `access_denied`, `sign_in_expired` for an unknown state. | B17 37. |
| 7 | Complete is `POST /api/integrations/connections/oauth/complete { code, state }`. It runs under `oneAtATime` and `findRepeat`, so a retry with its idempotency-key answers the first answer. The state is taken first (`DELETE … RETURNING`), so a refused try ends it too. A different person is refused 403 `oauth_not_yours`, a different business 403 `oauth_other_business`, and an old or used state 400 `oauth_sign_in_invalid`. A code the provider refuses is 400 `oauth_exchange_refused`. | Request; B17 36. |
| 8 | The scopes granted are the token answer's `scope`, else `grantedScopes`, else the declared ones. Fewer granted than declared is 400 `oauth_scopes_missing` with `missing: [...]`, and nothing is stored. | Request. |
| 9 | The write is `integrations.connection.oauth_connect` through `runWrite`. It creates the connection (`auth: 'oauth'`, `owner: 'business'`), or replaces a connection's grant when the start named it (signing in again keeps the accounts already picked). The tokens are sealed under `connection:<tenant>:<id>`, the B10 AAD. Its audit uses the token-free view. It records `connection.oauth_connected { connector, userId, scopes, public, accounts }`. Account tokens (page tokens) are sealed under `account:<tenant>:<connection>:<account>`. | Request; B10 4 and 8. |
| 10 | `describe` gives `{ public, accounts: [{ id, name, token? }] }`, read from the provider's own answer (at most 200 accounts). Without `pick` every account is held at once. With `pick` they are offered, and `POST /api/integrations/connections/:id/oauth/pick { accountIds }` (op `integrations.connection.oauth_pick`) holds the ones picked. After the commit, `pick.subscribe` runs for each, and the answer says which subscribed. | Request. |
| 11 | An account is held by one connection anywhere: a partial unique index `(connector, account_id) where held`, checked first so the refusal names the accounts (409 `account_connected_elsewhere`). This closes B10 decision 20's risk. The account id is written only by the complete step, from the provider's answer, never typed by a business. | Request; B10 20. |
| 12 | Tokens in use: `connectorRequest(db, { tenantId, connectionId }, init)` (exported from `@hykr/api`) and, in a handler, `ctx.request(init)` and `ctx.accessToken(account?)`. The access token is refreshed when fewer than 60 s remain and sealed again with the current `SECRETS_KEY` (old keys still open through `SECRETS_KEY_PREVIOUS`). A 401, or `isAuthError`, refreshes and retries once. | Request. |
| 13 | What marks a connection `needs_reauth`: `invalid_grant` (or a 400 or 401) on a refresh, a second refusal, a refused account token (an account token is not refreshed), a grant that does not open on this server, and the end of a grant that does not refresh. `markNeedsReauth` sets the status and `last_error`, writes an audit row (`integrations.connection.needs_reauth`, actor system `integrations.oauth`) and records `connection.needs_reauth`, in one transaction, once. Its calls then throw `ConnectionNeedsReauth` (409 `connection_needs_reauth`). | Request; B17 6, made audited and told. |

## Assumptions to review

- **Who connects.** `integrations.manage` (owner, admin), as for other connections. Should an
  operations role connect lead sources without managing webhooks?
- **Unrouted events.** Kept by key only for 30 days, logged, never assignable. Should an operator
  see them (a page connected later would have wanted them)?
- **A lead brief has no customer.** A lead becomes a brief with no customer record, so a
  request to forget that person finds it only through the business's own search. Its retention
  (365 days) still applies. Should a lead also make or match a customer by phone?
- **Long-lived Meta user token.** Its 60 days are not tracked (page tokens do not expire), so
  picking pages again after 60 days needs signing in again (error 190 marks it). Fine?
- **Scopes missing.** Refused, with the grant left at the provider (not revoked). Should the server
  withdraw it?
- **Expiry notice timing.** Checked every minute by the sweep; told once, 7 days ahead.

## Deferred

- A person's own OAuth connection (`owner: 'person'`) and moving the calendar onto this flow.
- Assigning an unrouted event by hand.
- A screen per connector, and connection screens in the back office.
- Providers that need a client per business, device-code or client-credentials grants.
