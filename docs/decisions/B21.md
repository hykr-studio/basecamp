# B21: images in documents

## Summary

A document (B2) could only show text and tables: `DocumentBlock` was a closed union and the page
header and footer took text only. Quotes, invoices and receipts want the business's logo, an
invoice wants a payment QR code, and site reports and handover packs want photos. An application
could not add a block itself, and drawing its own PDF would lose what documents give: a stored
snapshot per version, the SHA-256, sending, and one-time-code acceptance bound to the PDF's hash.

This unit adds three blocks and a header or footer image:

- `image`: one picture, fitted into a box at its own proportions, aligned, with a caption.
- `images`: a grid of pictures (1 to 4 columns) with captions. A row never splits across pages.
- `qr`: a QR code of text the template gives (a payment or share link), drawn as vector squares.
- `header.image` / `footer.image`: one image (a logo) beside the line's text, on every page. The
  margin grows so the content never runs under it.

`load` picks the pictures with `ctx.image(fileId)` and `ctx.images(fileIds)`. They give only image
files the requester may open, as `ImageRef`s (file id, SHA-256 of the bytes, type, size). The
snapshot keeps the refs, and the worker reads the bytes from storage and checks them against the
SHA-256 before it draws. Requirement: the "Basecamp requirement: Images in documents" doc. Asked
for by Interioring.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | The blocks join `DocumentBlock` in `features/documents/layout.ts` and are checked by the same Zod schema when the document is asked for. Sizes are points. `image`: `image`, `width?`, `height?` (neither: the content width; one: the other follows the picture's proportions; both: fitted inside, never stretched), `align` (default `center`), `caption?` (500), `alt` (200, required). `images`: `items` (1 to 60, each `image`, `caption?`, `alt`), `columns` (1 to 4, default 2), `height?` (each cell's; default its width × 3/4). `qr`: `data` (1 to 1 000 characters), `size` (72 to 288, default 108, quiet zone included), `align`, `caption?`, `errorCorrection` (L, M, Q, H; default M). `PageLine` gains `image?: { image, height (12 to 48), side (default left) }`; the text on the image's side is not drawn. | Requirement, "The new blocks". |
| 2 | **An image is an `ImageRef`** `{ kind: 'image', fileId, sha256, mime, width, height }` that `load` got from `ctx.image`. A template never types one: when the document is asked for, every ref the layout names must be one this `load` was given, with the same file and SHA-256, or the request fails 422 `image_not_loaded` (with the ref's path). So a template cannot name a file nobody checked. | Requirement, "Where images come from". |
| 3 | **Who may see a picture.** `ctx.image` gives a file only when the requester reaches it as `GET /api/files/:id` would (`FilesService.reaches`: the same business, on a record they reach, in a field they still see once the record is projected for them), it is `ready`, its type (stored and sniffed from its bytes) is PNG or JPEG, and it is within the limits. Otherwise it answers `null` and `ctx.images` leaves it out, as a file read answers 404. A refused type or size is logged with its reason (`image_too_large` for the size). | Requirement; developer guide 5.19 (load reads as the requester). |
| 4 | **Bytes are read when asked for.** Uploaded files carry no stored SHA-256, so `ctx.image` reads the file's bytes through the storage driver to hash and sniff them. This reads storage inside the write's transaction; the total is bounded by the limits (decision 6). The alternative, hashing at confirm, would change the files feature for every upload. | Default. Assumption to review. |
| 5 | **The worker** reads each snapshot image's bytes through the storage driver (`FilesService.bytesOf`, by the row's key), never from a web address, and checks the SHA-256 before drawing. A file erased, swept, detached or changed since fails the render at once, not after its retries (`ImageUnavailable`): the document is `failed` with `image_unavailable: <fileId>` and no PDF is stored. Asking again makes a new version from what the record holds now. `branding.logoUrl` (an https address) is not used. | Requirement ("A file gone before drawing fails clearly"); open question 3 (no hold on files). |
| 6 | **Limits** are deployment settings with defaults: images per document 200 (`DOCUMENTS_IMAGES_MAX`, 422 `too_many_images`), bytes per image 10 MB (`DOCUMENTS_IMAGE_MAX_BYTES`) and pixels per image 40 M (`DOCUMENTS_IMAGE_MAX_PIXELS`): such a file is not given to `load` (null, logged `image_too_large`); image bytes per document 60 MB (`DOCUMENTS_IMAGES_MAX_BYTES`, 422 `images_too_large`); the finished PDF `FILES_MAX_BYTES`, as before. The requirement asked both that `ctx.image` answer null for a file over a limit and that each limit answer its error: the per-image limits answer null (with the reason logged), the per-document ones the error. | Requirement, "Limits"; boundary rule (technical defaults only). |
| 7 | **A layout's mistakes are 422, not 500.** A layout that fails its checks when asked for answers `bad_layout` with the issues and their paths; a QR text too long for its correction level answers `qr_too_long` with the block's path. The encoder is called in the schema check, so the worker never meets it. | Requirement ("never a 500"). |
| 8 | **Drawing** (`engine/pdf.ts`): pictures are drawn at their own proportions inside their box, never stretched or cropped, never wider than the content and scaled down to one page when taller. pdfkit turns a JPEG by its EXIF orientation, and the box is computed from the turned size. Each file is embedded once however often it is drawn. Captions use the document's fonts and shaping. A picture's `alt` is written as the alternate text of a marked `Span` around it. QR codes come from the `qrcode` package (pure JavaScript, matrix only), with a 4-module quiet zone, as one filled path of rectangles. | Requirement, "Drawing rules". |
| 9 | **What the fake engine and `layoutLines` write:** `[Image: <alt>]` then the caption for `image` and for each grid item; `[QR: <data>]` then the caption; `[Image: header]` / `[Image: footer]` before that line's text. | Requirement. |
| 10 | **Versions and acceptance.** The snapshot keeps the refs that the layout shows (`Snapshot.images`), so version N keeps its pictures. Acceptance already binds the PDF's SHA-256, which covers the pictures. Its evidence also lists each picture's file and SHA-256: a new nullable column `audit.acceptances.document_images`, hashed into the row's chain hash only when set, so rows written before it keep their hashes. `AcceptanceInfo.document.images` shows it. | Requirement, "Versions, acceptance and failures"; B8 decision 15 (hashed fields only added at the end). |
| 11 | **Events and audit** stay free of content: the events are unchanged; `document.rendered`'s audit row adds `images: <count>`. | Requirement. |
| 12 | **`load` gets `appUrl`** (APP_URL), for a link a document shows or encodes, so a QR code can open the record in the app. | Default (the sample's QR code). |
| 13 | **Uploads for a commands-only entity.** The files feature's presign checks the target entity's write decision. It now names itself to the entity's rules as `ctx.via === 'file.upload'` (`EntityDef.decide(p, action, row, input, via?)`, default `'crud'`). An entity changed only by its commands (the sample's orders) can let that through: the record still changes only when its command puts the file on it. The money plugin still refuses an upload for a new money record (it decides on the empty input), so the sample uploads a photo for an order that exists. | Found while building the sample. |
| 14 | **Sample.** Orders gain an optional `photo` (an image file field, written by `order.save`; a revision does not copy it, as files stay with the old revision). The order PDF shows the photo and a QR code of the order's address in the app. | Requirement ("the sample's order document shows one picture from a record's file field, and a QR code of a link"). |
| 15 | **Fixture.** The documents fixture's `memos` gain `photo`, `photos` and `secretPhoto` (hidden without `memos.secret.read`), and a `memos.photos` document whose body drives the tests (probes, a forged ref, a QR line). The acceptance fixture's agreements gain a `logo` on the agreement's PDF. | CLAUDE.md (framework tests on the fixture app). |

## Open questions (with the answers taken here)

| Question | Answer taken |
|---|---|
| Shrink photos to the size they are drawn at, so photo-heavy PDFs stay small enough to send? | Not in this change. It needs an image library (`sharp` is native code) running in the worker. A 40-photo pack of phone photos can pass what WhatsApp and email accept. |
| Convert WebP and HEIC to JPEG, or refuse them? | Refused (`ctx.image` answers null, the reason logged). Convert later with the same library as shrinking. |
| Hold the image files while a document waits to be drawn? | No. Renders run within seconds; `image_unavailable` and asking again is enough. |
| A person's file erased: PDFs already made that show it? | The same as PDFs that show their name: documents already made are kept as they are (developer guide 5.27). The team should confirm. |
| The business's logo from `branding.logoUrl`? | Not in this change: fetching an https address in the worker would need the egress guard. A logo is a file on one of the application's records. A later change can store it as a file and offer `ctx.business.logo`. |
| Images in table cells? | Later; listed in developer guide section 14. |
