# F4: identity, roles registry, tenant config

## Summary

F4 widens who can act (`actor.kind` `system` and `guest`, assurance `otp`, five more channels)
and replaces the closed role enum with validated role names plus a role/capability registry.
Framework code now asks `can(p, capability)` instead of naming roles. The server works out a
principal's capabilities from its roles when it resolves the request. Agents are identified by
a chain of `AgentIdentityProvider`s (the agent key is the first), `systemPrincipal()` gives
background work a principal, `TenantConfigService` (core) caches a business's settings and
answers `isEnabled` failing closed, and auth plugins and trusted origins come from the
`authPlugins` registry. The built-in roles and capabilities reproduce today's behaviour exactly:
the same people reach the same things.

## Assumptions to review

- **Built-in roles.** The framework always registers `owner`, `admin`, `ops`, `staff` and
  `customer`, and an application cannot remove them. Should the PRD's six roles replace them as
  the framework default (A4), or live in the application?
- **Who manages roles.** Roles and capabilities are code today (per process). Studio-editable
  roles need a per-business table (A4). Should a studio be able to grant framework capabilities
  such as `queues.admin`, or only the product's own?
- **History for owners.** Owners do not get `history.all` (only admin and ops), because that is
  how it works today. Should an owner see the whole business's history?
- **MCP and WebMCP assurance.** Both count as `session`. Is an OAuth bearer token from MCP as
  trustworthy as a signed-in session for tier-3 decisions?
- **System principal reach.** A system job reaches every row of its business. Should system
  jobs instead declare which entities they may touch?
- **Settings cache.** A settings change reaches other processes within 10 seconds. Is that
  acceptable for quiet hours and feature flags?
- **Agent channel.** The assistant can forward only `app`, `voice` and `whatsapp`. When studio
  agents (A6) run in the background, should they use a run-token provider (planned) rather than
  the assistant's key?

## API sketch

```ts
// @hykr/contracts
ActorKind = z.enum(['user', 'agent', 'system', 'guest'])
Principal.actor = { kind: ActorKind; id: string; role?: string /* unused, going */ }
Principal.capabilities?: string[]          // set by the server from roles; absent: none
Assurance = 'whatsapp_number' | 'otp' | 'session';  ASSURANCE_ORDER; atLeast(have, need)
Channel = 'app' | 'voice' | 'whatsapp' | 'mcp' | 'webmcp' | 'api' | 'background' | 'share'
TURN_CHANNELS = ['app', 'voice', 'whatsapp'];  type TurnChannel
TenantRole = z.string().regex(ROLE_NAME)   // type string
Me = { userId, tenantId, roles: string[], capabilities: string[], customerId }
featureEnabled(settings | undefined, key): boolean   // only `true` is on

interface RoleDef { name: string; label: Labels; capabilities?: readonly string[] }
interface CapabilityDef { name: string; label: Labels; roles?: readonly string[] }
defineRole(def): RoleDef;  defineCapability(def): CapabilityDef   // check the shape; register through contributes
roles: HookRegistry<RoleDef>               // collects 'roles'
capabilities: HookRegistry<CapabilityDef>  // collects 'capabilities'
FrameworkRoles = { owner, admin, ops, staff, customer }             // registered on load
FrameworkCapabilities = { backOffice: 'backoffice.use', messageCustomers: 'customers.message',
  wholeHistory: 'history.all', channelSetup: 'channels.manage', queues: 'queues.admin' } // defs, registered on load
knownRoles(names): string[]               // registered ones, in order, deduplicated
capabilitiesOf(roleNames): string[]       // sorted, unique
checkRoles(): void                        // a role naming an undefined capability throws

// @hykr/policy
can(p: { capabilities?: readonly string[] }, cap: string | CapabilityDef): boolean  // unknown cap throws
accessFor(p, access, op)                  // actor.kind 'system' with a tenant: grants ['tenant']
type RoleAccess = Readonly<Record<string, AccessRule>>

// @hykr/core
systemPrincipal({ tenantId, job, runId?, capabilities? }): Principal
requireCapability(p, cap, { rule?, reason? }): void   // 403 { error: 'forbidden', rule, reason }
agentKeyProvider(agents: readonly AgentKey[]): AgentIdentityProvider   // name 'agent-key', always first
ApiRequest.agent?: AgentIdentity          // the identity PrincipalGuard recognised
Standing = { subject, tenantId, roles, capabilities, assurance, customerId? }
class TenantConfigService {               // global, from CoreModule
  get(tenantId): Promise<{ name: string; settings: TenantConfig }>
  isEnabled(tenantId: string | undefined, key: string): Promise<boolean>   // fails closed
  invalidate(tenantId?: string): void
}
CoreOptions.tenantConfigTtlMs?: number    // default 10_000

// @hykr/api (internal)
getAuth()                                 // Better Auth, built once after setRuntime
trustedOrigins(): string[];  corsOrigins(): string[];  checkOrigin(origin): string
```

Adding a role or capability from an application or module:

```ts
defineServer({ ..., contributes: {
  capabilities: [defineCapability({ name: 'orders.cost.read', label, roles: ['owner'] })],
  roles: [defineRole({ name: 'manager', label, capabilities: ['backoffice.use', 'orders.cost.read'] })],
} });
// in a controller or command
if (!can(p, 'orders.cost.read')) ...;  requireCapability(p, 'orders.cost.read');
```

## Test plan

- `framework/policy/src/capabilities.test.ts` (unit): `can` reads the principal's capabilities,
  refuses when absent, throws for an unknown capability; `capabilitiesOf` joins both directions
  and ignores unknown roles; `checkRoles` catches a role naming an undefined capability;
  `knownRoles`; the built-in mapping equals today's checks; a system principal reaches its
  tenant and nothing without one; a guest reaches nothing; the assurance order includes `otp`.
- `framework/api/test/framework/identity.e2e.test.ts` with the fixture's
  `src/features/identity/` (a contributed role, capability, bearer identity provider and auth
  plugin):
  - `/api/me` lists capabilities per role; an unknown role in a membership grants nothing and
    reaches no rows; a contributed role gets its capability;
  - history: `history.all` sees the business, others only their own;
  - back office: staff in, a role without `backoffice.use` refused `staff_only`;
  - identity chain: a bearer token acts for its person (audit actor, channel `mcp`, run id);
    a bad token is 401 even with a session cookie; another tenant's row is 404; a mismatched
    `x-tenant-id` is 403; a provider claiming `assistant` is 401; human-only routes and
    human-only actions refuse it; its delete parks and the park is audited;
  - the assistant cannot forward `x-channel: background`;
  - `systemPrincipal`: updates a row of its business through `runWrite` (audited as `system`,
    channel `background`), gets 404 for another business's row, cannot create, and bad
    options throw; no header produces a system actor;
  - `TenantConfigService`: cache, `invalidate`, `isEnabled` off for absent, non-`true`,
    unknown tenant and unparseable settings;
  - auth plugins: a contributed origin is trusted for sign-up, an unknown one is not; a
    contributed Better Auth plugin's endpoint answers; `checkOrigin` refuses `*` and paths.
- `seams.e2e.test.ts`: the settings read is cached now, so the test invalidates after its SQL
  update.
- Everything else stays green (tenancy, whatsapp, wa-approvals, handoff, voice, application).

- Switching `dispatch.processor.ts`, `inbound.processor.ts` and `channels.module.ts` from
  `TenantsService` to `TenantConfigService` (their owners).

  `otp` assurance (B8). Platform operators above the tenant (B19).

  validation can call `knownRoles`).
- History's `actor` is `you` or `assistant`: a system row (and, with `history.all`, another
  person's row) shows as `you`, as other people's rows did before. A `system` value in
  `HistoryEntry` is for whoever next changes the history contract and its screen.
