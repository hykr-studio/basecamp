# R1: references on line items

## Summary

Asked for by Interioring on 18 Nov 2026, checked against `feat/platform-gaps` at `4ce7192`.
Quote lines name the studio's price-list items, purchase-order lines name agreed vendor rates,
and work-order lines name work items. Each line keeps its own copied rate, so a later change to
the price list never moves a sent quote.

Before this change, a record with a parent could not declare `traits.references`.
`referenceProblems` refused it at boot (V2 decision 7), because `children.insert` and
`children.replace` insert new rows in raw chunks and never reach `repo.insert`, where
`checkReferences` runs. Each application loaded every id itself in the parent's command
(developer guide section 14), and a missed check let a line name another business's record or
one its writer may not read. A line's read carried only the id.

Now a child spec declares references exactly as a top-level spec does. The tree writes check
every new line's references, and every changed line's changed ones, in bulk: one query per
target entity, before any row is written. They refuse with the same 404 body as a top-level
reference, plus the line's `path` and `ref`. A reference may also name a label field, which
lists and gets read back with each record, under the reader's scope and field policy. The
sample's orders module gains `product`, and its order items reference it.

## Decisions

| # | Decision | Source |
|---|----------|--------|
| 1 | `referenceProblems` (`framework/contracts/src/framework/references.ts`) no longer refuses a child. It still refuses an unknown target and a field in neither write schema, with the same messages, and now refuses a `label` its target's read schema does not have. A child may name any entity of the catalog: another module's, or a shared one (`defineSharedEntity`, whose `findMany` also reaches the platform's rows). | The requirement ("The contract"). |
| 2 | The trait value is the target's name (`'product'`), as before, or `{ entity, label? }`. `referencesOf` still returns `[field, entity]` pairs, so V2's callers are unchanged. `referenceLabelsOf` gives `[field, entity, label]`. | The requirement ("Labels on read"); keeps V2's form valid. |
| 3 | **Where it is checked: both.** `children.insert` and `children.replace` always check, in `run`, so every path that writes a tree has the check with no code of the command's own, and an approved replay checks again. A command that can park calls `Child.children.checkReferences(tx, p, nodes, { at, parent })` to refuse before it parks. That call goes in its `load`, not its `authorize`, because `authorize` is synchronous; the sample's `order.save` and the fixture's `sheet.save` do this. | Open question 1 (suggested answer); `defineCommand`'s `authorize` returns a decision, not a promise. |
| 4 | **How: `repo.findMany`.** `EntityRepository.findMany(conn, p, ids)` selects `scoped(p, 'read', inArray(id, ids))`, the same scope as `find` (business, read access, plugins' scopes), in one query, and returns the rows found. It does not use `repo.list` with an `id in (...)` filter, which would need `id` filterable on every target and stops at a page. | Open question 2 (suggested answer). |
| 5 | `checkReferencesMany(conn, p, spec, items)` (`framework/core/src/entity/references.ts`) collects the distinct ids per target entity across every item and every field (two fields naming one entity share its query), skipping null and undefined. It loads them with one `findMany` per target, then walks the items in tree order. The first id not found refuses the whole write: 404 `{ error: 'not_found', message: 'No such <target label>', field, path, ref? }`. This is the same body for an unknown id, another business's id and an unreadable record (V2 decision 5), plus `path` (the line's place in the tree, after the `at` prefix the command passes, e.g. `['items', 0, 'children', 2, 'productId']`) and `ref` (the node's own key, when it carries a string `ref`). | The requirement ("Refuse"). |
| 6 | At most 1,000 distinct ids per target entity per write (`MAX_REFERENCES`, which matches the most items `order.save` accepts). More is 400 `{ error: 'too_many_references', message, field }`, refused before that target's query. | The requirement ("Limits"). |
| 7 | **Changed lines.** `children.replace` adds to the same bulk check each kept line whose patch changes a reference to a value, then marks that patch (`referencesChecked`, a WeakSet internal to the core) so `repo.update` does not load it again one by one. A kept line whose reference is unchanged, or set to null, is not checked: no query, as V2 decision 4 says for a top-level update. | The requirement ("Changed nodes"); one query per target for the changed lines too, not one per line. |
| 8 | **Revisions copy lines as they are.** `reviseWithChildren` copies a quote's lines with their stored links. A copy is not checked again, and keeps a link its writer can no longer read, exactly as a revision keeps its parent's own unchanged link (V2 decision 4, V10's `plan.revise` test). The lines a command then writes on the new revision (`children.replace` or `insert`) are checked. | Default: consistent with the parent's revision. A check on copies would make a revision stricter for a line than for its record. |
| 9 | **Undo.** Undoing a tree write that removed lines puts them back one by one, each checked by `checkReferences` (V10). That restore was refused before any reference check: the parent plugin refuses a child created on its own (`children_through_parent`), so no undo of a save that removed lines ever worked. A restored child now asks its parent instead. The parent must still be readable, the person must be allowed to update it (`decide`), and its plugins' `childWrite` must allow it (a frozen record's lines stay as they are). Undoing a created line is a delete, and undoing a changed line is `repo.update`, which checks a changed link. | The requirement ("Where it runs": undo); found while testing it. |
| 10 | **Imports.** The importer writes top-level records one row at a time, through their own create and update. It writes no child tree: a child spec's create is not exposed, and the parent plugin refuses a line made on its own. No import can write lines around the check, and the test shows an import of quote lines writes none. An import of a tree, through a command, is not built (section 14's "bulk update of plain entities" row is the nearest). | Found: `framework/api/src/features/imports/importer.service.ts`. |
| 11 | **Audit.** A declared reference's 404 is audited as `denied` by `runWrite`, with the rule `unknown_reference` and the target's "No such …" as the reason, and then answered unchanged. This holds for top-level references (the CRUD load step, `repo.insert`, `repo.update`) and for children alike. Before, only a `RuleDenied` (a 403) was audited. A database key's 404 (no field) is still not audited. | The user's choice ("audit both", 2026-11-19); the requirement's acceptance ("audited as denied, as other refusals are"). Amends V2 decision 5. |
| 12 | **Labels on read: shipped now.** `def.readMany(conn, rows, p)` is `toRead` for each row, then, when the spec declares a label, one `findMany` per target over the page's ids, as the reader. Each label is read from `target.toRead(row, p)`, so the target's plugins and field policy apply: a target the reader cannot reach, or a label field hidden from them, reads `{ id, label: null }`, never its value. A null link has no entry. The list and get handlers, a document's child rows and a shared record's children read through it. Webhooks, live events, summaries, a write's own result and `order.placed` keep carrying the id only (V2.md, "Read paths"). | Open question 3 (the user chose "ship now"). |
| 13 | **No price snapshot.** A line never copies fields from its target at save. A quote line keeps its own rate, so a later price-list change never moves a sent quote; copying is the application's choice, in its command. | Open question 4 (suggested answer). |
| 14 | **The database key.** A child column is keyed with its business like any reference. Use `foreignKey({ columns: [t.tenantId, t.productId], foreignColumns: [products.tenantId, products.id] })` in `schema.ts` for NO ACTION, RESTRICT or CASCADE, with `tableRef(name)` (which already has `tenantId`, V2 decision 12) for a target in a module that depends on this one. Use a guarded SQL post hook for `ON DELETE SET NULL (product_id)` (V2 decision 11). The sample shows the hook (`application/domain/sql/post/order-products.sql`); the fixture shows both forms. A delete a NO ACTION key blocks is 409 `in_use`, and a bulk insert the key refuses is already mapped by `runWrite` (V2 decision 8). | The requirement ("The database key"). |
| 15 | **Sample.** The orders module gains `product` (`orders_products`: a name and a code, read by the whole team, written by owners, admins and ops). Order items get `productId` (optional, nullable), declared with `{ entity: 'product', label: 'name' }`. `order.save` sends each line whole, so a kept line sent without its product loses it. It calls `checkReferences` in its load and has no check of its own. The product has no list price: the money trait would need a currency on every product. | The requirement ("The sample orders module gains a small products entity"). |

## Sites of the same pattern

| Site | What now holds |
|---|---|
| `children.insert`, `children.replace` (`framework/core/src/entity/children.ts`) | Every new line's references, and every changed line's changed ones, checked in bulk before any row is written. |
| `reviseWithChildren` copies (`framework/core/src/versions/revise.ts`) | Copied as stored (decision 8); the revision's own `values` are checked as in V10. |
| Undo restoring removed lines (`framework/core/src/write/undo.ts`) | Works now (decision 9); each restored line is checked by `checkReferences`. |
| The importer | Writes no child rows (decision 10). |
| Shared entities as targets (`framework/core/src/plugins/shared.ts`) | `findMany` returns the business's rows, then the platform's for the ids left: two queries for such a target. |
| Labels | Only lists, gets, documents and shared records. A command's own result (`toRead`) carries ids. |

## Assumptions to review

- The early check in a command's `load` and the tree write in `run` each query, so a save that
  calls both makes two reference queries per target. One that does not park can leave out the
  `load` call.
- The early check's `path` is the input's own index when the command passes its flat input
  (`order.save` passes `input.items`). The tree write's `path` is the place in the tree. The two
  differ for a nested line, and an approved replay reports the tree's. `ref` is the same in both.
- A label is read as a string (`String(value)`), so a numeric label field reads `"100"`.
- A line made before this change, in another business's or an unreadable product's name, is
  impossible: `product_id` is new with its key.

## API sketch

```ts
// contracts
traits: { parent: { entity: 'order', field: 'orderId' },
          references: { productId: { entity: 'product', label: 'name' } } }
referenceLabelsOf(spec): [field, entity, label][]
type ReferenceLabels = Record<string, { id: string; label: string | null }>

// core
Target.repo.findMany(conn, p, ids): Promise<Row[]>
Child.children.replace(tx, p, parent, nodes, via, { at: ['items'] })
Child.children.insert(tx, p, parent, nodes, via, { under?, at? })
Child.children.checkReferences(conn, p, nodes, { at?, parent? })   // in a command's load
def.readMany(conn, rows, p): Promise<reads with references>
checkReferencesMany(conn, p, spec, [{ values, path, ref? }]); MAX_REFERENCES = 1000
//   404 { error: 'not_found', message: 'No such product', field, path, ref }
//   400 { error: 'too_many_references', message, field }
```

## Test plan

Framework, a fixture feature `child-references` (price items, sheets with revisions, a tree of
sheet lines naming one or two items; neutral names, as the boundary check keeps product words
out of `framework/`; `child-references.e2e.test.ts`):

- A child spec with references boots; a line naming a readable item is saved.
- 500 lines naming 200 items: one `findMany` (counted on the target's repository) for
  `children.replace` and for `children.insert`, none by `find`; a save with the early check: two.
- An unknown item, another business's and one staff cannot read: 404, equal bodies, `path` and
  `ref`, nested lines included; nothing written, the stored sheet's version unchanged; the
  refusal audited `denied` with `unknown_reference`.
- A kept line with its reference unchanged makes no query; a changed one is checked; null passes.
- 1,001 distinct items: 400 `too_many_references`, before any query.
- The assistant refused before it parks; a parked save whose item is deleted fails on approval.
- MCP; an offline replay with the same idempotency key; a revision keeping copies and checking
  its new lines; undo of a save that removed a line (refused once the item is out of reach, done
  while it is not); an import of lines writes none.
- NO ACTION: deleting a named item is 409 `in_use`; SET NULL (post hook): the line's other field
  is cleared in the same write; a line naming another business's item is refused even by SQL.
- Labels: one query per target for a page of 100; staff read `label: null` for an item they
  cannot read and for a field hidden from them (the item's cost).

Top-level (`references.e2e.test.ts`): a refused reference is audited `denied`.
Unit (`modules.test.ts`): a child's references boot; an unknown target or field on a child is
refused with the top-level messages; a label its target has not is refused.
Sample (`orders.e2e.test.ts`, "a line's product"): a line reads its product's name, for the owner
and staff; another business's product and an unknown one are refused with the line's `ref`, the
assistant's save before it parks; deleting a product nulls the lines; the database refuses a
cross-business product.

## Deferred

- References from a line to another line of the same tree (`nest` covers the line above).
- Bulk update of plain entities and line-level assistant tools (section 14).
- An audited unlink when a referenced record is deleted (section 14, V2 decision 13).
- An import of a tree through its parent's command.
