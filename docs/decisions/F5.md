# F5: runtime registries

## Summary

F0 declared the server's registries; F5 makes them run. Queues and schedules come from the `queues`
and `schedules` registries, under the process's queue prefix. Framework features are Nest modules
listed one per line in `framework/api/src/features/index.ts` and loaded by `FeaturesModule.forRoot`.
An event relay puts each committed event on the queue of every subscriber that wants it, deduped by
event id. Every assistant turn passes the turn hooks, which can refuse it, add context, pick its
model or take tools away. The agent's model, tools and instructions are resolved per turn from the
request context. Contributed tools join the generated ones, and a duplicate tool id stops the
start. Notifications reach any registered delivery channel, and a notification no longer needs a
WhatsApp template. Inbound WhatsApp messages pass the inbound hooks, and "delete my data" runs the
erasure contributors in its transaction.

Subscribers get F3's stored events. The `outbox` feed reads `app.domain_events` in the worker, so
each envelope carries the stored id and the real actor, a row gets `relayed_at` once it is on its
subscribers' queues, and an event survives a process that stops after commit. The in-process bus is
no longer relayed.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | One mechanism for every queue: Nest's `BullModule`, registered by a global `QueuesModule.forRoot({ processors })` from the `queues` registry, with `prefix: config.queuePrefix`. The framework's own queues (`wa-inbound` …) are registered in the registry too (`registerQueue` in `channels/queues.ts`), so a feature cannot take their names and `shutdown()` empties every queue by iterating the registry. | Plan F5 ("`registerQueue`/`defineSchedule` (prefixed)"), task note ("prefix from config.queuePrefix; testing shutdown iterates the registry"). |
| 2 | A `QueueDef` may carry `process(job, ctx)`. For each such def the worker gets a generated `@Processor` class, so Nest's BullMQ explorer runs and closes it like the hand-written ones. A def without `process` is run by a Nest `@Processor` class its owner lists (the framework's channel queues). | Default. F0 left the binding to F5 (F0 decision 19). Generated classes keep one lifecycle for all workers. |
| 3 | A queue's `attempts` and `backoffMs` become its default job options (exponential backoff), next to the same `removeOnComplete`/`removeOnFail` as before. `@nestjs/bullmq` replaces, not merges, `defaultJobOptions`, so each queue repeats them. | Read from `@nestjs/bullmq` 12 (`createQueueOptionProviders` spreads the shared config). |
| 4 | Queue and schedule names: lowercase letters and digits, words joined by `.` or `-`, no `:` (BullMQ's key separator). Owners prefix their names (`credits.alerts`); the existing framework names stay. | F0 hooks.ts doc comments ("prefixed by its owner"). |
| 5 | `defineSchedule` takes exactly one of `every` and `cron` (UTC). The worker upserts one BullMQ job scheduler per schedule at bootstrap, keyed by the schedule's name. A schedule whose queue is not registered stops the start. Schedulers removed from code are not deleted from Redis (A6 will add schedulers at run time on its own queues, and a sweep would delete them). | Default, fail closed at boot. |
| 6 | Hooks and handlers that need Nest services get a `ServerContext` (`get(token)`, `db`, `jobs`). Queue processors and subscriber handlers receive it as their second argument. Hooks with F0 signatures (turn, inbound, delivery) that need services are written as Nest providers that register themselves in `onModuleInit` (`turnHooks.register(this)`); the fixture shows both. | Default: no change to F0's hook signatures, and DI stays Nest's. |
| 7 | A framework feature is `defineFeature({ name, enabled?, imports, controllers, providers, processors, exports, contributes })`. `features/index.ts` exports one `FeatureDef` per line (union merge). `FeaturesModule.forRoot({ http, processors })` builds one Nest module per enabled feature: controllers only where HTTP is served, processors only where jobs run. | Plan F5 ("A `FeatureDef` `forRoot` pattern in `api/src/features/index.ts`") and "Where each gap lives" ("A feature is a Nest module at `framework/api/src/features/<x>/`"). |
| 8 | A feature's static `contributes` are installed once per process, before the queues are registered (`installFeatures()`, idempotent; `QueuesModule.forRoot` calls it first). `runEval` and `startStudio` call it too, so a feature's tools reach Studio and the evals. Features load in barrel order (alphabetical after `pnpm format`); nothing may depend on the order between features. | Default. `setRuntime` (F1's file) installs only the application's contributions. |
| 9 | The relay reads committed events from **event feeds** (`eventFeeds` registry), polled every second by the worker (`EventFeedPoller`, one tick at a time), with `{ limit: 100, prefix: config.queuePrefix }` so processes sharing a database never take each other's events. A feed gets the worker's `ServerContext` as its last argument (`pending(a, ctx)`, `relayed(ids, a, ctx)`), so it reads its store through `ctx.db` and can be a plain contribution. The framework's feed is `outbox` (`features/events/outbox-feed.ts`, contributed by `eventsFeature`). `pending` returns F3's `app.domain_events` rows with `queues = prefix`, `available_at <= now()` and `relayed_at` and `cancelled_at` both null, ordered by `seq`, each through `toEnvelope`. `relayed` sets `relayed_at = now()` on those ids under the same prefix guard. A batch is marked only after every subscriber's job is added. A crash in between relays it again, and the job id (decision 10) still runs each event once. The same holds when two processes share a prefix (an API with `WORKER_INLINE=1` beside a worker) and read the same batch. Order holds within a batch only: a transaction that commits after a later `seq` is relayed on the next tick. | Plan F3 ("durable event outbox") and F5 ("event relay … outbox → queues, deduped by event id"); F3 decisions 18 and 24 and its API sketch ("a relay (F5) reads app.domain_events where queues = eventQueues(), available_at <= now(), relayed_at is null and cancelled_at is null, order by seq"); review round 2. |
| 10 | `defineSubscriber({ name, on, when?, handle? | queue?, attempts?, backoffMs? })`. `on` lists event names or prefix patterns (`'task.*'`, `'*'`). With `handle`, the job runs on the shared `events` queue (concurrency 10); with `queue`, the envelope is added to that queue and its processor runs it (webhooks, agent runs). Exactly one of the two. The job id is `<subscriber>--<event id>`: relaying an event twice runs it once while the job is kept. | Plan F5, task note ("prefix filter"): read both ways, the queue prefix (decision 9) and name prefixes. A shared queue keeps Redis connections flat as subscribers grow. |
| 11 | An event with `availableAt` in the future is added with that delay. A feed should not return it before then anyway (tier 1 undo is the feed's job: an undone write's event is never returned). | F0 `DomainEventEnvelope.availableAt`; plan A5 ("tier-1 undo through outbox `available_at`"). |
| 12 | The in-process `EventBus` is not relayed. The bus bridge and `envelopeOf` are removed: once the outbox feed is always registered they could never run, and they built envelopes with a fresh id and an unknown actor and lost an event on a crash. Nothing is missing because of that. F3 stores every `NamedEvent` a write produces (entity events, command events, approvals), and the bus's other events (`DeliveryFailed`) were never relayed. A subscriber's envelope has the stored id, the actor that wrote (`actor_kind`, `actor_id`) and the business. An event without a business cannot be stored, because F3 fails the write. The bus still carries events in the process after commit, for `NotifyService` (Deferred). | Review round 2 (item 6: remove or justify); F3 decisions 18 and 24; fail closed. |
| 13 | Subscribers are server code and get the stored row unfiltered (F3 decision 19). Anything that sends an event to people or systems outside (webhooks, live updates) must pass it through `eventFor(event, p)` (F3) first: another business's event is null, and the row and the row before it are projected for the reader. Whether that reader may see the record at all is the deliverer's check (`def.repo.find`). | Gap map ("Event payloads are raw DB rows … must apply A4 field hiding"); F3 decision 19. |
| 14 | Turn hooks run in `ChatService` for chat turns and back-office drafts (`kind: 'chat' | 'draft'`), so a cap holds for every model call. `before` hooks run before the person's message is saved: a refused turn leaves the thread as it was, as the old key check did. A `before` hook that throws fails the turn (fail closed); an `after` hook that throws is logged. | Plan F5 ("`TurnHooks` in `chat.service.ts`"); F0 `TurnHook` doc comments. |
| 15 | A gate is `{ refuse: { rule, reason, status?, say? } }` or `{ context?, model?, withoutTools? }`. The first refusal wins and throws `TurnRefused` (an `HttpException`, status 403 unless given, body `{ error: 'turn_refused', rule, reason }`). Context lines from every hook are joined in order. The first hook that names a model wins. `withoutTools` from every hook are removed; a hook can take tools away, never add one. | Default, fail closed. Needed by A3 (refuse at 100%), A8 (recalled memory as context), A10 (per-studio model) and A11/A1 (flags and scopes hide tools). |
| 16 | The `OPENROUTER_API_KEY` check is the framework's default turn hook (`model-key`), run before the registry's hooks. It refuses with status 503, as before. | Task note ("move the OPENROUTER key check into a default hook"). |
| 17 | On WhatsApp, a refused turn answers with the refusal's `say` in the person's language, or the usual "something went wrong" when it has none. The job does not retry. | Default: a refusal is an answer, not a failure. |
| 18 | The assistant resolves per turn from the request context: the model (`model`, set from the gate, else `AGENT_MODEL`; the scripted model in fake mode), the tools (generated tools for the profile, cached, plus contributions, minus `withoutTools`), and the instructions (turn context lines are appended as data, not instructions). | Plan F5 ("Mastra dynamic model, tools and instructions from requestContext"); Mastra 1.74 `DynamicArgument`. |
| 19 | `toolsFor` in `@hykr/core/tools` merges the generated tools with every `ToolContribution` and throws on any duplicate tool id, naming both owners (two entities with one plural, a command tool named like an entity tool, two contributions). `ChatService` builds the full set once at bootstrap, so a duplicate stops the start. | Plan F5 ("A `ToolContribution` registry with duplicate checks"); gap map MOD ("Tool ids … Object.assign, last wins"). |
| 20 | Notification channels are names: `'whatsapp'`, `'email'` (built in) and any registered `DeliveryChannel`. `NotificationChannels` is an open interface, so a feature adds its channel's name by declaration merging and `channels: ['push', 'whatsapp']` type-checks. `NotificationDef.whatsapp` is optional; `defineNotification` requires it only when `'whatsapp'` is a channel. | Plan F5 ("A `DeliveryChannel` registry (`whatsapp` becomes optional)"); gap map ("The channel list is a hard-coded union"). |
| 21 | A delivery channel may not be named `whatsapp` or `email`. At bootstrap, every notification's channels must be built in or registered, or the start stops. | Default, fail closed. |
| 22 | Dispatch tries a registered channel in its place in the fallback order. `sent`: done. `unavailable` or a `final` failure: the next channel now. A non-final failure: the same channel and the ones after it are retried for that one recipient, up to 3 times with backoff, then the next channel. A channel that learns of a failure later (push receipts) calls `NotifyService.fallback(meta)` with the `meta` it got in the request. | F0 `DeliveryOutcome` doc comments; plan A9 ("fallback in the order push → WhatsApp → email"). |
| 23 | `TemplateSync.check` skips notifications without a WhatsApp template. | Task note. |
| 24 | Inbound hooks run on every message of a burst that the code did not answer (approval and notification buttons, keywords), before the handoff check, so a photo is stored even while staff have the conversation. A burst with "delete my data" passes no hook: once the erasure is queued the burst is done, so nothing a hook stores can outlive an erasure the person is told is complete (review round 1). `{ handled: true }` drops that message from the turn; `{ context }` adds lines the turn reads with it. A hook that throws is logged and skipped: a retry would repeat keyword confirmations. Slow work belongs on the hook's own queue. | Plan F5 ("`InboundHook`s"); F0 `InboundHook` doc comment ("store a photo's media"). |
| 25 | "Delete my data" runs every erasure contributor inside the erasure's transaction, with the contact as the subject and its business, and records each contributor's count on the audit row. `exportPersonalData(subject, db)` collects every export contributor's records; two contributors returning the same kind stop the export instead of overwriting. | Plan F5 ("Erasure and export contributors"); F0 `ErasureContributor`/`ExportContributor`. |
| 26 | New registry keys: `subscribers` and `eventFeeds`, declared in `hooks.ts` beside F0's, so their collectors load whenever the runtime does. | F0 decision 22 (every collector loads before `setRuntime`). |

## Assumptions to review

- **One second, and only where jobs run.** The worker polls the outbox every second, so a subscriber
  runs up to a second after commit plus its queue time. An API that runs without a worker (and
  without `WORKER_INLINE=1`) relays nothing until a worker starts. Is that fast enough for A6
  triggers and B10 webhooks, or should a commit wake the poller (Postgres `LISTEN/NOTIFY`)?
- **No order across writes.** Events go out in `seq` order within a batch. A transaction that commits
  after a later one is relayed on a later tick, and the shared `events` queue runs 10 jobs at once.
  Do any later units (A6 automations, B10 webhooks) need events of one record in order?
- **A burst with "delete my data" is dropped whole.** A photo or a question sent with it is neither
  stored nor answered; only the erasure runs and is confirmed. Should the person be told that the rest
  of what they sent was not kept?
- **Relayed, not delivered.** The outbox feed sets `relayed_at` once every subscriber's job is added,
  not when the jobs succeed. A job that fails for good stays in BullMQ's failed set, not in the outbox.
  Is that the intended meaning of `relayed_at`?
- **Shared `events` queue.** Subscribers with `handle` share one queue (concurrency 10), so a slow
  handler delays others. Should every subscriber get its own queue instead (two Redis connections
  each)?
- **Refused turns are not saved.** A turn refused by a hook (credits at 100%) leaves no message in the
  thread and no audit row. Should a refusal be saved to the thread, or audited, so the person and the
  studio can see why the assistant was silent?
- **Drafts pass the hooks.** Back-office drafts count against caps and get recalled memory. Is that
  the intended billing for drafts?
- **Model by name.** A hook picks a model by id string (`openrouter/...`, later the gateway's ids).
  The audit's `agentVersion` still names the default model until A10 makes it per request. Is a
  per-turn version required before A10?
- **Inbound hook failures are swallowed.** A hook that throws (storage down) is logged and the turn
  goes on without it. Should a failing media hook instead tell the person their photo was not saved?
- **Channel retries.** A non-final channel failure is retried 3 times for that recipient, then the
  next channel is tried. Is 3 the right number for push and in-app channels?

## API sketch

```ts
// @hykr/api: queues and schedules
interface QueueDef<D = any, R = unknown> {
  name: string; concurrency?: number; attempts?: number; backoffMs?: number;
  /** Runs one job in the worker (and in the API with WORKER_INLINE=1). */
  process?(job: Job<D>, ctx: ServerContext): Promise<R>;
}
defineQueue<D, R>(def: QueueDef<D, R>): QueueDef<D, R>   // checks the name
registerQueue(...defs: QueueDef[]): void                  // framework code, at import
defineSchedule(def: ScheduleDef): ScheduleDef             // exactly one of every / cron
interface ServerContext { get<T>(token): T; db: Database; jobs: Jobs }
interface Jobs { add<D>(queue: QueueDef<D> | string, data: D, opts?: JobsOptions & { name?: string }): Promise<Job<D>>; queue<D>(name): Queue<D> }
JOBS                                                      // DI token: @Inject(JOBS) jobs: Jobs (QueuesModule is global)
QueuesModule.forRoot({ processors: boolean })             // internal; AppModule and WorkerModule import it

// @hykr/api: features (framework/api/src/features)
interface FeatureDef { name; enabled?(): boolean; imports?; controllers?; providers?; processors?; exports?; contributes?: Partial<Contributions> }
defineFeature(def): FeatureDef
FeaturesModule.forRoot({ http: boolean, processors: boolean })   // internal
installFeatures(): readonly FeatureDef[]                  // internal, idempotent
// features/index.ts, one line per feature:
export { eventsFeature } from './events/index.js';

// @hykr/api: events
interface Subscriber { name; on: readonly string[]; when?(e): boolean; handle?(e: DomainEventEnvelope, ctx: ServerContext): Promise<void>; queue?: string; attempts?; backoffMs? }
defineSubscriber(def): Subscriber;  subscribers            // collects 'subscribers'
interface EventFeed {
  name;
  pending(a: { limit; prefix }, ctx: ServerContext): Promise<readonly DomainEventEnvelope[]>;
  relayed(ids, a: { prefix }, ctx: ServerContext): Promise<void>;
}
eventFeeds                                                // collects 'eventFeeds'
matchesEvent(pattern, name): boolean
EventRelay.publish(events: readonly DomainEventEnvelope[]): Promise<void>   // internal provider (features/events)
outboxFeed: EventFeed      // features/events/outbox-feed.ts, name 'outbox': app.domain_events (F3)
// eventsFeature.contributes = { queues: [EventsQueue], eventFeeds: [outboxFeed] }
EVENTS_QUEUE = 'events'

// @hykr/api: turns
interface TurnInfo { kind: 'chat' | 'draft'; principal; runId; threadId?; message; channel; surfaces; lang? }
type TurnGate = { refuse: TurnRefusal } | { context?: readonly string[]; model?: string; withoutTools?: readonly string[] }
interface TurnRefusal { rule; reason; status?: number; say?: Labels }
class TurnRefused extends HttpException { refusal: TurnRefusal }
// request context keys the agent reads: 'model', 'withoutTools', 'turnContext'

// @hykr/core/tools
toolsFor(kit, catalog, { canvas }): ToolsInput            // generated + contributed, duplicate ids throw
generatedTools(kit, catalog, { canvas }): ToolSet         // { tools, owners }: who defined each id
withContributions(kit, set: ToolSet): ToolSet             // + toolContributions, per run
// @hykr/agents
modelFor({ requestContext }): string                      // the turn's model id ('model', else AGENT_MODEL)

// @hykr/notifications
interface NotificationChannels { whatsapp: true; email: true }   // open
type NotificationChannel = keyof NotificationChannels & string
NotificationDef.channels: readonly NotificationChannel[];  NotificationDef.whatsapp?: {...}

// @hykr/api: delivery
interface DeliveryRequest { tenantId; notification; to: { userId?, contactId? }; reader; row; dedupe; meta: NotificationMeta }
NotifyService.fallback(meta, ref): Promise<void>          // a channel that failed later moves on
// personal data (@hykr/api)
exportPersonalData(a: DataSubject & { db: Conn }): Promise<Record<string, readonly unknown[]>>
eraseWithContributors(a: DataSubject & { tx: Tx }): Promise<Record<string, number>>
// Hooks that need DI: a Nest provider that registers itself, e.g.
//   @Injectable() class MediaHook implements InboundHook, OnModuleInit {
//     onModuleInit() { inboundHooks.register(this) } … }
```

  - a subscriber on `task.*` gets `task.created` with the creator's business and the row;
    another business's task reaches it with that business's id, never Ana's; relaying the same
    event twice runs it once; a subscriber with `queue` gets the envelope on that queue;

## Deferred

- `NotifyService` still schedules notifications from the in-process `EventBus` after commit. Making
  it a subscriber of the outbox (so a crash after commit cannot lose a reminder) changes when every
  application's reminders are scheduled, and needs its own tests. The notifications units (A9, B7)
  can do that next.
- Deleting relayed rows from `app.domain_events` after a retention period. The table grows with
  every write.
- A poison row. A stored row that `toEnvelope` refuses would fail its batch on every tick. F3's
  `recordEvents` runs `toEnvelope` on each row it inserts, in the write's transaction, so such a row
  cannot commit through the write path. Done by V6: such a row (or one a subscriber's `when` throws
  on) is marked failed with its reason and the rest of the batch goes on.
- Per-turn `agentVersion` when a hook picks the model (A10).
- Moving the channel's own job schedulers (template status, retention, stale handoffs) to
  `defineSchedule`: those processors belong to later units (B18, A5).
- Removing schedulers that code no longer declares.
