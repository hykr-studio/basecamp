# V12: a keyset page never repeats or skips a row that shares its time

## Summary

Acceptance on the merged branch found a paging defect older than the branch. A list sorted by a
timestamp kept the boundary row's time in its cursor as a JavaScript `Date`, which keeps
milliseconds, while Postgres stores microseconds (`defaultNow()`).

- **Ascending** (`created_at > T_ms`) took the boundary row again. The to-dos' default sort is
  `createdAt` ascending, and at limit=1 the walk never advanced: 60 pages showed one to-do.
- **Descending** (`created_at < T_ms`) skipped every row between `T_ms` and the boundary row's
  real time. Rows written in one transaction share their time exactly: after two imports,
  `sort=-createdAt` at limit=1 returned 12 of 17 to-dos.

The same cut was made by every other keyset in the framework. Three logs were worse: the credits
ledger and the integrations delivery log handed out the last row's time alone as their next page,
and the platform routing log took only a time. A cut on time alone skips the rows of one
transaction at any precision.

The fix is one mechanism, in `framework/core/src/query/exact-time.ts`:

- A keyset read selects each time key **beside its row, as text to the microsecond**, in the same
  statement (`exactTime`: `to_char(<expr> at time zone 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.US')`).
- The cursor keeps that text.
- The next page compares it **in SQL** against the same expression the query orders by
  (`<expr> > '<text>Z'::timestamptz`). It never passes through a `Date`.

The SLA cursor already worked this way (S3), and now uses the same helpers. Every log pages by
(time, id).

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | One mechanism for every keyset: `exactTime(column, expr?)` selects the value as text, `readTimeKey` reads a cursor's time back, and `timeAfter`, `timeSame` and `timeFrom` compare in SQL. They are in `@hykr/core` (`query/exact-time.ts`, exported). The text is S3's form: UTC, six fractional digits, no zone letter. The comparison adds `Z` and casts to the column's own type (`timestamptz`, or `timestamp` for a column without a zone, which `to_char` reads without `at time zone`). | Brief ("one mechanism … prefer a cursor that carries the stored value exactly, compared in SQL against the same expression the query orders by"); S3's `dueKey`. |
| 2 | The text is selected in the **same statement** as its row, never looked up by id afterwards. An `updatedAt` can move between two statements, and a row looked up later may be gone. | Review (advisor); default. |
| 3 | Entity lists: `buildListSql` returns `fields`: `{ row: table, key<i>: exactTime(...) }`, one `key<i>` per `PgTimestamp` sort key. It also returns `cursorAfter(selected)`, which replaces `cursorValues(row)`. `define-entity.ts` and `plugins/shared.ts` select `built.fields` (the shared list for both its platform half and its re-select) and return `r.row`, so no extra key leaves. A key is taken through its sort expression, so a nullable column's `coalesce` gives the far-off time in the same form, and `farValue`'s `Date` for timestamps is gone. | Brief (list-grammar: keep, encodeCursor, after, farValue); review. |
| 4 | Only `PgTimestamp` (mode `date`) keys are selected beside the row. A string-mode timestamp already arrives as Postgres's text (drizzle's `PgTimestampString.mapFromDriverValue` returns the string). A date, number, text, uuid, enum or boolean value is exact in JavaScript. A geo key keeps the row's point, whose float8 coordinates round-trip exactly, and recomputes the distance in SQL. | Checked in drizzle 0.45.3's `timestamp.js`; default. |
| 5 | A cursor made before this change holds a millisecond (`toISOString`) and **keeps paging**. It never gets a 500 or a 400. Its time lies somewhere inside that millisecond, so `timeAfter` descending takes the whole millisecond (`< T + 1 ms`) and `timeSame` the range (`>= T and < T + 1 ms`). Ascending, `> T_ms` already skips nothing. That one page may repeat a row of its millisecond, but skips none, and the cursor it hands out is exact, so the walk goes on normally. | Brief ("a cursor a client already holds … must still page without a 500"); review: legacy repeats rather than skips. |
| 6 | A tampered time is 400 `bad_cursor`, as before (V1 decisions 4 to 7). `readTimeKey` takes exactly the two forms a server wrote: six digits with no zone, or `toISOString`. The text must name a real instant (no 31 February, no hour 24) and a year Postgres can store (not 0000). Seven digits, a space for the `T`, a `Z` on the six-digit form, and five digits are each refused. | Brief; V1 decisions 4 to 7; V10 decision 6. |
| 7 | The (time, id) keysets (inbox, comments, agent runs) share `framework/api/src/features/inbox/cursor.ts`. Its `Keyset` now holds a `TimeKey`. `keysetTime(column)` is what a read selects beside its row (`select({ row, at: keysetTime(...) })`), and `encodeKeyset({ at, id })` takes that text. `keysetOf`, `badKeyset` and `decodeKeyset` keep V10's names and signatures and add its checks: id at most 128 characters, with no NUL and no lone surrogate (self-contained here, since V10's `textFault` is not on this base). Old cursors (`<ms ISO>|<id>`, and agent runs' `[<ms ISO>, id]`) still decode. | Brief (build on V10's shapes); V10 decision 6. |
| 8 | Agent runs' `decodeCursor` is V10's text, unchanged. A bad cursor is 400 `bad_cursor` instead of being ignored. The merge therefore takes that hunk cleanly. | V10 (gap/V10); merge plan. |
| 9 | The **credits ledger** and the **integrations delivery log** page by (time, id). `next` and `nextBefore` are tokens, opaque base64url of `<exact time>|<id>`. `before` takes either such a token or an ISO time. A time stays a plain bound (entries strictly before it), as before: for someone choosing a moment, not paging. `beforeOf` tells the two apart: only base64url text that decodes to a keyset counts as a token, and an ISO time holds a `:`, which base64url never does. Text that is neither is what each route did before: the ledger takes it as no bound, the delivery log answers 400 `invalid`. | Review (advisor point 1: precision alone does not fix a time-only cut); brief ("the credits ledger … the integrations delivery log"). |
| 10 | The **platform routing log** returns a bare array, so it has no page-level `next`. Each row gains **`cursor`** (additive, optional on `RoutedRequest`). The client passes the last row's `cursor` as `before`. The log now orders by `(created_at desc, id desc)`, so rows that share a time keep one order. `before` still takes an ISO time. Text that is neither is 400. | Review (advisor point 1: "decide an additive way"); default: no breaking change to the response shape. |
| 11 | The SLA cursor keeps its own format and decoding (S3, and V10's change to `decodeSlaCursor`). Only `dueKey` and `afterCursor` now go through `exactTime`, `timeFrom` and `timeAfter`, so there is one mechanism with the same SQL. | Brief ("the SLA cursor"); merge plan: stay out of V10's hunks. |
| 12 | No schema change. The tests set `created_at` with SQL on existing fixture tables. | Default; review. |

## Assumptions to review

- **An old descending cursor repeats.** For one page, a cursor made before this change may show
  rows of its last millisecond again, ascending or descending. It skips none. Clients that
  de-duplicate by id see no difference.
- **`next` is now a token.** The ledger's `next` and the delivery log's `nextBefore` used to be
  ISO times. A client that passes them back as `before` (the documented use, and the only one in
  the repo) keeps working. One that read `next` as a date would not, and none in the repo does.
- **A time stays a time-only bound.** `before=<ISO time>` on the ledger, delivery log and routing
  log still means "strictly before this moment". Rows at that very moment are excluded on
  purpose: they are not a page boundary.
- **Each routed row carries `cursor`.** That costs one more selected expression per row. The
  alternative was `before=<id>`, looking up the row's time by id, which fails once retention has
  deleted that row.

## API sketch

```ts
// @hykr/core
exactTime(column: Column, expr?: SQL | Column): SQL<string>   // '2026-11-12T16:55:48.123456'
type TimeKey = { text: string; exact: boolean };               // exact: false = an older cursor's ms
readTimeKey(value: unknown): TimeKey | undefined
timeAfter(column, expr, key: TimeKey, dir: 'asc' | 'desc'): SQL
timeSame(column, expr, key: TimeKey): SQL
timeFrom(column, expr, key: TimeKey): SQL                      // >=, for an index-served bound

const built = buildListSql(table, spec.list, q);
const found = await conn.select(built.fields).from(table)...;  // { row, key0?, key1?, ... }[]
const items = found.slice(0, limit).map((r) => r.row);
const nextCursor = found.length > limit ? built.cursorAfter(found[limit - 1]) : null;

// framework/api/src/features/inbox/cursor.ts
keysetTime(createdAt)                       // select({ row: t, at: keysetTime(t.createdAt) })
encodeKeyset({ at, id }) / decodeKeyset(c) / keysetOf(at, id) / badKeyset()
olderThan(keyset, time, id)                 // (time desc, id desc)
beforeOf(before, readTime) → Keyset | Date | undefined; beforeWhere(bound, time, id)
```

```
GET /api/credits/ledger?before=<next>           → { items, next: <token> | null }
GET /api/integrations/endpoints/:id/deliveries?before=<nextBefore> → { items, nextBefore }
GET /api/platform/routing?before=<last row's cursor>  → [{ …, cursor }]
```

## Test plan

Each test below failed on the base (38fe9cf3) and passes with the fix. To show this, I checked
out the base `framework/{core,api,contracts}/src`, rebuilt, and ran the new tests.

- **Fixture e2e `framework/api/test/framework/keyset.e2e.test.ts`** (fixture app). Seven rows:
  three of one time, one before and one after them within the same millisecond, the next
  millisecond, and the next day. Every read is walked to its end at limit=1 and limit=2, and must
  match Postgres's own `ORDER BY` exactly.
  - Entity lists, with six sorts: `createdAt`, `-createdAt`, `createdAt,title`,
    `-createdAt,-title`, `dueOn,createdAt` and `-dueOn,-createdAt` (a time after a nullable key).
    Base: ascending, "the walk never ended" (60 and 120 rows over 60 pages); descending, 3 or 4
    of 7.
  - A cursor made before the fix (the millisecond), both ways: it pages to the end and shows
    every row after it. Base: ascending, the walk never ended.
  - Tampered times (seven digits, 31 February, year 0000, hour 24, a `Z` on six digits, a space
    for the `T`): 400 `bad_cursor`. This passed on the base too, as V1 had made it.
  - The inbox (with an old cursor, and a tampered one: 400), agent runs, the credits ledger (and
    an ISO `before` as a bound), the delivery log, and the routing log (and an ISO `before`, and
    `nonsense`: 400). Base: 3 of 7 for each. On the base, a routed row had no cursor, and a
    client paging by `createdAt` lost the rows of one time.
- **Fixture e2e `framework/api/test/framework/keyset-shared.e2e.test.ts`** (settings app). A
  shared entity's list mixes the platform's rows and the business's own, interleaved and sharing
  times, `createdAt` both ways at limit 1 and 2. Base: 4 of 4 failed (the walk never ended, or 2
  of 6).
- **Unit `framework/core/src/query/list-grammar.test.ts`**, "a time a cursor keeps (V12)":
  - the selected fields, and the SQL of each key, a nullable one's included;
  - that the cursor keeps the selected text rather than the row's `Date`;
  - the comparison SQL and its parameters, asc, desc and with a second key;
  - an old cursor's widened millisecond;
  - a column without a zone.
  
  The existing "cursor values" tests now go through `cursorAfter`, and the tampered list gained
  the forms above. `geo.test.ts` moved to `cursorAfter` too.
- **Application e2e `application/api/test/domain/todo-keyset.e2e.test.ts`**: two real CSV imports
  (8 and 9 rows; asserted to share a time) and three to-dos within one millisecond. Walked with
  the default sort, `createdAt`, `-createdAt` and `-createdAt,title`, at limit 1 and 2. Base: 8 of
  8 failed (the walk never ended ascending; 3 or 6 of 20 descending).
- Still passing: `comments`, `sla`, `settings`, `geo`, `untrusted-keys` e2e, and the whole
  `@hykr/core` unit suite.

## The sweep: every keyset that holds a time

| Site | Was | Now |
|---|---|---|
| Entity lists (`list-grammar.ts`, `define-entity.ts`, `plugins/shared.ts`) | Date in the cursor | exact text, decision 3 |
| Inbox (`inbox.service.ts`) | `encodeKeyset(row)` with a Date | `keysetTime`, decision 7 |
| Comments (`comments.service.ts`) | same | same |
| Agent runs (`agents.service.ts`) | `[toISOString(), id]` | `[exact, id]`, decision 8 |
| SLA clocks (`sla-read.ts`) | exact already (S3) | through the shared helpers, decision 11 |
| Credits ledger (`credits.service.ts`), both its routes | `next` = last row's time; `at < before` | token and (at, id), decision 9 |
| Integrations delivery log (`manage.service.ts`) | `nextBefore` = last row's time | token and (created_at, id), decision 9 |
| Platform routing log (`platform.controller.ts`) | `before` = a time, ordered by time only | row `cursor` and (created_at, id), decision 10 |

These were checked and are not keysets, so they were left as they are:

- **Jobs** (`GET /api/jobs`): `ListJobsQuery` has no cursor or `before`. The route returns the
  latest `limit` jobs.
- **History** (`GET /api/history`): `since` is the device's own clock (the app's previous visit,
  `AssistantActivity.tsx`), not a row's time. The feed returns no next value, and a record's
  history is one page of 50.
- **Versions** (`revise.ts`): ordered by revision number, with no cursor.
- **Credits usage and platform usage**: a `from`/`to` range summed. The usage report and the
  tenant list page by `after` (a tenant id), not a time.
- **Chat threads and memory recall**: by `seq` (an integer).
- **Export** (`export/build.ts`) and MCP tools: they pass entity lists' `nextCursor` through, so
  the fix covers them.
- No keyset in the sample (`application/`) holds a time of its own: its lists are entity lists.

## Merging with V10

`git merge-tree --write-tree gap/V10 gap/V12` conflicts in four files. `list-grammar.ts`,
`list-grammar.test.ts` and `sla-read.ts` merge cleanly.

- `framework/api/src/features/inbox/cursor.ts`: **take V12's side for the whole file.** It keeps
  V10's `keysetOf`, `badKeyset` and `decodeKeyset` names, signatures and checks. Optionally
  replace V12's local `TEXT_FAULT` with V10's `textFault` from `@hykr/contracts`.
- `framework/api/src/features/agents/agents.service.ts`, the import line: take V12's
  (`badKeyset, type Keyset, keysetOf, keysetTime, olderThan`). The `decodeCursor` hunk is
  identical on both sides and merges cleanly.
- `framework/api/src/features/platform/platform.controller.ts`, `RoutingQuery.before`: take
  V12's (`routingBefore`, which goes through `storableInstant`, so V10's year bound holds). Then
  drop V10's now-unused `storableDateTime` import.
- `docs/developer-guide.md`: the conflict is V10's undo paragraph against V8's (section 5.8).
  V12 does not touch it. Keep both sentences.

## Deferred

Nothing. Guide section 14 needs no line: every keyset found keeps its time exactly. The one
