# B22: Microsoft 365 (Outlook) calendars

## Summary

A person can now connect a Microsoft 365 or Outlook.com calendar as well as, or instead of, a
Google one. They get the same three things Google gives them (B17): busy and free time read from
it, their schedulable records written into it, and moves or deletions made there reported back
as `calendar.event_moved` / `calendar.event_removed`.

- **One interface.** `CalendarProviderDef` (`framework/api/src/features/calendar/providers/`)
  covers the sign-in, `freeBusy`, `upsertEvent`, `deleteEvent`, `changes`, `watch` and
  `stopWatch`. Google's code moved behind it unchanged: every B17 test passes as it was.
  Tokens, sign-in states, `needs_reauth`, feeds and invites stay the feature's own, shared by
  both providers.
- **Microsoft Graph** (`@hykr/connectors/microsoft-calendar`, transport only, with an in-memory
  fake):
  - sign-in: the identity platform's authorization code flow with PKCE;
  - busy times: `getSchedule`;
  - events: `/me/events`, keyed by an extended property;
  - changes: a `calendarView` delta query;
  - notifications: change subscriptions posting to the B10 inbound webhook, with Graph's
    validation handshake answered.
- **Generic routes.** `/api/calendar/:provider/start | callback | complete`. Google's old paths
  still work.
- **Both at once.** Busy time is merged across every calendar the person connected. Records
  are written to one of them: the one the person chose (`writeTo`), else the first connected.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | `@hykr/connectors` gains the subpath `@hykr/connectors/microsoft-calendar`. It is transport only (no database, Nest or policy), like `google-calendar`. It holds: OAuth helpers (authorization URL, code exchange, refresh, admin-consent and revoked-grant checks); a Graph client (getSchedule, event upsert/delete, delta, subscribe/unsubscribe); the `microsoft-calendar` inbound connector; and `fakeMicrosoft()`, one per process on `globalThis`, so a test and the server share it. | Requirement; B17 decision 1 (same shape). |
| 2 | The server's calendar feature reaches each provider through `CalendarProviderDef`. `google.ts` adapts the existing Google functions without changing a request, so B17's tests (which assert Google's requests) pass untouched. The services call only the interface. The connector modules are imported in two places: the provider adapters, and the feature's registration of connectors and handlers. | Requirement ("behaviour stays the same"). |
| 3 | `CALENDAR_PROVIDERS` (comma list) turns providers on. Unset means `google`, so an existing deployment changes nothing. An unknown name stops the start. A provider is offered when it is turned on and its OAuth client is set, and `GET /api/calendar/providers` lists the turned-on ones with `available`. Microsoft's settings: `MICROSOFT_CALENDAR_CLIENT_ID`, `_CLIENT_SECRET`, `_TENANT` (default `common`), `_REDIRECT_URL` (default `<BETTER_AUTH_URL>/api/calendar/microsoft/callback`), `_TRANSPORT` (`live` or `fake`; production refuses fake), and the overrides `MICROSOFT_LOGIN_URL` and `MICROSOFT_GRAPH_URL` (https only). Google's variables are unchanged. | Requirement; open question 1 (`common`: work and personal accounts; a deployment can set its tenant id). |
| 4 | Sign-in: authorization code with PKCE S256 against `<login>/<tenant>/oauth2/v2.0/authorize`, `response_mode=query`, `prompt=select_account`, and `login_hint` set to the member's address. The scopes are `openid email profile offline_access Calendars.ReadWrite`. `profile` is added to the requirement's list because work accounts often have no `email` claim, and `preferred_username` comes only with `profile`. The account is the ID token's `email`, else `preferred_username`. The token came from the token endpoint over TLS, so it is not verified again (OIDC Core 3.1.3.7, as for Google). Microsoft rotates refresh tokens: each new one is stored. | Requirement; default (the `profile` scope). |
| 5 | The sign-in state, its binding to the person and business, the single use and the app finishing it under its session are B17 decisions 36 and 37, unchanged. The sign-in row also records its provider. A callback for another provider lands with `sign_in_expired` and leaves the row alone. A complete for another provider is refused with `calendar_sign_in_invalid`, and the row is used up. The landing now also carries `provider`, so the app knows which `complete` to call. | Default (fail closed). |
| 6 | Admin consent: Microsoft's refusal is recognised in two places. On the consent screen it comes back on the callback's query (`consent_required`, AADSTS65001, AADSTS90094, AADSTS90008, AADSTS900941). At the code exchange it comes back in the token error. Either way it becomes `admin_consent_required`: the landing's `error`, or the complete's 400 `rule`, with the message "ask your Microsoft 365 administrator…". Any other refusal at the exchange is `microsoft_refused` (Google's stays `google_refused`). | Requirement. |
| 7 | Events: Graph makes its own event ids, so our event carries the record's deterministic key (the same `bc…` value Google's id is) in a `singleValueExtendedProperty` with a fixed GUID. The link row stores Graph's id. An upsert PATCHes the known id; on a 404, or with no id known, it looks the key up (`$filter` on the property) and PATCHes what it finds, else POSTs. A retry whose first answer was lost therefore finds the event instead of making a second. The key is checked against `[A-Za-z0-9_-]` before it goes into a filter. | Requirement ("a retry never makes two"). |
| 8 | Events are written with the business's time zone (`tenantZone`). The framework has no per-person zone (a channel link's zone is the only one, and not every member has one), so "the person's time zone" in the requirement is read as the business's. Times are stored and compared as instants, and every Graph call sends `Prefer: outlook.timezone="UTC"`, so what Graph returns is UTC. | Default; logged as an assumption. |
| 9 | Free/busy: `POST /me/calendar/getSchedule` for the connection's own address. Only `start` and `end` of items whose status is `busy`, `tentative` or `oof` are kept; subjects and locations are dropped in the connector, before anything reaches the server. `free` and `workingElsewhere` leave the time open. | Requirement ("only free/busy is read"). |
| 10 | Changes: `GET /me/calendarView/delta` over a window from a day back to 365 days ahead. The delta follows `@odata.nextLink` for up to 40 pages, and the `@odata.deltaLink` is the cursor, stored where Google's sync token is (`sync_token`). Items marked `@removed`, or `isCancelled`, are removals; Graph also reports an event moved out of the window as removed. A 410 or `syncStateNotFound` starts the listing again, and like Google's first look it notes nothing. Each item is reduced to its id and times in the connector; a subject never reaches the server. Our events are recognised by their link row (connection and Graph id), because a delta does not return extended properties. | Requirement; Graph's delta semantics. |
| 11 | Subscriptions: `POST /subscriptions` on `/me/events` (`created,updated,deleted`), expiring 4200 minutes on (Graph's limit for events is 4230). `notificationUrl` is `/webhooks/microsoft-calendar/<inbound connection>`, and `clientState` is 32 random bytes sealed in that inbound connection. The subscription id is stored as the connection's `channel_id`; there is no resource id. `calendar.maintain` renews a subscription with less than a day left by making a new one and then deleting the old one, as for Google channels. Notifications from an old subscription are ignored. Without an https `CALENDAR_PUBLIC_URL` no subscription is made and the poll does the work (B17 decision 9). Lifecycle notifications are not asked for: the renewal and the poll cover a lapsed subscription. | Requirement. |
| 12 | The inbound bus gains `ConnectorInbound.handshake(req, credentials)`. A POST that is a handshake (Graph sends `?validationToken=` with an empty body) is answered 200 `text/plain` (`nosniff`) with the token and stores nothing. The connection must still exist (404 otherwise). Only printable tokens up to 1 KB are echoed. Such a check carries no proof, so it can only echo. A notification is verified by every item's `clientState` (`safeEqual`); one wrong value refuses the whole request (401). Graph signs nothing, so the connector sets `signedIds` and gives each notification a fresh id, as Google's does: the handler only reads the delta again, so a replay changes nothing. | Requirement; B10 (GET `challenge` stays for senders that use GET). |
| 13 | Disconnect deletes our events, the subscription, the tokens and the inbound connection. Microsoft has no revoke endpoint for this flow, so nothing is revoked. The person can remove the app at myapps.microsoft.com (work) or account.live.com/consent/Manage (personal), and the developer guide says so. Clean-up refreshes an access token that has run out before it calls the provider. | Requirement. |
| 14 | Live calls go through the egress guard (`safeRequest`: https, public addresses, a 15 s timeout, 4 MB answers) and only to the hosts of the configured endpoints (`login.microsoftonline.com`, `graph.microsoft.com`, or the overrides). Google keeps B17 decision 2's plain `fetch`: changing it was out of scope. | Requirement. |
| 15 | Both at once: one connection per person and provider (the existing unique index). `free()` and `busy()` read every active connection in parallel and merge (`mergeBusy`). A connection whose grant is gone is left out and marked `needs_reauth`. `connected` is true if any answered. | Requirement; open question 2. |
| 16 | One write target per person: the connection with `write_to` (new column, default false), else the first connected among the person's active connections of providers turned on here. `PATCH /api/calendar/connections/:id { writeTo: true }` is the op `calendar.connection.target`, through `runWrite`, the person's own and audited. It clears the flag on their other connections and stores `calendar.target_changed`. That event, and `calendar.disconnected`, queue a `retarget` job, which takes the person's records out of their other calendars and backfills the target. A second connection is only read: its records are not backfilled. `GET /api/calendar/connections` shows each connection's effective `writeTo`. | Open question 2 ("one target per person"). |
| 17 | Routes: `POST /api/calendar/:provider/start`, `GET /api/calendar/:provider/callback` and `POST /api/calendar/:provider/complete`. An unknown provider is a 404. `google/callback` and `google/complete` are now these routes with `google`, and the older `POST /api/calendar/connections { provider }` stays, both for one release. The client (`api.calendar.connect(provider)`, `complete(input, key, provider)`, `setWriteTo(id)`) uses the new routes. | Open question 3. |
| 18 | The per-person calendar flow stays apart from any business-wide OAuth flow: calendar sign-in is per person, and keeps its own flow behind this interface. | Open question 4. |
| 19 | Personal data: erasure and export iterate connections whatever the provider (H4). A Microsoft connection is exported with its provider and account, never a token. Erasure deletes it, and afterwards our events and the subscription are taken out, as a disconnect does. | Requirement. |
| 20 | App: `useConnectCalendar(provider)`, `useCompleteCalendar` (the provider from the landing), `useSetCalendarTarget`. The `/calendar` screen shows a connect button per offered provider, each connection's provider, and "Write events here" when there are several. `admin_consent_required` shows its own message. The `needsReauth` and `notOffered` words no longer name Google. | Requirement. |

## Assumptions to review

- **Time zone of events.** Microsoft events are written in the business's zone, because members
  have no zone of their own. Should members get one (settings, or the device's)?
- **Delta window.** Changes are read from a day back to a year ahead of when the cursor was
  made. A record further ahead than that is written, but a move of it is not noticed (and a move
  out of the window reads as a removal). Should the cursor be renewed periodically?
- **Work accounts' address.** Free/busy asks Graph for the connection's account address
  (`preferred_username`). For the rare tenant whose sign-in name differs from the mailbox
  address, should the address be read from `/me` (which would need `User.Read`)?
- **Calendars.ReadWrite.** Graph has no scope narrower than this that writes events. The
  connector reads only busy intervals and our events' times, but the grant itself is wider than
  Google's two scopes.

## Test plan

- `framework/connectors/src/microsoft-calendar/microsoft-calendar.test.ts`:
  - the authorization URL;
  - the exchange, rotation and a refused refresh;
  - the account claims and the admin-consent detection;
  - getSchedule dropping subjects;
  - the upsert retry (one event after a lost answer), with its zone and extended property;
  - delta paging, moves, removals, out-of-window and a lost cursor;
  - a refused subscription;
  - the connector's handshake and clientState checks;
  - the transport refusing other hosts and http.
- `framework/api/test/framework/calendar-microsoft.e2e.test.ts` (fixture appointments, both
  fakes, `CALENDAR_PROVIDERS=google,microsoft`):
  - both providers offered;
  - start, callback and complete, single use, refused to another person, another business,
    another provider and the assistant;
  - admin consent at the screen and at the exchange;
  - an unknown provider is a 404;
  - a record written once despite a lost answer and the job's retry; updated by PATCH; deleted
    with the record; written in the business's zone;
  - a move and a deletion in Outlook through the subscription; the handshake echoed; a wrong
    clientState refused;
  - polling without a subscription; a lost delta cursor;
  - renewal with a moved clock (new subscription, old deleted);
  - a refused refresh marking `needs_reauth`;
  - with Google and Microsoft both connected: busy and free time from both; the first connected
    as the target; `writeTo` moving the event to Google;
  - no subject of the person's own events stored anywhere;
  - export and erasure of a Microsoft connection.
- `framework/api/test/framework/calendar.e2e.test.ts` and
  `application/api/test/domain/calendar.e2e.test.ts` run unchanged.

## Deferred

- CalDAV and Apple iCloud (they stay on ICS feeds).
- Picking a calendar other than the primary one, for both providers.
- Two-way sync: a move or deletion in the provider stays an event for a module to act on.
- Reading invite replies.
- Graph lifecycle notifications and rich (encrypted) notifications.
- Removing the old `POST /api/calendar/connections` alias after one release.
