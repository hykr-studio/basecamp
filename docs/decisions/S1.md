# S1: support access leaves nothing behind its time box

## Summary

A fix found by the security review of B19. Support access (an operator's consented, time-boxed
standing in a business) was meant never to hold a capability that changes who reaches the
business, or lets its data leave, beyond the time box. It was enforced by a central deny-list
(`FRAMEWORK_WITHHELD`) that later features did not join: `shares.create`, `shares.manage` and
`privacy.manage` could be asked for and consented to. With them an operator could make a share
link that kept working for up to `shares.maxDays` after the grant ended, or download a full
personal-data copy of anyone in the business.

The fix has two layers:

- **Support holds only what is declared supportable.** `CapabilityDef` gains `supportable`.
  Support access may hold a capability only when its definition says `supportable: true`. The
  default is false, so a capability nobody thought about is never held (fail closed). Every
  framework capability now states its choice where it is defined. The central list is gone. An
  application can still withhold a framework capability declared supportable
  (`supportWithheld`).
- **What support makes ends with the grant.** A share link remembers the standing it was made
  under (`share_links.on_behalf_of`, `support:<grantId>`, as audit stores it). It never outlives
  the grant's end (`expires_at` is capped at the grant's `until`). Revoking or ending the grant
  revokes its links in the same write. A link whose standing is no longer in force (the grant
  ended, expired, or its operator was disabled or lost `platform.support`) reaches nothing (410
  `link_revoked`). This holds even if a capability that makes links is ever made supportable.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | `CapabilityDef.supportable?: boolean`. Support access may hold a capability only when it is defined, grantable (`grantable` is not false), declared `supportable: true` and not in the application's `supportWithheld`. Both places that check (the request, 400 `capability_withheld`, and the standing read on every request, which drops the capability) use one function, `supportMayHold`. | Task ("mark capabilities supportable: false where they are defined, instead of relying on a central deny-list"); plan rule: fail closed. |
| 2 | The default is **false** (opt in). A capability whose author never considered support access is never held by it, so a missed capability cannot leak again. Each framework capability states `supportable` explicitly, `true` or `false`, so the choice is visible where the capability is defined. | Task ("make the guard structural, so a missed capability cannot leak again"); default: fail closed. |
| 3 | Not supportable: `members.manage`, `records.grant`, `parties.manage`, `support.consent`, `channels.manage`, `settings.manage`, `models.manage`, `credits.manage`, `integrations.manage` and `data.export` (B19's list); **`shares.create`, `shares.manage` and `privacy.manage`** (this fix); `approvals.decide` and `marketing.approve` (support never decides, B19 decision 11, so holding them only misleads); `agents.create` (an agent acts later, by itself) and `agents.manage` (running someone's agent acts as its owner, with more than the business consented to). `shared.publish` is not grantable, so it is not supportable either. | Task; B19 decision 10 ("support never leaves behind lasting access"); default. |
| 4 | Supportable: `backoffice.use`, `customers.message`, `history.all`, `members.read`, `credits.view`, `parties.read`, `calendar.availability.read`, `calls.read_all`, `memory.read`, `memory.write`, `memory.manage`, `comments.internal`, `comments.moderate`, `acceptances.evidence` and `imports.run`. Each reads, or writes the business's own records, inside the time box, audited on behalf of the operator. Nothing it does lasts past the grant: an import job refreshes its principal before it runs, so it fails once the grant has ended. | Default; B19 decisions 8 and 12. |
| 5 | `privacy.manage` covers every privacy step: reading the business's requests, filing one for someone else, processing, refusing, configuring, and downloading an archive. One capability, not supportable, closes all of them, so no privacy-specific check for support access is added. Like anyone, a support principal still reaches requests about its own person, and only those. | Task scenario 2; `reachesRequest` and the privacy commands read the capability only. |
| 6 | `share_links.on_behalf_of` (nullable text) records `onBehalfOfKey(p.onBehalfOf)` when a link is made: `support:<grantId>` under support access, null for a member. It uses the same key as `audit.events.on_behalf_of`, so the link and its audit row name the same standing. | Task ("store the support grant id on share_links made under support"); B19 decision 7. |
| 7 | A link made under support never expires after the grant: `expires_at = min(now + days, onBehalfOf.until)`. The guard's expiry check, the `share` grant's row check and a form's use count all honour it, with no extra code. | Default: the simplest bound that every live check already reads. |
| 8 | `support.revoke` and `support.end` revoke the grant's live links in the same transaction (`revoked_by = 'support.ended'`). The links are listed in the write's `touched`, so the audit shows them. | Task ("have endSupport revoke those links"). |
| 9 | The structural check: a link with `on_behalf_of` reaches something only while that standing is still in force. `StandingProvider` gains an optional `stillStands({ db, userId, tenantId, onBehalfOf })`. It answers true or false for its own keys, null for others'. The support provider answers true only for a grant of that person and business that is consented, not ended and not past `ends_at`, whose operator is enabled and still holds `platform.support`. `PrincipalResolver.forShareLink` asks the providers. When none says true, the link is refused (403 `maker_gone`), and `ShareGuard` answers 410 `link_revoked`, as it does for a page whose maker left. This also covers expiry and a disabled operator, where no write happens. | Task ("or have ShareGuard refuse a link whose creating grant has ended"); default: fail closed (a key no provider vouches for reaches nothing). |
| 10 | Links made by a member are unchanged. A record or form link still survives its maker leaving, as B9 decided. Only a link made under a platform standing is bound to that standing. | B9 decision 15 (only page links follow their maker); default: reversible, smallest change. |
| 11 | `ShareLinkInfo.onBehalfOf` shows the team which links support made. | Default: the business should see what support left. |
| 12 | The sample marks `orders.cost.read` `supportable: true` (seeing a cost is a read). `orders.approve` and `todos.cost.read` stay undeclared, so support never holds them. | Plan, "Sample proof". |
| 13 | Schema: one nullable column and a partial index on `app.share_links`. Additive. No migration is committed (the integrator generates it). | Plan migration rule. |

## Assumptions to review

- **Opt in, not opt out.** A capability support may hold must say `supportable: true`. An
  application's existing capabilities (a cost column, an approval) are no longer held by support
  until their module declares them. Is opting in the right default, or should only exits be
  marked?
- **Messaging customers.** `backoffice.use` and `customers.message` stay supportable: a reply or a
  template sent while the grant lasts is audited and ends with it. Should support never message a
  business's customers, even with consent?
- **Agents.** Support can no longer make, run or pause agents (`agents.create` and
  `agents.manage`). Pausing a runaway agent is a fair support task. Should pausing be split from
  running into its own capability, so support could hold it?
- **Approvals.** `approvals.decide` and `marketing.approve` are refused in a request now, instead
  of being held and never working. Is a 400 clearer for operators than the earlier silent no-op?
- **Links already made.** Links made under support before this fix have no `on_behalf_of`. They
  keep working until they expire. Should the migration bind them (by `created_by`, the grant's
  window and tenant), or revoke them?

## API sketch

```ts
// Where a capability is defined: may a consented support access hold it? Default false.
defineCapability({ name: 'orders.cost.read', label, roles: ['owner'], supportable: true });

// An application withholds a framework capability declared supportable.
defineServer({ ..., contributes: { supportWithheld: ['customers.message'] } });

// A platform standing that can vouch for what was made under it.
const provider: StandingProvider = {
  name: 'support',
  forUser: async ({ db, userId, tenantId, channel }) => /* OtherStanding | null */,
  stillStands: async ({ db, userId, tenantId, onBehalfOf }) => /* true | false | null */,
};
```

| Route | Change |
|---|---|
| `POST /api/platform/support` | `shares.create`, `shares.manage`, `privacy.manage`, `agents.*`, `approvals.decide`, `marketing.approve` and any capability not declared supportable: 400 `capability_withheld` |
| `POST /api/shares` | Under support: `on_behalf_of = support:<grant>`, expiry capped at the grant's end |
| `POST /api/support-access/:id/revoke`, `DELETE /api/platform/support/:id` | Also revoke the grant's links |
| `GET /api/share/:token` (and every share route) | A link whose standing ended: 410 `link_revoked` |
| `GET /api/shares` | `onBehalfOf` on each link |

## Test plan

`framework/api/test/framework/platform.e2e.test.ts` (the platform fixture now shares `issue` and
declares an application capability without `supportable`):

- Every capability the framework registers (all but the fixture's, and the ones not grantable)
  states `supportable` as true or false, so a new one fails this test until its author decides.
- A request for `shares.create`, `shares.manage`, `privacy.manage`, `agents.manage`,
  `data.export` or an application capability not declared supportable: 400 `capability_withheld`.
- Scenario 1, share links. A grant stored before the fix with `shares.create` (written by SQL):
  `/api/me` does not list it, and `POST /api/shares` is 403 `shares_create`. Then, as if a
  capability that makes links were ever supportable (the registry flipped for the test), the
  operator makes a link. It records `support:<grant>`, its expiry is capped at the grant's end, and
  it opens with no session. When the owner revokes the grant, the link is revoked (410, status
  `revoked`, `revoked_by = support.ended`, listed in the revoke's audit). A second grant's link
  answers 410 while its operator is disabled and 200 again once they are enabled; when the
  grant's time is up (no write), 410. A member's link to the same record keeps working.
- Scenario 2, personal data. The owner's own export completes with an archive. A write grant
  stored with `privacy.manage` (by SQL) does not hold it. The operator does not see the request
  (404), cannot download the archive (404), cannot list it, and cannot file an export or an
  erasure for the owner (403 `needs_privacy_manage`).
- The existing support tests still pass; `fixture.issue.note` is declared `supportable: true`.

## Deferred

- Binding or revoking links made under support before this fix (assumption above).
- A `supportable` flag in `GET /api/members/roles`, and a picker of supportable capabilities in
  the back office's support request form (operators type capability names today).
- Other kinds of lasting things made under support. Today none exist outside the withheld
  capabilities: invitations, record grants, webhook endpoints, agents, privacy requests and
  exports need a capability support cannot hold, and calendar feeds and syncs resolve their person
  on the background channel, which support never stands on.
