# A8: memory and semantic recall

## Summary

The assistant already keeps one thread per person, shared by the app, WhatsApp and voice. A8 adds
three kinds of memory and a recall step that finds them by meaning:

- **Business memory**: a framework entity, `memory` (`/api/memories`), for lasting facts the
  whole business shares ("we close on Sundays"). People write it, and the assistant writes it when
  asked (`create-memory`). Reading and writing it are capabilities (`memory.read`, `memory.write`,
  `memory.manage`), so an application's own roles opt in.
- **Record memory**: any entity can declare that its records are memory with the `memory` trait
  (`traits: { memory: { text, about } }`). `about` names the record they are memory of (a project,
  a meeting). Access is the entity's own, so whatever decides who reads that entity (access, grants,
  a parent's scope) decides who recalls it. The sample's notes are memory of their meeting.
- **Conversation memory**: what the person said in earlier turns, on any channel and in any of
  their threads, keyed by business and person (`tenant + subject`). Only their own words.

**Recall** runs before every chat turn (a turn hook): the person's message is embedded with the
business's embedding model (A10's policy), the nearest memories are found (pgvector when the
database has it, otherwise cosine over `real[]` in SQL), and **each one is loaded again as the
person** before it is used: a record through its entity's scoped repository and projection (a
record they can no longer read, or one whose `about` record they cannot read, is dropped; hidden
fields stay hidden because the text is rebuilt from the projected record), a message only while it
is still in one of their own threads. What survives becomes the turn's context lines, which the
model reads as data, not instructions. The same search is an API, `GET /api/memory/recall`, and a
tool, `recall-memory`.

Indexing is durable and off the write path: a write hook marks every touched record whose entity
has the trait (CRUD and commands alike, from `touched`) as pending in the write's transaction, and
a worker job embeds pending rows every second. Conversation messages are indexed with the vector
recall already computed for them, so they cost no second embedding.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | Three kinds of memory: business-wide (the framework's `memory` entity), record memory (records of any entity with the `memory` trait, `about` a record) and conversation memory (the person's own earlier messages). | PRD tab 1, 7.1 ("Memory: per-person threads across app, WhatsApp, voice; project and studio memory; semantic recall"); gap A8. |
| 2 | Record memory is declared by the application, not stored in a framework table: an entity opts in with `traits: { memory: { text(record), about?(record) } }`. Which records are memory, and who sees them, change with the business. The framework stores only the index. | Boundary rule (mechanisms only); plan A8 ("project and studio memory entities"); gap map risk ("memory can leak cost or margin after a role change"): the entity's own access, A4 grants and B5's parent scope then apply with no extra code. |
| 3 | The framework's `memory` entity holds business-wide memory only (no `about`). A framework entity `about` any record would need the target entity's scope in SQL, which `EntityDef` does not expose (`define-entity.ts` is a hot file A8 may not edit); checking it afterwards in code would leak through every generic read path (history, approvals, events). | Plan hot-file table; fail closed. |
| 4 | `memory` is a platform entity (`platformEntities.memories`): CRUD routes `/api/memories`, the list grammar, tools `list-memories`, `get-memory`, `create-memory`, `update-memory`, `delete-memory`, history and approvals, all generated. It carries the `memory` trait itself, so it is indexed like any record. | CLAUDE.md ("declare an entity once"); plan ("Its specs go in `contracts/src/platform/<x>.ts`"). |
| 5 | Who reaches business memory is decided by capabilities, not role names: `memory.read` (reads and recall; owner, admin, ops, staff by default), `memory.write` (add memory, change or delete your own; same roles), `memory.manage` (change or delete anyone's; owner, admin). A customer holds none. An application gives its own roles these capabilities (`defineRole({ capabilities })`). The entity's `access` grants every role the business (a small helper, `anyRole`), and the feature's entity plugin narrows it by capability: no `memory.read`, no rows; writes only to your own rows without `memory.manage`. | CLAUDE.md ("Anything else is a capability"); boundary rule (no product roles in the framework); fail closed. |
| 6 | The assistant may add business memory without an approval (it is an internal, undoable write, asked for by the person), but changing or deleting memory through the assistant waits for the person's approval. An application can park more with a write hook. | PRD tiers (tier 1: internal write, undoable); default: like the sample's to-do deletes. |
| 7 | Recall is a turn hook (`memory.recall`), registered by the feature. It runs for chat turns only, never for back-office drafts: a draft goes to a customer, and business memory must not leak into it. | F5 decision 15 (turn hooks add `context`); default, fail closed. |
| 8 | The query is the person's message, embedded with `ModelPolicyService.embeddingFor(tenantId)` (the business's embedding model under its policy). A refused embedding model, a provider error or settings that do not parse mean no recall for that turn, never a refused turn: recall only adds context. | A10 decision 16 and 22 ("a business without memory recall may be deliberate"); default. |
| 9 | Vectors are stored as `real[]` with the model ref that made them; recall compares only rows of the same model. With pgvector installed (`sql/pre/memory.sql` creates it when the server offers it), distance is pgvector's `<=>` on the arrays cast to `vector`; otherwise `app.memory_cosine(real[], real[])`, a SQL function (`sql/post/memory.sql`). The API logs which one it uses at startup. | Plan A8 ("pgvector if present, otherwise `real[]` cosine"); gap map (the compose and CI images have no pgvector, confirmed: `pg_available_extensions` has no `vector`). A `vector` column cannot be declared conditionally in a generated migration, so the column is `real[]` either way. |
| 10 | Every recalled candidate is re-checked as the turn's principal before it is used. A record: its entity must still be served, carry the trait and expose `get` to the assistant (`expose.get === 'all'`); `def.repo.find(db, p, id)` must find it (its scope, grants and plugins); the text is `trait.text(def.toRead(row, p))`, so fields hidden from that person are never in it; when the trait names an `about` record, that record's entity must be served and expose `get`, and `repo.find` must find it as the same person. A message: it must still be a `user` message in a thread of the same person in the same business. Anything that fails is skipped. | Gap A8 ("access re-checked on recall"); gap map risk ("Semantic recall returns old text outside API policy"); plan Harden (memory recall in the security review). |
| 11 | The index holds no text: only the source's type and id, its `about`, the model, the vector and its state. Text is always rebuilt from the source as the reader may see it. The vector itself is made from the record as projected for a reader with no capabilities other than `memory.read` (`systemPrincipal`), so capability-hidden fields are not embedded either. | Default; data minimisation (nothing to erase twice), fail closed. |
| 12 | Conversation memory covers only the person's own words (`role = 'user'` messages), keyed by business and subject (`user:<id>` or `contact:<id>`), across all their threads and channels. The assistant's replies are not recalled: they may quote records the person can no longer read, and free text cannot be re-checked. The last 12 messages of the current thread are excluded (they are already in the model's history). | Plan note ("resource key tenant+subject"); gap map risk ("A person in two studios must never recall across tenants"); fail closed. |
| 13 | A message is indexed in the turn hook's `after`, with the vector recall computed in `before` (the message is saved between the two). No second embedding call. A turn whose recall did not run (off, refused, failed) indexes nothing. | Gap map risk ("Every turn adds embedding calls, which affects cost (A3)"). |
| 14 | Records are indexed off the write path. A write hook (`memory.index`) marks each touched record of a trait entity as pending in the write's transaction (deleted: its index row goes), with the process's queue prefix; the queue `memory.index` (a schedule every second) embeds pending rows of its own prefix, grouped by business, with `FOR UPDATE SKIP LOCKED`. A record whose text is empty, or that is gone, leaves the index. Failures retry five times, then the row is `failed`. | Plan F3 (write hooks see `touched`, commands included: "Repo calls inside a command publish no entity events"); F5 decision 9 (the prefix guard); default. |
| 15 | When a business's model policy changes (`models.policy.changed`), its index is rebuilt: every row is marked pending and re-embedded with the new model, and records of trait entities that were never indexed are added (backfill). A daily schedule (`memory.backfill`, 03:17 UTC) backfills every business, so records written before the feature existed are found. | A10 decision 23; default (vectors of two models cannot be compared). |
| 16 | Per-business settings section `memory`: `{ recall: true, conversation: true, limit: 5, minScore: 0.3 }`. `recall: false` stops recall before turns and the keeping of messages (the recall API and tool still search); `conversation: false` leaves the person's messages out everywhere; `limit` is how many memories a turn gets (0 to 10); `minScore` the lowest cosine similarity kept. | Plan conventions (`contracts/src/settings/<x>.ts`); boundary rule (values that change per business are settings, with neutral defaults). |
| 17 | A turn's context lines say where each memory comes from (`memory`, a note, what the person said and when) and are cut to 400 characters each. The assistant's instructions already present them as data, not instructions (F5). | F5 decision 18; default. |
| 18 | `GET /api/memory/recall?q=&about=<type>:<id>&limit=&kinds=record,message` returns the same re-checked results, for people and the assistant. `about` keeps only memory of that record (and checks first that the caller may read it: 404 otherwise). The route segment `memory` is reserved. The tool `recall-memory` calls it. | Default; rule 2 (the assistant reaches data only through the API). |
| 19 | Erasure: a contributor removes the person's conversation index rows (and, for a person with an account, the business memories they own and their index rows). Rows of messages that are deleted go with them (`message_id` references `thread_messages` with `ON DELETE CASCADE`), so an erased WhatsApp thread leaves no vectors. Export: the business memories a person wrote. Vectors are derived data and are not exported. | F5 decision 25 (contributors); gap map ("DPDP erasure and retention must cover … vectors"). |
| 20 | The fake embedding (`fake/embedding`, A10) makes recall testable offline: texts that share words are close. | A10 decision 18. |
| 21 | Mastra's `Memory` and `SemanticRecall` (`@mastra/memory`, added by F6) are not used: they return stored message text without the API's access checks, keep a second copy of the thread, and need pgvector for semantic recall. The package stays installed but unused. | Gap map extension points (the framework-owned option "respects agents-not-to-db, and policy applies"); rule 2. |
| 22 | The `memory.list` view (inline, canvas, WhatsApp text, speech) shows business memories; the app binds it with the framework's other views. `list-memories` presents with it. | Coverage checklist ("Memory (person, project, studio)": the Assistant screen, phone n/a). |
| 23 | The scripted model gets a `memory` script set (order 300): "remember (that) …" calls `create-memory`; "what do you remember about …" and "recall …" call `recall-memory` and say the best match. | Developer guide 7.3 ("A new framework tool gets its script there"). |
| 24 | A recalled memory is folded onto one context line (whitespace collapsed), so a memory's own line breaks can never start a line of the assistant's prompt. | Found in review: the scripted model reads instruction lines with `^…$` patterns, and so may a real model. |
| 25 | Failures stay with their memory: a trait that throws (it reads a field hidden from the reader) or a check that fails drops that one memory from recall; at indexing, the row is marked `failed` under a savepoint and the rest of the batch goes on. | Fail closed, without blocking the index. |

## Assumptions to review

- **Who reads business memory.** Every member with `memory.read` (owner, admin, ops and staff by
  default) reads all of the business's memory; customers never. Should some memory be visible to
  managers only (a per-memory audience), or should staff not see it at all?
- **Who writes it.** Anyone with `memory.write` adds memory and edits or deletes their own;
  `memory.manage` (owner, admin) edits anyone's. Should business memory instead need an owner's
  approval before it is recalled for everyone?
- **The assistant writes memory without approval.** "Remember that we close on Sundays" is saved at
  once (changes and deletes wait for approval). Should the assistant's memory writes wait for
  approval, given that recalled memory reaches every member's turns?
- **No automatic memory.** Memory is written by people or by the assistant when asked. Nothing is
  extracted from conversations automatically. Is automatic extraction (with review) wanted?
- **Record memory is the application's entity.** A product that wants project memory declares an
  entity (or reuses one) with the `memory` trait and `about: project`. Is that the intended shape,
  or should the framework ship a generic "memory about any record" entity once entities can share
  their scope (an `EntityDef` change)?
- **Only the person's own words are recalled from conversations**, never the assistant's replies.
  Is recalling replies (with the risk that they quote what the person may no longer see) wanted?
- **Recall is on by default** for every business whose policy allows an embedding model. A
  business turns it off in its `memory` settings or by leaving the embedding model out of its
  policy. Should it be off until a business turns it on (it costs an embedding per turn)?
- **Defaults**: five memories per turn, similarity at least 0.3, 400 characters each. Are these
  right for the production embedding model?
- **Drafts get no recall.** Back-office reply drafts are written without memory, so internal facts
  never reach a customer. Should drafts recall the customer's own conversation, at least?
- **Erasure deletes the memories a person wrote** (when the person has an account). Should they be
  kept for the business and only their author removed?
- **Index lag.** A new record is recallable about a second after it is written (the index job runs
  every second in the worker). Is that acceptable?

## API sketch

```ts
// @hykr/contracts
declare module '@hykr/contracts' {
  interface EntityTraits {
    memory?: MemoryTrait;            // traits: { memory: { text, about } }
  }
}
interface MemoryTrait<R = any> {
  text(record: R): string;                             // from the record as the reader may see it
  about?(record: R): { type: string; id: string } | null | undefined;
}
memoryTraitOf(spec): MemoryTrait | undefined
MemorySpec                    // entity 'memory', plural 'memories' (platformEntities.memories)
Memory, CreateMemoryInput, UpdateMemoryInput
MemoryRead, MemoryWrite, MemoryManage   // capabilities memory.read / memory.write / memory.manage
MemorySettings                // section 'memory': { recall, conversation, limit, minScore }
RecallQuery                   // { q, about?: 'type:id', limit?, kinds? }
RecallItem                    // { kind: 'record' | 'message', type, id, about?, text, score, at }
RecallResult                  // { items: RecallItem[]; model: string | null }

// @hykr/db
memories                      // app.memories: id, tenant, owner, text, createdBy, timestamps
memoryIndex                   // app.memory_index: tenant, kind, source_type, source_id, message_id
                              // (→ thread_messages, cascade), subject, about_type, about_id,
                              // model, embedding real[], state, queues, attempts, error, timestamps
// framework/db/sql/pre/memory.sql   CREATE EXTENSION vector when available (else a notice)
// framework/db/sql/post/memory.sql  app.memory_cosine(real[], real[])

// @hykr/api (features/memory)
GET    /api/memories, /api/memories/:id; POST /api/memories; PATCH, DELETE /api/memories/:id
GET    /api/memory/recall?q=…&about=type:id&limit=5&kinds=record,message  → RecallResult
RecallService.recall(p, { query, about?, limit?, kinds?, excludeThread? }): Promise<RecallResult>
turn hook   'memory.recall'      context lines before each chat turn; indexes the message after
write hook  'memory.index'       touched trait records → pending (deleted → removed)
queue       'memory.index'       embeds pending rows (schedule every 1 s)
queue       'memory.backfill'    { tenantId? }: pending rows for unindexed records (daily schedule)
subscriber  'memory.models'      models.policy.changed → rebuild that business's index
erasure     'memory'             conversation vectors; a person's own memories
export      'memory'             { memories: [...] }
tool        'recall-memory'      { query, about?, limit? } → GET /api/memory/recall

// @hykr/api-client
api.memory.recall({ q, about?, limit?, kinds? }): Promise<RecallResult>

// @hykr/ui-registry
MemoryListView                // 'memory.list'
```

## Test plan

- Unit (`framework/contracts`): the `memory` settings defaults and bounds; `MemorySpec` exposes
  and approvals; `memoryTraitOf`.
- Unit (`framework/api/src/features/memory/*.test.ts`): `anyRole` answers every role and works with
  `accessFor`; `parseAbout`; the context line format and its cut.
- E2E (`framework/api/test/framework/memory.e2e.test.ts`, fixture `features/memory/`: a `memos`
  module with a `memo` entity that has the trait, `about` a task, a field hidden by a read
  projector without a fixture capability, and a `private_memo` entity whose `get` is people-only;
  a tool that returns the turn's context):
  - business memory: an owner and a staff member add memory, both read all of it; staff cannot change
    another's (403 `memory_not_yours`), the owner can; a customer contact sees none; another
    business's id is a 404; the assistant adds memory when asked (`createdBy: assistant`, audited)
    and its delete parks (audited `needs_approval`);
  - indexing: a created memo is indexed with `fake/embedding`; an update re-indexes; a delete
    removes it; a command's touched record is indexed too;
  - recall in a turn: the turn's context holds the memo's text; another member who cannot read the
    memo (own access) gets nothing; another business gets nothing; the hidden field never appears
    (and a query made of its words finds nothing); the people-only entity is never recalled; a memo
    whose `about` task the reader cannot read is skipped; a source deleted behind the index is
    skipped; the business's settings turn recall off; a policy that refuses the embedding model
    leaves the turn running without recall;
  - conversation memory: what Ana said in an earlier thread is recalled in a new one; Bob in the same
    business and Ana in another business do not get it; the assistant's replies are not recalled;
  - `GET /api/memory/recall`: results, `about` filtering, an `about` record the caller cannot read
    is a 404, bad parameters are a 400, another business sees nothing; the `recall-memory` tool via
    the scripted model;
  - erasure: a contact's "delete my data" removes its conversation vectors; export lists a
    person's memories;
  - a policy change re-embeds the index with the new model (the stub gateway's embedding model).
- Application e2e (`application/api/test/domain/memory.e2e.test.ts`): notes are memory of their
  meeting; "what do you remember about …" recalls a note through `recall-memory`; a staff member
  without access to the note does not recall it; `about=meeting:<id>` keeps that meeting's notes.
- Updated: tests that list the platform's entities, tool ids or capabilities.

## Deferred

- A per-memory audience (managers only), memory expiry and retention periods (B18 settings).
- Automatic memory extraction from conversations, and summaries of old threads.
- An approximate index (HNSW) for large businesses: recall scans one business's vectors exactly.
- Recalling the assistant's replies; recall for back-office drafts.
- Using the record the person is looking at to prefer its memory in a turn (`TurnInfo` does not
  carry the chat context; the tool and API take `about`).
- Metering embedding calls for credits (A3): the usage is available from the embedding calls.
- A screen to edit business memory and the `memory` settings in the app or back office (the API and
  the `memory.list` view are there).
- pgvector in the compose and CI images: the pgvector path is written but runs only on a server
  that offers the extension.
