# F1: application modules (server side), and the sample split into modules

## Summary

An application is now a list of modules. Each module is a folder,
`application/domain/src/modules/<name>/`, with the same layers as before (`contracts`, `db`,
`server`, `views`, `notifications`, `agent`) plus an `index.ts` that bundles them with
`defineModule`. `defineServer({ name, persona, help, channel, modules })` merges them into one
server. Every merge point that used to let the last entry win silently now runs one validation
pass at boot and throws, listing every collision it finds. Each spec is stamped with its module
id. The sample is split into the `todos`, `notes` and `meetings` modules, with one shared
migration journal. The CLI gains `basecamp module add`, `basecamp eval --module` and
`basecamp db rebase`. dependency-cruiser enforces the module boundaries.

## Assumptions to review

- **Composition time.** Modules are composed when the server is defined, not switched per studio
  at runtime. A11's flags can gate a module by its stamped id. Is that enough, or must a module's
  routes disappear entirely for a studio that does not have it?
- **One assistant.** One persona for the whole product, with every module's tools on every turn.
  Should the assistant see only the tools of the module the person is in (and A1's MCP scopes)?
- **Per-module eval gates.** Each module's eval runs on its own. Should CI run
  `basecamp eval --module <m>` per module as a blocking gate, or is the whole-app eval enough?
- **Name collisions instead of prefixes.** Entity names, tool ids and routes have no module prefix,
  and a collision fails at boot. Is that acceptable for Interioring (two modules both wanting a
  `line`), or should specs carry a prefix such as `quote.line`?
- **Table naming.** A module's tables must be named after it (`orders`, `orders_lines`). Should
  shared lookup tables (a catalog of brands) be allowed outside that rule?
- **Downward foreign keys.** `tableRef` lets a lower module's table reference a higher one by name
  (`notes.meeting_id → meetings`). Should such links instead move to the higher module (a link
  table), so a lower module never knows a higher one exists?
- **Module name rules differ between halves.** F1 allows `^[a-z][a-z0-9_]*$` (the name prefixes
  SQL tables and becomes a JS identifier); F2's app side allows `^[a-z][a-z0-9-]*$`. A name of
  lower case letters and digits fits both. Which one should win when F2 merges?
- **`db rebase` base.** It defaults to `main`. Should it read the base from the branch's upstream?
- **Module without evals.** `basecamp eval --module notes` fails when notes has no cases. Should a
  module with no cases pass instead?
- **Eval cost.** Each scripted eval turn takes about 6 s (in Mastra's `runEvals`, not the fake
  model), so the sample's full evals take minutes. Only the meetings module's assistant evals run
  in the e2e tests. Should CI run `pnpm eval` per module as its own job?

## API sketch

```ts
// @hykr/contracts
moduleSpec<const E, const C>(spec: ModuleSpec<E, C>): ModuleSpec<E, C>
  // checks the name and plural keys; stamps spec.module on every entity and command spec
interface EntitySpec { readonly module?: string }   // by module augmentation (module.ts)
interface CommandSpec { readonly module?: string }
const PLATFORM_MODULE = 'platform';  MODULE_NAME = /^[a-z][a-z0-9_]*$/
stampModule(spec, module)                      // once; a second module throws
assertNoProblems(problems)                     // throws ModulesError when non-empty
type CatalogPart = { name: string; dependsOn?: readonly string[]; entities; commands }
createCatalog<const P extends readonly CatalogPart[]>(...parts: P): Catalog<EntitiesOf<P>>
interface Catalog<E> {
  entities: E & typeof platformEntities; commands: readonly CommandSpec[];
  entityNames; entityByName(name); commandByName(name);
  modules: readonly CatalogModule[];  // { name, dependsOn, entities: names, commands: names }
  moduleOf(nameOrPluralOrCommand: string): string | undefined;   // 'platform' for the framework's
  toolModule(toolId: string): string | undefined;
  toolIds: readonly string[];
}
reserveRoutes(...segments: string[]): void     // first segments under /api/ the framework serves
reservedRoutes(): ReadonlySet<string>
CANVAS_TOOLS: readonly ['canvas-open', 'canvas-compose', 'canvas-patch']
entityToolIds(spec): string[]; commandToolId(spec): string | undefined
ModulesError extends Error { problems: string[] }   // "Modules do not fit together: …"

// @hykr/ui-registry
type UiPart = { name?: string; views?: readonly ViewDef[]; screens?: readonly ScreenDef[] }
createUiRegistry(...parts: (UiPart | undefined)[]): Registry     // duplicate view/screen throws
registry.moduleOf(viewOrScreenName): string | undefined           // 'platform' for the framework's

// @hykr/notifications
createNotificationCatalog(...parts: (NotificationsDomain | undefined)[]): NotificationCatalog
  // duplicate template or notification key throws; a notification's template must be in it

// @hykr/db
tableRef(name: string, schema = app)           // a table with only `id`, for .references(() => tableRef('x').id)

// @hykr/cli (internal): module-add.ts moduleAdd({ root, db, app?, name, entity? }), MARKER,
// insertSorted, insertEntry; db-rebase.ts dropBranchMigrations(pkg, base, name?)

// @hykr/agents
interface AgentModule { rules?; help?; scripts?; evalCases?; voiceEvalCases?; evalSetup? }
interface EvalSuite { module: string; evalCases: EvalCase[]; voiceEvalCases: VoiceEvalCase[]; evalSetup? }
interface AgentDomain { persona; rules; help; scripts; suites: readonly EvalSuite[] }
mergeAgentModules(app: { persona; help? }, modules: readonly { name; agent? }[]): AgentDomain
scriptConflicts(modules: readonly { name; agent? }[]): string[]
suitesFor(domain, module?: string): EvalSuite[]                  // unknown module throws
// @hykr/agents/evals
evalAssistant(agents, { module? }); evalVoice(agents, { module? }); evalWhatsapp(agents, { module? })
prepare(what, setup?): Promise<userId>

// @hykr/api
defineModule<const E, const C>(def: ModuleDef<E, C>): ModuleDef<E, C>
interface ModuleDef extends ModuleSpec { server?; views?; screens?; notifications?; templates?;
  agent?: AgentModule; tables?: Readonly<Record<string, unknown>>; contributes? }
interface ServerDefinition { name; persona; help?; channel?: { does: Labels }; modules: readonly ModuleDef[];
  migrations?: MigrationSet[]; contributes?; tablePrefix? }
defineServer(definition): Basecamp            // throws ModulesError listing every collision
Basecamp.agentDomain: AgentDomain               // merged persona, rules, scripts, suites
runEval(app, suite, { module? })
```

How a later unit uses it:

```ts
// a framework feature with its own routes (framework/api/src/features/files/index.ts)
reserveRoutes('files');
// a module id, from a spec or a tool (A1 scopes, A4 grants, A11 flags)
spec.module;  runtime().catalog.moduleOf('todo');  runtime().catalog.toolModule('create-todo');
// a fixture feature as one more module
defineServer({ ...fixture.definition, modules: [...fixture.definition.modules, filesModule] });
```

Application layout:

```
application/domain/src/
  contracts/index.ts       aggregate for the apps: export * per module; moduleSpecs
  views/index.ts           aggregate for the apps: export * per module; moduleViews
  db/index.ts              migrations (the one journal)
  server/access.ts         BUSINESS_ACCESS, shared by the modules
  modules/index.ts         modules = [todos, notes, meetings] (server only)
  modules/<m>/contracts/   isomorphic: specs and <m>Spec = moduleSpec({...})
  modules/<m>/db/schema.ts tables
  modules/<m>/server/      Nest module, defineEntity/defineCommand; public.ts for other modules
  modules/<m>/views/       isomorphic: <m>Views = { name, views, screens }
  modules/<m>/notifications/ isomorphic: <m>Notifications = { templates, notifications }
  modules/<m>/agent/       <m>Agent: AgentModule
  modules/<m>/index.ts     <m> = defineModule({ ...<m>Spec, server, views, …, tables })
```

## Test plan

- `framework/api/test/framework/modules.test.ts` (no boot): every collision class throws with a
  readable line: entity name, plural, a framework prefix (`approvals`), the platform's `pages`, a
  route reserved with `reserveRoutes`, command name, approval op (`task.create` as a command),
  tool id, overlapping method + path, `touches` naming no entity, unknown or later `dependsOn`,
  duplicate module, bad module name, duplicate view and screen, duplicate notification key, a
  template that is not in the catalog, a spec view that does not exist, a view action naming no
  command, table names (prefix, duplicate, framework table), a script that steals another module's
  eval turn. Several problems are reported together. `moduleSpec` stamps specs and refuses a spec
  in two modules. `mergeAgentModules` concatenates in order and defaults `help`.
- `framework/api/test/framework/modules.e2e.test.ts` (boots the fixture as two modules): both
  modules' routes serve; specs carry their module id and `catalog.moduleOf` / `toolModule`
  answer; another tenant gets 404 on a module's record; an agent's delete parks and is audited;
  `runEval(fixture, 'assistant', { module: 'tasks' })` runs only that module's cases and passes;
  an unknown module fails.
- Existing suites stay green: the framework e2e tests on the fixture, the application e2e and
  golden WhatsApp tests on the split sample, `@application/domain` view and notification tests,
  ui-registry and notifications unit tests.
- `drizzle-kit generate` on the split schema reports no changes (same tables, same foreign keys).
- `basecamp module add widgets` in the worktree: the result builds, typechecks, lints and passes
  `lint:deps`; then it is removed. A CLI unit test checks the files and registration lines on a
  minimal layout.
- `pnpm lint:deps` fails on a module importing another's `server/`, a module not in its
  `dependsOn`, the aggregates from a module, a module's server from its views, and an app
  importing `@application/domain/modules` or a module's notifications (checked by hand with
  deliberate violations, not committed).
- `framework/cli/src/{module-add,db-rebase}.test.ts`: the scaffold's files and registration lines
  on a minimal layout, its refusals, and `db rebase` in a temporary git repository.
- `basecamp db rebase --base feat/platform-gaps` on the scaffolded module's WIP migration: dropped
  and generated again under the same name.

## Deferred

- The app half: `defineAppModule`, `<AppShell modules>`, the app barrel and the mobile split (F2).
  `basecamp module add` writes the app files and registers them once F2's barrel exists.
- Tool ids contributed through `toolContributions` (F5) are not part of the tool-id check: they
  are known only when the tools are built. F5 can call `catalog.toolIds` to check its own.
- `registerOp` throwing on a duplicate is F3's (`approvals.ts`). The catalog check already refuses
  a command named like an entity op.
- Event names of `NamedEvent`s are free strings: only `<entity>.created|updated|deleted` in a
  notification schedule are checked against the catalog.
- A per-module tool filter for the assistant, and per-module MCP scopes (A1).
- Per-module pg schemas: all module tables stay in `app`.
- The dependency-cruiser rule per module reads `dependsOn` from `contracts/index.ts` with a regular
  expression: a `dependsOn` built from variables is not seen (the boot check still is).
- The golden WhatsApp conversations do not run in worktrees (whaloc-test is the main checkout's);
  they exercise the split sample only at integration.
