# B3 + B5: money, numbering, line items, and the sample `orders` module

## Summary

B3 gives the framework money as integer minor units with an ISO 4217 currency, exact rounding
helpers, a tenant `money` settings section (currency, fiscal-year start, named thresholds and
bands), a locale-aware `moneyText` in `@hykr/i18n`, a tax-line primitive whose computation is a
function the application supplies, and gapless number series per business. The application
declares each series' format template and its reset period (none, yearly, or fiscal year from
the business's `fyStartMonth`).

B5 gives entities children: a `parent` trait and plugin (a child is reachable only through a
parent the principal reaches, in the same business), `defineChildEntity` with bulk `insert` and
a diffing `replace` for trees of any depth (parent → group → line), a multi-row audit insert in
`runWrite`, a JSON body limit large enough for a 200-line unit, and an approval preview that
summarises money and long arrays.

The sample's new `orders` module proves both: an order with nested items, money in minor units
(INR in the sample's settings), its own series `ORD/{fy}/{seq:4}`, its own percentage tax-line
function, and a 200-line order saved, parked and approved as one operation.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | Money in contracts is `Money = { minor, currency }`: a safe integer of the currency's minor units and an ISO 4217 code (already present). `MinorUnits` bounds it to ±`Number.MAX_SAFE_INTEGER`. | Plan B3, task note ("use the contracts Money type everywhere money moves"). |
| 2 | Storage: one `bigint(mode: 'number')` column per money field, under **the same key as the read field** (`total` holds minor units), plus one `currency` column per record. `@hykr/db` exports `minorUnits(name)` and `currencyColumn()`. A record has one currency. | Gap map B3 ("Integer or bigint({mode:'number'}) paise, never numeric"). Default: same key, so the list grammar sorts and filters the column with no mapping, and pg never returns a string. |
| 3 | The `money` entity trait (`traits: { money: { fields, currency? } }`) and its plugin: stored minor units become `Money` on read (`toJson`); `MoneyInput` on write becomes minor units plus the currency column (`toValues`). Its rules refuse amounts in different currencies (`currency_mismatch`), a change of a record's currency (`currency_fixed`), a create with no currency anywhere (`currency_required`), and an amount the currency cannot hold (`money_invalid`, e.g. three decimals in a two-decimal currency). | Plan F3 hooks; fail closed. |
| 4 | A record's currency on create comes from its input. The business default is resolved on the server: `money.currency` in tenant settings, else the deployment's `DEFAULT_CURRENCY`, else `XXX` (ISO 4217 "no currency"). `tenantMoney(conn, tenantId)` (core) and `GET /api/money` return the resolved settings. | Task note ("default from a deployment env such as DEFAULT_CURRENCY and a neutral fallback"). `XXX` is the standard's own neutral code. |
| 5 | `DEFAULT_CURRENCY` is read by `@hykr/api`'s config, checked at boot (an invalid code refuses to start), and handed to core through `CoreOptions.defaultCurrency`. Contracts never read the environment. | Default: contracts are isomorphic (the Expo apps load them). |
| 6 | The `money` settings section: `currency?`, `fyStartMonth` (1–12, default 1: the calendar year), `amounts: Record<string, Money>` (named thresholds) and `bands: Record<string, Money[]>` (ascending upper bounds). Keys are the application's (`orders.approval`); the framework gives `moneyAmount(money, key)` (the section, or `tenantMoney`'s result), `exceeds(amount, limit)` (fails closed: no limit, or another currency, counts as exceeded) and `moneyBand(amount, bounds)`, and no values. Approval levels and approvers per band are A5's `approvals` section; these are amounts an application reads for its own rules. The helper names avoid A5's (`approvalThreshold`, `overThreshold`, `bandApprover`). | Task note ("amount bands/thresholds as tenant settings the app reads"); Money everywhere money moves. Boundary: thresholds are business values. |
| 7 | The sample sets INR as its deployment default in `application/.env.example` (`DEFAULT_CURRENCY=INR`). The sample's tests set the tenant's `money` settings themselves (INR, `fyStartMonth: 4`), as a business would, so they do not depend on the environment. | Task ("INR in the sample settings"). Default for tests: no hidden env dependency. |
| 8 | Rounding helpers are exact integer arithmetic (BigInt inside): `mulDiv(minor, num, den, rounding)`, `scaleMoney`, `allocateMinor` (largest remainder: the parts add up to the whole), `sumMoney`, `addMoney`, `subtractMoney`. Modes: `half-up` (default, away from zero), `half-even`, `down` (toward zero), `up`, `floor`, `ceil`. Mixed currencies throw `CurrencyMismatch`; results past the safe-integer range throw. | Plan B3 ("rounding helpers"). Default: no floats on money. |
| 9 | Decimals become minor units only with the currency's exponent (Intl: EUR 2, JPY 0, BHD 3): `toMinor('1234.5', 'EUR')` is 123450; more decimals than the currency has are refused. `MoneyInput` accepts `{ minor, currency? }` or a decimal string, resolved against the record's currency with `resolveMoneyInput`. | Gap map risk ("Agent-produced amounts must be validated as integers; LLMs emit decimals"). |
| 10 | `moneyText(m, lang)`, `spokenMoney(m, lang)` and `currencyExponent(code)` live in `@hykr/i18n` (`money.ts`) and use `Intl.NumberFormat` with the language's locale and the currency's own exponent (contracts already depend on i18n). | Plan B3 ("locale-aware moneyText in i18n via Intl"). |
| 11 | Tax: `TaxLine = { code, label?, basis: Money, rateBp?, amount: Money, included? }` (`rateBp`: the rate in basis points, for display). `defineTaxFunction({ name, compute(lines, ctx) })` is the application's computation; `applyTax(fn, lines, { currency })` checks its output (integers, one currency, unique codes) and returns `{ subtotal, taxLines, taxTotal, total }`. `included` tax lines (prices that already contain them) do not add to the total. No rates, names or rules in the framework. | Plan B3 ("a tax-line primitive whose computation is an app-supplied function"). Boundary section. |
| 12 | Number series: `defineNumberSeries({ name, format, reset })` (contracts, isomorphic) checks the template: `{seq}` or `{seq:N}` exactly once; `{yyyy}`, `{yy}`, `{mm}`; `{fy}` ("2026" when the year starts in January, "2026-27" otherwise), `{fyStart}`, `{fyEnd}` and their `:yy` forms. A yearly reset needs a calendar-year token and a fiscal reset a fiscal-year token, so a reset never repeats a number. Unknown tokens throw. | Plan B3 ("format template and reset period declared by the app"). Fail closed. |
| 13 | Series are registered (`contributes: { numberSeries }`, a core registry): `nextNumber` refuses a series that is not registered, so two modules cannot share a name with different formats. | Default, fail closed; plan F1's boot validation spirit. |
| 14 | Allocation: `app.number_series (tenant_id, series, period, last)`, one upsert `INSERT … ON CONFLICT DO UPDATE SET last = last + 1 RETURNING last` in the write's transaction. The upsert takes the row lock (as `SELECT … FOR UPDATE` would) until commit, so concurrent writes wait and a rolled-back write gives its number back: no gaps, no repeats. | Plan B3 ("FOR UPDATE"). Gap map risks (lock held for the whole command; acceptable at this scale). |
| 15 | Allocate only in a command's `run`. A parked write stores its input and allocates on the approved replay, so a rejected or expired request uses no number. | Gap map B3 ("a number allocated in run is taken only on the approval replay"). |
| 16 | Periods use the business's time zone (`timeZone`) and `money.fyStartMonth`, read in the same transaction. Period keys: `-` (none), `Y2026` (yearly), `FY2026` (fiscal, by start year). Changing `fyStartMonth` mid-year keeps the current key's counter. | Gap map risk ("financial-year boundary must use the tenant's time zone"). |
| 17 | The `parent` trait: `{ entity, field, nest?, position?, maxDepth?, maxNodes? }` (field names only, isomorphic). `nest` names the child's own field pointing at its parent node, so one table holds a tree of any depth; a child entity whose parent is itself a child chains the same way. `buildTree(rows, { key, parent, order? })` (contracts) builds a tree from rows (by id) or from flat input (by a client's `ref`). | Gap "parent → group → line style trees of any depth". |
| 18 | `define-entity.ts` is not edited (B5 is not listed for it in the hot-file table), so a child's reach is inherited by **mirroring**: `defineChildEntity` writes each child with its parent's owner and customer, and the child is given the parent's `access`. The child's own grants then resolve exactly as the parent's. | Plan hot-file table; F3 owns `define-entity.ts`. |
| 19 | The `parent` plugin narrows every child query (read and write) to rows whose parent exists **in the same business with the same owner and customer**, and passes the parent's own plugins' scopes (a chain of parents is checked to the root). A child whose mirror has drifted is unreachable, never visible. | Plan B5 ("scope inherited from the parent, tenant check on foreign keys"). Fail closed. |
| 20 | The plugin's rules: a child is never created by `repo.insert` (`children_through_parent`; the owner would be the author, not the parent's); its parent field never changes (`parent_fixed`); its `nest` and `position` change only inside a command, never by plain CRUD (`tree_through_parent`). | Fail closed. |
| 21 | `insert(tx, p, parent, nodes, via)` and `replace(tx, p, parent, nodes, via)` take a parent row and nested nodes (`{ id?, …fields, children? }`). The parent is loaded again through its repository (404 if not theirs) and must be writable by the principal under the child's access (404 if not). New nodes get server-made ids so a whole tree goes into one multi-row `INSERT` (chunks of 500). `replace` diffs by id: unchanged rows are skipped, changed rows go through `repo.update` (scope, rules, plugins, 409 on stale), and removed subtrees through `repo.delete` (the top of each removed subtree; the table's own cascade takes the rest, each one still audited). | Plan B5 (`insertMany`/`replaceChildren`, "a 200-line unit saved at once"). Gap map risk (200 round trips). |
| 22 | A node id that is not a child of that parent is a 404 (`No such …`), whatever business it belongs to: an id's existence elsewhere is never revealed. Nesting deeper than `maxDepth` (default 8) or more than `maxNodes` (default 1000) nodes is a 400. | Gap map risk ("FK success or failure reveals whether a foreign id exists"). |
| 23 | DB-level tenant check (sample and fixture): a composite foreign key `(tenant_id, parent_id) → parent (tenant_id, id)` and, for nesting, `(parent_fk, nest) → child (parent_fk, id)`, so a row can point only at its own business's parent and at a node of the same tree. | Gap map B5 risk. Additive. |
| 24 | `insertMany(tx, p, def, inputs, via)` for any entity is one `repo.insert` per row (the framework's ownership and rules unchanged) with one touched list. Only children are inserted in bulk (their ownership is the parent's, known without `define-entity.ts`). | Hot-file rule (decision 18). B20 can use either. |
| 25 | Multi-row audit: `writeAuditMany(tx, rows)` in `@hykr/db` (one `INSERT` per 1000 rows). `runWrite` writes a run's touched rows and the command's own row with it, in one statement for up to 1000 rows. | Plan B5 ("multi-row audit (pipeline.ts audit loop hunk)"). |
| 26 | JSON body limit: `JSON_BODY_LIMIT` (default `1mb`, Express's default is 100 KB) on the Better Auth Nest module's JSON parser. A 200-line order is about 60 KB; 1 MB leaves room for 1000 nodes. | Task note ("body size limit"). Gap map risk. |
| 27 | Children inherit the parent's currency: `defineChildEntity` gives a child with the `money` trait its parent's currency, and money in another currency is refused (`currency_mismatch`). | Default: one record, one currency (decision 2). |
| 28 | `ApprovalPreview` shows `Money` values with `moneyText`, and an array of more than five objects as a count (with the nested total), its first three titles, and the sum of each money field when they share a currency, instead of one bullet per item. | Plan hot-file table (`ApprovalPreview.tsx`: B3+B5). Gap map B5 ("counts and totals instead of 200 bullets"). |
| 29 | The sample `orders` module: `order` (number, title, status open/cancelled, currency, subtotal, taxTotal, total, taxLines) and `orderItem` (a child of `order`, nested: group or line, quantity, unitPrice, taxRateBp, amount, cost). Plain CRUD writes are `internal`: orders change only through commands. `order.save` creates or replaces an order with its whole tree (a flat list with `ref`/`parent`, so the tool's schema is not recursive); it allocates `ORD/{fy}/{seq:4}` (fiscal reset) on create, computes line amounts, group subtotals and tax lines with the module's own percentage function, and parks: an assistant's save at level 2 for the person, a total above the business's `money.amounts['orders.approval']` at level 3 for the owner in the app. `order.cancel` cancels; orders are never deleted, so numbers stay gapless. | Task ("Sample demo"); plan "Sample proof". |
| 30 | The sample's level meanings and threshold default live in the orders module (`server/policy.ts`), not the framework. Its default threshold, used when the business has set none, is 5,00,000.00 INR. A threshold in another currency than the order's counts as exceeded. Level 3 applies to the assistant and to people without the module's capability `orders.approve` (owner and admin by default), so an owner saving a large order directly is not asked to approve their own request. | Boundary section; fail closed. A5 owns self-approval rules. |
| 31 | The orders module declares the capability `orders.cost.read` (owner and admin) and a read projector that hides each item's `cost` from anyone without it: in item reads, the `order.save` result and its approval card. A4's field policy can replace the projector later. | Plan "Sample proof"; test rule "hidden fields stay hidden". |
| 32 | The fixture's `line-items` feature (baskets and their items, its own migration set) tests every framework part with neutral data (`XXX`, `EUR`, `JPY`, `BHD`); framework tests never use the sample. | CLAUDE.md, plan "Verification". |
| 33 | The `money` and `parent` plugins, the `money` list field type's SQL and `GET /api/money` are one framework feature, `features/money` (one line in `features/index.ts`). | Plan conventions ("a feature is a Nest module at `framework/api/src/features/<x>/`"). |

## Assumptions to review

- **One currency per record.** An order and all its lines share one currency, and money in
  another currency is refused. Is a multi-currency document (lines priced in another currency
  and converted) ever needed?
- **Neutral fallback `XXX`.** With no tenant currency and no `DEFAULT_CURRENCY`, money shows as
  `¤1,234.50`. Should a deployment instead refuse to start without `DEFAULT_CURRENCY`?
- **Fiscal label.** `{fy}` reads "2026-27" for a year starting in April 2026 and "2026" for a
  calendar year. Is another label form wanted (`FY27`, `2026/27`)? Templates can already compose
  `{fyStart}`, `{fyEnd}` and their `:yy` forms.
- **Rounding.** The sample rounds tax per rate group, half up. Should it be per line, and is a
  round-off line to the nearest whole unit wanted?
- **Tax-inclusive prices.** The primitive supports `included` tax lines; the sample prices are
  exclusive. Which does the product use?
- **Changing `fyStartMonth` mid-year.** The running fiscal year keeps its counter under its start
  year's key. Should a change start a new series?
- **Number lock.** The series row is locked until the write commits, so two saves of the same
  series in one business wait for each other. Fine at small-business scale; is a pool of
  pre-allocated numbers ever needed?
- **Children are written through their parent only.** Plain CRUD cannot create a child, and
  moving a node between groups is a parent-level save. Should single-line edits after approval
  be possible (that is B4's revision question)?
- **Who owns a line.** A line belongs to its order's owner and customer, not to whoever added it,
  so everyone who reaches the order reaches all its lines. Confirm.
- **Depth and size.** Trees are limited to 8 levels and 1000 nodes per save, and the JSON body to
  1 MB. Are larger units expected?
- **Deleting a parent.** The database cascades its children, and only the parent's delete is
  audited. The sample never deletes orders (it cancels them). Should the framework refuse a
  parent's delete while it has children?
- **Who sees amounts.** `GET /api/money` returns the currency, its exponent and the fiscal start
  to every member, never the named amounts and bands, which only server rules read.
- **Order approval.** In the sample, an assistant's save waits for the person (level 2) and a
  total above the threshold waits for an owner in the app (level 3). A5 owns the levelled
  policy; when it lands, the sample's mapping should move to its level rules, and
  `money.amounts['orders.approval']` to its `approvals.thresholds` if they mean the same.

## Test plan

- Unit (`framework/core/src/money/*.test.ts`, `framework/i18n/src/money.test.ts`): rounding modes on halves and
  negatives, `mulDiv` exactness past 2^53 intermediates, `allocateMinor` sums, `toMinor` per
  exponent and refusals, `applyTax` validation and included lines, number templates (tokens,
  refusals, padding), periods across the fiscal boundary in the tenant's zone, `buildTree`,
  `moneyText` per language and exponent, `writeAuditMany` chunking.
- Fixture e2e (`framework/api/test/framework/money.e2e.test.ts`): `GET /api/money` resolves
  tenant → deployment → `XXX`; money in and out as `Money`, stored as minor units; currency
  mismatch and change refused; list filter and sort on a money field; concurrent saves get
  numbers 1..N with no gap or repeat; a failed save gives its number back; a parked save takes no
  number until approved, and a rejected one never; fiscal reset at `fyStartMonth` in the tenant's
  zone; an unregistered series is refused; another business gets 404.
- Fixture e2e (`framework/api/test/framework/line-items.e2e.test.ts`): a 200-line tree saved in
  one request, as one INSERT and one audit statement, read back in tree order; another business
  gets 404 for the parent, its children, and a node id smuggled into a replace; a child is not
  creatable by plain CRUD; a staff member reaches the lines of a parent they reach and not
  others; a hidden field (`cost`, by a read projector) stays hidden in list, get, command result
  and approval; an assistant's 200-line save parks as one approval, is audited as parked, and the
  approval replays it in one transaction with one audit row per line plus the command's.
- Sample e2e (`application/api/test/domain/orders.e2e.test.ts`): an INR order with groups and
  lines, `ORD/2026-27/0001` style numbers, tax lines from the module's function, threshold park,
  200 lines parked and approved, cancel instead of delete, another business 404, cost hidden
  without `orders.cost.read`.
- `children.insert` appends under a node (positions continue; a stored id is 400, a node of another
  parent 404) and `insertMany` writes through each record's repository (line-items e2e).
- Scripted model: the orders module's `order …` script calls `save-order`; its eval cases run in
  `basecamp eval --module orders` and in `application/api/test/domain/modules.e2e.test.ts`.

## Deferred

- Editing tenant settings (`money` included) through the API: tenant settings editing is A11's
  (`features/settings`). Tests and operators set them in the database.
- Bulk insert for plain (non-child) entities and a bulk update path: they need the ownership and
  scope that `define-entity.ts` keeps private (hot file: B19, B12).
- Line-level agent tools (`add-order-lines` and the like): `tool-factory.ts` is A7's. The sample's
  `save-order` takes the whole tree.
- Refreshing children in the app after a command (`touched.ts`, `hooks.ts`): a command's
  `touches` already lists both entities, which is enough for the sample.
- Exchange rates, multi-currency documents, e-invoicing.
