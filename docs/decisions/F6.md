# F6: infrastructure for parallel work (PAR), barrels and the dependency preflight

## Summary

F6 makes the repository safe for many agents working at once, and adds every dependency the
gaps are expected to need, in one go:

- Tests read the worktree's `.env` themselves, including in Vitest's `globalSetup`, so the
  migrations and the tests always hit the same database. Turbo runs tests uncached and passes
  them the whole environment.
- `runMigrations` runs idempotent `sql/pre` and `sql/post` hook files around each migration
  set. It takes an advisory lock, and it fails when drizzle would silently skip a migration.
- The fixture can have one migration set per feature (`test/fixture/src/features/<x>/migrations`),
  found by name, so parallel features never share a drizzle journal.
- The framework's phrases (`@hykr/i18n`) and the scripted model's platform scripts
  (`@hykr/agents`) are split into one file per feature, behind barrels with one line per
  feature. A new feature adds a file and a line and edits nothing shared.
- Postgres in Compose allows 400 connections.
- The dependency preflight adds the expected new packages, at versions that match the
  lockfile, and commits the lockfile.

## Assumptions to review

- **Tests see the whole environment.** Turbo now passes every variable to test tasks. Is
  that acceptable, or should tests run with an allowlist even though they are not cached?
- **Hooks run on every migrate.** `sql/pre` and `sql/post` files are not recorded; they run
  each time and must be idempotent. Should they instead run once, recorded by checksum, like
  migrations?
- **Production privileges.** A hook that creates an extension (B13's PostGIS) needs a role
  that may create it. Is the production migration role allowed to, or must extensions be
  created by an operator beforehand?
- **The skip guard.** `db:migrate` now stops when an unapplied migration is older than an
  applied one. A developer database that applied a migration which was later regenerated
  with an older timestamp must be recreated. Is failing preferable to drizzle's silent skip
  for every environment, production included?
- **Fonts in the server package.** The Noto fonts (about 19 MB unpacked, all weights) are
  dependencies of `@hykr/api`, so every application installs them. Should they move to an
  optional package, or should only Regular and Bold be vendored?
- **CI connections.** CI keeps Postgres' default 100 connections. Enough for one suite at a
  time; is CI ever expected to run suites in parallel?
- **Expo config plugins** are left to each gap (decision 26). Should one unit add them all at
  once instead, accepting the push entitlement early?
- **Package placement.** `@mastra/memory` and `@ai-sdk/openai-compatible` went to
  `@hykr/agents`; `@mastra/mcp`, the S3 SDK, the PDF engine, `expo-server-sdk` and
  `@better-auth/oauth-provider` to `@hykr/api`. A gap that needs one elsewhere moves it.

## API sketch

```ts
// @hykr/db
type MigrationSet = {
  folder: string;   // drizzle-kit's output (meta/_journal.json)
  table: string;    // in the `drizzle` schema
  sql?: string;     // hooks: <sql>/pre/*.sql and <sql>/post/*.sql; default: join(folder, '..', 'sql')
};
runMigrations(url: string, sets?: MigrationSet[]): Promise<void>
  // framework set first; per set: pre → migrations → post; under pg_advisory_lock;
  // throws if a set has an unapplied migration older than its last applied one
migrationSetsIn(root: string, prefix: string): MigrationSet[]
  // <root>/<name>/migrations → { folder, table: `__${prefix}_${name}_migrations`, sql: <root>/<name>/sql }
sqlHookFiles(set: MigrationSet, phase: 'pre' | 'post'): string[]   // absolute paths, name order

// @hykr/api
migrate(app: Basecamp, more?: MigrationSet[]): Promise<void>   // `basecamp db migrate`, test globalSetup

// fixture (framework/api/test/fixture)
src/migrations.ts:  export const featureMigrations: MigrationSet[]   // migrationSetsIn('src/features', 'fixture')
src/features/<x>/{schema.ts, migrations/, sql/pre/*.sql, sql/post/*.sql}
FIXTURE_FEATURE=<x> pnpm --filter @hykr/api fixture:generate --name <x>

// @hykr/i18n (internal layout; public API unchanged: catalogs, MessageKey, t)
src/messages/define.ts:   defineMessages<const E>({ en: E, hi: Record<keyof E, string>, te: Record<keyof E, string> }): MessagePart<keyof E>
src/messages/<feature>.ts: export const <feature>Messages = defineMessages({ … })
src/messages/index.ts:    export { <feature>Messages } from './<feature>.js';   // one per line
src/messages.ts:          catalogs, MessageKey (union of the parts' keys), t(lang, key, vars)

// @hykr/agents (internal; platformScripts unchanged)
src/fake/script-set.ts:   defineScriptSet({ name, order, scripts }): ScriptSet
                          orderScriptSets(sets: readonly ScriptSet[]): Script[]   // by order, then name; duplicates throw
src/fake/scripts/<feature>.ts: export const <feature>Scripts = defineScriptSet({ … })
src/fake/scripts/index.ts:     export { <feature>Scripts } from './<feature>.js';   // one per line
src/fake/platform-scripts.ts:  platformScripts = orderScriptSets(Object.values(sets))
```

Notes for B2: `harfbuzzjs` is ESM with a top-level `await` (WASM), so import it lazily in the
worker. Replace each embedded font's fontkit `layout` with a HarfBuzz one (`Buffer.addText`,

script (`scriptOf` in `@hykr/i18n`) and switch fonts per run.

## Test plan

- `framework/db/src/migrate.test.ts` (unit, no database): `migrationSetsIn` finds feature
  folders in name order, skips folders without a journal, and refuses a bad name;
  `sqlHookFiles` lists `*.sql` in name order and returns nothing for a missing folder.
- `framework/api/test/framework/migrations.e2e.test.ts` (fixture, real Postgres):
  - `globalSetup` applied the fixture's `par` feature set (its tracking table and table
    exist), in the database the tests use: the `.env` reached `globalSetup`.
  - The `par` pre hook (a function) ran before its migration and the post hook (a trigger)
    after it: an insert gets its slug filled.
  - Running `runMigrations` again changes nothing (still one trigger, one recorded migration).
  - Two concurrent `runMigrations` on a new set both succeed and apply it once (the lock).
  - A migration older than the last applied one stops the run with its tag in the error.
  - A failing hook stops the run and names the file.
- `framework/i18n/src/messages.test.ts`: every part has the same keys in `en`, `hi` and `te`;
  no key is in two parts; merging two parts with one key throws; `t()` reads a key from each part.
- `framework/agents/src/fake/script-set.test.ts`: sets sort by `order` then name, keep their
  script order, and refuse a duplicate set or script name; `platformScripts` keeps the old
  order (`save-page`, `open-page`, `draft-reply`, `request-human`, `fail`).
- Unchanged and green: the i18n and core unit tests, every framework e2e test (pages, seams,
  handoff and threads use the platform scripts), `pnpm lint`, `pnpm lint:deps`, build and
  typecheck of everything the new dependencies touch, including `@application/mobile`.
