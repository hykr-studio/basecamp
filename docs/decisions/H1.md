# H1: notifications and approval delivery

## Summary

A fix group from the completeness and security review, over four gaps that earlier units left
open.

1. **Field policy in notification words (A4).** The dispatcher used to hand the stored row to a
   notification's `whatsapp.params`, `email`, `push` and `inapp` functions as it was. Now each
   recipient's words are built from the record as that recipient may read it: the dispatcher
   resolves the recipient's principal (`PrincipalResolver`) and projects the row with the
   entity's read schema, its plugins (field policy) and the read projectors, as `eventFor` does
   for stored events. Who receives it (`to`, `when`, `dedupe`, `approval`) still sees the stored
   row.
2. **Approval requests on every channel (A5, A9).** `approval.request` went out on WhatsApp only,
   and only when the request could be decided there, so a request decided in the app, or for a
   decider without WhatsApp, reached nobody. It now goes by push, then WhatsApp (with Approve
   and Reject, only where the request may be decided on WhatsApp), then email, and always lands
   in the decider's in-app inbox. Every channel opens `/approvals/:id`.
3. **Undo holds the sends (A5).** Notifications were scheduled from the in-process event bus
   right after commit, and outbox sends went out at once, so undoing a write did not withdraw
   them. Notifications are now scheduled from the stored events (`app.domain_events`, through a
   subscriber), which an undo window already holds back and an undo withdraws. Outbox sends
   written inside an undoable write wait for the same window, and the undo withdraws them too.
   This also closes the crash window between commit and scheduling.
4. **The configured contact role (A4, A5).** Who decides a parked request compared role names
   with the literal `customer`. It now compares them with the roles the framework hands to
   contacts and participants (`givenRoles`), so an application that renames the contact role
   cannot let a signed-in customer decide their own request.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | **Who a recipient is, for reading.** Per recipient, the dispatcher builds a principal: a person (`forUser` in the notification's business, channel `app`), or a contact without an account (`forContact`, acted for by `notify`). A person who is no longer in the business, or a recipient who is neither, gets nothing (fail closed, logged). | Task (A4 item); A4 decision 31 (capability recipients through the business's roles); default, fail closed. |
| 2 | **What the words see.** For an entity's record: its read schema (a partial parse when the event's row is not a whole record, as a command's event may be), then `def.project(read, p)` (entity plugins, then read projectors). Keys of the stored row that are neither the entity's columns nor read fields (an event's own data, such as the SLA on `<entity>.sla.breached`) stay; the record's other columns (owner, customer) do not; `id` and `tenantId` are always there. Any other record (an approval, a comment mention, a credits threshold) goes through the read projectors as its resource type. A row that does not parse at all is not sent (logged). The words see the record's read shape, as the API returns it (money as `{ minor, currency }`), not its columns: the sample's order breach notification now formats `total` as money. | Task ("project the row for each recipient's principal (toRead/eventFor)"); default: the words see what the recipient could read, plus the event's own data. |
| 3 | **Who receives it still sees the stored row.** `to`, `when`, `dedupe`, `approval`, `schedule.at` and the new `channelWhen` read the row as stored: routing is the server's decision, not something the recipient reads. A channel's fallback (`NotificationMeta.row`) keeps the stored row too; each try projects it again. | Default. |
| 4 | **The record's type travels with the notification.** `DispatchJob`, `NotificationMeta` and outbox payloads carry `resourceType` (the stored event's, or what `queueNotification` is told). A job without one (queued before this change) takes it from the first event the notification names (`visit.created` → `visit`). A template sent by hand (`notify.send`) carries the sender's own parameters and is not projected. | Default: an older scheduled reminder still goes out. |
| 5 | **Approval request channels.** `channels: ['push', 'whatsapp', 'email']` (the PRD's order), `also: ['inapp']`. A framework default the application changes with `overrideNotification('approval.request', { channels, also })`. | PRD Platform & AI 7.1 Channels ("push → WhatsApp → email order"); A9B15 decision 2 (the order is each notification's); plan boundary (framework defaults neutral and overridable). |
| 6 | **The in-app inbox is not a step of the chain, it is always kept.** The task's order put the inbox second, after push. Every decider is a member with an account, so the inbox would always take it there and nobody would ever get WhatsApp's buttons or an email (the golden WhatsApp conversation, where the owner gets `approval_request_v1`, would fail). A new generic field, `NotificationDef.also`, lists channels a notification goes to besides the first of `channels` that reaches the person: the approval request is always kept in the decider's inbox, and reaches them by push, WhatsApp or email. | Task (A5/A9 item) read against the PRD order and A5 decision 25; default. |
| 7 | **WhatsApp only where it can decide.** `NotificationDef.channelWhen: { [channel]: (row) => boolean }` skips a channel for a row. The approval request uses WhatsApp only when its `approverChannels` allow WhatsApp and its `minAssurance` is at most `whatsapp_number` (a tap there is only as sure as the number). Otherwise the next channel (email). No WhatsApp text without buttons: that would need a new template approved by Meta, and email already carries the link. | Task ("WhatsApp with buttons only where approverChannels allows deciding there"); A5 decision 25. |
| 8 | **Opening the request.** Push and the inbox open `/approvals/<id>`; the email says the summary and links `<APP_URL>/approvals/<id>`. `Reader` gains `appUrl` (the deployment's `APP_URL`), filled by the dispatcher, so a notification's email can link into the app. | Task ("The notification must open /approvals/:id"); A5 decision 16 (the deep link answers deciders and the requester). |
| 9 | **Still not the requester's own.** A request the person decides themselves (their own assistant's) is asked in the conversation as before, not notified. A capability's holders are asked without the requester. | A5 decisions 14 and 25. |
| 10 | **Notifications from stored events.** `NotifyService` no longer listens to the in-process event bus. The framework feature `notifications` contributes a subscriber, `notify.events`, on every stored event that some notification names (`send.on`, `schedule.on`, `schedule.cancelOn`), on its own queue `notify.events` (one job at a time per worker, 3 tries). An event held for an undo window is scheduled only when the window closes; an undone write's events are never relayed, so nothing is scheduled. | Task (A5 tier-1 undo item); developer guide 14 ("Notifications from stored events"); F5 subscribers. |
| 11 | **Order of a record's schedules.** Events reach the subscriber in the order they were stored, one at a time per worker. Across workers, an older event never replaces a newer one's schedule: the last applied event's time is kept per notification (`<prefix>:ntf-ev:<dedupe>` in Redis, two days) and an older one is skipped. | Default: a schedule must not go back in time when events are relayed late (an undo window) or in parallel. |
| 12 | **Outbox sends in an undoable write wait.** `app.outbox` gains `available_at` (default now), `cancelled_at`, `undo_id` and `xact` (the top-level transaction id, `pg_current_xact_id()`, by default). A write hook (`notify.held-sends`, after the work) moves the rows its own transaction wrote to `available_at = until` and names the undo window, when the write opened one. The relay passes on only rows that are due and not withdrawn. | Task ("give outbox sends of an undoable write the same delay"); hot-file table (`pipeline.ts` is not this unit's: a write hook instead). |
| 13 | **Undo withdraws them.** The same hook, on the framework's `write.undo`, sets `cancelled_at` on the window's held rows; a held row already relayed refuses the undo (409 `too_late`, as for events). | A5 decision 23 (fail closed). |
| 14 | **Sending from a command.** `queueNotification(tx, def, row, { type })` (`@hykr/api`) writes a notification to the outbox in the write's transaction, so a command's `run` can send one without a service. `NotifyService.notify(def, row, { type, tx })` does the same. | Developer guide 8.2 (commands inserted into the outbox by hand); default. |
| 15 | **Outside the team.** A principal is outside the team when its standing is `participant`, or every role it holds is one the framework hands to a contact or a participant (`givenRoles('contact')`, `givenRoles('participant')`: the application's `roleDefaults`, else `customer`). Its parked requests go to the holders of `approvals.decide`. A named approver who holds no role but those is replaced the same way. | Task (A4/A5 item); A4 Deferred ("customer only checks"); A5 decision 14. |
| 16 | **Errors while finding the reader.** A recipient the resolver refuses (403, 401: not in the business) reads nothing and gets nothing; any other error fails the dispatch job, which is tried again. | Default, fail closed. |
| 17 | **Withdrawn rows expire.** The retention targets `outbox.relayed` and `events.relayed` also delete rows an undo withdrew (`cancelled_at`): they are never passed on, and each holds a copy of its record. | Default (B18 retention); a withdrawn row must not outlive a relayed one. |

## Assumptions to review

- **Inbox always, not a fallback step.** The approval request always lands in the decider's
  inbox and reaches them by the first of push, WhatsApp and email that works (decision 6). Should
  a pushed request skip the inbox, or should the inbox item go when the request is decided?
- **WhatsApp without buttons.** A request decided in the app only does not go to WhatsApp at
  all; the decider gets push or email (decision 7). Should it go to WhatsApp as a plain message
  with a link, which needs a new template?
- **Push on a lock screen.** The approval request's push shows the request's summary. Is the
  summary acceptable on a lock screen, or should it say only that something waits?
- **Recipients who cannot read the record.** The words leave out what a recipient may not read,
  but the dispatcher does not check that a recipient may read the record at all: `to` decides
  who. Should a notification about a record skip a recipient who cannot open it?
- **Internal columns.** The words no longer see the record's columns that its read schema does
  not show (its owner, its customer). Should a notification be able to name an internal column
  in its words?
- **Undone writes and reminders.** A reminder is scheduled only when the write's undo window
  closes (the sample's to-dos: 10 seconds). Is a reminder due within the window acceptable to
  lose?
- **Requests the person decides.** The requester's own (their assistant's) request is not
  notified; it is asked in the conversation. A background agent's request then shows only in the
  app's approvals. Should it be pushed to the person too?
- **Outcome to a person.** The outcome is still told only to a contact who asked on WhatsApp. A
  team member whose request someone else decided learns it in the app. Should they be notified?

## API sketch

```ts
// @hykr/notifications
type Reader = { lang: Lang; timeZone: string; appUrl?: string };
interface NotificationDef<R> {
  // …as before, plus:
  /** Also these channels, whatever the chain does (the inbox keeps every request). */
  also?: readonly NotificationChannel[];
  /** A channel used only when this holds for the stored row. */
  channelWhen?: Partial<Record<NotificationChannel, (row: R) => boolean>>;
}
type NotificationPatch = Partial<Pick<NotificationDef, 'channels' | 'also' | 'whatsapp' | 'email' | 'push' | 'inapp'>>;
ApprovalRequestNotification // channels ['push', 'whatsapp', 'email'], also ['inapp'], opens /approvals/:id

// @hykr/api
queueNotification(tx, def, row, { type }): Promise<void>
NotifyService.notify(def, row, { type, tx? })
NotifyService.onStored(event: DomainEventEnvelope)        // the subscriber's work
notificationsFeature  // queue + subscriber 'notify.events', write hook 'notify.held-sends'
readAs(resourceType, row, p): Row | null                  // what a recipient's words see
DispatchJob.resourceType?, NotificationMeta.resourceType?

// @hykr/db (app.outbox, additive)
available_at timestamptz not null default now(), cancelled_at timestamptz,
undo_id text, xact bigint default (pg_current_xact_id()::text)::bigint
```

## Test plan

- Unit (`framework/notifications`): `also` and `channelWhen` checks in `defineNotification`; the
  approval request's channels, WhatsApp gate (channels, assurance), push, inbox and email content
  with the link; an override of `channels` and `also`.
- Fixture e2e, members (`members.e2e.test.ts`, fixture `features/members`):
  - a notification whose words name `cost` reaches the owner with the cost and the estimator
    (no `fixture.cost.read`) without it, in the inbox and by email; another business's member
    gets nothing;
  - with the contact role renamed (`fixture_client`), a signed-in client's assistant's request is
    decided by `approvals.decide` holders, not by the client (403 `own_request`), and is audited;
    a named approver who is only a client is replaced by the business.
- Fixture e2e, approval levels (`approval-levels.e2e.test.ts`, fixture `features/approval-levels`):
  - an app-only request (`fixture_final`): the decider gets an inbox item and an email linking
    `/approvals/<id>`, never WhatsApp (even with a linked number); with a device, push first,
    opening `/approvals/<id>`;
  - a decider without WhatsApp (a customer's request decided by `approvals.decide` holders): inbox
    and email;
  - undo: an undoable write's notification is held until its window closes, and an undone one
    never arrives; an outbox send written in an undoable write waits for the window
    (`available_at`, `undo_id`) and an undo withdraws it (`cancelled_at`, nothing dispatched).
- Fixture e2e, notifications (`notifications.e2e.test.ts`): a stored event schedules its
  notification with nothing published in-process.
- Existing suites: notifications, wa-approvals, push, comments, approval-levels, members,
  live, write-path, and the sample's API tests.

## Deferred

- A WhatsApp message without buttons for app-only requests (needs a new template).
- Removing or marking read an approval's inbox item when it is decided.
- Notifying a team member of the outcome of a request someone else decided.
- A check that a notification's recipient may read the record.
- Outbox rows written by a second write sharing the same transaction (a write that calls
  `runWrite` with its own `tx`) are held with the first undoable write in it.
