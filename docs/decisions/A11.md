# A11: feature flags, custom fields, white label, shared records, wording overrides

## Summary

A11 adds five platform basics, all as plugins, registries and one framework feature
(`framework/api/src/features/settings/`), without editing a hot file:

- **Feature flags** (fail closed). An application declares flags (`defineFeatureFlag`) and what
  each one gates: whole modules, entities, commands, tools and app destinations. A business has a
  flag on only when its settings store `true`. A gated thing that is off answers 404 on its
  routes, is refused (404, rolled back) on every other write path (commands, approval replays,
  system jobs), is taken out of the assistant's tools for the turn, and is hidden from the app's
  navigation. `GET /api/me` lists the flags that are on.
- **Custom fields** (typed, filterable). An entity opts in with the `customFields` trait and a
  `custom` jsonb column. A business defines its fields (`app.custom_fields`: key, type, label,
  options, required, filterable) through `/api/custom-fields`. Values are validated against the
  business's definitions on every write path, merged on update, and filterable in the list
  grammar (`custom[priority]=high`, or `custom={"estimate":{"gte":3}}`). The assistant reads the
  business's fields as turn context, and the sample's to-dos screen sets them (add form, row
  editor) and filters on them.
- **White label**: a `branding` settings section (name, logo URL, colours), custom domains
  (`app.tenant_domains`) verified by a DNS TXT record before they are trusted for CORS and sign-in,
  a public brand endpoint for a verified domain, and an app theme provider. The logo and name show
  on the sample's Today screen and in the back office (header and sign-in); the app shell's rail
  and sign-in wait for `AppShell`'s next owner (Deferred).
- **Platform-scoped shared records**: any entity can opt in (`defineSharedEntity`). Rows owned by
  the platform's business (`PLATFORM_TENANT_ID`) are readable by every business, read-only to
  them; a business overrides one by creating its own row that names it (`sharedId`), and then
  reads its own instead. What is shared (a catalog, say) is application data.
- **Wording overrides** (boundary audit): an application overrides framework phrases
  (`overridePhrases`) and framework notifications (`overrideNotification`, through
  `defineServer({ wording })`); a business overrides phrases and notification emails in its
  `wording` settings section.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | Flags are declared, not free strings: `defineFeatureFlag({ key, label, description, managedBy, gates })` in `@hykr/contracts`, contributed as `featureFlags`. A key is dotted lower case (`todos.clear-done`). Declarations are isomorphic, so the apps can read them. | Gap list A11; plan "Contributions". |
| 2 | A flag is on for a business only when its settings store `features[key] === true` (`TenantConfigService.isEnabled`). No business, an unknown key, unparseable settings: off. | PRD Overview "feature flags that fail closed"; F4 decision 21. |
| 3 | A flag gates `modules`, `entities` (by name), `commands` (by name), `tools` (any tool id, generated or contributed) and `nav` (app hrefs). Something gated by several flags is on only when all of them are on. A module's gate covers its entities, commands and their tools. | Gap list A11 "gating entities/tools/nav". |
| 4 | Enforcement, all fail closed: (a) a global interceptor answers 404 `not_found` for the routes of an entity or command that is off, before the handler runs (no probing: the same body as a missing record); (b) a write hook rolls back any write whose operation or touched records are off, with 404, on every path (commands, approval replays, system jobs); (c) a turn hook removes the tools of what is off (`withoutTools`), and, since H3, the MCP endpoint lists no tool or write action of what is off for the token's business; (d) the app hides destinations of what is off. | Gap map A11 risks "a disabled feature must answer 404 consistently", "replay after the flag is off must fail". |
| 5 | Reads that are not the entity's own routes (history entries, approvals already listed, stored events) are not filtered by flags: a flag is a product switch, not an access rule. | Default: reversible; access rules stay in `access`, grants and field policy. |
| 6 | `managedBy` is `platform` by default: a business cannot switch on what it was not given (pilot roll-out). A `tenant` flag can be switched by a holder of the new capability `settings.manage` (owner, admin) with `PUT /api/features/:key`. A platform flag is set by server code (`FeatureFlagsService.set`) until B19's operators exist; the HTTP route refuses it (403 `platform_managed`). | PRD Overview "pilot studios first"; gap map owner question "who sets them". |
| 7 | Every settings change (a flag, branding, wording, a domain, a custom field) goes through `runWrite` as a command or entity write: validated, idempotent, audited, refused with a rule. Settings commands have no tool: the assistant does not change a business's setup. | CLAUDE.md "one write path". |
| 8 | Custom field values live in one jsonb column per entity (`customFieldsColumn()`, key `custom`), definitions in `app.custom_fields` per business and entity. Types are a registry (`defineCustomFieldType`); the framework's are `text`, `number`, `boolean`, `date` and `select`. A key is camelCase letters (`priority`), at most 32, so it also works in a query string. Key, type and entity cannot change after creation (remove and add again). | Gap list A11 "typed, filterable"; gap map extension point. |
| 9 | Values are checked in the write's transaction, after the work (write hook `afterRun`): unknown key, wrong type, an option not in the list, a required field missing: 400 `custom_field_invalid`, and the whole write rolls back. Only the values a write sets are checked, so a value kept from a removed field (or a dropped option) stays until someone changes or clears it, and does not block the record's other changes. A parked write's input is checked when it parks (a parked create for its required fields too, custom values sent or not). An update merges the patch into the stored object (`null` removes a key). A required field binds only a writer that could fill it: the entity's own create (CRUD, its approval replay, a system job using it), a write that sets custom values on a record, and an update that changes them. A record another operation creates without any custom values (a command such as closing a meeting, which makes to-dos from action items) is made with the field unset. | Default: plugin hooks are synchronous; the check needs the business's definitions. Removing a field must not lock records that still carry it. Review finding (fix round 1): a required to-do field made every meeting close with action items a 400. |
| 10 | Filtering: the list field type `custom` (`filterable: { custom: 'custom' }`) takes `{ key: value }` or `{ key: { op: value } }` with `eq`, `ne`, `in`, `lt`, `lte`, `gt`, `gte`, `contains`. The SQL compares by the stored JSON type (numbers as numbers, text and dates as text), so it needs no definitions. On HTTP, the interceptor refuses (400) a key the business has not defined as filterable. Sorting by a custom field is not built. | Gap map risk "jsonb fields cannot use the column-based sortExpr". |
| 11 | Who reads definitions: every member role the framework knows (owner, admin, ops, staff); who writes them: a holder of `settings.manage`. Customers and roles an application adds do not read definitions (their records still carry the values). | Default: fail closed until A4's per-business roles. |
| 12 | Branding is a settings section: `name`, `logoUrl` (https only) and colours (`primary`, `primaryText`, `rail`, `#rrggbb`). Empty means the framework's theme. The logo is a URL until B1's files merge. | Gap list A11; B1 not merged. |
| 13 | A custom domain is an exact https origin. A business adds it (pending, with a token), publishes a TXT record `_basecamp-verify.<host>` holding the token, and verifies it; only then is it trusted for CORS and Better Auth's origin check, and served by `GET /api/branding/public`. Several businesses may claim an origin while it is pending; the first to verify holds it (a partial unique index on verified origins), and anyone else's add or verify is a 409 `domain_taken`. Verification uses DNS (`node:dns`); tests use a fake resolver. | Security default: a business must not make another site trusted for everyone's cookies, nor squat a domain with a claim it cannot prove. |
| 14 | Trust reaches Better Auth through an auth plugin whose `init` returns a dynamic `trustedOrigins(request)` (supported by Better Auth 1.7.7), and CORS through a new optional `AuthPlugin.originAllowed(origin)` that `startApi` asks after the static list. No hot file changes. | Better Auth `context/helpers.mjs` (plugin `trustedOrigins` functions); plan hot-file table (`auth.ts`). |
| 15 | Shared records reuse the entity's own table: the platform's rows have `tenant_id` = `PLATFORM_TENANT_ID` (deployment config, never a business setting: a business that could mark itself as the platform would push rows into everyone's lists). Unset: nothing is shared. | Plan boundary table "platform-scoped shared records"; default fail closed. |
| 16 | `defineSharedEntity(spec, config)` wraps `defineEntity`: `list`, `find` and `get` read the business's own rows plus the platform's rows it has not overridden, in one keyset order (the platform's page and the business's page are merged by a second query that Postgres orders, so collation is Postgres's). Writes are the plain entity's: a platform row is never written by another business (403 `shared_read_only`). | Default: `define-entity.ts` is a hot file (F3 → B19 → B12), so the read path is wrapped, not edited. |
| 17 | An override is a row of the business with `sharedId` naming a platform row of the same entity, at most one per business (checked in the write's transaction: 400 `shared_override_invalid`, 409 `shared_override_exists`). The read schema carries `shared` (true for a platform row) and `sharedId`. | Gap list A11 "tenant overrides". |
| 18 | Phrase overrides: `overridePhrases({ en: {...}, hi, te })` in `@hykr/i18n` replaces framework phrases for the whole process (server: `defineServer({ wording: { phrases } })`; app: call it at startup). An unknown key or a phrase whose `{placeholders}` differ throws. A business's phrases (`wording.phrases`) apply in the app (the settings plugin sets the tenant layer) and through `tenantPhrase(settings, lang, key, vars)` on the server. | Boundary audit note. |
| 19 | Notification overrides: `overrideNotification(key, { channels?, whatsapp?, email? })` in `@hykr/notifications`, passed as `defineServer({ wording: { notifications } })`. `createNotificationCatalog` applies them after every definition; an unknown key or a second override of one key is a problem at boot. A replacement WhatsApp template must be in the catalog (Meta approves wording, so a template is replaced by another template, never edited). | Boundary audit note ("add overrides rather than duplicates"). |
| 20 | A business's email wording (`wording.notifications[key].email.subject/body`, per language, `{field}` filled from the record) replaces the application's at send time. The catalog wraps each email function with a resolver the settings feature installs, reading the business's cached settings. | Default: `dispatch.processor.ts` is a hot file. |
| 21 | A flag that names a module, entity, command or tool the application does not have stops the start (`featureFlagProblems`, checked by the settings feature at bootstrap, with every generated and contributed tool id). Nav hrefs are not checked on the server (the app owns them). | Fail closed: a typo in a gate would leave the feature on for every business. |
| 22 | Anyone can ask whether an origin is verified (CORS preflights, which no throttler sees, and `GET /api/branding/public`). So each process holds a copy of every verified origin (`originLookup`: one query for the whole set, at most every 30 seconds, shared by concurrent askers, dropped when a domain is verified or removed in this process), and anything that is not a `DomainOrigin` (an exact https origin of at most 200 characters) is never looked up. A question costs no query and adds nothing to memory; the copy grows only with verified domains, which take a DNS proof. A failed load is not kept. | Review finding (fix round 1): a per-origin cache of misses grew without limit and cost one query per unauthenticated request. |
| 23 | A business's logo and name show where A11 owns the screen: the sample's Today (`<BrandMark>`, only when the business has a name or logo, since the shell already prints the product's), the back office's header (its settings) and the back office's sign-in (`api.settings.publicBranding(window.location.origin)`, the product's name on a 404 or a refused request). The app shell's rail, phone bar and sign-in are `AppShell`'s and stay the product's until its next owner (Deferred). | Review finding (fix round 1); plan hot-file table (`AppShell.tsx`: F2 → B9 → B12). |
| 24 | `publicBranding` takes the origin to ask about (`?origin=`, else the request's Origin), because a browser sends no Origin on a same-origin GET. The answer is public (name, logo, colours of a verified domain), so naming another origin reveals nothing a visit to that domain would not. | Default. |
| 25 | The sample app sets custom fields: the to-dos add form renders `<CustomFieldInputs>` and sends `customForCreate(collected)` (`@hykr/contracts`: the cleared keys left out, nothing when empty), keeps Add disabled until every required field has a value, and remounts the inputs (`key`) after an add. Each row has a "Fields" button that opens the same inputs and saves one `custom` patch. A filterable `select` field gets its own filter chips (`custom[key]=option`), only while the business still has it as filterable. | Review finding (fix round 1): the mechanism stopped before the app's UI. |
| 26 | `<CustomFieldInputs>` text, number and date inputs are controlled and report every change (`customValueFromText`: empty clears, a number field's text becomes a number when it is one, anything else is sent as typed so the server names the problem). They used `onEndEditing`, which react-native-web does not fire, so a typed value never reached the form on the web. | Found while fixing #25; react-native-web 0.21 `TextInput` (no `onEndEditing`). |
| 27 | `GET /api/me` reads the business's settings through `TenantConfigService` (cached 10 s), so tests change settings with `setTenantSettings(tenantId, patch)` from `@hykr/api/testing` (each key replaces a section, `null` removes it, then the process's cached copy is dropped), never a bare `UPDATE app.tenants`. Every framework and application test that wrote settings by SQL uses it, except identity's, which tests the cache itself. | Integration CI finding (fix round 1): the notifications e2e failed between 21:00 and 09:00 IST because its first reminder read the cached default quiet hours. |
| 28 | An update merges its custom patch in SQL, on the row as the UPDATE finds it: `(coalesce(custom, '{}') \|\| <keys set>) - <keys removed>` (`mergeCustomSql`, returned by the plugin's `toValues`). The row a CRUD update or a command loaded was read without a lock at READ COMMITTED, so a JSON object built from it would overwrite a key a concurrent update set in between; with the merge in SQL each update changes only the keys it sends, as an update of plain columns changes only its own columns, and nobody gets a 409 for touching different keys. Two updates of the same key: the last one wins, as for a plain column. The write hook compares the stored `after` (RETURNING) with the row this write read, so a key a concurrent update changed in between is checked again. `EntityPlugin.toValues` may now return SQL; a child entity counts such a value as a change (`children.ts` `changes`). | Review finding (fix round 2): two PATCHes of different custom keys on one record lost the first one's key, both answering 200. Option rejected: an `updateWhere` stale guard (409 `stale`) would refuse writes that do not conflict. |

## Assumptions to review

- **Who switches flags.** Flags default to platform-managed. Which flags may a business owner
  switch on by themselves, and are some flags plans (billing, B19)?
- **Gated reads elsewhere.** A record of a switched-off module still shows in history and in
  approvals made before the switch. Should switching a module off hide those too?
- **Required fields and records made by commands.** A required field does not stop a command
  that makes the record without custom values (closing a meeting makes its to-dos with the field
  unset). Should such records be flagged for someone to fill in (a list filter "missing
  priority", a reminder), or should a business be able to give a required field a default?
- **Custom field types.** Text, number, yes/no, date and one-of-a-list. Are multi-select,
  money (minor units) or a link to another record needed, and should custom fields be sortable
  and searchable?
- **Who defines fields.** Owners and admins (`settings.manage`). Should a business's own roles
  (A4) be able to read or manage definitions?
- **Custom domains.** Verification is a DNS TXT record. Does the product also need the domain's
  own sign-in cookies (one session per domain), and who issues TLS certificates?
- **Logo.** A URL today. Should the logo be an uploaded file (B1) and per-language?
- **Where the brand shows.** Today a business's logo and name show on the sample's Today screen
  and in the back office; the app's rail, phone bar and sign-in still show the product's name
  (`AppShell` is B9's, then B12's). Should the business's name replace the product's everywhere,
  or sit beside it ("Acme, on Basecamp")? And on a business's own domain, should the app's
  sign-in show only the business's brand?
- **Shared records.** One platform business holds every shared row, curated by its members.
  Can other businesses publish to the shared set (a supplier's library), and should an override
  follow later changes to the shared row (today it is a full copy)?
- **A business's email wording and hidden fields.** A business's email subject and body fill
  `{field}` from the whole record, so a settings manager can put any field of it in an email,
  one hidden from the recipient by a capability included. Should a business's wording be limited to
  the fields the recipient may read (A4 field policy)?
- **Wording per business on WhatsApp.** A business's phrases reach the app and anything that
  calls `tenantPhrase`. The WhatsApp replies in `inbound.processor.ts` (a hot file) still use the
  application's phrases until that file's owner switches to `tenantPhrase`.

## API sketch

```ts
// contracts (isomorphic)
defineFeatureFlag({ key: 'todos.clear-done', label, managedBy: 'tenant',
  gates: { commands: ['todo.clearDone'], nav: ['/todos/done'] } });
entitySpec({ ..., traits: { customFields: {} }, list: { filterable: { custom: 'custom' } } });
entitySpec({ ..., traits: { shared: {} } });             // read schema: ...SharedFields

// db
custom: customFieldsColumn(),  sharedId: sharedFromColumn(),

// server
export const Item = defineSharedEntity(ItemSpec, { table, owner, access });
defineServer({ ..., wording: { phrases, notifications: [overrideNotification('approval.request', { whatsapp })] } });

// HTTP
GET  /api/me                          → { ..., features: ['todos.clear-done'] }
GET  /api/features                    → [{ key, label, managedBy, on, gates }]
PUT  /api/features/:key { on }        (settings.manage; tenant-managed flags)
GET  /api/settings                    → { features, off, branding, wording }
PATCH /api/settings/branding | /api/settings/wording
GET|POST /api/custom-fields, PATCH|DELETE /api/custom-fields/:id
GET|POST /api/settings/domains, POST /api/settings/domains/:id/verify, DELETE …/:id
GET  /api/branding/public             (no session; a verified Origin)

// app
<AppShell plugins={[settingsPlugin()]} />;  useFeature(key); useBranding(); useCustomFields(entity)
<CustomFieldInputs entity="todo" values={collected} onChange={(p) => collect(p)} />
create({ title, custom: customForCreate(collected) });  update(id, { custom: patch })

// tests (@hykr/api/testing)
await setTenantSettings(tenantId, { quietHours: { from: '00:00', to: '00:00' }, files: null });
```

## Test plan

- `framework/api/test/framework/settings.e2e.test.ts` on the fixture's `settings` feature
  (its own migration set): flags off by default (404 on routes, tools removed, writes through a
  command rolled back, an approval parked while on and approved after it is turned off fails),
  tenant-managed vs platform-managed switching, `/api/me` features; custom field definitions
  (capability, another business's definition is 404), value validation (400 and rollback),
  filters (eq, ops, unknown key 400), merge on update, a parked write's custom values audited;
  a value kept from a removed field; branding and wording validation; domains (add, verify
  with the fake resolver, 409 on a verified origin, a pending claim does not squat, another
  business's domain 404, trusted origin check, public branding, a malformed or repeated origin
  refused before any lookup, a plain-http preflight refused); shared records (another
  business reads platform rows, cannot write them, overrides one, sees its own instead, a
  business's own rows stay private, paging across both, a field hidden from staff stays hidden
  on the platform's rows).
  Fix round 1: a command that makes a gadget without custom values succeeds while a required
  field exists (`gadget.copy`), the same command setting custom values without the required one
  rolls back, and a parked create without it is refused when it parks.
  Fix round 2: three updates of one gadget held behind a row lock (one sets `priority`, one sets
  `estimate`, one only the title) all answer 200 and the record keeps all three changes (the test
  checks that all three were waiting on the lock, so it exercises the race).
- Unit tests: list SQL for `custom`, custom value validation, a form's typed-in values
  (`customValueFromText`) and a create's values (`customForCreate`), flag gate computation, a flag
  naming nothing, phrase and notification overrides, the app's nav filter, and the verified-origin
  lookup (2000 unknown origins cost one load, malformed ones none, concurrent askers share a load,
  a load overtaken by a change is not kept, a failed load is retried).
- Application: `application/api/test/domain/todo-settings.e2e.test.ts`: the `priority` field on
  to-dos and the `todos.clear-done` flag; a required `area` field set through the app's own typed
  client (`createApiClient`, the add form's `customForCreate`, the row editor's patch, the filter
  chips' `custom` query), refused without it, and a meeting's close still making its to-dos.
- Settings in tests: every e2e that changes a business's settings uses `setTenantSettings`, so
  none depends on the hour it runs at (the notifications e2e's quiet hours).

## Deferred

- Data export (A11-export, its own unit after B1 and B11).
- Sorting and full-text search on custom fields; custom fields in tool descriptions (they are
  turn context instead).
- Per-domain sessions and cookies, TLS, and per-business app icons (Expo cannot change them at
  runtime).
- Hiding a switched-off module's records from history and approvals.
- Pushing changes of a shared row into the overrides made from it.
- A screen or route for platform-managed flags (B19's operators); `FeatureFlagsService.set` today.
- A business's phrases in WhatsApp replies and voice (`inbound.processor.ts` is a hot file), and
  per-business WhatsApp template wording (templates are approved per application).
- A logo upload (B1 had not merged when A11 started): `logoUrl` is an https URL.
- **For `AppShell`'s next owner (B9, then B12):** (1) replace `app.title` and `app.tagline` in the
  rail and the phone's top bar (`framework/app/src/AppShell.tsx`, the rail's heading) with
  `<BrandMark fallback={app.title}>` from the settings feature, or add an `AppPlugin` header slot
  that `settingsPlugin` fills; (2) have the app's sign-in (`screens/SignIn.tsx`, which `AppShell`
  renders) call `api.settings.publicBranding(window.location.origin)` on the web and show the
  answer's name and logo, and apply its colours (the plugin's `brandTokens`), falling back to the
  product's on 404 or a refused request. A11 did not edit `AppShell.tsx` (a hot file), and left
  `SignIn.tsx` to the same owner so the sign-in and the shell change together. The back office
  already does both.
- The back office shows the business's logo and name, not its colours.
