# V8: erasure reaches every feature's copies

## Summary

A fix unit from the live validation of `feat/platform-gaps` (`docs/decisions/VALIDATION.md`,
row 3, the class of C8-2 and C8-3), on the critic's two leads, V8-L0 and V8-L3. V3 made
`redactCopies` find every copy of an erased record at any depth, but only for the record sets
that contributors return in `erased`. Most framework features returned only a count, so after a
person was forgotten their name, email, number and words stayed in the copies those features
write. Redis was never touched, and BullMQ keeps each queue's last 1,000 completed and 5,000
failed jobs, each holding its whole data: an event's envelope with its row and before, or a
notification's row.

The test (`framework/api/test/framework/erasure-copies.e2e.test.ts`) seeds the lead's steps
through the API: a member's comments, a comment naming him, party members by email and by
number, share links naming him and a contact, a business memory, an agent with its run, an
agent run started by the contact's WhatsApp message, a job started for him, another member's
inbox item and push log. It erases the member at his own request and the contact by a team
filing, approved by a second person. It then reads every row of every table in every schema,
and every key under the run's queue prefix in Redis (hashes, lists, sets, sorted sets, streams),
for the markers. On the code before this unit, it found 22 rows and 19 Redis keys:

| Where | What stayed |
|---|---|
| `audit.events` | `comment.create` (the member's words; a mention's name), `party_member.create` (email; the contact's name and number), `party.create` (the contact's person party), `shareLink.create` (`to.email`, the label), `memory.create` (the text), `agent.create` (the instructions), `job.start` (the input), `file.attach` (a job file's name) |
| `app.domain_events` | `comment.added`, `comment.mentioned` (`author.name`, `excerpt`, `target.label`), `memory.created`, `agent.created` |
| Feature rows | `app.party_members` (a pending invitation to the member's email), `app.share_links` (his email; both labels), `app.agent_runs` (the contact's message and name in `input`, the reply), `app.thread_messages` (the run's turn in the agent's thread), `mastra.mastra_scorers` (that run's scores) |
| Redis | completed jobs of `events` (every subscriber's copy of each event), `notify-dispatch`, `notify.events`, `privacy.requests` (its return value named the contact's number), and the `privacy.requests` event stream |

Two more sites showed up once the member mentioned someone: the inbox item in the other
member's inbox (`channel.inbox_items`: his name and the excerpt), and a push ticket's
`meta.row` (`channel.push_tickets`, the record kept for the next channel). On the code after this
unit, the sweep finds nothing. Two more classes showed up as the test grew, each red first: the
copies of what the member had deleted himself before (a comment, a memory, an agent), and the
run of another member's agent that his @-mention started (its input, label, reply, thread turns
and Mastra rows).

Two parts of the lead did not hold. The record-level row of a comment command (`comment.remove`
on the to-do) holds only `{ touched: [{ type, id, change }] }` (`runWrite`, pipeline.ts), and the
comment's own `comment.delete` row is now redacted (decision 14). The members feature has a
contributor since V3 (`invites`), and a membership's copies hold ids and roles only.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | **Every feature's contributor returns what it erased** as `ErasedRecords`, named by the literal resource type its `touched` rows and events use, so `redactCopies` (V3) takes the fields out of every copy. comments: the person's own (`comment`, `body`, `mentions`, `anchor`, `excerpt`, `author`, `target`, deleted), and the comments that named them (`body`, `excerpt`, `mentions`, `target`). parties: `party_member` (`name`, `address`, `email`, deleted), an emptied person `party` (`name`, deleted), its `participation` rows (`party`, read before the cascade). share: `shareLink` (`to`, `otp`, `label`, `email`, `otpAddress`). memory: `memory` (`text`, deleted). jobs: `job` (`input`, `output`, `message`, `error`, `principal`) and its files as a `file` set (`fileCopies`), since it erases them itself. agents: `agent` (`name`, `description`, `instructions`, `triggers`, deleted) and each run (`agent_run`, the run's input, reply and trigger, deleted with the agent). | Lead V8-L0; V3 decision 1 ("V8 only has to return sets"). |
| 2 | **A comment that named the person loses its words and mentions in its copies**, and keeps its rewritten text (`@—`). A mention token and a mention carry the name they were written with (`label`), so a copy keeps it otherwise. The copies lose the whole body, not only the token: they are copies, and rewriting free text inside them is not worth the risk of missing one. | Found by the test (`mentions[].label`, `target.label`). |
| 3 | **Party members are found by email too.** For a person, the parties contributor also deletes the invitations to join sent to their account's email (`party_members.email`, lower case, no user yet), as V3's members invitations do. Its export lists them. | Found by the test (C8-3's class). |
| 4 | **A share link names a person by email.** For a person, the links sent to their account's email are revoked and forget the email, as a contact's links forget the contact. Every such link also loses its label (`label` is null): the maker wrote it for them ("For Ravi"). | Lead V8-L0; found by the test. |
| 5 | **Another person's agent's run that carried the subject** (a contact's message, a person's @-mention of the agent, an event whose input names them): the run stays (another person's agent did the work, and its log is theirs), without its input, reply and label (a mention's label names its author). Its turns in the agent's thread (`app.thread_messages` of the run) are deleted, and its Mastra rows go with the subject's own: `ErasureResult.runs` lists the runs a contributor erased, and the erasure adds them to the runs `eraseMastra` deletes. A contact's runs are found by `input.message.from.contactId`, a person's by their user id anywhere in the input. The agents contributor also returns the runs of the person's deleted agents. | Lead V8-L0 (C6's inbound trigger data); found by the test (`mastra_scorers`; the mention run). |
| 6 | **Other people's inbox items about an erased record are deleted** (`recordCopies`: `inbox`). An item is about the record when it links to it (`record_type`, `record_id`), or when its notification's key names it as a whole word: a notification's `dedupe(row)` names the row it was made from (a mention links to the record the comment is on, and its key names the comment). Its words were made from the record (the author's name, the excerpt). | Found by the test. |
| 7 | **Push tickets lose the record's fields from `meta`** (`recordCopies`: `push`), found by the record's id at any depth, as V3 does for `channel.messages.meta`. | Same class as V3's messages; found by reading `NotificationMeta`. |
| 8 | **Redis: an erasure removes the finished jobs that name the person.** After the erasure commits (its `afterCommit`), `forgetJobs` (`queues/forget.ts`) goes through every registered queue's completed and failed jobs, in pages of 500, with a script that runs in Redis and returns only the matching ids: a job matches when its data, return value or failure holds one of the person's ids (account, contacts, customer records), one of the ids of every record erased with them (whole words), or one of their emails or numbers (anywhere, lower case). Matching jobs are removed (`Queue.remove`); entries of the queue's event stream that match are deleted (`XDEL`). It uses its own Redis connection (BullMQ 6's queue client is a backend wrapper). A failure is logged, and the erasure stands. | Lead V8-L0; task ("bound the kept jobs or redact them"). |
| 9 | **Jobs still waiting, delayed or running are left to finish.** They are the work in flight (an undo window's delayed event, a retry's backoff, the privacy request's own job while it runs). Removing them would drop other people's work; their data finishes with them. | Default. |
| 10 | **Finished jobs are kept for a bounded time**, not only a bounded number: 24 hours for completed jobs and 7 days for failed ones by default, at most 1,000 and 5,000 per queue as before (`JOBS_KEEP_COMPLETED_HOURS`, `JOBS_KEEP_FAILED_DAYS`, `JOBS_KEEP_COMPLETED`, `JOBS_KEEP_FAILED`; `config.keepJobs`, used by `jobDefaults` and `BullModule.forRoot`). A copy of a record therefore outlives it in Redis by at most the bound after an erasure (decision 9) or a retention rule, whose periods are days. BullMQ applies the age when the queue next finishes a job, so on an idle queue a job can stay longer; the erasure's sweep does not depend on it. The relay's job-id dedupe (`<subscriber>--<event id>`) needs the completed job only for the seconds between adding and marking an event relayed. | Task; advisor (age is lazy; dedupe). |
| 11 | **What a queue's job returns is not kept.** The registry's processors await the job and return nothing, so BullMQ stores no return value (the privacy request's run returned its outcome, which named the contact's number for the WhatsApp confirmation). Nothing reads return values (`returnvalue`, `waitUntilFinished`: no use in the framework or the sample). The channel's own processors return short reasons only. | Found by the test. |
| 12 | **A job's result files are kept on erasure, until their period.** A business export's archive and an import's error report copy other people's records; erasing one of them leaves the copies made before. They are on the register as a part (`jobs.files`, `erase: 'keep'`, keep reason `business_copy`), and a retention target (`jobs.files`, per business, `delete`) erases the result files of every job finished before the period, with their copies (`fileCopies`); a record keeps the copy a job's `complete` put on it. Without a period they stay, as before. The sample sets 30 days and says why in en, hi and te. An import's own file is an upload on no record: the files sweeper deletes it after its grace period. | Lead V8-L3; A11X Deferred ("How long should an export archive be kept"); read from `jobs/start.ts` (input files are only checked) and the files sweeper. |
| 13 | **The sample's briefs are their customer's personal data** (`traits.privacy`: subject `customerId`; fields `name`, `phone`, `summary`, `notes`, `custom`; deleted on erasure; `briefs.personal`, 365 days from the last change, delete; purpose in en, hi and te). A brief answered on the form is filed as its customer's: the share link's recipient, or a new customer record named by the answer (`share/ops.ts`, the form's `customerName`). | Lead V8-L3; task ("declare it in the application"). |
| 14 | **What the person wrote and deleted before keeps no copy either.** A comment they removed, a memory or an agent they deleted is gone, but its audit rows and events are not, and the contributor no longer finds it. The comments, memory and agents contributors add the ids of the records of their type the person created (`createdBy`: their `<type>.create` audit rows, as themselves or through their assistant) to their erased sets. | Found by the test (a removed comment, a deleted memory and agent). |
| 15 | **Members**: V3 added the `invites` contributor. The membership's own copies hold ids and roles only (`membershipJson`), and the sweep finds nothing else there. | Checked by the test. |

## Assumptions to review

- Copies of other people's comments that named the person lose their whole body and mentions
  (decision 2), not only the token. The live comment keeps its rewritten text.
- Inbox items are matched by their notification's key when they link to another record
  (decision 6). An application whose `dedupe(row)` does not name the row leaves such an item
  until its owner clears it; the item links to the record and the record's other copies are
  gone.
- The Redis sweep removes any finished job naming one of the ids, including jobs about
  records that stay and that only name the person (an event of a task they created, with
  `createdBy`). Finished jobs are history, not work; removing more is the safe side.
- A person's carried runs (decision 5) are found by their user id anywhere in a run's input:
  a run of another member's agent on an event the person caused (its `actorId`) loses its input,
  reply and turns too, though the record it was about stays.
- 24 hours and 7 days are defaults for a deployment to change, not business settings: they bound
  an operational cache, not a business's retention.
- Briefs: 365 days from the last change is the sample's choice. A brief the team typed in for
  nobody in particular has no customer, so no subject: neither erasure nor the retention rule
  reaches it (as a note with no customer). A form answer on a link that names nobody files the
  brief as a new customer record with no account or contact, which nobody can file a request
  for: only the retention rule reaches it.

## API sketch

```ts
// hooks.ts (additive)
export interface ErasureResult {
  count: number;
  erased?: readonly ErasedRecords[];
  kept?: readonly KeptData[];
  /** Assistant runs whose turns it erased: their Mastra rows go with the subject's own. */
  runs?: readonly string[];
  afterCommit?: (ctx: ServerContext) => Promise<void>;
}

// queues/forget.ts
export interface Forget { ids: readonly string[]; texts: readonly string[] }
export function forgetJobs(jobs: Pick<Jobs, 'queue'>, redisUrl: string, who: Forget): Promise<number>;

// queues/define.ts
export interface KeepJobs {
  completed: { age: number; count: number }; // seconds, jobs
  failed: { age: number; count: number };
}
export function jobDefaults(def: QueueDef, keep: KeepJobs): JobsOptions;

// features/inbox, features/push: recordCopies (inboxCopies, pushCopies)
// features/jobs/privacy.ts: jobsFilesRetention ('jobs.files'), jobsParts
// features/members/privacy.ts: emailOf is exported (parties and share read it)
// privacy/contributors.ts
export function createdBy(conn: Conn, a: { type: string; userId: string; tenantId?: string }): Promise<string[]>;
```

  lead's seven steps plus the inbox and push copies; then no row in any table and no key under

  the six texts; another member's words stay. Before erasing it waits for the queues to be idle

## Deferred

- Text already delivered to other people is not rewritten: a WhatsApp message's or an email's
  text, a push already sent, an inbox item about a record that stays (V3 redacts
  `channel.messages.meta`, not the text). It is what the recipient was told.
- The approval of a parked comment **add** names no comment (V3's Deferred, parked creates):
  once decided, its input keeps the words.
- A finished job that names the person by none of the ids, emails or numbers (only by a display
  name) is not matched; it goes within the keep bound (decision 10).
- Rendered PDFs stay with their record (`documents/privacy.ts`, by decision); export archives of
  a person's own requests stay under `privacy.archives`, as before.
