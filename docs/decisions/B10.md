# B10: integration bus and `@hykr/connectors`

## Summary

A business can send its records' events to other systems and take events in from them.

- **Outbound.** People with `integrations.manage` register webhook endpoints (a URL and the event
  names it wants). Each committed event (F3's outbox, F5's relay) becomes one delivery per matching
  endpoint. The payload is the record as the endpoint may read it (`eventFor`, so hidden fields stay
  hidden), signed with the endpoint's secret (Standard Webhooks), sent through an egress guard that
  refuses private and internal addresses, and retried on a schedule. Every attempt is logged.
- **Inbound.** A business configures a connection: a connector (a kind of sender) plus its
  credentials, encrypted with `SECRETS_KEY`. The sender posts to `/webhooks/<connector>/<connection>`.
  The connector verifies the request, each event is stored once and queued, and the handlers that
  modules declare run as the business's system principal, writing through `runWrite`.
- **`@hykr/connectors`** is the transport SDK both use: HMAC helpers (the WhatsApp adapter's moved
  here), Standard Webhooks signing and verification, the secret box, the egress guard with a guarded
  HTTP request, the `Connector` interface, and two generic connectors.

The framework ships no named provider. Which events a business sends, where, and which connectors
it uses are tenant data; what an inbound event does is the application's handler.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | New package `@hykr/connectors` (`framework/connectors`), transport only: `hmac.ts`, `signature.ts` (Standard Webhooks), `secret-box.ts`, `egress.ts` (address checks, URL checks, `safeRequest`), `connector.ts` (`Connector`, `defineConnector`), `standard-webhooks.ts`, `hmac-connector.ts`. It depends on zod, `@hykr/i18n` (labels) and Node built-ins only. The dependency-cruiser rule `connectors-is-transport` keeps the database, policy, core, agents, Nest, queues and models out. It is published like the other packages (`exports`, `files: ["dist"]`, `publishConfig`), so the CI consumer job packs it. | Plan B10 row ("transport-only, with its own dependency-cruiser rule"); task note (consumer-job readiness). |
| 2 | The WhatsApp adapter's signature check uses `verifyHmac` from `@hykr/connectors`; `@hykr/channels` depends on `@hykr/connectors`. Behaviour is unchanged (HMAC-SHA256 over the raw body, `sha256=` hex, constant time). | Plan ("HMAC helpers moved out of the WhatsApp adapter"). |
| 3 | Outbound requests are signed with Standard Webhooks v1: headers `webhook-id`, `webhook-timestamp` (seconds) and `webhook-signature: v1,<base64 HMAC-SHA256 of "<id>.<timestamp>.<body>">`; the secret is `whsec_<base64 of 32 random bytes>`. `verifyWebhook` checks it with a 5-minute tolerance either way, so a captured request cannot be replayed later. | Default: an open, documented scheme with verifiers in many languages, so a receiver needs no Basecamp code. |
| 4 | Secrets at rest: AES-256-GCM with a key derived by HKDF-SHA256 from `SECRETS_KEY` (at least 32 characters, like the other secrets). The sealed text is `v1.<key id>.<iv>.<tag>.<ciphertext>` and its associated data binds it to its row (`endpoint:<tenant>:<id>`, `connection:<tenant>:<id>`), so a sealed value copied to another row or business does not open. `SECRETS_KEY_PREVIOUS` (comma list) opens values sealed with an older key; new values use `SECRETS_KEY`. | Plan ("encrypted credentials (`SECRETS_KEY`)"); default. |
| 5 | Without `SECRETS_KEY`, saving an endpoint or a connection is refused (503, rule `secrets_unavailable`), and a delivery or an inbound request that needs a secret fails. A `SECRETS_KEY` shorter than 32 characters stops the API and the worker at start. Deployments that do not use integrations start as before. | Default, fail closed without breaking environments that have no key. |
| 6 | Egress guard. An endpoint URL must be `https` (credentials in the URL are refused). Its host may not be an IP literal or a name that resolves to a loopback, private, shared, link-local, documentation, benchmark, multicast or reserved address, IPv4 or IPv6 (IPv4-mapped, NAT64 and 6to4 forms are checked as the IPv4 address they carry). Single-label names (`redis`) and `localhost`, `*.localhost`, `*.local`, `*.internal`, `*.lan`, `*.intranet` and `*.home.arpa` are refused. The address is checked before the scheme, so the reason given is the one that matters. The URL is checked when it is saved, and the address is checked again when the connection is made (in the socket's DNS lookup), so a name that later resolves inside cannot be reached. Redirects are not followed (a 3xx is a failure). A request has 10 s (`INTEGRATIONS_TIMEOUT_MS`) and at most 64 KB of response is read. `INTEGRATIONS_ALLOWED_HOSTS` (comma list of host names) lets named hosts through on any address and over `http`, for development receivers. | Gap map risk (Redis, Postgres, MinIO and LiveKit listen on localhost); default. |
| 7 | Endpoints and connections are the business's data, managed over `/api/integrations/*` by people whose roles have the new capability `integrations.manage` (owner and admin by default, the same generic built-ins as `channels.manage`). Agents cannot reach these routes (`HumanOnlyGuard`), so the assistant never sees a secret or an endpoint. | Gap owner question ("Do businesses configure their own webhooks?"); default, like the WhatsApp number. |
| 8 | Every change to an endpoint or a connection goes through `runWrite` as one of the feature's ops (`integrations.endpoint.create`, `.update`, `.delete`, `.rotate`, `integrations.connection.create`, `.update`, `.delete`, `integrations.delivery.retry`). Each authorizes `integrations.manage` (a refusal is audited), passes the write hooks, and audits its row before and after with secrets left out. The ops are registered for replay, and their inputs carry only sealed secrets, so a write hook that parks one stores no secret in the approval; approving it replays the op. | CLAUDE.md design rule 1 (one write path). |
| 9 | The server generates an endpoint's signing secret before the write and seals it into the op's input, so the secret is returned once, on create (also when the create is parked: it starts signing once approved) and on rotate; reads never include it. Rotating keeps the previous secret signing for 24 hours, so a request carries two `v1` signatures and a receiver can switch over. A read projector removes sealed values from approval cards. | Default (Standard Webhooks allows several signatures). |
| 10 | An endpoint subscribes to event names in the subscriber grammar: `task.created`, `task.*` or `*`. Only events about a registered entity are offered, because those records have a read schema to project. An entity can opt out with `traits: { webhooks: false }`. Approval events and other records without an entity (commands' own resource types) are not sent until read projectors cover them. | Gap owner question ("Which events may leave the platform?"); default, fail closed for records nothing can project. |
| 11 | Field filtering. An endpoint reads as `systemPrincipal({ tenantId, job: 'integrations.webhooks', capabilities })` with the capabilities the endpoint was given (none by default), through F3's `eventFor`: the read schema drops internal columns, and entity plugins and read projectors drop fields that need a capability. A person can give an endpoint only capabilities they hold (403 `capability_not_held`), and changing an endpoint's URL or capabilities, or rotating its secret, needs every capability the endpoint will have, so nobody can point another person's reads at their own server; pausing or describing it needs none. An event whose record the read schema refuses is not sent. The delivery stores the exact payload it sends, and the delivery log projects that payload again for whoever reads the log. | Plan ("Payloads are field-filtered"); gap map risk (cost and margin); F5 decision 13. |
| 12 | The endpoint reads every record of its business, like the system principal; capabilities limit fields, not rows. | Default: a business-level integration. Logged as an assumption. |
| 13 | Fan-out is a subscriber, `integrations.webhooks` on `*`, on the shared `events` queue: for each active endpoint of the event's business whose patterns match, one `integration_deliveries` row (unique per endpoint and event, so a relayed-twice event is one delivery), then one job on `integrations.deliver`. The outbox feed already holds back events in an undo window and never returns an undone write. | F5 (subscribers, outbox feed). |
| 14 | The body is `{ type, timestamp, data: { eventId, tenantId, resourceType, resourceId, row, before? } }` (`type` is the event name). `webhook-id` is the delivery's id, the same on every retry and on a manual redelivery, so a receiver can drop repeats. The actor is not sent. | Default (Standard Webhooks' payload shape); least data. |
| 15 | Retries follow `INTEGRATIONS_RETRY_SCHEDULE`, by default `5s,5m,30m,2h,5h,10h,10h`: 8 attempts over about 27 hours, as Standard Webhooks recommends. Any non-2xx answer, a network error or a timeout is retried; a blocked address is final. Each job names the attempt it makes and claims the delivery only at that attempt (a lease of the timeout plus 30 s covers a worker that died mid-send), so duplicate jobs send once. A sweeper on the same queue, every minute, re-queues due deliveries whose job was lost. A manual retry (`POST /api/integrations/deliveries/:id/retry`, an audited op; refused while a try is in flight) makes one more attempt now, under a job id of its own so a delayed retry job does not swallow it; that job finds the attempt taken and does nothing. The deliver queue has no BullMQ retries of its own: a job that throws leaves its delivery to the sweeper. | Default. |
| 16 | The delivery log: `integration_deliveries` (status `pending`, `sending`, `retrying`, `delivered`, `failed` or `cancelled`; attempts, last HTTP status, last error, next attempt) and `integration_attempts` (one row per attempt: URL, HTTP status, error, duration, the first 512 characters of the answer). Read with `GET /api/integrations/endpoints/:id/deliveries` (newest first, `status`, `before`, `limit`) and `GET /api/integrations/deliveries/:id` (payload and attempts). | Plan ("deliveries, retries, a delivery log"). |
| 17 | A paused endpoint gets no new deliveries; a pending retry for it is cancelled when its time comes. Deleting an endpoint deletes its deliveries and attempts. | Default. |
| 18 | A connection is a business's instance of a connector (`integration_connections`): its credentials are validated against the connector's schema and sealed; only the connector's `publicFields` are stored in the clear and shown back. A connector with `generate()` can make the credentials itself (the secret a sender needs), returned once. A business may have several connections of one connector. A connection reads back as `{ id, connector, label, status, public, inboundPath }`, never its credentials. | Plan ("per-studio encrypted credentials"); gap map. |
| 19 | Inbound: `POST /webhooks/<connector>/<connection id>`, anonymous and not throttled (like the WhatsApp webhook). An unknown connector, an unknown or disabled connection, or a connection of another connector is 404. The connector verifies the request with the connection's credentials (401 otherwise). Each event it parses is stored once per connection and sender's event id (`integration_inbound`, a redelivery is a no-op) and queued on `integrations.inbound`; the answer is 200 `ok`. `GET` on the same URL answers a connector's challenge (403 when it has none). | Plan ("inbound `/webhooks/:connector` (verify → store once → queue → system principal)"). |
| 20 | The inbound URL names the connection, so a request is verified only with the credentials of the business it is addressed to. Routing one shared URL per connector by a provider's account id is not built: a business could claim another's account id and receive its events when the provider signs with one app-wide secret. | Default, fail closed. |
| 21 | Handlers: `defineConnectorHandler({ name, connector, on, capabilities?, handle(event, ctx) })`, contributed as `connectorHandlers` by a module or the application. Each runs as `systemPrincipal({ tenantId, job: 'integrations.<connector>', runId: <inbound id>, capabilities })`, so its writes are audited as actor `system`, channel `background`, with the inbound event's id as the run. `ctx.write(op, input)` runs `runWrite` with an idempotency key per inbound event, handler and write. A handler that finished is recorded and not run again; an error with a 4xx status (a 404 for another business's record, a 403) is final; other errors retry (3 attempts, 2 s backoff doubling), and on the last try they are final too. Each handler's result is kept on the row (`handled: { '<handler>': 'done' | 'failed: …' }`), so a retry runs only what has not finished. An event no handler takes is `ignored`. A system principal cannot create rows or park yet (F4), so a handler that tries fails and the inbound row says why. | Plan; F4 decision 20. |
| 22 | Built-in connector `standard-webhooks` (any sender that signs as in decision 3; `generate()` makes its secret), registered by the feature. `hmacConnector({ name, label, header, prefix?, encoding?, eventId?, eventType? })` builds a connector for a sender that signs the raw body with HMAC-SHA256 in one header. Named providers (a payment gateway, accounting, calendars) are application modules' or later units' (B17) work. | Default; gap map risk ("each named connector is its own project"). |
| 23 | The registries `connectors` and `connectorHandlers` are in `features/integrations/registry.ts`, loaded by `@hykr/api`'s index, so an application can contribute to them. What the index exports from the feature (`registry.ts`, `capability.ts`, `settings.ts`, `credentials.ts`) reads no configuration when it loads: tests set `WA_*` and other variables after importing the package. A connector name is lower case (`[a-z][a-z0-9-]*`); `whatsapp` is reserved, because `/webhooks/whatsapp` is the channel's. The feature reserves `/api/integrations`. | F5 pattern; F1 (`reserveRoutes`). |
| 24 | Configuration is read from the environment when used, in the feature's own `settings.ts` (not `config.ts`): `SECRETS_KEY`, `SECRETS_KEY_PREVIOUS`, `INTEGRATIONS_ALLOWED_HOSTS`, `INTEGRATIONS_TIMEOUT_MS`, `INTEGRATIONS_RETRY_SCHEDULE`. | Default; hot files. |
| 25 | Tables in the `app` schema, each with `tenant_id`: `integration_endpoints`, `integration_deliveries`, `integration_attempts`, `integration_connections`, `integration_inbound` (`framework/db/src/schema/integrations.ts`). Deliveries and inbound rows carry the queue prefix, like `domain_events`, so the sweeper and the queues of processes sharing a database never take each other's. Additive only; the migration is the integrator's. | Plan migration rule; gap map risk (prefix isolation). |
| 26 | Sample proof: there is no `orders` module yet, so the demo is the fixture's `features/integrations`: a capability `fixture.tasks.dates` and a read projector that hides a task's `dueOn` without it, a write hook that parks an endpoint marked `[ask]`, a `memo` entity with `traits: { webhooks: false }`, an HMAC connector (`fixture-sender`), and handlers that complete a task as the system (one fails once for now, to show the retry). The sample application's entities (to-dos, meetings, notes) send webhooks with no code of their own. When `orders` lands, its module declares its own handler and a capability for its cost fields. | Task note ("when orders exists; else fixture"). |
| 27 | `integrations.manage` is a framework capability contributed by the feature (`IntegrationsCapability`), with the generic built-in roles `owner` and `admin`; an application grants it to its own roles with `defineRole({ capabilities: ['integrations.manage'] })`. `/api/me` lists it, so a client can show the screens. | Plan boundary (generic built-ins only); F4. |
| 28 | `SECRETS_KEY` shorter than 32 characters (or an entry of `SECRETS_KEY_PREVIOUS`) stops the API and the worker when the feature starts (`checkSecretsKey()` in the service's `onModuleInit`), not in `config.ts`'s `assertConfig`, which is not the feature's file. | Default; hot files. |
| 29 | The approval card of an integrations op shows no sealed value: a read projector (`integrations.sealed`) removes `sealed` from the parked input. | Decision 8. |

## Assumptions to review

- **Who manages integrations.** Owner and admin (`integrations.manage`). Should other roles (an
  operations or accounts role) manage them, or only see the delivery log?
- **Signature scheme.** Standard Webhooks (`webhook-*` headers, `whsec_` secrets). Is there a
  receiver (an accounting tool, a marketplace) that needs another scheme?
- **Which events leave.** Every entity's events, unless the entity opts out with
  `traits: { webhooks: false }`. Should it be opt-in per entity instead?
- **Rows an endpoint reads.** An endpoint reads every record of its business and capabilities only
  hide fields. So `integrations.manage` lets a person send every record of the business elsewhere
  (and read it in the delivery log), even one their own row access would not show them: give it
  only to roles that may read the whole business. Should an endpoint instead be limited to the
  rows its creator can read, or to chosen entities?
- **Retries.** 8 attempts over about 27 hours, then `failed`, with no automatic pause of an endpoint
  that keeps failing. Is that right, and should a business be told when an endpoint fails?
- **No order.** Deliveries of one record's events can arrive out of order (retries, parallel
  workers). Does any receiver need per-record order?
- **Payload.** The record, the record before (updates and deletes), the event name and time. No actor.
  Should receivers learn who made the change (person, assistant, system)?
- **HTTPS only.** Plain `http` is refused except for hosts in `INTEGRATIONS_ALLOWED_HOSTS`. Is any
  receiver on plain http in production?
- **Inbound replay window.** A Standard Webhooks request older than 5 minutes is refused.
- **Per-connection inbound URLs.** Each connection has its own URL. Providers that send every
  account's events to one URL per app need routing by account id (deferred, decision 20).
- **Log retention.** Deliveries, attempts and inbound events are kept until their endpoint or
  connection is deleted. How long should they be kept (B18)?
- **Previous secret.** A rotated endpoint secret keeps signing for 24 hours. Long enough?
- **Inbound handler failures.** A 4xx refusal (another business's record, a missing capability)
  fails the event for good; nothing tells anyone except the inbound log. Should a failed inbound
  event notify the people who manage integrations?

## Test plan

- `framework/connectors/src/*.test.ts` (unit): HMAC sign and verify (prefix, encodings, tampering,
  length mismatch); Standard Webhooks sign and verify (the published test vector, two signatures,
  tolerance both ways, wrong secret, missing headers); the secret box (round trip, wrong associated data, tampering, an older
  key, an unknown key id, a short key); the egress guard (IPv4 and IPv6 ranges, mapped, NAT64 and
  6to4 forms, URL rules, allowed hosts, a name that resolves inside is refused at connect time, a
  redirect is not followed, the response cap, the timeout); the two connectors (verify, parse,
  ids, `generate`).
- `framework/channels/src/channels.test.ts`: the WhatsApp signature check still passes and fails as
  before.
- `framework/api/test/framework/integrations.e2e.test.ts` with the fixture's
  `src/features/integrations/` and a local receiver:
  - access: staff without `integrations.manage` get 403 (audited as denied); the assistant is
    refused; another business gets
    404 for an endpoint, its deliveries, a delivery, a retry, a connection and its inbound log;
  - endpoints: the secret is returned once and stored sealed; private, internal, `http` and
    credential URLs are refused; a capability the person lacks cannot be given, nor can an
    endpoint that has one be pointed elsewhere (pausing it can);
  - outbound: a task's events reach a matching endpoint, signed (verified with `verifyWebhook`),
    with internal columns and the hidden `dueOn` left out; an endpoint given the capability gets
    `dueOn`; the log projects a payload again for a reader without it; another business's endpoint
    gets nothing; a paused endpoint gets nothing; an entity that opts out sends nothing;
  - retries: a failing receiver is retried until it answers, every attempt is logged; one that
    keeps failing ends `failed`; a manual retry delivers it with the same `webhook-id`;
  - egress at delivery: an endpoint whose URL is changed to a loopback address behind the API's
    back is blocked when it is sent, final, and the receiver gets nothing;
  - rotation: two signatures, both verify;
  - parked write: a write hook parks an endpoint create, the approval card shows no sealed
    secret, the park is audited, and approving it creates the endpoint, which signs with the
    secret returned at the park;
  - inbound: a signed event is stored once (a redelivery is a no-op), its handler completes the
    task as the system principal (audited as `system`, channel `background`, run = inbound id); a
    bad or stale signature is 401; an unknown connector or connection, or a connection of another
    connector, is 404; a handler reaching another business's task fails final and changes nothing;
    an unhandled type is `ignored`; a sealed credential copied to another connection does not open;
    the HMAC connector verifies its header; credentials are never returned and stored sealed.

## Deferred

- A back-office or app screen for endpoints, connections and the delivery log, and typed
  `@hykr/api-client` methods for them (the HTTP API is complete).
- Pausing an endpoint automatically after repeated failures, telling the business, and a per-endpoint
  rate limit.
- Per-record ordering of deliveries.
- One shared inbound URL per connector, routed by a provider's account id (decision 20).
- Retention of deliveries, attempts and inbound events, and erasure of personal data in stored
  payloads (B18).
- Re-sealing stored secrets after `SECRETS_KEY` changes (old keys stay in `SECRETS_KEY_PREVIOUS`
  until then).
- Webhooks for approvals and other records without an entity read schema.
- OAuth flows and token refresh for connectors (B17 adds the first, Google Calendar).
- A test ("ping") delivery for a new endpoint.
