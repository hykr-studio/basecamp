# A9 + B15: push notifications and live updates

## Summary

**Push (A9).** `push` is a delivery channel of the framework (`framework/api/src/features/push`).
A signed-in person's phone registers its Expo push token for the business they work in. A
notification that lists `push` in its `channels` reaches that person's devices through Expo's push
service, with the title, body and app link the notification declares (`NotificationDef.push`).
The fallback order is the notification's own `channels` list, so the sample's to-do reminder says
`['push', 'whatsapp', 'email']`. Push "fails", and the next channel is tried, when the person has
no device here, when Expo refuses every device at once, or later, when the receipt of every
device's message reports an error. A schedule polls Expo's receipts every minute. A token Expo
calls `DeviceNotRegistered` is forgotten. The app side is an `AppPlugin` (`pushPlugin()` in
`@hykr/app`) that asks for permission after sign-in, registers the token, opens the notification's
link when it is tapped, and forgets the token at sign-out.

**Live (B15).** `GET /api/live` is a server-sent event stream for signed-in people
(`framework/api/src/features/live`). Every committed event in the outbox reaches a subscriber in
the worker, which publishes the event's ids (never its row) on a Redis channel per business. Each
API process sends an event to a connection only if that person may read the record now (the same
scoped read as `GET /api/<plural>/:id`, or a registered check for non-entity records such as
approvals). The app's `livePlugin()` reads the stream and invalidates the matching React Query
keys, so other people's changes and new approvals appear without a reload. It also refetches when
the app comes back to the foreground and after every reconnect.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | `push` is a registered `DeliveryChannel` named `push`, provided by the `push` feature, which every server loads. The name is in `NotificationChannels`, and `NotificationDef.push` is `{ title(row, reader), body(row, reader), url?(row) }`. `defineNotification` refuses `push` in `channels` without it. | Plan A9 ("a `push` DeliveryChannel", "define-notification push section"); F5 decision 20 (open channel names). |
| 2 | The framework has no fallback order of its own. The order is each notification's `channels`. The sample's to-do reminder declares `['push', 'whatsapp', 'email']`. | PRD Platform & AI 7.1, Channels ("push → WhatsApp → email order"); plan boundary section (the order is product configuration). |
| 3 | Tokens live in `channel.push_tokens`: business, person, Expo token, platform (`ios` or `android`), first and last seen. A token is registered by a signed-in person for the business their session works in. A notification reaches only devices registered in that notification's business. | Default, fail closed: a business's message never reaches a device registered under another business. Gap map owner question ("is push for staff only…"). |
| 4 | One device belongs to one person. Registering a token removes it from everyone else, in every business. | Default: a shared or handed-on phone must stop receiving the previous person's notifications. |
| 5 | Forgetting a token is `POST /api/push/tokens/forget { token }` and needs no session. Holding the token is the proof, and the call can only stop pushes to that device. It answers 204 whether or not the token was known. A signed-in person can also list their devices (`GET /api/push/tokens`, the token masked). | Default. The shell signs out before plugins' cleanups run (F2 decision 13), so the cleanup has no session. |
| 6 | A token must be an Expo push token (`Expo.isExpoPushToken`). Web push (VAPID) is not supported: the app plugin does nothing on the web. | Gap map risk ("the web build needs a separate Web Push path or must skip push"); `expo-server-sdk` 8.0.0 (F6 decision 25). |
| 7 | When push counts as failed. (a) The person has no device in this business: `unavailable`, the next channel now. (b) Expo refuses every device's message at send time: a final failure, the next channel now. (c) Expo's HTTP call fails, or every refusal is a rate or service error: a failure for now; the dispatcher retries push (3 tries, F5 decision 22), then moves on. (d) Later, the receipts of every device's message report an error: `NotifyService.fallback(meta)` moves the notification on. One device that accepts it is enough. A message that is not opened does not count as failed. | Gap map risk ("fallback needs a receipt-polling job"), owner question ("when does push fail"); F0 `DeliveryOutcome`. |
| 8 | Receipts: a `push.receipts` queue and a `push.receipts` schedule every minute. A poll reads this queue prefix's pending tickets older than `PUSH_RECEIPT_DELAY_MS` (default 60 s), asks Expo for their receipts, and records `ok` or `error`. A ticket with no receipt after a day is `expired` and counts as delivered. Tickets carry the queue prefix, as outbox rows do, so test runs and dev workers on one database never poll each other's. | Plan A9 ("Expo receipt polling schedule"); `expo-server-sdk` README (receipts are usually quick, allow up to 30 minutes, kept about a day); F5 decision 9 (prefix guard). |
| 9 | `DeviceNotRegistered`, from a ticket or a receipt, deletes that token. | Expo's guidance in the SDK's README (Apple and Google may block apps that keep sending to such devices). |
| 10 | Push sends are not written to `channel.messages`, which is the WhatsApp conversation per contact (its 24-hour window). `channel.push_tickets` is the log of push sends: business, person, token, notification, dedupe key, the fallback `meta`, status and error. | Default: no change to the WhatsApp window logic. |
| 11 | Consent and quiet hours. The dispatcher applies quiet hours before any channel, as before (not for `service` topics). Push has no consent row: the phone's notification permission is the consent. | Default, as WhatsApp's service topic. Owner question below. |
| 12 | Push text is what the notification's functions return, the same as WhatsApp and email. Field policy (A4) does not apply to it: the notification's author decides what a lock screen may show. | Default. Owner question below. |
| 13 | Expo settings are read by the feature from the environment: `EXPO_ACCESS_TOKEN` (optional, Expo's push security) and `PUSH_RECEIPT_DELAY_MS`. The SDK reads `EXPO_BASE_URL` itself (tests point it at a stand-in), so the feature imports the SDK on first use. | Default: no edits to the shared `config.ts`. |
| 14 | Personal data. Erasing a person deletes their tokens and push tickets. Their export lists their devices (platform, dates, the token's first characters only: its prefix and 6 characters of its id, the device list's mask, V7). Contacts have no tokens. | F5 decision 25 (erasure and export contributors); plan B18 direction. |
| 15 | App side: `pushPlugin({ projectId?, androidChannel? })`, an `AppPlugin`. After sign-in on a physical iOS or Android device it asks for permission (once; a refusal is respected), creates the Android channel `default`, gets the Expo push token (the EAS project id from the option or the app config), and registers it. A tapped notification opens its `url` when that is an app path (`/…`), also when the tap started the app. In the foreground the notification shows as a banner. Sign-out forgets the token. | Plan A9 (`app/features/push`); F2 decision 11 (plugin slots). |
| 16 | `application/mobile/app.json` adds the `expo-notifications` config plugin. There is no EAS project id, so a dev build cannot get a token until EAS is set up; the plugin logs and stops. | F6 decision 26 (each gap adds its plugin); gap map risk (no `eas.json`). |
| 17 | Live updates are a server-sent event stream, `GET /api/live`, for people only (`PrincipalGuard`, `HumanOnlyGuard`; a session cookie, or the Cookie header on native). The client reads it with streaming `fetch` (Expo's `fetch` on native, the browser's on the web), not `EventSource`, which cannot send the native app's Cookie header. | Plan B15 ("SSE"); gap map ("React Native has no EventSource"). |
| 18 | Source: the durable outbox. The subscriber `live.relay` (on `*`, in the worker) publishes `{ event, name, tenantId, resourceType, resourceId, actor, subject }` to the Redis channel `<BULL_PREFIX>:live:<tenantId>`. The row is never published. Each API process subscribes to the channels of the businesses it has connections for. | Plan B15 ("Redis pub/sub fed by an outbox subscriber"); F5 decisions 9, 10 and 13; gap map risk (events raised in the worker must reach the API). |
| 19 | Per connection, an event is sent only to the same business, and only when that person may read the record now: an entity's record through `def.repo.find(db, p, id)`, which is the scoped read `GET` uses (the role grants of `accessFor`/`rowAllowed`, plus every plugin's scope); any other record type through a registered `liveResources` check. The framework registers `approval`, checked with `ApprovalService.get` (the approvals a person may decide). A type with no check is never sent. | Plan B15 ("filtered per connection by access"); gap map ("filtered with the same access grants as list/get"). The entity definition does not expose its access map, and `define-entity.ts` is not this unit's to edit (hot-file table), so the scoped repo read stands in for a pure `accessFor`/`rowAllowed` call. It is stricter: plugin scopes count too. |
| 20 | A record that cannot be read now (deleted, or moved out of the person's reach) is announced only to connections already told about that record on this connection, and to the person who made the change (the actor, or the person an assistant acted for). Everyone else sees it go at their next refetch. | Default, fail closed: a deleted record can no longer be checked against the reader's access. |
| 21 | Ids only. A connection receives `{ name, type, id }` (the event name, the record type and its id). It never receives fields. | Plan B15 ("carry ids only"); `DomainEventEnvelope` doc comment. |
| 22 | The stream sends `ready` when it opens and a comment every 25 s. A connection is closed after `LIVE_MAX_MS` (default 15 minutes), so a revoked session or changed roles take effect when the client reconnects. A person may hold at most 8 streams per API process; another one is answered 429. Checks are cached per person within one event. | Default (proxies drop idle streams; sessions and roles are read when a request starts). |
| 23 | Client: `livePlugin({ onEvent? })`, an `AppPlugin`. An entity event invalidates that entity's plural and `history`; an event that is not a create, update or delete also invalidates what the type's commands declare they touch; an approval event invalidates `approvals` and `['approval', id]`. Invalidations are batched for 250 ms. Every reconnect invalidates all queries (events missed meanwhile). Reconnects back off from 1 s to 30 s, and happen at once when the app returns to the foreground. React Query's `focusManager` follows `AppState` on native (the web uses page visibility already), so stale screens refetch on focus. | Plan B15 ("app invalidation on events and focus"); gap map ("refetch all on reconnect"). |
| 24 | An event held back by an undo window (`available_at`) goes live when it is relayed, after the window. An undone write is never announced. | F3/F5 outbox semantics. |
| 25 | The back office keeps polling. Its inbox and conversations are channel state (`channel.messages`, handoffs), which writes no outbox events; streaming them needs the inbound and send paths to publish, and those processors are other units' files. | Task note ("replace back-office polling where easy"); hot-file table (`inbound.processor.ts`). |

## Assumptions to review

- **Who gets push?** Any person with an account who installs the app and allows notifications,
  staff or customer. Should customers (participants) get push at all, or WhatsApp only?
- **Expo's push service.** Messages pass through Expo, then Apple or Google, outside India. Is that
  acceptable for production, or must the product send through FCM and APNs directly (a second
  sender behind the same channel)?
- **When push has failed.** No device, a refusal, or an error receipt moves on to the next channel.
  An unread push does not. Should "not opened within N minutes" also fall back to WhatsApp?
- **Receipt timing.** Receipts are checked a minute after a send, every minute. A failure is found
  1 to 2 minutes later, so the next channel is that much later. Is that acceptable for reminders?
- **Quiet hours and service pushes.** Service-topic notifications ignore quiet hours on every
  channel, push included. Should push respect quiet hours even for service topics?
- **Lock-screen text.** Push text is not filtered by field policy. Should push carry only a neutral
  title ("You have a reminder") for some notifications?
- **Per-business devices.** A person in two businesses registers the device once per business (the
  app registers again after a switch). Is per-business the right scope?
- **Live coverage of deletions.** A deletion reaches only people told about the record earlier on
  that stream, and the person who deleted it. Others see it go at their next refetch (focus,
  reconnect, their own write). Is that enough, or must every reader see deletions at once (which
  needs the entity's access map exposed for a check on the deleted row)?
- **Live latency.** Events go out after the worker's outbox poll (up to a second) and a queue job.
  Is about 1 to 2 seconds acceptable?
- **Stream limits.** 8 streams per person per process, 15 minutes per stream. Right numbers?
- **Back office.** It still polls its inbox every 10 s and an open conversation every 5 s. Should
  inbound messages and handoffs publish live events too?

## API sketch

```ts
// @hykr/notifications
interface NotificationChannels { whatsapp: true; email: true; push: true }
interface NotificationDef<R> {
  push?: {
    title: (row: R, reader: Reader) => string;
    body: (row: R, reader: Reader) => string;
    /** The app path a tap opens: '/todos'. */
    url?: (row: R) => string;
  };
}

// @hykr/contracts
RegisterPushToken = z.object({ token, platform: z.enum(['ios', 'android']) })
ForgetPushToken = z.object({ token })
PushDevice = z.object({ id, platform, token /* masked */, createdAt, lastSeenAt })
LiveEvent = z.object({ name, type, id })          // what one live message carries
reserveRoutes('push', 'live')

// HTTP
POST /api/push/tokens          { token, platform } -> 201 PushDevice (people only)
GET  /api/push/tokens          -> PushDevice[] (mine, in this business)
POST /api/push/tokens/forget   { token } -> 204 (no session needed)
GET  /api/live                 -> text/event-stream: `event: ready`, `event: change` + LiveEvent

// @hykr/api-client
api.push.register({ token, platform }); api.push.devices(); api.push.forget(token)
api.live({ signal, onOpen?, onEvent })   // resolves when the stream ends

// @hykr/api
interface LiveResource { type: string; visible(p: Principal, id: string, ctx: ServerContext): Promise<boolean> }
liveResources                             // collects 'liveResources'; entities need none
// features: pushFeature (channel 'push', queue + schedule 'push.receipts', contributors),
//           liveFeature (subscriber 'live.relay', GET /api/live, liveResources: approval)

// @hykr/app
pushPlugin(opts?: { projectId?: string; androidChannel?: string }): AppPlugin
livePlugin(opts?: { onEvent?: (e: LiveEvent, client: QueryClient) => void }): AppPlugin
liveKeysFor(e: LiveEvent, catalog): string[][]   // the query keys an event invalidates (pure)
```

## Test plan

- `framework/notifications/src/notifications.test.ts`: `push` in `channels` without `push`
  content throws; with it, it defines.
- `framework/api/test/framework/push.e2e.test.ts` (fixture `features/push`, a stand-in Expo push
  service through `EXPO_BASE_URL`, Mailpit):
  - register: a non-Expo token is 400; the device is listed with the token masked; the other
    business's person does not see it; registering the same token as another person moves it;
    forget needs no session and answers 204 either way; an agent cannot register;
  - a notification with `push` first reaches the person's device with its title, body and link,
    and not the device of a person of another business; no device: email at once;
  - Expo refuses with `DeviceNotRegistered`: the token is gone and email goes at once;
  - a ticket whose receipt is an error: after a poll, email (fallback) and the ticket is `error`;
    an `ok` receipt sends no email;
  - erasing the person deletes their tokens and tickets.
- `framework/api/test/framework/live.e2e.test.ts` (fixture app, the real outbox, relay and Redis):
  - no session: 401; the assistant's key: 403;
  - Ana's stream gets `task.created` for her task, with exactly `name`, `type`, `id`;
  - a person of another business gets nothing of Ana's;
  - in Ana's business, staff (own rows) do not get Ana's task; ops (the whole business) do;
  - a deletion reaches Ana (who deleted it) and ops (told earlier), not staff;
  - the assistant's delete parks: Ana's stream gets `approval.requested` with the approval id,
    the parked write is audited, and the approval is listed for her;
  - a contributed `liveResources` check decides a non-entity type; an unknown type is never sent.
- `framework/app/src/features/live/keys.test.ts` (unit): the keys an entity, command, approval
  and unknown event invalidate; batching.
- `framework/api-client/src/live.test.ts` (unit): the SSE reader parses `change` events across
  chunk boundaries, skips comments and other events.
- Existing suites stay green: delivery, notifications, runtime, whatsapp, write-path, the
  application's tests.

## Deferred

- Web push (VAPID) for people working in a browser.
- Sending through FCM and APNs directly instead of Expo.
- Fallback when a push is not opened within a time.
- Streaming the back office's inbox and conversations (decision 25).
- Replaying missed events with `Last-Event-ID`: a reconnect refetches everything instead.
- A per-tenant setting to turn push off for a business.
