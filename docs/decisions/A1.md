# A1: MCP server and OAuth 2.1

## Summary

People connect an outside AI client (Claude, ChatGPT, an IDE) to the application over the Model
Context Protocol. The framework's `mcp` feature (`framework/api/src/features/mcp/`) serves:

- an OAuth 2.1 authorization server, Better Auth's `@better-auth/oauth-provider` plugin
  contributed as an auth plugin: dynamic client registration, authorization code with PKCE,
  refresh tokens, revocation, server metadata, and a sign-in page and a consent screen served by
  the API;
- an MCP endpoint, `/mcp`, served by `@mastra/mcp`'s `MCPServer` over Streamable HTTP, with its
  protected-resource metadata and a `WWW-Authenticate` challenge;
- a bearer identity provider (F4's chain): a token acts for its person, in the business they
  consented in, as the agent `mcp:<client id>`, on the `mcp` channel, limited to its scopes;
- consolidated tools: two per module (`<module>_read`, `<module>_write`), so a product of 10 to
  20 modules has 20 to 40 tools. `<module>_write` runs the module's creates, updates, deletes,
  commands and state transitions. They call the same HTTP API with the token, so tenancy, access,
  field hiding, approvals and audit are the API's. A write that parks answers with a link to the
  request in the app (`<APP_URL>/approvals/<id>`), where a person decides it;
- the person's connections: `GET /api/mcp/connections`, `DELETE /api/mcp/connections/:clientId`.

Scopes are per module (`<module>:read`, `<module>:write`) and come from the application's
modules. The API enforces them for every scoped credential, on every route (`PrincipalGuard`),
not only in the tool list. Domain names are deployment configuration (`MCP_URL`, `BETTER_AUTH_URL`,
`APP_URL`).

| 9 | The MCP endpoint is `/mcp` on the API (any method), `@mastra/mcp` 2.1.2's `MCPServer.startHTTP`. It serves MCP revision 2026-07-28 only: stateless requests, no session header. The issuer is `<BETTER_AUTH_URL>/api/auth`. | RFC 8414, RFC 9728; MCP authorization spec. |
| 11 | Domain names are deployment configuration: `MCP_URL` (the MCP endpoint's public URL and the token audience, default `<BETTER_AUTH_URL>/mcp`), `BETTER_AUTH_URL` (issuer, pages) and `APP_URL` (approval links). | 12 | Tools are consolidated per module: `<module>_read` (`{ entity, id }` gets one record; `{ entity, query }` lists with the list grammar; `{ entity, summary }` counts and totals) and `<module>_write` (`{ action, input }`, where `action` is one of the module's tool ids: `create-<name>`, `update-<name>`, `delete-<name>`, a command's tool, and `transition-<plural>` for each of its entities with states). The consent screen checks the query's signature, needs the session, names the client (as it registered itself: "unverified"), the business and each module asked for, with read/write choices; the person may narrow them or deny. No sign-up there: an account is made in the app. | Gap A1 "consent screen"; default: no Expo dependency for a browser flow that starts in another app. |
| 16 | Connections: `GET /api/mcp/connections` lists the person's consents in the current business (client, scopes, when); `DELETE /api/mcp/connections/:clientId` deletes the consent, which ends every token of that client for the person in that business (decision 23), and revokes its access and refresh tokens as cleanup. | 18 | Lifetimes are Better Auth's defaults: access token 1 hour, refresh token 30 days, code 10 minutes. | Default. |
| 19 | Better Auth's plugin needs seven tables (`oauth_client`, `oauth_resource`, `oauth_client_resource`, `oauth_access_token`, `oauth_refresh_token`, `oauth_consent`, `oauth_client_assertion`) in `public`, next to Better Auth's own, in `framework/db/src/schema/oauth.ts`. `AuthPlugin` gains `schema` (its tables for the adapter), and `infra/auth.ts` adds them to the adapter's schema: a two-line hunk, the only change A1 makes there. `AppModule` installs the features' contributions before it builds Better Auth (`authWithFeatures()` in `app.module.ts`, which is not a hot file), so a feature's auth plugin is never missed. `auth.ts` is a hot file A1 is not listed for (F4 → B7 → B19): this is a deviation from the hot-file table, the first item under "Assumptions to review", and the integrator records A1 in that file's editor order when this merges. | Plan A1 row (Better Auth plugin); hot-file table (`auth.ts`); precedent A4 decision 12. |
| 20 | No scripted-model scripts: the MCP tools are not the assistant's, and the server's model never calls them. | A2 decision 19. |
| 21 | Throttling, audit and history treat an MCP client like any agent. Audit actor `mcp:<client id>` with channel `mcp` and a run id per tool call. Throttle: every tool call reaches the API from the API's own process (one address), so `CallerThrottlerGuard` keys a request by its credential, not its IP: the agent key as before, and any credential a contributed identity provider recognises (`identityProviders`, asked in PrincipalGuard's order) as `agent:<agent id>:user:<person>@<business>` (for MCP, `agent:mcp:<client id>:user:<person>@<business>`). A credential its provider refuses falls back to the IP, as a wrong agent key does. The token is checked once per request (`grantOf`, memoised on the request's headers) for the throttle, PrincipalGuard and `/mcp`. | F4; review finding (fix round 1: every MCP call shared one bucket, across businesses). |
| 22 | `@hykr/api/testing` gains `connectMcp(person, scope)`: a client that registers, gets the person's consent and a token (PKCE), then an `MCPClient` over HTTP with `tools()` and `call()`. The framework's and the application's tests use it. | Default: one way to connect in tests, as a real client does. |
| 23 | The consent row is the source of truth for a connection. `verifyAccessToken` joins `oauth_consent` on the token's client, person and business and refuses a token without one, at `/mcp` and on the REST API. Better Auth's refresh grant rotates the old refresh token, then inserts the new refresh and access tokens, in separate statements outside any transaction (upstream marks the race `TODO(invalidate-family-race)`), and it never reads the consent; an authorization code issued before a disconnect can also be redeemed after it, within its ten minutes. Revoking rows alone would lose to either: the late tokens are inserted unrevoked, and with the consent gone the person sees nothing left to disconnect. With the join they are dead. Every client has a consent: dynamic registration refuses `skip_consent` (the provider's schema), and A1 registers no client any other way. A client created with `skipConsent` by an operator would get no consent row, so its tokens are refused (fail closed) until that is handled explicitly. | Review finding (fix round 1); Better Auth 1.7.7 `introspect-*.mjs` refresh grant; default (fail closed). |

## Assumptions to review

- **A1 edits a hot file it is not listed for.** The plan lists `auth.ts`'s editors as
  F4 → B7 → B19, and everyone else plugs in through hooks. A1 changes
  `framework/api/src/infra/auth.ts` in one place (decision 19): it spreads each auth plugin's
  `schema` (`authPlugins.all().map((p) => p.schema)`) into the drizzle adapter's `schema`, two
  lines, with no import change (`authPlugins` was imported already). This cannot be a hook:
  Better Auth's drizzle adapter (`@better-auth/drizzle-adapter` 1.7.7) reads only
  `config.schema || db._.fullSchema` and has no per-model fallback, so the `oauth_*` tables must
  be in the object `auth.ts` passes, and F4's `AuthPlugin` seam gave no way to add them.
  Installing the features' contributions before Better Auth is built (without which every
  framework feature's auth plugin, the MCP provider's and A11's `custom-domains`, is left out)
  moved to `AppModule` (`app.module.ts`, not a hot file). B7 has merged; its `auth.ts` hunks (the
  `createsBusinessOnSignUp` import and sign-up hook) and A1's merge cleanly. Accept A1 into the
  file's editor order (F4 → A1 → B7 → B19, or F4 → B7 → A1 → B19 now that B7 is in)? On merge,
  the integrator records A1 in the `auth.ts` row of the plan's hot-file table, as was done for
  A4's `define-entity.ts` deviation, so that B19 rebases on it knowingly.
- **The framework features' tools over MCP.** An MCP client gets each module's entities,
  commands and state transitions. It does not get the framework features' assistant tools:
  attaching and reading files (`files`), making documents (`documents`), a business's jobs
  (`jobs`), memory recall (`memory`), comments and mentions (`comments`), nor the platform's
  commands (handoff, notify, saved pages). Their routes declare no scope, so a token is refused
  there. Which of these should an outside client have, and under which scope (the record's
  module's, or a scope of their own such as `files:read`)?
- **Protocol revision.** `@mastra/mcp` 2.x serves only MCP 2026-07-28; a client that speaks only
  an older revision is refused. Should we also serve older clients (a `@mastra/mcp` 1.x server
  beside it)? Which clients must work at launch (Claude, ChatGPT, Cursor)?
- **Who may connect.** Any signed-up person who is a member of a business, customers included,
  reaches what they reach in the app. Should customers (homeowners) be refused?
- **Open registration.** Any client may register itself. Should registration need an initial
  access token, or should only listed clients (CIMD) be trusted?
- **Write includes read.** `<module>:write` also reads that module. Separate scopes?
- **Every park links.** Every parked write answers with the app link, not only the highest
  level. Is a lower level (an external send) better waited on silently?
- **One business per connection.** The token works in the business the resolver gives the person
  at consent (their default one, else where they last became a participant). Should the consent
  screen let a person in several businesses choose (B7's switcher is in the app now)?
- **Throttle per client.** An MCP client gets the API's limit (120 calls a minute per route) for
  each person and business it acts for, like the assistant. Should outside clients get a lower
  limit, or one per business across all its clients?
- **Lifetimes.** One hour access, thirty days refresh. Shorter for some modules (Better Auth's
  `scopeExpirations`)?
- **Branding.** The consent screen shows the application's name, not the business's branding
  (A11's white label). Should it?
- **Credits.** MCP tool calls count as tool calls and stop when the business is paused. Right?
- **A token that outlived a disconnect.** A refresh racing a disconnect leaves unrevoked tokens
  that are dead because the consent is gone (decision 23). If the person later connects that
  same client again within thirty days, those tokens work again, under the new consent (its
  scopes, the same client, person and business). Acceptable, or should connecting again revoke
  every older token of that client first?
- **Signing out.** Signing out of the browser does not disconnect a client; the person
  disconnects it (`DELETE /api/mcp/connections/:clientId`) or it lapses when its refresh token
  does (thirty days). Should signing out everywhere also revoke every MCP token?

## API sketch

```ts
// @hykr/contracts
scopeOf(module, access: 'read' | 'write'): string        // 'orders:write'
moduleScopes(modules: readonly { name: string }[]): string[]   // read and write per module
scopeCovers(scopes, module, access): boolean             // write covers read
scopesWithin(scopes, granted): string[]                  // cut down to what granted covers

// @hykr/core
RequireScope({ module, access }) / scopeOfRoute           // route metadata; generated routes set it
AgentIdentity.scopes                                      // present: a scoped credential (enforced)

// @hykr/api
AuthPlugin.schema?: Record<string, Table>                 // its tables for Better Auth's adapter
mcpFeature                                                // features/mcp
verifyAccessToken(db, token, resource): McpGrant | null  // needs the consent; scopes cut to it
mcpToolsFor(catalog, scopes, call): Record<string, Tool>  // the consolidated tools

// HTTP
GET  /.well-known/oauth-protected-resource[/mcp]          // RFC 9728
GET  /.well-known/oauth-authorization-server[/api/auth]   // RFC 8414 (Better Auth's)
POST /api/auth/oauth2/register | GET /api/auth/oauth2/authorize | POST /api/auth/oauth2/token
POST /api/auth/oauth2/consent | POST /api/auth/oauth2/revoke    // Better Auth's
GET  /oauth/sign-in?<signed query>  GET /oauth/consent?<signed query>   // pages
ALL  /mcp                                                 // MCP 2026-07-28, Bearer mcp_at_…
GET  /api/mcp/connections  DELETE /api/mcp/connections/:clientId   // people only

// Env
MCP=off                      // no MCP for this deployment
MCP_URL=https://mcp.example.com/mcp    // default <BETTER_AUTH_URL>/mcp
```

## Deferred

- The framework features' assistant tools over MCP: files (attach, read), documents, jobs,
  memory recall, comments and mentions, and the platform's commands (handoff, notify, saved
  pages). Their routes declare no scope, so a token is refused there (owner question above).

- Choosing the business on the consent screen (B7's tenant switcher); one token per business.
- Clients that skip consent (`skipConsent`, an operator's first-party client): refused today
  (decision 23); they need an explicit rule before one is created.
- Refusing the refresh grant itself for a client with no consent (a `before` hook on
  `/oauth2/token`): its tokens are already dead at the API, so only the provider's rotation
  continues.
- A back-office view of every client connected in a business (each person sees their own in the
  app).
- Client ID metadata documents (`@better-auth/cimd`), the device grant, DPoP, JWT access tokens.
- Serving MCP revisions before 2026-07-28.
- MCP Apps cards (PRD P2) and resources or prompts.
- ~~Hiding the tools of a module a business's feature flag switches off (A11)~~: done in H3
  (`docs/decisions/H3.md`): the tool list and the write actions follow the token's business's
  flags, failing closed, and every tool carries MCP annotations (read-only, destructive).
- A client registered before a module existed keeps the scopes it registered with: it registers
  again to ask for the new module.
- CORS for browser-based MCP clients: `/mcp` answers only the application's web origins.
