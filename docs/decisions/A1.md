# A1: MCP server and OAuth 2.1

## Summary

People connect an outside AI client (Claude, ChatGPT, an IDE) to the application over the Model
Context Protocol. The framework's `mcp` feature (`framework/api/src/features/mcp/`) serves:

- an OAuth 2.1 authorization server, Better Auth's `@better-auth/oauth-provider` plugin
  contributed as an auth plugin: dynamic client registration, authorization code with PKCE,
  refresh tokens, revocation, server metadata, and a sign-in page and a consent screen served by
  the API;
- an MCP endpoint, `/mcp`, served by `@mastra/mcp`'s `MCPServer` over Streamable HTTP, with its
  protected-resource metadata and a `WWW-Authenticate` challenge;
- a bearer identity provider (F4's chain): a token acts for its person, in the business they
  consented in, as the agent `mcp:<client id>`, on the `mcp` channel, limited to its scopes;
- consolidated tools: two per module (`<module>_read`, `<module>_write`), so a product of 10 to
  20 modules has 20 to 40 tools. They call the same HTTP API with the token, so tenancy, access,
  field hiding, approvals and audit are the API's. A write that parks answers with a link to the
  request in the app (`<APP_URL>/approvals/<id>`), where a person decides it;
- the person's connections: `GET /api/mcp/connections`, `DELETE /api/mcp/connections/:clientId`.

Scopes are per module (`<module>:read`, `<module>:write`) and come from the application's
modules. The API enforces them for every scoped credential, on every route (`PrincipalGuard`),
not only in the tool list. Domain names are deployment configuration (`MCP_URL`, `BETTER_AUTH_URL`,
`APP_URL`).

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | One framework feature, `features/mcp` (`defineFeature`), owns everything: the OAuth plugin and its tables, the identity provider, the MCP endpoint, the metadata, the pages, the connections API and its phrases. It reserves `/api/mcp`. `MCP=off` switches it off for a deployment (no routes, no plugin, no provider). | Plan A1 row ("features/mcp"); conventions "a feature is a Nest module at framework/api/src/features/<x>/". |
| 2 | OAuth 2.1 is `@better-auth/oauth-provider` 1.7.7 (Better Auth 1.7.7 has no `mcp` or `oidc-provider` plugin; F6 added this package for A1). Grants: `authorization_code` and `refresh_token` only. No `client_credentials`: every token acts for a person. PKCE `S256` is required for public clients and, by Better Auth's default, for dynamically registered confidential ones. | Plan A1 ("verify it exists in 1.7.7"); F6 decision 25; PRD 7.2 "Better Auth plus OAuth 2.1 for MCP". |
| 3 | Access tokens are opaque (`disableJwtPlugin: true`), stored hashed, with the prefixes `mcp_at_` (access) and `mcp_rt_` (refresh). The prefix tells the `mcp` identity provider its tokens from another provider's bearer tokens (a token without it is not its credential: `null`, the next provider is asked). No JWT plugin, no JWKS table, no ID tokens (no `openid` scope). | Default: the smallest surface; revocation takes effect at once (a JWT would live until it expires). |
| 4 | Dynamic client registration (RFC 7591) is open (`/api/auth/oauth2/register` without a session), as MCP clients expect. A registration that names no `application_type` and whose redirects are all a native app's (http on `localhost`, `127.0.0.1` or `[::1]`, or a reverse-domain app scheme) is registered as `native` (RFC 8252): desktop and IDE clients send loopback redirects without saying so, and the provider would take them for web clients and refuse them. Anything else is checked as sent (web clients need https). Client ID metadata documents (CIMD) and the device grant are not enabled. | Gap A1 "dynamic client registration"; MCP clients register themselves. Better Auth 1.7.7 refuses loopback redirects for `web` clients. CIMD needs `@better-auth/cimd`, not installed. |
| 5 | Scopes are per module: `<module>:read` and `<module>:write` for every application module (the catalog's `modules`, so the framework holds no list), plus `offline_access` (refresh tokens). `write` includes `read`. The framework's own `platform` specs (saved pages, `notify.send`, `handoff.request`) have no scope: they are the app's own surfaces. | PRD 7.1 "scopes per module"; F1 module stamp (`spec.module`). Default for write ⊇ read: a client that may change a module's records must be able to find them. |
| 6 | A token acts in one business: the person's default business when they consent (Better Auth's `referenceId`, from `postLogin.consentReferenceId`). The consent screen names it. Consent is remembered per client, person and business. | Default (fail closed: the business is the server's fact, never the client's); choosing among several businesses is deferred to the tenant switcher (B7). |
| 7 | The bearer identity (`mcp` provider): agent id `mcp:<client id>`, acting for the token's user, `tenantId` fixed to the token's business, channel `mcp` (assurance `session`, F4 decision 5), `scopes` from the token, `agentVersion` the client's registered name (truncated). A token is valid when its hash is stored, it is not revoked or expired, its client exists and is enabled, the session it was issued in (if any) is alive, and its resources are none or include `MCP_URL`. These are Better Auth's own introspection rules. The resolver then checks the person is still a member of that business (403 `not_a_member` otherwise). | Gap map A1 risk "token-derived principals in PrincipalGuard are safer" than the agent key acting for anyone; F4 decisions 14 to 16. |
| 8 | Scopes are enforced by the API for any scoped credential (an identity whose provider returns `scopes`, the MCP token or any contributed provider's): `PrincipalGuard` lets it reach only routes that declare a scope, and only with that scope. The generated entity routes declare `<module>:read` (list, summary, get) or `<module>:write` (create, update, delete), and command routes `<module>:write`. Every other route (`/api/me`, history, approvals, files, members, chat…) answers 403 `out_of_scope`. Unscoped credentials (the agent key, the voice relay) and sessions are unchanged. The fixture's bearer provider now names the scopes its tests use. | F4 decision 18 ("A1 defines MCP scopes and their check"). Default: fail closed, a token reaches no route nobody scoped. |
| 9 | The MCP endpoint is `/mcp` on the API (any method), `@mastra/mcp` 2.1.2's `MCPServer.startHTTP`. It serves MCP revision 2026-07-28 only: stateless requests, no session header. A request without a valid token gets 401 with `WWW-Authenticate: Bearer resource_metadata="<base>/.well-known/oauth-protected-resource/mcp"` (RFC 9728). Host and Origin checks (DNS rebinding) are off: every request needs a bearer token a page cannot get. | Plan A1 ("MCPServer over HTTP"); F6 decision 17 (2.1.2 is the newest that takes `@mastra/core` 1.74). |
| 10 | Metadata: `/.well-known/oauth-protected-resource` and `/.well-known/oauth-protected-resource/mcp` (resource `MCP_URL`, the authorization server, the scopes); `/.well-known/oauth-authorization-server` and `/.well-known/oauth-authorization-server/api/auth` (Better Auth's, RFC 8414 path insertion). The issuer is `<BETTER_AUTH_URL>/api/auth`. | RFC 8414, RFC 9728; MCP authorization spec. |
| 11 | Domain names are deployment configuration: `MCP_URL` (the MCP endpoint's public URL and the token audience, default `<BETTER_AUTH_URL>/mcp`), `BETTER_AUTH_URL` (issuer, pages) and `APP_URL` (approval links). Nothing in code names a host. | Gap A1 "domain names are deployment config"; PRD "mcp.interioring.com" is the product's. |
| 12 | Tools are consolidated per module: `<module>_read` (`{ entity, id }` gets one record; `{ entity, query }` lists with the list grammar; `{ entity, summary }` counts and totals) and `<module>_write` (`{ action, input }`, where `action` is one of the module's tool ids: `create-<name>`, `update-<name>`, `delete-<name>`, a command's tool). Only actions exposed to agents (`expose: 'all'`, as for the assistant). A module with nothing to read or write gives no tool of that kind. The tool list is per token: a module the token has no scope for gives none, and `read` gives no `_write`. The assistant's own tools (`list-todos`…) are unchanged. | PRD 7.1 "20–40 consolidated tools"; gap map risk "consolidating breaks the scripted model's scripts: a separate MCP tool set avoids this". |
| 13 | Results are text (MCP `content`), never present intents or cards: a short sentence, then the API's JSON answer (already projected for the person). A refusal is an error result (`isError`) with the status, rule and reason. | Gap map A1 risk "an external MCP client renders none of this, so it needs a text-only result mode". |
| 14 | A write that parks answers with the request's link, `<APP_URL>/approvals/<id>`, who decides it, its level and when it expires. Every park does: an MCP client can never decide (`HumanOnlyGuard`), so each waits for a person in the app (or on WhatsApp where the level allows). The tier-3 meaning (money, legal, irreversible; a named human, `channels: ['app']`) is the application's level, not the framework's. The app already serves `/approvals/:id` (A5), and WhatsApp already links there, so `inbound.processor.ts` needs no change. | PRD 7.1 "tier-3 tools return an approval link"; plan boundary (levels are the app's). |
| 15 | The sign-in page (`/oauth/sign-in`) and the consent screen (`/oauth/consent`) are plain HTML served by the API, in the person's language (`Accept-Language` or `?lang`, en/hi/te), named with the application's name. Sign-in posts to Better Auth's email sign-in with the signed `oauth_query`, which continues the authorization. The consent screen checks the query's signature, needs the session, names the client (as it registered itself: "unverified"), the business and each module asked for, with read/write choices; the person may narrow them or deny. No sign-up there: an account is made in the app. | Gap A1 "consent screen"; default: no Expo dependency for a browser flow that starts in another app. |
| 16 | Connections: `GET /api/mcp/connections` lists the person's consents in the current business (client, scopes, when); `DELETE /api/mcp/connections/:clientId` deletes the consent and revokes that client's access and refresh tokens for the person in that business. People only, audited (`mcp.connection.revoke`). | Gap map owner question "token lifetime and revocation UI". |
| 17 | Credits: each MCP tool call checks the business's `tool_calls` meter (variant `mcp`) and is refused when the business is paused (402 text), then records one use (ref: the call's run id). The client's model tokens are not ours to meter. | PRD 7.1 "tool calls metered"; A3's `metering()` slot. |
| 18 | Lifetimes are Better Auth's defaults: access token 1 hour, refresh token 30 days, code 10 minutes. | Default. |
| 19 | Better Auth's plugin needs seven tables (`oauth_client`, `oauth_resource`, `oauth_client_resource`, `oauth_access_token`, `oauth_refresh_token`, `oauth_consent`, `oauth_client_assertion`) in `public`, next to Better Auth's own, in `framework/db/src/schema/oauth.ts`. `AuthPlugin` gains `schema` (its tables for the adapter), and `infra/auth.ts` (hot: F4 → B7 → B19) adds them in two lines; `getAuth()` installs the features' contributions before building, so a feature's auth plugin is never missed. | Plan A1 row (Better Auth plugin); hot-file rule (smallest edit, logged here). |
| 20 | No scripted-model scripts: the MCP tools are not the assistant's, and the server's model never calls them. | A2 decision 19. |
| 21 | Throttling, audit and history treat an MCP client like any agent: throttle key `agent:mcp:<client>:<person>`, audit actor `mcp:<client id>` with channel `mcp` and a run id per tool call. | F4. |
| 22 | `@hykr/api/testing` gains `connectMcp(person, scope)`: a client that registers, gets the person's consent and a token (PKCE), then an `MCPClient` over HTTP with `tools()` and `call()`. The framework's and the application's tests use it. | Default: one way to connect in tests, as a real client does. |

## Assumptions to review

- **Protocol revision.** `@mastra/mcp` 2.x serves only MCP 2026-07-28; a client that speaks only
  an older revision is refused. Should we also serve older clients (a `@mastra/mcp` 1.x server
  beside it)? Which clients must work at launch (Claude, ChatGPT, Cursor)?
- **Who may connect.** Any signed-up person who is a member of a business, customers included,
  reaches what they reach in the app. Should customers (homeowners) be refused?
- **Open registration.** Any client may register itself. Should registration need an initial
  access token, or should only listed clients (CIMD) be trusted?
- **Write includes read.** `<module>:write` also reads that module. Separate scopes?
- **Every park links.** Every parked write answers with the app link, not only the highest
  level. Is a lower level (an external send) better waited on silently?
- **One business per connection.** The token works in the person's default business at consent.
  Should the consent screen let a person in several businesses choose?
- **Lifetimes.** One hour access, thirty days refresh. Shorter for some modules (Better Auth's
  `scopeExpirations`)?
- **Branding.** The consent screen shows the application's name, not the business's branding
  (A11's white label). Should it?
- **Credits.** MCP tool calls count as tool calls and stop when the business is paused. Right?

## API sketch

```ts
// @hykr/contracts
scopeOf(module, access: 'read' | 'write'): string        // 'orders:write'
moduleScopes(modules: readonly { name: string }[]): string[]   // read and write per module
scopeCovers(scopes, module, access): boolean             // write covers read

// @hykr/core
RequireScope({ module, access }) / scopeOfRoute           // route metadata; generated routes set it
AgentIdentity.scopes                                      // present: a scoped credential (enforced)

// @hykr/api
AuthPlugin.schema?: Record<string, Table>                 // its tables for Better Auth's adapter
mcpFeature                                                // features/mcp
McpTokens.verify(token): McpGrant | null                  // used by the identity provider
mcpToolsFor(catalog, scopes, call): Record<string, Tool>  // the consolidated tools

// HTTP
GET  /.well-known/oauth-protected-resource[/mcp]          // RFC 9728
GET  /.well-known/oauth-authorization-server[/api/auth]   // RFC 8414 (Better Auth's)
POST /api/auth/oauth2/register | GET /api/auth/oauth2/authorize | POST /api/auth/oauth2/token
POST /api/auth/oauth2/consent | POST /api/auth/oauth2/revoke    // Better Auth's
GET  /oauth/sign-in?<signed query>  GET /oauth/consent?<signed query>   // pages
ALL  /mcp                                                 // MCP 2026-07-28, Bearer mcp_at_…
GET  /api/mcp/connections  DELETE /api/mcp/connections/:clientId   // people only

// Env
MCP=off                      // no MCP for this deployment
MCP_URL=https://mcp.example.com/mcp    // default <BETTER_AUTH_URL>/mcp
```

## Test plan

- `framework/contracts/src/scopes.test.ts`: scope names, `write` covers `read`, module lists.
- `framework/api/test/framework/mcp.e2e.test.ts` (fixture app, `features/mcp` fixture: a staff
  projector hiding a task's due date):
  - metadata: protected resource and authorization server documents; `/mcp` without a token is
    401 with `WWW-Authenticate` naming the metadata; a wrong or unknown token is 401;
  - OAuth: dynamic registration; authorize without a session redirects to the sign-in page;
    sign-in with the signed query continues to the consent screen; the consent page lists the
    client, the business and the modules (and refuses a tampered query); accepting narrowed
    scopes returns a code; the code with the wrong verifier is refused, with the right one gives
    a prefixed token; a second authorization skips consent; refresh works;
  - MCP client over HTTP (`MCPClient`, 2026-07-28): the tool list follows the token's scopes;
    reading lists and gets the person's records; another business's record is a 404 as data;
    a field hidden from staff stays hidden in a list and a get; a write runs and is audited as
    `mcp:<client>` on channel `mcp` with a run id; a write that parks returns the
    `/approvals/<id>` link and its park is audited; a command runs; an unknown action is an error;
  - scopes on the API: a read-only token's write is 403 `out_of_scope` on the REST route;
    `/api/me`, `/api/history`, `/api/approvals` are 403; a module outside the scopes is 403;
    human-only routes stay refused;
  - connections: listed for the person; revoking makes the token 401 and removes the consent;
    another person cannot revoke it (404);
  - credits: a paused business refuses a tool call.
- `framework/api/test/framework/identity.e2e.test.ts`: the fixture bearer's scopes cover its
  calls; a scoped token outside its scopes is 403.
- `application/api/test/domain/mcp.e2e.test.ts`: the sample app's tools for every module; a to-do
  added; an order above the business's limit parks at `irreversible` and answers with its link.

## Deferred

- Choosing the business on the consent screen (B7's tenant switcher); one token per business.
- A screen for connections in the app or the back office (the API exists).
- Client ID metadata documents (`@better-auth/cimd`), the device grant, DPoP, JWT access tokens.
- Serving MCP revisions before 2026-07-28.
- MCP Apps cards (PRD P2) and resources or prompts.
- Hiding the tools of a module a business's feature flag switches off (A11): the API answers 404
  for them meanwhile.
- A client registered before a module existed keeps the scopes it registered with: it registers
  again to ask for the new module.
- CORS for browser-based MCP clients: `/mcp` answers only the application's web origins.
