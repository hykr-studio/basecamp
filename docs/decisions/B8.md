# B8: OTP acceptance and evidence

## Summary

A person accepts a record's document (an order's PDF) with a one-time code: the framework sends
a 6-digit code to the person's own WhatsApp number (an authentication template) or email, and the
code they type back accepts exactly that PDF (its SHA-256) of exactly that version of the record.
The acceptance is a write through `runWrite`: audited, refused with rule codes, and it can move
the record along a transition the application names (the sample's orders go `approved` →
`accepted`, frozen). Each acceptance leaves one evidence row in `audit.acceptances`: who signed,
the code's channel and address, when it was sent and verified, the IP, user agent and device,
the record's version, the document's version and hash, and the words they agreed to. The table
is append-only (a trigger refuses UPDATE, DELETE and TRUNCATE) and every row is chained to the
business's previous one by hash, so a changed or missing row shows.

One-time codes are a framework service now: `OtpService` (extracted from the WhatsApp linking,
which uses it) keeps codes in `channel.otp_challenges`, by purpose, hashed, with a time to live,
attempts spent before each guess, limits per person and per address, and a binding (what the code
is for). An `ESignProvider` interface (start a signing, report its verified result) is declared,
with a registry and the evidence path for it, and no provider ships.

## Assumptions to review

- **One signer.** One acceptance per document per signer; with a transition, the first one moves
  the record and later ones are refused. Should some documents need several signers (both
  co-owners), each accepting before the record moves?
- **OTP is enough.** OTP on WhatsApp or email is the acceptance; e-sign (Aadhaar eSign or a
  DigiLocker vendor) is an interface only. Which documents, if any, must be e-signed, and with
  which provider?
- **Email is the account's.** The email channel uses the person's account email, which Better
  Auth does not verify today. Is an unverified sign-up email acceptable as an OTP channel, or
  should email OTP wait for verified emails?
- **Evidence is kept forever.** Acceptance evidence (including the number or email the code went
  to, and the IP) survives "delete my data". How long must it be kept, and what may be redacted
  after the retention period?
- **No withdrawal.** An acceptance cannot be withdrawn; the business cancels the record (the
  sample allows cancelling an accepted order). Can a signer withdraw an acceptance, and what
  happens to the frozen record then?
- **Who sees the evidence.** The full evidence (address, IP, device) is for `acceptances.evidence`
  holders (owner and admin); colleagues who reach the record see that it was accepted, by whom
  and when. Is that the right split for disputes?
- **A stale PDF is refused.** A PDF made before the record's last write (even a state change) is
  refused: make it again. Should a state change alone keep a PDF current?
- **Behind a proxy.** The IP recorded is what Express sees. Production behind a load balancer
  needs `trust proxy` configured, which this unit does not add. Which proxies does production run
  behind?

## API sketch

```ts
// A module's server/acceptance.ts, contributed in its index.ts: contributes: { acceptances: [OrderAcceptance] }
export const OrderAcceptance = defineAcceptance<OrderDocumentData>({
  name: 'orders.order',
  document: 'orders.order',             // the PDF that is accepted
  label: { en: 'Accept the order', … },
  statement: ({ order }, ctx) => `I accept order ${order.number} for ${ctx.money(order.total)}, as shown in this PDF.`,
  by: 'customer',                       // or { capability: 'x.sign' }, or (p, row) => boolean
  channels: ['whatsapp', 'email'],
  transition: 'accept',                 // approved → accepted, expose: 'system', frozen
});

// The provider interface (none ships): contributes: { esignProviders: [MyProvider] }
export interface ESignProvider {
  name: string;
  label?: Labels;
  start(request: ESignStart): Promise<{ ref: string; url?: string; expiresAt?: Date }>;
}
// Its verified webhook: AcceptanceService.completeESign({ provider, ref, status: 'signed', certificate })
```

```
GET  /api/acceptances/kinds?entity=order
GET  /api/acceptances/documents/:documentId?lang=hi   → { acceptance, statement, document, channels: [{ channel, sentTo }], can, accepted }
POST /api/acceptances/challenges { documentId, channel?, lang? } → { status: 'done', value: { id, channel, sentTo, expiresAt, statement } }
POST /api/acceptances { challengeId, code, device? } → { status: 'done', value: AcceptanceInfo }
POST /api/acceptances/esign { documentId, lang? }   → { status: 'done', value: { id, provider, url, ref } }
GET  /api/acceptances?entity=order&id=…             → { items: AcceptanceInfo[] }
GET  /api/acceptances/:id                            → AcceptanceInfo & { verified }
```

## Test plan

- `framework/api/test/framework/acceptance.e2e.test.ts` (fixture `agreements`):
  the customer accepts an offered agreement by an emailed code (Mailpit) and by a WhatsApp code
  (the outbound message); a wrong code spends an attempt, the right one accepts; the record moves
  to `accepted` and is frozen; the evidence has the PDF's hash, the record version, the channel,
  the address, the IP and user agent; the hash chain verifies; UPDATE, DELETE and TRUNCATE of the
  evidence fail; a used code, an expired code and a sixth guess are refused; the sixth code an
  hour is 429; another business gets 404 on every route; a colleague who reaches the record is
  refused `not_signer` (audited as denied) and sees no IP or full address; the assistant is
  refused; a PDF made before the record's last write is `document_stale`; a record moved after the
  code was asked for is `record_changed`; e-sign through the fixture's provider records method
  `esign`, and a signed result for a changed record is refused.
- `framework/api/test/framework/whatsapp.e2e.test.ts` (unchanged): linking still takes its code,
  spends attempts and limits codes per number.
- `application/api/test/domain/order-acceptance.e2e.test.ts`: an order saved by its customer,
  submitted, approved by the owner, its PDF made, accepted by the customer's code: the order is
  `accepted`, frozen (no save, no revise), its evidence holds the PDF's hash; a stranger gets 404.

## Deferred

- An e-sign provider (Aadhaar eSign, DigiLocker vendors): the interface, registry and evidence
  path exist; a provider ships as a connector with its verified webhook.
- Share links and guest signers (B9): a contact without an account reaches a record by a link
  and signs with the same operations; nothing produces `actor.kind: 'guest'` or assurance `otp`
  yet.
- SMS codes (no SMS channel); several signers per document; withdrawing an acceptance.
- Assistant tools to read acceptances; evidence packets as a PDF; dropping `channel.link_codes`.
- `trust proxy` for deployments behind a load balancer (decision 21).
- Hashing the stored PDF's bytes again at acceptance time (the hash kept when it was made is
  trusted).
