# B12: offline capture

## Summary

People on weak networks keep working. An entity or command opts in with the `offline` trait.
The app then puts each write to it in a persisted outbox on the device (SQLite on iOS and
Android, IndexedDB on the web) with an idempotency key fixed when the write is queued, and sends
it at once when it can, or later when the network comes back. The write takes the same path as
any other: the server validates, deduplicates by key, loads, authorizes, parks or runs, and
audits it. A write that needs approval parks when it syncs. Two devices editing the same
versioned record offline do not silently overwrite each other: the app sends the version the
change was based on as `If-Match`, and a stale one is refused with 409 `stale` and kept on the
device for the person to discard or apply again. Reads come from a persisted query cache while
offline, and an app opened without a network opens on the last signed-in person instead of the
sign-in screen.

On the server, B12 adds three general mechanisms that every write benefits from:
- client-chosen ids on create for entities with the `offline` trait (so a record made offline
  has its id before it syncs, and later writes can refer to it);
- `If-Match` on entity updates and deletes, mapped to B4's version check;
- an advisory lock per idempotency key, so two requests with the same key at the same moment run
  once, and a schedule that forgets stored replies after a retention the deployment sets.

The sample's to-dos are offline-capable and versioned: a to-do added or ticked offline shows as
"Waiting to sync", syncs when the network returns, and a tick made on two phones offline is
refused for the second with a conflict the person resolves.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | Offline capture is opt-in per spec: `traits: { offline: { writes?: ['create', 'update', 'delete'] } }` on an entity (default: every write people may make), `traits: { offline: {} }` on a command. Without it, writes stay online only, and an offline call fails at once with "You're offline". | Gap map extension points ("guarded by spec opt-in"); default, fail closed: a command with side effects should not be replayed hours later unless its module says it may. |
| 2 | An entity with the trait accepts a client-chosen `id` (a UUID) on create, from people only (an agent, a guest or the system gets 400 `client_id_people_only`). The framework adds `id: z.uuid().optional()` to the create input itself (`createInputOf(spec)`: the HTTP body, the write op and its approval replay); the spec's own schemas, the assistant's tools and MCP are unchanged. Without the trait an `id` in the body is dropped, as before. | Gap map risk ("offline creates followed by child writes need client ids, but create strips id"). People only: the assistant has no reason to choose ids. |
| 3 | An id already in use anywhere (any business) answers 409 `id_taken`, the same for every caller: a pre-check, and the primary key's unique violation for a race. Knowing an id is needed to probe it, and UUIDs are not guessable. | Default; no hint which business holds it. |
| 4 | A create's audit row and a parked create's approval name the client id as `resourceId`, so a create that parks on sync says which record it will make, and the approved replay makes it with that id. | Gap list ("approval-needing writes park on sync"). |
| 5 | `If-Match` on `PATCH`/`DELETE /api/<plural>/:id`: `"<version>"`, `W/"<version>"`, a bare number, a list of them, or `*`. For a versioned entity (B4) the record's version must be one of them, checked against the row the write loads (in its transaction, and the update or delete is conditional on that version): otherwise 409 `stale`, nothing changes. `*` matches any existing record. Another business's record is 404 first. A tag on an entity without versions or a tag that is not a version is 400 `if_match_unsupported`; so is `If-Match` on any route that does not check it (a create, a command, a transition, a read, a feature's route): one interceptor (`IfMatchInterceptor`, installed by the `offline` feature) lets it reach only routes marked `HonorsIfMatch()`. A precondition the server cannot check is never ignored. | Gap list ("If-Match conflict → 409"); B6B4 decision 19 ("The If-Match header is B12's"). RFC 9110 says 412 for a false condition; 409 `stale` keeps one answer with B4's body `version`. |
| 6 | The If-Match versions travel in the write op's `args`, so they are part of the request hash (the same key with another precondition is a different request, 409) and a parked write keeps them (B4's pins already refuse a replay on a moved record). | Default. |
| 7 | Concurrent duplicates: inside the write's transaction, `pg_advisory_xact_lock(hashtextextended('idempotency:<principal>:<key>', 0))`, then the stored reply is looked up again. The second request waits for the first to commit and returns its reply; one write, one audit row. The fast lookup before the transaction stays. | Gap list (plan notes: "advisory lock for concurrent duplicate idempotency keys"); developer guide section 14 ("can both run"). |
| 8 | Stored replies are forgotten after `IDEMPOTENCY_KEEP_DAYS` (deployment setting, default 30, at least 1), by an hourly schedule (`idempotency.purge`, in batches). A key reused after that runs again; client ids make a repeated create a 409 `id_taken`, which the app resolves (decision 15). | Gap map risk ("the idempotency table has no retention"); plan notes ("idempotency TTL schedule"). A technical replay window, not a business retention period, so a deployment setting with a neutral default. |
| 9 | The app's outbox (`@hykr/app`, `features/offline`) is a persisted, per-person FIFO queue. Each item keeps the person, the business it was captured in (sent as `x-tenant-id` when it syncs, whichever business is chosen then), the operation (entity create/update/delete or command), its input, its idempotency key (fixed at enqueue), its `If-Match`, and its state (`queued`, `sending`, `failed`). | Gap list ("persisted outbox, idempotency key fixed at enqueue"). |
| 10 | Every write on an offline-capable spec goes through the outbox, online or not: it is stored first, then sent. A person online gets the server's answer as before (and a refusal as an error, with the item removed); a write that cannot be sent resolves `{ status: 'queued' }` and stays. A write the app was killed in the middle of is sent again with its key. | Default: one path; exactly-once through the key. |
| 11 | Sync order is first in, first out, one at a time. A network failure stops the run and it starts again on reconnect (and with back-off). A server error (5xx) or 429 is retried with back-off, up to 5 tries, then the item fails. A 401 pauses the queue until the person signs in again (the items wait, for the same person). A refusal (400, 403, 404, 409, 422) fails the item, keeps it with the server's reason, and the run goes on with the next. | Gap map risks ("a queued write can fail long after the user moved on, and the UI must show this per item"; "queued writes must survive re-login"). |
| 12 | A write that parks when it syncs leaves the outbox: the person is told ("Waiting for approval: …") and the request is on the approvals card, like any parked write. | Gap list ("approval-needing writes park on sync"); owner question answered: queued and parked on sync, not blocked at capture. |
| 13 | The version a queued update or delete is based on: after a pending write to the same record, the version that write will make (a create makes 1, an update adds 1); else the version of the record in the app's cache (the row the person saw); else none (B4's loaded version). The cached row is patched at once (and its version moved on), a queued delete takes the row out of cached lists, and a queued create is listed by `usePendingWrites`. | Default; the gap map's "two devices editing offline get silent last-write-wins". |
| 14 | A failed item offers Discard, and Retry. Retry after a `stale` conflict sends the change again on the current version (a new key, no `If-Match`): the person chose to apply it over the other change. | Owner question ("conflict policy"): reject and ask; no per-field merge. |
| 15 | A queued create answered 409 `id_taken` is settled as done when its record can be read (an earlier try made it, its stored reply already forgotten). | Default; follows decision 8. |
| 16 | The query cache is persisted per person and business (`@tanstack/react-query-persist-client`, the same SQLite or IndexedDB store), successful queries only, kept 7 days by default (`offlinePlugin({ maxAgeMs })`), removed at sign-out. While offline, queries pause and show it (`EntityList.offline`). | Gap list ("persisted cache"); plan F6 (the persist packages). |
| 17 | The shell remembers the last signed-in person on the device. When the session check fails for want of a network (not a refusal), it opens on that person, and checks again when the network is back (a refusal then shows the sign-in screen; the outbox keeps their items). Signing out forgets the person and the cached data, not their unsynced items. | Gap map extension point ("trust the cached session when the network is unreachable"); default: never lose captured work. |
| 18 | Network status: `expo-network` on iOS and Android, `navigator.onLine` and its events on the web, wired into React Query's `onlineManager`. A network error from the API counts as offline whatever they say. | Gap map ("onlineManager wired to expo-network"). |
| 19 | The outbox's UI: a strip the shell draws above the screen (a new `AppPlugin.Banner` slot) saying "Offline: N changes saved on this device", "Syncing…", or "N changes could not be saved", linking to `/offline` (the pending changes, each with its state, reason, Retry and Discard). Phrases in `@hykr/i18n` (`offline.*`, en/hi/te). A second new slot, `AppPlugin.onSignOut`, runs at an explicit sign-out only (not when the shell remounts), so the plugin forgets the persisted cache then. | Gap map ("the UI must show this per item"). |
| 20 | `@hykr/api-client`: write methods take `WriteOptions` (`{ key, ifMatch, headers }`) where they took a key (a string still works); a fetch that never reached the server throws `NetworkError` (`isNetworkError(e)`). | Gap map files ("expose key/precondition options; network-error typing"). |
| 21 | Sample: the to-dos module opts in (`traits.offline: {}`) and is versioned (`version` column, B4's trait without frozen states). Its screen lists to-dos waiting to sync; the app lists `offlinePlugin()`. An assistant's delete of a to-do now names its version on the approval ("(version 1)"). | Plan ("todos: B12"). |

## Assumptions to review

- **Opt-in per spec.** Only entities and commands whose module says so are queued offline. Should
  every entity be capturable offline by default?
- **People only choose ids.** The assistant, MCP clients and the server's own work never choose a
  record's id. Is there a client (an integration) that should?
- **One conflict answer.** A stale `If-Match` answers 409 `stale` (as B4's body version does), not
  RFC 9110's 412. Do outside clients need 412?
- **Conflicts are whole-record.** Any change to the record since the person saw it makes their
  queued change conflict, even on another field. Should only the fields it changes count
  (per-field merge)?
- **Replies kept 30 days.** A device offline longer than `IDEMPOTENCY_KEEP_DAYS` may apply a
  queued update twice if its first try reached the server (creates are safe through their ids).
  Is 30 days right, and should the app refuse to sync items older than that?
- **Parked items leave the outbox.** A write that parks on sync is shown once (a toast) and then
  lives on the approvals card. Should the pending list keep it until it is decided?
- **Sign-out keeps unsynced items.** They stay on the device for the same person and sync after
  they sign in again (the cached data is removed). On a shared device, should sign-out warn, or
  discard them?
- **Cached data kept 7 days.** The persisted cache holds what the person read (projected for them)
  for a week, on the device, until sign-out. Is that acceptable under the business's data policy,
  and should a business be able to switch it off?
- **Files offline.** A photo taken offline is not queued (B1 uploads need the network). Which
  flows need offline photos first?
- **Which flows.** The PRD names site capture (daily reports, photos, material requests). The
  framework makes any entity or command capturable; which of the product's modules opt in is the
  product's choice.

## API sketch

```ts
// @hykr/contracts
interface OfflineTrait { writes?: readonly WriteAction[] }
interface EntityTraits { offline?: OfflineTrait }
interface CommandTraits { offline?: OfflineTrait }        // writes is ignored on a command
offlineOf(spec): OfflineTrait | undefined
queuesOffline(spec, action): boolean                       // entity: may this write be queued?
commandQueuesOffline(spec): boolean
takesClientIds(spec): boolean
createInputOf(spec): ZodObject                              // create schema (+ id: uuid optional)
parseIfMatch(header): { any: true } | { versions: number[] } | undefined   // throws on garbage
etagOf(version): string                                     // '"3"'

// @hykr/contracts (also)
ifMatchHolds(spec, row, ifMatch): boolean; IfMatchError; ClientId (z.uuid())

// @hykr/core
WriteCtx.ifMatch?: string                                   // the request's If-Match
RequestMetaValue.ifMatch?: string
entityOp(def, action, { id?, pins?, ifMatch? })
ifMatchFor(def, action, header): IfMatch | undefined        // 400 when it cannot be checked
HonorsIfMatch(); IfMatchInterceptor                         // only marked routes take If-Match

// @hykr/api
IdempotencyService.purge(now?) → { deleted }                // features/offline
idempotencyKeepDays()                                       // IDEMPOTENCY_KEEP_DAYS, default 30

// @hykr/api-client
type WriteOptions = { key?: string; ifMatch?: string | number; headers?: Record<string, string> }
entity(spec).create(input, opts?: string | WriteOptions)   // update, remove, command alike
class NetworkError extends Error; isNetworkError(e)

// @hykr/app
offlinePlugin({ maxAgeMs?, cacheVersion? }): AppPlugin      // Provider, Banner, /offline, sign-in/out
usePendingWrites(plural?, actions?) → PendingWrite[]        // queued, sending, failed
useOutbox() → { items, online, syncing, paused, waiting, failed, retry(id, {overwrite}), discard(id), sync() }
useOnline(); PendingWrites, PendingWriteRow, pendingLabel, OfflineBanner, OfflineScreen
createOutbox(deps), memoryStore()                           // the engine, pure (tested in Node)
type QueuedWrite = { status: 'queued'; item: PendingWrite }; isQueued(r)
useEntityMutation / useCommand: WriteResult | QueuedWrite for offline-capable specs
writeEntity(client, plural, action, { id?, input? }); writeCommand(spec, input); cachedRecord(client, plural, id)
EntityList.offline: boolean
AppPlugin.Banner?: ComponentType; AppPlugin.onSignOut?(user)
```

## Test plan

- Framework e2e (`framework/api/test/framework/offline.e2e.test.ts`, fixture feature `offline`:
  an `entries` entity, versioned, offline, with a field hidden by capability and a create that
  parks when asked for review):
  - a person's create with a client id makes that id; the audit row names it; GET finds it;
  - the same id again (another key, another business) is 409 `id_taken`; a bad id is 400; an
    agent's id is 400; an entity without the trait drops the id;
  - replay with the same key answers the first reply, one row; another body with the key is 409;
  - five concurrent requests with one key make one row and one audit row, and all answer alike;
  - `If-Match` on update and delete: matching version runs, stale is 409 and changes nothing,
    `W/` and lists and `*` work, garbage and unversioned entities and commands are 400, another
    business's record is 404 (not 409);
  - a create that parks on sync: needs_approval, audited with the client id, the same key answers
    the same approval, approving makes the record with the client id;
  - hidden fields stay hidden in a client-id create's reply and its replay;
  - the purge forgets replies older than the retention and keeps newer ones.
- Unit tests (`framework/app`, without React Native): the outbox engine (key fixed at enqueue,
  FIFO, network stop with growing back-off, a write interrupted mid-send sent again with its key,
  5xx back-off and give-up, 401 pause, refusals fail and the run goes on, a refusal while the
  screen waits rejects and keeps nothing, parked settles, conflict retry as-is or over theirs with
  a new key, `id_taken` resolved by a read, items of another person untouched, the If-Match chain);
  the IndexedDB store under `fake-indexeddb` (order per person, key-value table, a queued write
  surviving a reload). `parseIfMatch` and the client-id input are exercised end to end by the
  framework e2e test.
- The concurrency test was checked to fail with the advisory lock taken out.
- Sample e2e: to-dos are versioned (`If-Match` conflict on a to-do), a client-id create of a
  to-do; existing approval summaries updated for "(version 1)".

## Deferred

- Files captured offline (photos): B1's presign → upload → confirm needs the network; the outbox
  queues records, not bytes.
- Coalescing several queued changes to one record into one write.
- Re-applying pending changes on top of data refetched before they sync (a list refetched on
  reconnect shows the server's rows until the outbox has sent them).
- An `ETag` header on reads (the version is in the body).
- Background sync while the app is closed (no background task).
- A per-business switch for the persisted cache.
