# B17: calendars (Google), ICS invites and feeds, calls

## Summary

Records with a time can reach people's calendars, and calls can be logged on records.

- **Schedulable trait.** An entity declares which of its fields are the title, start and end
  (and optionally the place and a description), and whose calendars it belongs on
  (`traits: { schedulable: { … } }`). Everything below works for any entity that carries it.
- **Google Calendar** (`@hykr/connectors/google-calendar`, transport only, plus the server's
  `calendar` feature). Each person connects their own Google account by OAuth (PKCE, offline
  access). Their schedulable records then appear in their primary calendar, read as they may see
  them (hidden fields never leave), and follow every change. Google tells us about changes made
  there through a watch channel that posts to the B10 inbound webhook; a change to one of our
  events is stored as a `calendar.event_moved` or `calendar.event_removed` event that the
  application may act on. Busy times from Google answer "when am I free?".
- **ICS.** A record's invite goes by email with an RFC 5545 `.ics` (METHOD:REQUEST); later changes
  send an update (SEQUENCE + 1) and a deletion sends a CANCEL. Each person can also make a private
  ICS feed URL (an unguessable token, stored hashed, revocable) that any calendar app subscribes to.
- **Calls.** A `TelephonyProvider` interface (no provider ships) and a call log on records:
  calls logged by hand or by the assistant, a click-to-call command that asks the business's
  provider to connect the call, and an op a provider's inbound webhook handler uses to record its
  status.

| 33 | One job at a time per record and per invite. Every job that sends a record's calendar events (its sync, a new connection's backfill of it, a change notice about it, a disconnect's clean-up) holds a Postgres advisory lock on the record (`calendar.record:<tenant>:<entity>:<id>`); every send of an invite (its own job and a follow-up after a change) holds one on the invite (`calendar.invite:<id>`). Each reads the record when its turn comes, so the last job leaves the calendar or the invite as the record is, and Google's report of our own change is never taken for the person's. The locks (`CalendarLocks`, `features/calendar/lock.ts`) live on a pool of their own, 4 connections per process: a holder keeps one of them in a transaction that does nothing else (`pg_advisory_xact_lock`), while its work reads and writes through the main pool and commits as it goes. So holders never take the connections their work needs, and no number of jobs (13 at once in one worker: sync 4, invites 4, inbound 5) can starve the main pool. A job waits at most 60 s for a lock connection and then 60 s for the lock (`lock_timeout`); past that it fails and its queue retries it. A holder that dies lets go with its connection. The main pool (`createDb`) now fails a query that waits 30 s for a connection (`connectionTimeoutMillis`) instead of waiting for ever. The invite's lease column is gone. | Review findings (overlapping jobs; a pool deadlock); default (Postgres is the one shared store; Redis locks would need fencing). |
| 34 | The worker's outcomes are audited and stored like any write's. The event's row is `CalendarInviteOutcome` (`@hykr/contracts`: the invite, the record, method and SEQUENCE; the address and the error are only in the audit row and on the invite), so an application can subscribe. A dial's steps go through `runWrite` as the system op `call.dial_outcome` (`started`: the worker takes a requested call, once, so a call is never dialled twice; `placed`: the provider's id and status; `failed`: why), audited on the call with `call.updated` stored. A provider's update that came first is never undone. | Review findings (CLAUDE.md rule 1: one write path, every outcome audited); default. |
| 35 | Free time without `hoursFrom`/`hoursTo` keeps to the business's own open time: its `businessHours` settings (the week of open intervals and the holidays that SLA clocks use, section 5.20), in its time zone. A slot lies wholly inside one open span and may run on past local midnight where the business stays open. No `businessHours` set: every hour of every day; holidays only: every hour but those days. The framework assumes no working day of its own (the scripted model asks for no hours either). | Review finding (no hard-coded 09:00 to 18:00 day in the framework); framework/application boundary. |
| 36 | A sign-in is bound to the person who started it, so no one can connect someone else's Google account to their own (or to anyone's but the consenting person's). `start` keeps a single-use row in `app.calendar_oauth_states`: the business, the person, the PKCE verifier (sealed for the row with `SECRETS_KEY`), where the browser returns, and a 10-minute expiry. The `state` Google carries is a random token (`cs` + 32 bytes) of which only its SHA-256 is stored; the verifier never leaves the server, so a code is useless without the row. The callback (anonymous) exchanges nothing: it sends the browser to the row's return address with `code` and `state` (or `error`). `POST /api/calendar/google/complete` takes the row once (`DELETE … RETURNING`, so a second try finds nothing) and only then checks it: unknown, used or expired is 400 `calendar_sign_in_invalid`; started by another person 403 `calendar_sign_in_not_yours`; by the same person in another business 403 `calendar_sign_in_other_business`. Either refusal has already used the row up, so the code can never be exchanged afterwards, even by the person who started it, and nothing is sent to Google. Only a match exchanges the code (with the stored verifier; one that no longer opens, sealed with another `SECRETS_KEY`, is `calendar_sign_in_invalid`) and writes the connection as the session's principal. Google refusing the code is 400 `google_refused`, a grant without offline access 400 `no_offline_access`. The pending row is a nonce, not a record: it is written outside `runWrite` (like a feed's last use), and the connection it leads to is the audited write. A refusal is logged as a warning. Expired rows are deleted on each start and by `calendar.maintain`. | Review finding (the callback trusted only the state; the verifier travelled inside it); default (fail closed: the session decides, the URL never does). |
| 37 | Where the browser lands after Google is the deployment's choice, never the request's: `CALENDAR_RETURN_URL` (default `<APP_URL>/calendar`) for the web, and `CALENDAR_APP_RETURN_URL` (a native app's deep link, such as `<scheme>://calendar`) when the app asks with `returnTo: 'app'`; unset, the web address is used. The choice is stored on the sign-in row, so the callback reads it from there. A request can only pick between these two, so a code never goes to an address an attacker chose. The app's `/calendar` screen reads `code` and `state` (or `error`), completes once, and clears them from its address. | Default (no open redirect with a code in it); keeps native apps working now that the session completes the sign-in. |

## Assumptions to review

- **Google only.** Microsoft 365 (Outlook) is not built; the connector shape (OAuth, upsert,
  changes, free/busy) is what a second provider would implement. Is Outlook needed for the first
  version (PRD Win 7.1 names "Google/Outlook")?
- **One way.** Records go to Google; changes made in Google are reported as events and the
  application decides (the sample moves the meeting). Should the framework instead overwrite
  Google with the record, or always accept the calendar's time?
- **Whose calendars.** The trait's `people` columns (default the owner). Should every member who
  can read a record get it, or should participants (B7) be invited automatically?
- **Primary calendar.** Events go to the person's primary calendar. Should a person pick a
  calendar, or should the framework make a dedicated one?
- **Invite replies.** Attendees' accept/decline replies are not read (no inbound mail); RSVP is
  off. Is tracking replies needed?
- **Automatic invite updates.** A change to an invited record emails every recipient an update.
  Should a person confirm updates to external recipients first (they are sends to others)?
- **Feed scope and window.** A feed shows the person's own records, 90 days back to a year ahead.
  Should a manager have a team feed?
- **Who reads others' availability.** `calendar.availability.read` (owner, admin, ops). Only busy
  times, never titles. Right?
- **Calls about no record.** Visible to who logged them, the member on them and
  `calls.read_all`. Right?
- **Recordings.** Not stored. Needed, with consent and retention (B18)?
- **Free time with no hours set.** A business without `businessHours` gets slots at every hour,
  night included (decision 35). Should it instead default to a working day, and whose (a
  deployment setting, or a required business setting before free time answers)?
- **How long a calendar job waits.** A job waits up to 60 s for a lock connection and 60 s for
  another job of the same record or invite, then fails and retries; at most 4 jobs per process
  hold or wait for a lock at once (decision 33). Are these right for the expected load (a
  backfill of 500 records, Google's push notices for each of our own changes)?
- **A failed invite is an event.** `calendar.invite_failed` is stored, but nobody is told. Should
  the person who asked be notified (an in-app item or an email), or is the invite's state on the
  record enough?
- **Signing in from another device.** A sign-in finishes only in an app signed in as the person who
  started it, in the same business (decision 36). Someone who starts on the phone and finishes
  consent in a desktop browser where they are not signed in has to sign in there first, or start
  again. Is that acceptable, or should the app keep the code across its sign-in screen?
- **Telling the person who was sent someone else's link.** The refusal says "someone else started
  this calendar sign-in" (403), not a plain 404, so the person can tell they were sent a link they
  should not trust. Should it also notify the business's owners, or be an audit row?

## API sketch

```ts
// @hykr/contracts: the trait
traits: {
  schedulable: {
    title: 'title', startsAt: 'startsAt', endsAt: 'endsAt',   // read-schema fields
    location?: 'address',                                      // text or Address
    description?: 'notes',
    people?: ['ownerId', 'assigneeIds'],                      // columns of user ids (default: owner)
    hiddenWhen?: { field: 'status', in: ['cancelled'] },
  },
}
freeSlots(busy, { from, to, minutes, stepMinutes?, hours?: { from: 'HH:MM', to: 'HH:MM' }, open?: OpenHours, timeZone?, days?, limit? })
openSpansBetween(start, end, open?: OpenHours, timeZone)   // the open time as spans of instants

// @hykr/connectors
icsCalendar({ method?, prodId, name?, events: IcsEvent[] }): string

// @hykr/connectors/google-calendar
googleOAuth / googleCalendarClient(transport, accessToken) / googleCalendarConnector / createFakeGoogle() / fakeGoogle()

// HTTP (people; the assistant only where noted)
GET    /api/calendar/providers                         → [{ name: 'google', available }]

                                                        the sign-in's return address with code and state)

                                                        started in; otherwise 403, and the sign-in is used up)
GET    /api/calendar/connections                       → mine

GET    /api/calendar/busy?from&to&userId               (assistant too)
GET    /api/calendar/free?from&to&minutes&step&hours&userId   (assistant too: find-free-time)
POST   /api/calendar/invites { entity, id, to: [{ email, name? } | { userId }], lang? }   (assistant: parks)
GET    /api/calendar/invites?entity&id
POST   /api/calendar/feeds { label? }                  → { feed, url } (url once)
GET    /api/calendar/feeds
DELETE /api/calendar/feeds/:id
GET    /api/calendar/feed/:token                        (anonymous, text/calendar)
POST   /webhooks/google-calendar/:connection           (B10 inbound)

POST   /api/calls { direction, status, from?, to?, entity?, id?, startedAt?, endedAt?, durationS?, notes? }
POST   /api/calls/dial { to, from?, entity?, id? }     (assistant: parks)

GET    /api/calls/provider                         → { available, name }

// server
contributes: { telephonyProviders: [...] }

```

## Test plan

- Unit (`framework/connectors`): ICS escaping, folding at 75 octets, UTC times, CANCEL; OAuth URL
  with PKCE, code exchange and refresh against the fake; the client's upsert (update, then insert
  on 404; a cancelled event restored), changes with a sync token and 410; free/busy; the connector's
  verify (token, constant time, missing headers) and parse; the fake's bookkeeping.
- Unit (`framework/contracts`): `freeSlots` (busy overlaps, steps, working hours in a time zone).
- E2E (`framework/api/test/framework/calendar.e2e.test.ts`, fixture `appointments`):
  - connect: the URL carries PKCE and an opaque state (the verifier only on the server, sealed);
    the callback exchanges nothing and hands code and state to the app; completing stores sealed
    tokens (no token in the database in the clear, none in the audit); a tampered, used or expired
    state is 400; the assistant cannot start or complete one; disconnect removes our events and
    revokes; another person's or business's connection is 404;
  - the sign-in is the starter's: person B completing person A's consent URL is 403 and connects
    nothing (no row for A or B, no token request to Google), and A cannot finish it afterwards
    either; the same person completing in another business is 403; no session is 401;
