# A2: WebMCP read tools

## Summary

A browser agent can read what the person can read on the screen they are on, through WebMCP.
Each screen's read tools are declared on its app module (`webmcp: { <screen>: { reads } }`,
F2). The `webMcpPlugin()` app plugin (`framework/app/src/features/webmcp/`) registers them with
the browser's model context while that screen is the person's screen context, and only when
the browser has one (`document.modelContext`, or the older `navigator.modelContext`). Each tool
is the assistant's own read tool for the entity (`list-<plural>`, `get-<name>`, same input and
description, from `entityReadTools` in `@hykr/contracts`). It runs through the API client with
the person's session (`runReadTool` in `@hykr/api-client`) and names the `webmcp` channel. The
API treats that channel as read-only and agent-driven: any write, chat turn, approval decision
or people-only route is refused at the door. Tenancy and field hiding stay on the server. The
sample app installs the plugin. The to-dos screen is the demo; Today, meetings and notes declare
theirs too.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | The browser side is an `AppPlugin`, `webMcpPlugin()`, in `framework/app/src/features/webmcp/`: the adapter (`adapter.ts`, the only file that touches the browser's API), the tool builder (`tools.ts`) and the hook and plugin (`plugin.tsx`). The application lists it in `<AppShell plugins>`. A module cannot bring it, because plugin names are unique and several modules declare screens. | Plan A2 row and task notes ("adapter + hook as an AppShell plugin"). F2 decision 11. |
| 2 | Declarations stay F2's: `webmcp: { [screen]: { reads: EntityName[] } }` on `defineAppModule` and on `AppSettings`, keyed by the screen's `useScreenContext({ screen })` name. A screen gets its tools while it is the person's screen context, and loses them when the context changes, at sign-out and when the shell unmounts. A screen without a declaration, or a screen shown inside the canvas (no context), has none. | F2 decision 10. PRD Platform & AI 7.1: "Read-only tools per screen". |
| 3 | Feature detection: `document.modelContext` first (the WebMCP Community Group draft of 2 November 2026 and Chrome's documentation), then `navigator.modelContext` (the gap's wording, Chrome's early preview). A context without `registerTool` counts as none. No context means no tools and no error: native apps, and browsers without WebMCP. | PRD 7.1 "behind feature detection"; gap map risk "draft browser API ... keep it in one adapter file". The draft moved the API; both are checked. |
| 4 | Registration: `registerTool(tool, { signal })` per tool; unregistering aborts the signal, and also calls `unregisterTool(name)` when the context has it (the older shape). `registerTool` may return a promise or not. A refused registration (another script holds the name, the browser rejects the schema) is logged with the tool's name and never thrown into the app; the other tools still register. A registration that settles after its screen went away is unregistered then. | WebMCP draft (`ModelContextRegisterToolOptions.signal`); F2 decision 13 (plugin failures are logged). |
| 5 | Tools per read entity: `list-<plural>` and `get-<name>`, only for the actions the spec exposes to agents (`expose: 'all'`). A browser agent is an agent, so `'human'` actions get no tool. A declared entity with neither stops the app at startup (`composeApp`), like an unknown entity. | Plan "read-only"; developer guide 5.7. Fail closed. |
| 6 | Tool ids, titles, descriptions and input schemas come from one place, `entityReadTools(spec)` in `@hykr/contracts` (next to `entityToolIds`), with the assistant's wording and its row cap (`list.toolPageSize`, default 20). The assistant's `tool-factory.ts` still builds its own text: it is A7's hot file. Switching it to `entityReadTools` is deferred. | Gap map risk "descriptions and tool naming will be duplicated unless they move to contracts". Plan hot-file table. |
| 7 | Input schemas are JSON Schema from zod 4 (`z.toJSONSchema`, `io: 'input'`, `unrepresentable: 'any'`), so a field type a feature adds never breaks registration. The input is validated again with the zod schema before any request; an invalid input answers `{ ok: false, error: 'invalid_input', issues }` and sends nothing. | Gap map extension point ("Tool schemas from listInputObject(spec) via zod 4 toJSONSchema"). |
| 8 | Execution: `runReadTool(client, tool, input)` in `@hykr/api-client`, so the browser and the e2e tests run the same code. It calls `client.entity(spec).list` (limit at most the cap; the cap is the default) or `.get(id)`, and answers `{ ok: true, result }` or, for an API refusal, `{ ok: false, status, error }`: the shape the assistant's tools return. The WebMCP tool returns that as JSON text. | Plan "through the same API client (same permissions)". WebMCP draft: `execute` returns a value serialised to JSON; Chrome's examples return strings. |
| 9 | The client is the app's own setup (the app's `credentials` and `authHeaders`, so the person's session and business) plus `x-channel: webmcp`. The tools have exactly the person's access; the server applies tenancy, scopes and field hiding to every call. | Gap map risk "Field-level hiding must be enforced server-side, never in the hook". |
| 10 | Annotations: `readOnlyHint: true` and `untrustedContentHint: true`. Records hold text people and contacts typed, so the agent is told to treat results as data, not instructions. | WebMCP draft `ToolAnnotations`. Default: the conservative hint. |
| 11 | Only a signed-in person gets tools: the plugin's `onSignedIn` switches it on and its cleanup off. Signed out, on the sign-in screen and on public routes (B9) there are none. | Gap map owner question "Also on the public or homeowner surfaces (B9)?". Fail closed until answered. |
| 12 | When the screen context names a record (`record: { type, id }`) of a read entity, that entity's `get-<name>` description says which record is open, so the agent need not search for it. | Default. |
| 13 | Server: a session request may name its own channel in `x-channel`, `app` or `webmcp` (`SESSION_CHANNELS`). The principal then carries it. Any other value is a 400 (`bad_channel`): a browser cannot claim `whatsapp`, `background` or `share`. Without the header nothing changes (no channel). Agent credentials are unchanged (F4 decision 4). | F4 added the `webmcp` channel and its assurance (`session`). Default: fail closed on an unknown value. |
| 14 | `webmcp` is a read-only channel (`READ_ONLY_CHANNELS`): `PrincipalGuard` refuses any method other than GET and HEAD with 403 `read_only_channel`. That covers entity writes, commands, chat turns, approval decisions and anything added later, before a handler runs. The refusal is not audited: it never reaches the write path, like a relay key refused at the door. | PRD 7.1 "P0 read / P3 actions". Default: enforce read-only on the server, not only by which tools exist. |
| 15 | `webmcp` is also agent-driven (`AGENT_DRIVEN_CHANNELS`, `drivenByAgent(p)`): software calls on the person's session. `HumanOnlyGuard` and `ChatAccessGuard` refuse it, so an `expose: 'human'` route (`humans_only`), an approval decision and a chat turn stay out of reach even when WebMCP actions come and the channel stops being read-only. | Developer guide 5.7 (`'human'`: "an agent call is denied"). Fail closed. |
| 16 | The header is not a security boundary. Any script on the page holds the same session and can omit it. What the header buys: the API knows the call came from the page's tools (read-only and people-only rules, and later metering), and a bug in the tools cannot write. | Gap map risk "Any in-page agent or extension can read everything the person can". |
| 17 | Reads are not audited or metered, as for every other read. The channel is on the principal, so A3 can meter WebMCP calls later. | Default; PRD 4 audits writes. |
| 18 | `exposedTo` is not set: the tools are offered the way the browser offers a page's tools by default. | Default. |
| 19 | No scripted-model scripts: WebMCP tools are not the assistant's tools, and the server's agent gains nothing. | Task rules (scripts are for new assistant tools). |
| 20 | The sample installs `webMcpPlugin()` in `application/mobile/src/app/_layout.tsx`. The to-dos module's `todos` screen reads `todos`; F2's other declarations (Today, meetings, a meeting, notes) now register too. | Plan "Sample demos": `todos` shows A2. |

## Assumptions to review

- **Which screens first.** Every screen that declares `reads` gets tools. Which screens and
  entities should a browser agent see first (the gap map asks about the record editor and the
  project board)? Declarations are per screen, so this is application configuration.
- **Read-only until P3.** The server refuses every write on the `webmcp` channel. When
  declarative actions come, should a WebMCP write park at a fixed level (wait for the person's
  approval in the app), or follow the action's own level?
- **Public and participant screens.** Tools exist only for signed-in members. Should a share
  link or participant page (B9) offer read tools too?
- **Untrusted content hint.** Every result is marked as untrusted content. Is that right for
  records only members wrote, or should it depend on the entity (records that outside parties
  write)?
- **Exposure.** Should tools be limited to particular agents or origins (`exposedTo`), or is
  the browser's default enough?
- **Open record.** The `get-<name>` tool says which record is open. Should a screen also offer
  a "what is on this screen" tool (the filter in use, the visible rows)?
- **Refusals not audited.** A write attempt on the `webmcp` channel is refused before the write
  path and leaves no audit row. Should such attempts be recorded?

## API sketch

```ts
// @hykr/contracts
type ReadToolDef = { id: string; action: 'list' | 'get'; spec: EntitySpec; title: string;
  description: string; input: z.ZodObject; maxLimit?: number };
entityReadTools(spec, opts?: { maxLimit?: number }): ReadToolDef[]   // only 'all' actions
CHANNEL_HEADER = 'x-channel'
SESSION_CHANNELS = ['app', 'webmcp']                 // a session may name these
READ_ONLY_CHANNELS = ['webmcp']                      // GET and HEAD only
AGENT_DRIVEN_CHANNELS = ['webmcp']                   // software on a person's session
drivenByAgent(p): boolean                            // an agent actor, or such a channel

// @hykr/api-client
type ReadToolResult = { ok: true; result: unknown }
  | { ok: false; status: number; error: unknown }
  | { ok: false; error: 'invalid_input'; issues: unknown[] };
runReadTool(client: ApiClient, tool: ReadToolDef, input: unknown): Promise<ReadToolResult>

// @hykr/app
webMcpPlugin(options?: {
  modelContext?: () => ModelContextLike | undefined;   // default: findModelContext()
  client?: ApiClient;                                   // default: the app's session + webmcp
}): AppPlugin                                           // name 'webmcp'
findModelContext(scope?): ModelContextLike | undefined  // document.modelContext, then navigator's
registerTools(mc, tools, log?): () => void             // the unregister
webMcpTools({ catalog, reads, client, context? }): WebMcpTool[]
type WebMcpTool = { name; title; description; inputSchema: object;
  annotations: { readOnlyHint: true; untrustedContentHint: true };
  execute(input: object): Promise<string> }

// the application
<AppShell app={settings} modules={modules} plugins={[webMcpPlugin()]} catalog registry />
defineAppModule({ name: 'todos', webmcp: { todos: { reads: ['todos'] } }, ... })
```

## Test plan

- `@hykr/app` (Vitest, no React Native). `@hykr/contracts` and `@hykr/api-client` have no test
  runner, so `entityReadTools` and `runReadTool` are tested here and in the e2e test below.
  - `features/webmcp/tools.test.ts`: tool ids equal the assistant's (`entityToolIds`); only
    actions exposed `'all'` give a tool, each once; titles, wording, annotations; JSON Schema
    (strict object, filters, enum values, the row cap); the open record in `get-<name>`'s
    description; `execute` sends one GET with the filters, the row cap, the session's
    `credentials` and `x-channel: webmcp`, asks for fewer rows when told, returns a 404 as data,
    and sends nothing for an input the schema refuses.
  - `features/webmcp/adapter.test.ts`: detection order (`document` before `navigator`), a context
    without `registerTool` and the global scope (none in Node); registration with a signal and
    unregistration by abort (the draft); `unregisterTool` (the early preview); a refused or
    throwing registration is logged and the others still register, and only this call's tools
    are taken back; a registration that settles after the unregister is undone; a returned handle
    is used; a failing unregister is ignored.
  - `features/webmcp/plugin.test.ts` (react-dom into a bare container, as F2's
    `signed-in.test.ts`, under the real `AssistantProvider`, `wrapProviders` and `SignedIn`):
    nothing signed out; a signed-in person's screen gets its tools, swapped when the screen or
    record changes (a module's screen and the app's own); nothing on an undeclared screen or
    without a screen (canvas); taken back at sign-out and on unmount; no browser API means
    nothing; the default client calls the configured API address with the session and the
    channel.
  - `framework/compose-app.test.ts`: a screen that reads an entity whose list and get are closed
    to agents stops the app.
- `framework/api/test/framework/webmcp.e2e.test.ts` (fixture app plus the `webmcp` fixture
  feature: a projector hiding a task's due date from staff, and a people-only `memo` entity),
  running the real `entityReadTools` and `runReadTool` with a person's cookie and
  `x-channel: webmcp`:
  - a list returns only the person's business's rows;
  - a get of another business's record is a 404 as data, without its content;
  - the due date stays hidden from staff in a list and a get (it is in the database);
  - an input the tool refuses is never sent;
  - create, update, delete, a command, an approval decision and a chat turn are 403
    `read_only_channel`: the task, the visit and the approval are unchanged, nothing is created
    and no audit row is written;
  - `expose: 'human'` list and get, and the approvals list, are 403 `humans_only` on the channel
    and 200 without it;
  - the same session writes without the header; naming `app` records `app` in the audit row;
  - `whatsapp`, `background`, `share`, `mcp`, a wrong case or any other value is 400
    `bad_channel`;
  - the assistant's key still forwards its turn channel.
- The sample: `pnpm turbo run build typecheck --filter=@application/mobile...` (the web export
  bundles the plugin), `pnpm lint`, `pnpm lint:deps`, `scripts/check-boundary.sh`.
- Not done: a run in a browser that ships WebMCP. The adapter is tested against fakes of both
  API shapes.

## Deferred

- **Declarative actions** (P3): WebMCP forms or write tools. The channel is read-only on the
  server until then (decision 14).
- **The assistant's tool text from `entityReadTools`**: `tool-factory.ts` is A7's hot file.
  When it is free, its list and get tools should take their id, description and input from
  `entityReadTools` and add only the "shown as" sentence.
- **Commands as read tools**: a read-only command (a report) has no WebMCP tool; specs do not
  mark a command as read-only.
- **Metering WebMCP calls** (A3) and **per-business switches** for WebMCP (A11).
