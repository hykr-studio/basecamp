# V2: a reference names a record its writer may reach in its own business

## Summary

A fix found by the live validation of the platform gaps (`VALIDATION.md` row 2: C1-1, C8-1,
C1-2, and the critic's lead V2-L2). A to-do's or a note's `meetingId` was a plain foreign key to
`meetings.id`. The database checked only that a meeting with that id existed, in any business,
and the write path checked nothing. So:

- a business could store a link to another business's meeting (201), through every entry
  point: the app, the assistant's tools, MCP, an import with a raw id, an offline replay;
- a member could link a meeting of their own business they cannot read (staff, whose meetings
  are their own), so the answer told them the meeting exists;
- an unknown id was a bare 500 (an unmapped 23503), so 201 against 500 told anyone whether an id
  existed anywhere;
- the other business's delete then nulled this business's rows through `ON DELETE SET NULL`,
  outside the write path, with no audit row and no version change.

Only `traits.parent` checked a reference against the writer's business. The guide taught the
plain foreign key (5.2, `tableRef`), so every new module would have repeated it.

Now a spec declares its references (`traits.references: { meetingId: 'meeting' }`, the target
named by string, so a reference down the module graph imports nothing). Every insert and every
update that sets or changes one loads the target through the target entity's own scoped
repository, as the writer, in the write's transaction. An unknown id, another business's id
and a record the writer cannot read get the same 404 body. A CRUD write checks before it can
park, and the approved replay checks again. A foreign-key violation that still reaches the
database (a race with a delete, or a key no spec declares) is a 404, or a 409 for a delete,
without the database's detail. The sample backs its two references with a composite foreign key
`(tenant_id, meeting_id) → meetings (tenant_id, id) ON DELETE SET NULL (meeting_id)`, after
nulling the links that already crossed businesses.

## Decisions

| # | Decision | Source |
|---|----------|--------|
| 1 | A new trait `references?: Record<field, entity>` (`framework/contracts/src/framework/references.ts`), declared by declaration merging like every trait. The value names the target entity by its name (`'meeting'`), resolved at run time from the entity registry (`entityDef`), never imported, so a reference down the `dependsOn` graph keeps it a DAG. | The user's design ("naming the target entity by string so a downward reference keeps the dependsOn order"). |
| 2 | The check is `checkReferences(tx, p, spec, row, input)` in `@hykr/core` (`entity/references.ts`). It is awaited in `repo.insert` and `repo.update` (`define-entity.ts`) after the schema parse and the rules, so every path that writes through a repository has it: CRUD, commands, the assistant's tools and MCP (both over HTTP), imports, offline replays and approved replays. It is not an entity plugin, because a plugin's `toValues` is synchronous and a lookup is not. | The user's design ("checked in the write path through the target's scoped repo"); `EntityPlugin.toValues` is synchronous. |
| 3 | The target is loaded with `target.repo.find(tx, p, id)`: the writer's business, the target's read access for the writer, and its plugins' scopes (parent, shared, participants, grants). Read, not write: linking to a record means naming it, which needs only being able to see it. | The user's design ("a record the writer cannot read"); default. |
| 4 | A field is checked only when the write sets it to a value and, on an update, the value differs from the stored one. Null (unlinking) always passes. A PATCH that resends the stored id, or changes another field of a record whose target the writer can no longer read, is not refused. | Default: an unchanged link was checked when it was made; refusing it would block every edit by someone who sees the to-do but not its meeting. |
| 5 | The refusal is 404 `{ error: 'not_found', message: 'No such <target label>', field }`, the same body for an unknown id, another business's id and a record the writer cannot read. It is the target repository's own `get` refusal plus the field. | The user's design ("the same 404 shape as 'not yours'"); design rule 1. |
| 6 | A CRUD create or update runs the same check in its load step, before it is authorized, so a write that would park is refused there and never reaches an approver. The replay checks again (decision 2): a park whose target was deleted or became unreadable before the decision fails (`approvals.ts` closes it as failed with "No such meeting") and makes no row. A command parks through its own `authorize`; its replay is checked by the repository. | Lead V2-L2 (approved replay); default. |
| 7 | `createCatalog` refuses at boot (in `ModulesError`) a reference whose target is not an entity of the catalog, whose field is in neither the create nor the update schema, and a reference on a spec with `traits.parent`: children are inserted in bulk by `children.insert` / `children.replace`, not through `repo.insert`, so their references would go unchecked. | Default: fail closed at boot rather than leave a declared reference unchecked. |
| 8 | A Postgres 23503 on the entity write path is mapped without the database's detail (no constraint, column or value): on `repo.insert` and `repo.update` to 404 `{ error: 'not_found', message: 'It names a record that does not exist' }`; on `repo.delete` to 409 `{ error: 'in_use', message: 'Other records still name this <label>' }`. `runWrite` maps any other 23503 from a write's own code the same way (a command's raw insert, a child's bulk insert). 404 and 409, not 400, because `approvals.ts` closes a failing replay only on 401/403/404/409. | The user's design ("map the remaining 23503 cases to a 4xx without database detail"); B20 decision 14. |
| 9 | The importer reports every record a row names that it cannot reach with one code, `unknown_reference` (the code its `refs` columns already used): a declared reference's 404 (its `field` is the report's `_field`) and the database key's refusal (no field), recognised by `refusedReference(e)` from `@hykr/core`. Before, an unknown id was `invalid` and another business's id was created. | C8-1 ("the importer reports both cases with one code"); advisor: the race path must not read differently. |
| 10 | Sample: `traits.references: { meetingId: 'meeting' }` on `todo` and `note`. | The user's design. |
| 11 | Sample database: `unique (tenant_id, id)` on `app.meetings` in its `schema.ts`; the plain keys `todos_meeting_id_meetings_id_fk` and `notes_meeting_id_meetings_id_fk` leave the schemas; `application/domain/sql/post/meeting-references.sql` nulls every link whose meeting is missing or in another business, then adds `todos_meeting_fk` and `notes_meeting_fk`: `FOREIGN KEY (tenant_id, meeting_id) REFERENCES app.meetings (tenant_id, id) ON DELETE SET NULL (meeting_id)`, behind a `pg_constraint` guard, so it runs once and every migrate after is a no-op. Drizzle cannot say a column list for SET NULL (it would null `tenant_id`, which is NOT NULL), so the key is SQL. Postgres 15+ is needed; compose and CI run 17. This overrides F1 decision 14's "additive only" for these two keys: the plain key is replaced, not kept beside the composite one, so the schema no longer shows a key that checks nothing. | The user's design; F1 decision 14 amended. |
| 12 | `tableRef(name)` also exposes `tenantId`, so a module can declare a composite key down the graph in its `schema.ts` (`foreignKey({ columns: [t.tenantId, t.meetingId], foreignColumns: [ref.tenantId, ref.id] })`) when its action is NO ACTION, RESTRICT or CASCADE. SET NULL of one column stays in a SQL hook. | C8-1 fix sketch ("give tableRef a tenantId column"); default. |
| 13 | **A business deleting its own meeting**: its to-dos and notes that named it keep existing with `meeting_id` null, set by the database's `ON DELETE SET NULL (meeting_id)`, now only ever rows of the same business. The meeting's delete is audited (`meeting.delete`, with the row before); the links it clears get no audit row of their own and no version change. Kept because every way a meeting goes (a person's delete, a command, erasure, a retention purge, a business deleted) clears its links the same way, in the same transaction, and no record can name a meeting that is gone. A phone that still holds the old to-do learns of it on its next read; a queued change that resends the old id is refused as 404 (decision 4 checks it as a change). In section 14. | The user asked to decide and document it; default. |
| 14 | The check runs before authorization (decision 6), so where an entity's access reaches rows through the reference itself (`{ grant, of, via: 'projectId' }`), a parent the writer cannot read answers the reference's 404 instead of access's 403 `no_access`. Both say nothing of whether it exists. The fixture's imports items declare their shelf; its steps and case notes do not, because their tests exercise that `via` refusal (a test-only fixture, not shipped). | Default; design rule 1 ("not yours" is a 404). |

## Assumptions to review

- The repair in `meeting-references.sql` nulls cross-business and dangling links with plain SQL,
  once, before the key is added. It writes no audit rows: the links should never have been
  stored, and the hook cannot go through `runWrite`. A business that relied on one loses it
  silently.
- The check reads the target as the writer. A command that links a record its principal cannot
  read now fails. In the sample, `meeting.close` links its own meeting, which its principal
  loaded through the scoped repository, and the background writers run as
  `systemPrincipal`, which reads the whole business.
- Read access is enough to link (decision 3). An application that wants "may write the target"
  writes an entity rule.
- A reference no spec declares is still checked only by the database. Without a composite key,
  another business's id is accepted and an unknown one is now a 404: the existence oracle stays
  for undeclared keys. The guide's checklist says to declare every reference.
- A note that named another business's meeting kept a memory row with `about` that meeting; the
  repair nulls the note's link but not that row (it is rebuilt on the note's next change).
  Recall drops a memory whose `about` record the reader cannot read, so it shows nothing.
- Undoing a delete puts the row back with the links it had (the business is checked, the
  database's key checks the meeting); undoing an update that changed a link checks the old link
  again, and fails with 404 if that meeting is gone.
- The integrator must generate the application's migration (the meetings unique, the two dropped
  keys) before migrating: the post hook needs the unique.

## API sketch

```ts
// contracts: a spec names its references; the target by entity name
traits: { references: { meetingId: 'meeting' } }

// core
checkReferences(tx, p, spec, row: Values | null, input: Values): Promise<void>
//   throws 404 { error: 'not_found', message: 'No such meeting', field: 'meetingId' }
referencesOf(spec): [field, entity][]           // contracts

// db
tableRef('meetings')                            // { id, tenantId }
```

```sql
-- application/domain/sql/post/meeting-references.sql (per table, guarded)
UPDATE app.todos t SET meeting_id = NULL WHERE meeting_id IS NOT NULL AND NOT EXISTS (
  SELECT 1 FROM app.meetings m WHERE m.id = t.meeting_id AND m.tenant_id = t.tenant_id);
ALTER TABLE app.todos ADD CONSTRAINT todos_meeting_fk FOREIGN KEY (tenant_id, meeting_id)
  REFERENCES app.meetings (tenant_id, id) ON DELETE SET NULL (meeting_id);
```

## Test plan

Framework, a fixture feature `references` (rooms and bookings, `references.e2e.test.ts`), on
its own server:

- An unknown room, another business's room and a room of this business the writer cannot read
  (staff, own-only): POST and PATCH answer 404 with equal bodies; the writer's own room is 201.
- An unchanged reference passes; null passes.
- The assistant (agent key acting for the person) and an MCP client get the same refusal; an
  offline create with a client id too; a command that writes the reference too.
- A park with a readable room, the room deleted, then approved: the approval fails, no booking.
- An import with raw ids: another business's and an unknown id are both `unknown_reference`
  on the field; an unknown id in a key no spec declares is `unknown_reference` without one.
- A key no spec declares: an unknown id is 404 with no constraint name; a delete a key refuses
  is 409 `in_use`.

Unit (`modules.test.ts`): `defineServer` refuses an unknown target, an unknown field, and a
reference on a child.

Read paths named by lead V2-L2, checked in the code: a summary groups by the stored id and
resolves no label (`query/aggregate.ts`); the to-do and note views' WhatsApp text and speech
name no meeting; a webhook body and a live event carry the record as its reader may see it
(`integrations/payload.ts`), with the meeting's id only. None reads the meeting.

Sample (`application/api/test/domain/references.e2e.test.ts`): a to-do's and a note's
`meetingId` naming another business's meeting, an unknown id, and (staff) the owner's meeting:
404, equal bodies; the database refuses a cross-business row written by SQL; a business deleting
its own meeting nulls only its own rows; the hook nulls an existing cross-business link and is
idempotent.

## Deferred

- References on child entities (refused at boot, decision 7).
- An audited unlink when a referenced record is deleted (decision 13).
- References that need write access to the target, and a reference to several entity types.
