# V10: untrusted input, references and money, what the reviews left

## Summary

The reviews of V1 (untrusted keys and query strings), V2 (references) and V4 (money) approved
those units and left findings of the same classes. Each defect below was reproduced on the
compiled API by a test that failed first.

- **A NUL character (U+0000) in any text that reached Postgres was a 500** (22021 for text,
  22P05 for jsonb): every entity list, summary and write, feature routes (`/api/jobs?kind=`,
  `/api/calls`, `/api/comments/mentionable`, `/api/parties?q=`, `/api/documents`, the operator's
  `/api/platform/tenants?q=`), and Better Auth's `update-user`. With a genuine list cursor the same
  filter was blamed on the cursor (`bad_cursor`). Now one check at the request edge refuses a NUL
  anywhere a request sends text, with 400 `nul_character`.
- **Keyset cursors answered 500 when tampered with.** The inbox, comments and agent runs took any
  time JavaScript reads (`99999`, `-100000-…`) and any id (a NUL). They now read through one helper
  (`keysetOf`): a time Postgres stores, an id with no NUL and at most 128 characters, else 400
  `bad_cursor`. The SLA cursor refuses a NUL id too.
- **Three writes skipped the reference check.** `reviseWithChildren`'s `values` were inserted raw
  (another business's room, or one the writer cannot read: 200), a public form's answer was
  checked only in `run` (a guest's answer that would wait was `guest_cannot_wait` instead of the
  reference's 404), and undo put a deleted row back with a link its person could no longer read.
  Each now goes through `checkReferences`.
- **An order stored in a made-up currency could never be saved**, and the assistant's save on it
  parked for an approval that could only fail. `currencyOf` checks the stored currency in
  `authorize` too.
- **The server's currency check failed open without ICU data.** The server now refuses to start
  when Intl cannot list currencies.
- The rest are missing tests (the delivery log's `before`, a note's PATCH, a member of two
  businesses, the importer's own-key read), a guard scoped to its table, and corrections to V1.md,
  V2.md, V4.md, the developer guide and CLAUDE.md.

**After V10's review.** The review found five ways around these fixes, each a 500 reproduced on
the compiled API, and one wrong line in this doc. Each now has a test that failed first:

- **Text decoded after the edge.** A custom filter's JSON (`custom={"colour":"a\u0000b"}`) became
  a NUL only when the list schema decoded it (a 500 on lists and summaries, `bad_cursor` with a
  genuine cursor). `CustomFilter` refuses it, and the API's validation pipe answers as the edge.
- **A query past 1000 keys.** Express's parser keeps 1000 keys, and the OAuth pages read the raw
  URL again: a NUL in the 1001st (`/oauth/consent?…&client_id=a%00b`) was a 500 with no session.
  The guard also walks the raw query.
- **Times Postgres cannot store.** The SLA cursor (year 0000), history's `since` and the routing
  log's `before` (year 0000), credits usage's `from` and `to` (`99999`), and, found while fixing
  them, a list's `date` filter (`dueOn=0000-01-01`). `storableInstant` moves to
  `@hykr/contracts`, where the list grammar and the SLA cursor read it.
- **A NUL in an import file** made the whole job fail with the driver's text (the SQL and its
  parameters) in `error.message`, and kept none of the good rows. Such a row is now its own
  `invalid` problem, and a job keeps no database error's text.
- Found on the way, the same class: half of a UTF-16 surrogate pair (a JSON `\ud800` escape) in a
  custom field's value was a 500 (jsonb refuses it). It is refused like a NUL (`lone_surrogate`).
- Found on the way too: **a filter value its column cannot hold** (`/api/gadgets?rank=1e12`,
  `rank=1.5` on an `integer`) was a 500 on lists and summaries and `bad_cursor` with a genuine
  cursor, so the claim that only a cursor's values reach the cursor backstop was false a third
  time. The list builder now refuses such values (400 `invalid`, with the field). And a job's own
  failed update holding a NUL (an import's "not JSON" message repeats the file's first
  character) could not be stored, so the job never finished; job updates are kept storable.
- **The second review** found the column table of that check written from belief and wrong both
  ways: it refused `price=10000` on a `numeric(6,2)` and `big[lt]=1e16` on a `bigint`, which
  Postgres answers, and let `ratio[lt]=1e300` on a `real` through to a 500. A test now runs each
  value through the builder and through Postgres and fails on any disagreement; it also found a
  `bigint` in bigint mode unchecked (a fraction was a 500). It found a CSV cell spelling JSON
  (`["a\ud800b"]`) decoded after the file's check, so half a surrogate pair was imported as
  U+FFFD; an agent's `once` time past 9999 in UTC a 500 (and, the same constant, a call's
  start and end); and a failed completion's error stored unchecked.
- **The third review** found the operator's usage report (`/api/platform/usage`) still a 500 for
  the year 0000, and for a `from` late in 9999 whose default end it computed in the year 10000:
  the fuzz's one-bad-parameter-at-a-time never reached its query. Its `from` and `to` are now
  storable days and a computed end Postgres cannot store is `invalid_range`. The sweep it asked
  for (a time computed from what someone sends) found an SLA `within` setting of any size, now
  ten years at most (its old 500 is shown piecewise, not end to end: decision 28). The review's three smaller findings are fixed too: the two docs that still
  said the cursor backstop sees only a cursor's values, the driver error `jobs-told.test.ts`
  built with a name node-postgres never sets, and the sample's own body dates (the public brief
  form's `neededBy` included), which now take section 14's workaround.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | One mechanism for the NUL character, at the request edge, not route by route and not in an exception filter: a global Nest guard (`UntrustedTextGuard`, `framework/api/src/infra/untrusted-text.ts`, `APP_GUARD` in `app.module.ts`) walks `req.params`, `req.query` and `req.body` (keys and values, arrays and plain objects at any depth, with its own stack so a deep body cannot overflow it) and throws 400 `{ error: 'invalid', rule: 'nul_character', message, where }` naming the first place (`body.lines[2].title`, `query.q`, `path.id`). A guard runs after the body parser and before every pipe and handler, so no route can read the text first. | V1 review (both findings: "refuse `\u0000` in strings at the request edge"; "better, refuse NUL at the edge, so the class-22 backstop only ever sees cursor values"); task ("one mechanism for every route"). |
| 2 | Not an exception filter mapping 22021 to 400. A filter would answer after a query ran or a write half-happened elsewhere (a Redis key, a model call), would not see a NUL that reaches no Postgres text, and would leave the cursor backstop blaming a filter on the cursor. The edge refusal covers all of these and needs no SQLSTATE list (22021 and 22P05). | V1 review (the reviewer offered both); default: refuse input before it is used. |
| 3 | Better Auth's routes never reach a Nest guard (its handler is Express middleware) and their bodies are not parsed by the API. | 16 | `CustomFilter` (`contracts/src/framework/custom-fields.ts`) refuses text Postgres cannot keep, in values and keys, with a zod issue `{ code: 'custom', params: { rule } }` from `unstorableTextAt`. | 18 | Half of a UTF-16 surrogate pair is refused like a NUL, rule `lone_surrogate`: jsonb refuses it (`POST /api/gadgets { custom: { colour: 'a\ud800b' } }` was a 500, checked on the compiled API) and text turns it into U+FFFD silently. One helper says what is wrong with a string (`textFault`, `@hykr/contracts`, using `String.prototype.isWellFormed` where it exists and a loop on Hermes); the guard, Better Auth's hook, `CustomFilter`, `keysetOf`, the SLA cursor and the importer use it. | Default: the same class, found while fixing the importer. |
| 19 | `storableInstant` moves to `@hykr/contracts` (`framework/instant.ts`; `infra/instant.ts` re-exports it), with `storableDateTime(opts)` and `storableDate()`: `z.iso.datetime()` and `z.iso.date()` refusing what Postgres cannot store. Each answers 400 (`bad_cursor` for the cursor, `invalid_range` for credits usage, a validation error for the rest). *The third review found one more:* the operator's usage report (`/api/platform/usage`, decision 27). *The fourth review found a way around the list filter's fix, closed at integration:* `storableDateTime` judged the UTC year only, and a filter on a `date` column (drizzle `date()`, `PgDateString`: the fixture's `tasks.dueOn`, the sample's `todos.dueOn` and `briefs.neededBy`) reaches Postgres as the text's day (`toColumnValue`, `core/src/query/field-sql.ts`, sends `value.slice(0, 10)`; a `PgDate` or `PgTimestampString` column would get the text itself). `0000-12-31T23:30:00-01:00` is UTC 0001-01-01 and the text year 0000, which Postgres refuses as a date and as a timestamptz (22008): `GET /api/tasks?dueOn[gte]=…` and its summary were 500, and with `&sort=dueOn&limit=1` 500 (`bad_cursor` with a cursor). A timestamptz column, which gets a Date, answered 200. Now `storableDateTime` and `storableDate` refuse a text written in the year 0000 as well as one the UTC year refuses (`storableText`), so no reader depends on which form it sends: the refusal is the schema's, not the column branch's, and decision 25's body times and decision 30's sample dates refuse such a text too (deliberately: they are stored, and a text year 0000 is nothing Postgres keeps). The assistant's list and summarize tools and the MCP server build through the same grammar. | The fourth review (blocking); the integrator. |

A `numeric` (whatever its precision) and a `double precision` take any finite number. The number checks judge numbers only: a string on a number column (an `id` filter on an integer key) is Postgres's to read, as before V10, since its integer input takes `' 5'`, `'+5'` and `'05'` (and, from 16, `'1_000'`); one it cannot read is the backstop's. ## Assumptions to review

- **A NUL is refused, never stripped.** A client that sends one gets a 400 and must fix its text.
  Stripping would change what was sent without saying so, and a key with a NUL has no safe
  stripped form.
- **Ten years is the longest SLA a business sets** (decision 28). A longer one is a setting
  mistake, and a due time past the year 9999 could not be stored anyway.
- **A usage report's `from` in the years 1 to 99 means that year** (decision 27), as the ISO date
  says, not the 1900s `Date.UTC` would read.
- **Signed webhooks too.** An inbound webhook (WhatsApp, an integration's `/webhooks/…`, a job
  callback) whose JSON holds a NUL is refused 400, whole, before its signature is read. Checked
  by reading: each receiver stores its events synchronously, one insert per event into a jsonb
  column (`inbound_events.payload`, `integration_inbound.data`), outside one transaction. So
  before, the events of that delivery ahead of the one with the NUL were stored and the request
  then failed with a 500; now none of the delivery is stored. Either way the event with the NUL
  never is, and the sender retries until it gives up. Refusing the whole delivery keeps one
  mechanism and no 500; exempting the receivers (`@TakesBytes()`) would keep the partial store
  and the 500. A connector cannot strip the character today, since the guard runs before its
  `parse`. In guide section 14.
- **An unknown key in a body is checked too.** A NUL in a field the schema would have dropped is
  still a 400: the guard runs before the schema and does not know which keys a route reads.
- **Undo refuses rather than unlinks.** A deleted record whose target the person can no longer
  read stays deleted (404, the reference's answer), instead of coming back without the link.
  Coming back changed would not be the undo the person asked for.
- **A guest names no room.** The fixture's form asks for a room as text; a guest reads none of the
  business's records, so any id it sends is refused. A form's `fixed` values do not help: they
  are merged into the answer (`shared.controller.ts`) and checked as the guest too, by `base.load`
  and by `repo.insert`, so a `fixed` reference works only for a target the answer's customer
  principal can read (one granting `customer` access). For any other target, the application
  sets the id in a command of its own. *Corrected after the review, which found the first
  wording wrong by reading.*
- **Half a surrogate pair is refused, not repaired.** A client sending `\ud800` alone gets a 400,
  as for a NUL. Only an import's report shows such characters, as U+FFFD, because it is made to be
  fixed and imported again.
- **A row of an import with such text adds no column.** Its keys are not the file's columns, so a
  JSON row with a NUL in a key is that row's problem, not an unknown column that fails the file.
- **The over-long id branch of `keysetOf` is defence in depth.** Over HTTP the cursor schemas
  (`max(200)`) refuse a cursor that long first, so the test asserts a 400, not `bad_cursor`.
- **No release notes exist** in the repository. The V2 repair (crossed meeting links nulled once)
  is recorded in V2.md's assumptions; whoever cuts the next release should mention it.

## Suggestions that did not hold

- **Second review: "a `numeric` column's precision bounds a filter".** It does not, as the review
  showed and `list-columns.test.ts` now pins: Postgres reads the parameter as `numeric` without
  the column's precision, so no comparison overflows. The branch is gone (decision 22).
- **Second review: "calendar `startsAt`/`endsAt` were not probed".** By reading: they are fields
  of `CalendarEventChange`, which the server reports when a provider moves an event, not a
  request's input. `/api/calendar/free`'s `from` and `to` were probed in the first round (Sites).
- **V2 review: "the integrator must generate the application migration, or `db:migrate` fails on
  a fresh database".** Already done on `feat/platform-gaps`: `application/domain/drizzle/0009_v2.sql`
  adds `meetings_tenant_id_uq` and drops both plain keys (checked with `grep -l
  meetings_tenant_id_uq application/domain/drizzle/*.sql`), and `app_tpl` was built from it.
- **V2 review: "mention the repair in the release notes".** The repository has no release notes
  or changelog (`ls docs`, no `CHANGELOG*`). The repair stays documented in V2.md's assumptions;
  recorded under Assumptions above for whoever cuts a release.
- **V4 review: "switch the fixtures' claims and payments to `KnownCurrencyCode`".** The reviewer
  marked it not required: those fixture entities have no money trait and store minor units
  only, so no exponent is guessed. Left as they are (Sites table).
- **A plain CRUD write of an amount on a stored-`ABC` row parks before it fails** (the same
  defect as the order's save, if it held). It does not: the money plugin's `decide`
  (`framework/core/src/plugins/money.ts`) runs `resolveMoneyInput` at the CRUD decision, so the
  assistant's PATCH is refused 403 `money_invalid` before it can park. Only commands, which the
  plugin sees in `run` alone, need their own check; the sample's only command that writes
  amounts is `order.save` (checked by `grep -l currency application/domain/src/modules/*/server/*.ts`:
  the other order files read or format amounts; `order.revise` copies them raw).

## Deferred

- A deployment's own currency codes (`VED` and the fund codes are refused today): V4's deferred
  item, now in guide section 14.
- The millisecond paging gap of timestamp sorts (V1's observation): guide section 14 ("Paging
  within one millisecond"). Fixing it changes every list cursor's format.
- A webhook payload holding a NUL is refused, not cleaned: guide section 14.
- A boot or lint warning for a drizzle foreign key to a table with `tenant_id` whose field is not
  in `traits.references` (V2 review, "later"): guide section 14.
- The fixture's claims and payments keep `z.string().regex(/^[A-Z]{3}$/)` (V4 review: none
  required).
- **A written value its column cannot hold** (found after the review, on the compiled API): a
  body's date or time in the year 0000 (`POST /api/tasks { dueOn: '0000-01-01' }`) and a number
  past its column's range (`POST /api/gadgets { rank: 1e12 }` on an `integer`) are 500s. The
  entity's schema is the application's and takes them. The fix is a check of values against
  their columns' types before a write can wait (the CRUD load, beside `checkReferences`, and each
  command's `authorize`), not a class-22 catch at the end, after which an assistant's write would
  already have waited for an approval. The importer reports such rows `invalid` already. In guide
  section 14, with the workaround (`storableDateTime()`, `storableDate()`, a `.max()`). The
  framework's own body times found so far take that workaround (decision 25), and the sample's
  (decision 30); the fixture's `dueOn` is the example.
