# F0: interfaces-only seams

## Summary

F0 lands the types and empty registries that F1–F6 and the gaps build on, so they can work in
parallel on separate files. Nothing reads the new registries yet, so behaviour is unchanged.
Each consumer wires its own reads in its own unit. One composition point is wired:
`defineServer({ contributes })` merges an application's contributions, and `setRuntime` pours
them into the registries once per process.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | One generic primitive, `createHookRegistry(kind, nameOf, { collects })`, in `@hykr/contracts`. Every registry uses it. A duplicate name throws. Items are listed in registration order. | Plan, "Foundation seams" F0 ("empty registries"). Default: one primitive, so 14 registries don't each reinvent duplicate checks. |
| 2 | `Contributions` is an open interface in `@hykr/contracts`. Each package that owns a registry adds its key by declaration merging (`declare module '@hykr/contracts'`). Each value is a list. `createHookRegistry(..., { collects: 'turnHooks' })` links a registry to its key. | Plan F0 ("open `Contributions` interface extended by declaration merging"). It lives in the leaf package so core, api and isomorphic code can all extend it. |
| 3 | `installContributions` fails closed: a key that no registry collects throws at startup. | Rule "fail closed". A misspelt key must not be silently ignored. |
| 4 | Contributions are installed in `setRuntime`, which runs once per process before the Nest modules load. It is idempotent for the same app. `defineServer` stays pure. | Default. `defineServer` can be called more than once in a process (tests, the CLI); `setRuntime` already guards against a second app. |
| 5 | Registries are process-global, like `registerOp` today. Readers must read them when a request runs, not when an entity is defined, because `defineEntity` runs at import, before `setRuntime`. | Existing pattern (`approvals.ts` registry, `bindView`). Documented for F3. |
| 6 | Contribution keys equal registry names: `entityPlugins`, `writeHooks`, `readProjectors`, `identityProviders`, `toolContributions`, `deliveryChannels`, `turnHooks`, `inboundHooks`, `queues`, `schedules`, `erasureContributors`, `exportContributors`, `authPlugins`. | Default: one name to search for. |
| 7 | `ModuleDef` (server, `@hykr/api`) extends `ModuleSpec` (isomorphic, `@hykr/contracts`: `name`, `dependsOn`, `entities`, `commands`). `defineModule`, the module merge and the boot validation are F1's. F0 only declares the shape. | Plan, "Module system" and F0 ("`ModuleDef`"). |
| 8 | `AgentModule` in `@hykr/agents` is the per-module slice of `AgentDomain`: rules, help, scripts, eval cases and setup. | MOD-agent gap map entry. F1 owns the merge. |
| 9 | `EntityTraits` and `CommandTraits` are open interfaces. Specs carry `traits?: Partial<EntityTraits>` (or `CommandTraits`). Each gap adds its key in `contracts/src/framework/<x>.ts`. | Plan F0 and "Where each gap lives" (traits in `contracts/src/framework/<x>.ts`). |
| 10 | `AuthorizeResult` gains optional `tier` (0–3), `approver` (`userId`, `roles`, `channels`, `minAssurance`), `amount` and `undoMs`. `allow`, `deny` and `needsApproval` accept these as an optional last argument. The pipeline ignores them for now. | Plan F0. Tiers: PRD Platform & AI 7.1 "Approval tiers" (0 read; 1 internal write, undoable; 2 client/vendor sends wait; 3 money, legal, irreversible need a named human). |
| 11 | `amount` is an integer in minor units (paise) of the tenant's currency. | Default, matching B3 ("Money columns in integer paise"). |
| 12 | `approver.roles` holds plain strings, not `TenantRole`. | F4 makes roles validated strings. This avoids a later contract change. |
| 13 | The function forms of `ApprovalRule` receive `(p, { action, input, row })`. `parksFor(rule, p, ctx)` takes the context. Tool descriptions, which know no payload, pass `input: null, row: null`. Rules written as `(p) => …` still compile. | Plan F0 ("`ApprovalRule` receives `{action,input,row}`"). |
| 14 | `DomainEventEnvelope` is a Zod schema in contracts: `id`, `name`, `tenantId`, `module?`, `resourceType`, `resourceId`, `row`, `before?`, `actor`, `subject?`, `channel?`, `requestId?`, `runId?`, `occurredAt`, `availableAt?`. `actor.kind` is a string, so F4's `system` and `guest` fit. | Plan F0 and F3 ("durable event outbox … with `available_at` … and a `before` row"). |
| 15 | `TenantSettings` gains `features: Record<string, boolean>` (default `{}`). There is no `isEnabled` here: F4 adds it, failing closed. | Plan F0 and F4. |
| 16 | Settings sections: `defineSettingsSection(key, schema)` registers a section. Each section's type is declared on the open `TenantSettingsSections`. A section must parse `undefined` (a default for everything), and it may not reuse a base key. `parseTenantSettings(raw)` returns base plus sections. `TenantsService` uses it. | Plan F0 ("`TenantSettings` sections") and "settings in `contracts/src/settings/<x>.ts`". "Every field has a default" comes from `TenantSettings` itself. |
| 17 | Core-side hooks go in `framework/core/src/hooks.ts`: `EntityPlugin`, `WriteHook`, `ReadProjector` (plus `projectRead`, which runs the chain) and `AgentIdentityProvider`. `ToolContribution` goes in `core/src/tools/contributions.ts`, because Mastra types are allowed only in `core/tools`. | Plan F3, F4 and F5 file lists. Also `.dependency-cruiser.cjs` (`core-not-to-mastra`). |
| 18 | API-side hooks go in `framework/api/src/hooks.ts`: `DeliveryChannel`, `TurnHook`, `InboundHook`, `QueueDef`/`ScheduleDef`, `ErasureContributor`/`ExportContributor` and `AuthPlugin`. | Plan F4 and F5. These need Nest, the database, Better Auth or channel types, which only the API has. |
| 19 | `QueueDef` is declarative (`name`, `concurrency`, `attempts`, `backoffMs`). How a processor binds to it is F5's choice. | Default: don't pre-empt F5's `registerQueue`. |
| 20 | `.gitattributes` sets `merge=union` on the barrels that are one entry per line, existing and planned. | Plan F0. |
| 21 | Two hot files changed by one line each: `define-entity.ts` passes `{ action, input, row }` to `parksFor`, and `tool-factory.ts` passes `{ action, input: null, row: null }`. No other hot file changed (`pipeline.ts`, `approvals.ts`, `chat.service.ts`, `auth.ts`, `AppShell.tsx` and the processors are untouched). | Plan hot-file table. F0 runs alone before every other unit, and the `parksFor` signature change needs both call sites. |
| 22 | `@hykr/api` re-exports every hook type and registry, the core's included. An application then imports them from one package, and loading `@hykr/api` loads every collector before `setRuntime` installs anything. | Default. This ensures decision 3 never fires for a framework key. |

## Assumptions to review

- **Amount units.** Is `AuthorizeResult.amount` always the tenant's single currency, in paise? Or
  can an approval band compare amounts in different currencies?
- **Contribution install time.** Contributions install in `setRuntime` (API, worker, templates
  CLI, eval, Studio, tests). `migrate` does not install them. Does any migration-time code need
  hooks?
- **Global registries.** One application per process is assumed, as `setRuntime` already
  enforces. Is a multi-app process (one API serving two products) ever wanted?
- **Read projection for external audiences.** `ReadProjector.project` receives a `Principal`.
  Webhooks and PDFs for outside parties will pass F4's system principal, or a guest principal
  (B9). Should outside audiences instead get a separate, stricter audience flag?
- **Tier on approved replays.** An approved replay turns `needs_approval` into `allow` and drops
  the tier details. A5 decides whether the replay keeps the tier for the audit trail.

## Test plan

- `framework/core/src/seams.test.ts` (unit): `parksFor` passes the action, input and row to
  the function and object forms. An entity's `decide` parks on a payload rule. The decision
  helpers carry tier details. `AuthorizeResult` keeps them.
- `framework/api/test/framework/seams.e2e.test.ts` (fixture): the fixture boots with one
  contribution of every kind. Each one lands in its registry, and the API still serves as before:
  sign up, create and list a task. Further cases:
  - a duplicate name throws;
  - an uncollected key throws;
  - `mergeContributions` concatenates in order;
  - `projectRead` runs the chain;
  - settings sections apply defaults, keep stored values, and refuse a section without defaults
    or one that reuses a base key;
  - `DomainEventEnvelope` parses an outbox-like event and refuses one without a tenant;
  - traits survive `entitySpec`.
- The fixture's `src/features/seams/` compiles the declaration-merging pattern (traits,
  sections, a `ModuleDef`) under `tsc`, so the types are checked as well as the runtime.
- Everything else stays green: `pnpm turbo run build typecheck`, `pnpm lint`, `pnpm lint:deps`,
  and the core, api and application tests.
