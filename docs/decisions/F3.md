# F3: the core write and read path

## Summary

F3 makes the F0 seams of the write and read path run. Entity plugins act on every entity they
apply to: rules, a decision that can park with a tier, extra scope, column values, JSON before
parsing, conditions that turn a stale write into a 409, and a per-principal projection. Reads
are principal-aware everywhere a record leaves the server: `toRead(row, p)` for lists, gets
and write results, command results, approvals and history titles. Write hooks run inside
`runWrite`. Every named event a write returns is stored in a durable outbox
(`app.domain_events`) in the write's own transaction, with a `before` row and an
`available_at` that holds back a tier-1 write's events for its undo window. `registerOp`
refuses a duplicate. List field types are a registry (contracts for the grammar, core for the
SQL). Served entities are a registry (`entityDefs()`). In-process events are published after
commit as before, so `NotifyService` behaves as it did.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | Entity plugins are read when a call runs, not when `defineEntity` runs: `entityPlugins.all()` filtered by `appliesTo(spec)` (absent: every entity), cached per registry snapshot. | F0 decision 5 (registries are filled at `setRuntime`, after modules load). |
| 2 | Plugin `rules` run after the entity's own rules, wherever those run: in `def.decide` (CRUD) and in the repository's writes (commands included). | Plan F3. Default: a plugin rule is a rule. |
| 3 | Plugin `decide` runs in `def.decide` only (CRUD), after the rules and before `spec.approval`. A deny returns at once. A park waits. An allow may carry details (a tier-1 undo window). A command's `authorize` decides the command; plugins reach commands through write hooks. | Plan F3 ("`decide` that can park with a tier"). A command cannot park halfway through its run. |
| 4 | Entity rules may now park a CRUD write: a rule's `needsApproval` parks it instead of being ignored. Inside a command a rule's `needsApproval` is still ignored (the command's `authorize` decides parking); its `deny` still refuses. | Gap map, roles area ("Entity rules cannot park"). Stricter than before, so it fails closed; nothing in the sample returns `needsApproval` from a rule. |
| 5 | Decisions combine with `strongerDecision(a, b)`: deny beats needs_approval beats allow. The winner keeps its decision, rule and reason. Its tier is the highest of both, its undo window the longest; amount and approver come from the winner, or from the other one only when it has the same decision. A hook or plugin that returns `allow` therefore never loosens anything, but can add an undo window. | F0 `WriteHook.decide` ("tighten it, never loosen it"). Default for the details. |
| 6 | Plugin `scope` is ANDed into every scoped query: reads (list, count, get, find) and the `where` of update and delete. | Plan F3. |
| 7 | Plugin `toValues` runs on insert and update, after the framework keeps only real columns, and before the framework sets `tenantId`, the owner, the customer and `createdBy`. Those always win, so a plugin cannot move a row to another business or owner. Keys that are not columns are dropped. | Plan F3 (server-computed columns such as a version or a number). Fail closed for the ownership columns. |
| 8 | Plugin `toJson` runs on reads after dates become ISO strings and before the read schema parses. `def.readJson(row)` exposes this step. | Plan F3. |
| 9 | Plugin `updateWhere` adds conditions to the `where` of an update or delete. When nothing matches but the row is still reachable without them, the answer is 409 `{ error: 'stale' }`. Otherwise it is 404, as before. | Plan F3 ("`updateWhere` → 409"). |
| 10 | `toRead(row, p)` takes the principal, always. It parses, then runs the plugins' `project`, then the read projectors with the entity's name. `def.project(read, p)` is the projection step alone. | Plan F3. Gap map ("Read results are projected without a principal … thread the principal through every present path"). Break the API: no unprojected variant. |
| 11 | `WriteOp.present(value, p)` takes the principal. Entity CRUD presents through `toRead`. | Plan F3. |
| 12 | A command's result is projected by its output schema. Any part of the output schema that is an entity's read schema object (by identity, also inside objects, arrays, optional and nullable) is read as that entity: `readJson`, the whole output parsed, then that entity's `project`. Then the read projectors run with the command's name as the resource type. `defineCommand({ present })` replaces this when a shape needs it. | Default. The sample's outputs reuse entity read schemas (`CloseMeetingResult`, `RescheduleMeetingResult`), so they are projected without changes. |
| 13 | Approvals are projected for whoever reads them: the requester's parked result, `GET /api/approvals`, `GET /api/approvals/:id` and the decide answers. The parked input of an entity write goes through that entity's `project`; then the whole approval goes through the read projectors as `'approval'`. | Plan F3 and A4 ("fields hidden in … approvals"). |
| 14 | History titles come from audit `before` and `after` projected for the reader (entity `project`, or the read projectors by resource type), so a hidden title is not shown. Audit rows themselves stay complete. | Plan F3 ("through every present path"); A4 lists history. |
| 15 | Write hooks run in `runWrite`. `decide` runs after the operation's own decision and before an approved replay turns a park into an allow, merged with `strongerDecision`. So a hook's refusal (a credit cap) still refuses an approved replay. `afterRun` runs in the transaction after the audit rows and the durable events, for done and parked writes alike, with the `result`. It does not run for an idempotent repeat or a refusal. Throwing rolls the write back. | F0 `WriteHook` docs. Default: parked writes are writes a meter may count. |
| 16 | An approved replay keeps the original decision's details (tier, amount, approver, undo window) on the allow it becomes. | F0 open question ("Tier on approved replays"). Default: the tier stays in the record and the undo window still applies. |
| 17 | A park uses the decision's `approver` over the rule's deciders: `userId`/`roles` replace who decides, `channels` and `minAssurance` replace where and how surely. The decision's tier, amount and approver are kept in the approval's stored payload and shown on `Approval` as `tier` and `amount`. No new approval columns. | Plan F3 ("park with a tier"). Approval columns and multi-step tiers are A5's (`approvals.ts` F3 → A5). |
| 18 | The durable outbox is `app.domain_events` (`framework/db/src/schema/events.ts`). Every `NamedEvent` a write returns is inserted in the write's transaction: entity events, a command's events, `approval.requested`, and `approval.decided` (approved, rejected, expired, failed). Other event objects stay in-process. After commit they are still published on the Nest `EventBus`, so `NotifyService` is unchanged. | Plan F3 ("durable event outbox written in the transaction"). Gap map, notifications area ("one shared durable event outbox"). Task note: NotifyService behaviour unchanged. |
| 19 | A stored event holds the raw row (all columns, dates as ISO strings) and, for an update or delete, the row before it. Nothing is filtered at write time. `eventFor(event, p)` is how it leaves: another business's event is `null`; an entity's row is read with its read schema and projected for `p` (a row the schema refuses is `null`); any other row goes through the read projectors. | F0 `DomainEventEnvelope` docs ("filtered out before it leaves the server"). Gap map ("Event payloads are raw DB rows … must apply field hiding"). |
| 20 | `available_at` is `occurred_at` plus the decision's `undoMs` when set, otherwise `occurred_at`. It is never null, so a relay asks `available_at <= now()`. | Plan F3 ("`available_at` (tier-1 undo)"). Default: any decision with an undo window delays, whatever its tier. |
| 21 | A stored event carries `queues`: the process's queue prefix (`BULL_PREFIX`, passed as `CoreOptions.queuePrefix`). A relay takes its own prefix's rows only. | Gap map, PAR ("New queues, Redis keys or relays must use config.queuePrefix"). Same as the notification outbox. |
| 22 | A command's event names its resource with `resourceType` and `resourceId` when it has them; otherwise the type is the event name up to its first dot (`visit.rescheduled` → `visit`) and the id is `row.id`. `EntityEvent` and `ApprovalEvent` set both. `NamedEvent` gains optional `before`, `resourceType` and `resourceId`. | Default: the sample's events follow `<entity>.<verb>`. |
| 23 | An event needs a business: the principal's tenant, else the row's `tenantId`. Without one, the write throws and rolls back. | Fail closed: an event without a tenant could reach anyone. |
| 24 | Event ids are UUIDs made by the server, so the envelope is complete before the insert. A `seq` column (bigserial) gives the relay an order. `relayed_at` and `cancelled_at` exist and nothing sets them yet: they are for the relay (F5) and tier-1 undo (A5), so neither edits this table's columns. | Default: fewer edits to a shared schema file later. |
| 25 | `registerOp(name, factory, owner?)` throws when another definition takes a name already registered. The same definition registering again (`owner` is the entity or command def) is a no-op. | Plan F3. Gap map ("registerOp is a process-global Map … last wins"). Default for the same definition: `ChannelsModule.forRoot` builds its handlers each time it is called, so a process that loads both the API and worker modules must not fail. |
| 26 | `entityDefs()` lists the entities this process serves: `entityHandlers(def)` registers each one. `entityDef(name)` and `entityDefForSchema(schema)` find one. Another entity with the same name or plural throws; the same definition again is a no-op. | Plan F3. Registered where an entity is served (as `registerOp` is), so a `defineEntity` in a unit test does not collide. |
| 27 | List field types are a registry in `@hykr/contracts`: `defineListFieldType({ name, ops, value, opValue? })`, with open interfaces `ListFieldTypes` and `ListFilterOps` for the names (declaration merging). It registers when its module loads, not through `contributes`, because the grammar is isomorphic: the app and the agent's tools validate with it too. The six built-in types are registered the same way. | Plan F3 ("a list field-type registry"). Gap map (B13 `near`/`within`, A11 custom fields filterable). |
| 28 | The SQL of a field type is a registry in `@hykr/core`: `listFieldSql` (contribution key `listFieldSql`), `{ name, where({ table, field, column, op, value }) }`. `column` is undefined when the field is not a column (a custom field in jsonb). The built-in types use the same registry. A filterable field whose type has no grammar fails when the schema is built; one without SQL fails the request (500). Neither ever runs an unfiltered query. | Default, fail closed. contracts must stay db-free (gap map, data area). |
| 29 | A bare value means `eq` only for types that have `eq`. An object whose keys are all operators of the type is the operator form; any other object is a bare value (a point). | Default, for object-valued types such as a geo point. |
| 30 | The fixture's `chore` entity (`framework/api/test/fixture/src/features/write-path/`) is served over the fixture's existing tasks table, only by the write-path test's server. No fixture tables or migrations change. | Per-feature fixture migration sets are F6's and have not merged. |

## Assumptions to review

- **Entity rules that park.** A rule's `needsApproval` now parks a CRUD write (it was ignored).
  Is that what you want, or should parking stay with `spec.approval` and plugins only?
- **Raw rows in the outbox.** Stored events keep every column, hidden fields included, and are
  filtered when they leave. Should the outbox instead store only what the read schema exposes
  (losing `tenantId`, owner and customer for routing)? Erasure (B18) must cover this table.
- **Undo window and tier.** Any decision with `undoMs` delays its events, whatever its tier.
  Should only tier 1 delay?
- **Approved replays keep the tier.** An approved replay keeps the original tier and undo
  window, so an approved tier-1 write's events wait again. Should an approval end the window?
- **Command results by schema identity.** A command output is projected per entity only where it
  reuses the entity's read schema object. `Meeting.extend({ … })` is a new schema and is not
  projected per entity (the command's own projector still runs). Is a `present` override enough?
- **A command's resource type for events.** The default is the event name up to the first dot.
  Should commands always name it?
- **History.** Only the titles the history endpoint returns are projected. The audit rows keep
  full `before` and `after`. Should the audit trail itself redact hidden fields (B18 redaction)?

## API sketch

```ts
// @hykr/contracts
interface ListFieldTypes { enum; date; text; number; boolean; id }       // open: declaration merging
type FieldType = keyof ListFieldTypes
interface ListFilterOps { eq; ne; in; lt; lte; gt; gte; contains }       // open
type FilterOp = keyof ListFilterOps
interface FieldValueContext { readField: z.ZodType | undefined; coerce: boolean }
interface ListFieldType {
  name: FieldType; ops: readonly FilterOp[];
  value(ctx: FieldValueContext): z.ZodType;                               // one value ('in': a list of them)
  opValue?(op: FilterOp, ctx: FieldValueContext): z.ZodType | undefined;  // an operator with its own value shape
}
listFieldTypes: HookRegistry<ListFieldType>
defineListFieldType(type): ListFieldType                                  // registers on load; duplicate throws
listFieldType(name): ListFieldType                                        // unknown name throws
opsOf(type): readonly FilterOp[]                                          // replaces OPS
Approval.tier?: Tier | null;  Approval.amount?: number | null

// @hykr/db
domainEvents  // app.domain_events: id, seq, tenant_id, name, module, resource_type, resource_id, row,
              // before, actor_kind, actor_id, subject, channel, request_id, run_id, occurred_at,
              // available_at, queues, relayed_at, cancelled_at

// @hykr/core: entities
EntityDef.toRead(row, p)          // readJson → read schema → plugins' project → read projectors
EntityDef.readJson(row)           // dates → ISO, then plugins' toJson
EntityDef.project(read, p)        // plugins' project, then projectRead(name, …, p)
entityDefs(): readonly AnyEntityDef[];  entityDef(name);  entityDefForSchema(schema)
entityRegistry: HookRegistry<AnyEntityDef>                                 // filled by entityHandlers
EntityEvent(entity, change, row, before?)   // + resourceType, resourceId
NamedEvent { eventName; row; before?; resourceType?; resourceId? }

// @hykr/core: decisions and writes
strongerDecision(a, b): AuthorizeResult | null
WriteOp.present(value, p)
CommandConfig.present?(value, p)            // default: presentOutput(spec.output, value, p, spec.name)
presentOutput(schema, value, p, resourceType)
WriteHook.afterRun({ ctx, op, input, loaded, tx, value, touched, result })
registerOp(name, factory, owner?)           // another definition of the same name throws
CoreOptions.queuePrefix?: string            // stamped on stored events (BULL_PREFIX)

// @hykr/core: the durable outbox
recordEvents(tx, { principal, requestId?, events, delayMs? }): Promise<DomainEventEnvelope[]>
toEnvelope(row: typeof domainEvents.$inferSelect): DomainEventEnvelope
eventFor(event, p): DomainEventEnvelope | null
eventQueues(): string                       // this process's prefix, for a relay's where

// @hykr/core: list SQL
interface ListFieldSql { name: FieldType; where(a: { table; field; column: Column | undefined; op; value }): SQL }
listFieldSql: HookRegistry<ListFieldSql>    // collects 'listFieldSql'

// approvals
toApproval(row) (raw);  approvalFor(row, p) (projected)
```

## Test plan

- Unit (`framework/core`):
  - `strongerDecision`: ranks, detail merge, never loosens.
  - `registerOp` throws on a duplicate.
  - A custom list field type: its grammar (contracts) and its SQL (core) build a filter; a type
    without SQL throws; an unknown type is refused when the schema is built.
  - `presentOutput` projects nested entity schemas and leaves other parts alone.
- Fixture e2e (`framework/api/test/framework/write-path.e2e.test.ts`, server in
  `test/fixture/src/features/write-path/`), with a `chore` entity that carries a trait:
  - each plugin hook: a plugin rule denies, a plugin decision parks with tier 2 and a named
    approver role, extra scope hides rows (404), `toValues` sets a column, `toJson` runs before
    parsing, `updateWhere` turns a stale repository write into a 409, `project` hides a field;
  - an entity rule that parks;
  - a hidden field stays hidden in list, get, the write result, a command result, the approval
    (list and get), an event read through `eventFor` and history titles;
  - a contributed read projector runs by resource type on a command result (the command's name)
    and on an approval (`'approval'`);
  - another business gets 404 for a chore, and `eventFor` gives it nothing;
  - parked writes are audited (`needs_approval` row) and carry the tier;
  - write hooks: `decide` refuses (403 and a `denied` audit row), `afterRun` sees the result in
    the transaction, and throwing from it rolls the write back;
  - durable events: create, update (with `before`) and delete rows in the write's transaction;
    a refused or rolled-back write stores none; a tier-1 undo window sets `available_at`;
    `approval.requested` and `approval.decided` are stored; a command's event is stored with
    its resource; rows carry this run's queue prefix;
  - `registerOp` and `entityDefs` duplicates throw; `entityDef('chore')` is the served one;
  - a custom list field type filters chores over HTTP.
- Everything else stays green: core, api and application tests; NotifyService tests unchanged.
