# A7: durable runs, suspended on approval and resumed on the decision

## Summary

An assistant run that makes a write the API parks no longer ends there. The tool that got
`needs_approval` suspends the run (Mastra's tool `suspend()`); Mastra keeps the run's snapshot in
its own Postgres schema (`mastra`). The turn still answers as it did: the parked call shows its
approval card and the person is told what is waiting, in the same words as before. When the
request is decided (approved, rejected, expired, or approved but failed), the stored
`approval.decided` event reaches a subscriber in the worker, which puts a job on the
`agent-resume` queue. The job finds the suspended run by its run id (the approval's `run_id`),
checks that it belongs to the same business and person, passes the turn hooks (credits, the model
policy) again, and resumes the run with the decision (`agent.resumeStream`). The tool does not
call the API again: it answers with the decision. The model then carries on with the rest of the
request, under the same run id, so every follow-on write is audited under it. The continuation is
appended to the person's thread as a new assistant message. A run that came in on WhatsApp sends
the continuation to the same number while the 24-hour window is open. The app hears of it through
a live event on the thread and reloads the conversation.

The sample's meetings module shows it: "close Site review …" parks the close; once Ana approves,
the run continues, lists the meeting's new to-dos and says how many there are to follow up. A
rejection says nothing changed.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | A parked write suspends the run. `safely` (`framework/core/src/tools/tool-factory.ts`), which every generated tool and most contributed tools call, suspends through the tool context's `agent.suspend(payload)` when the API answers `needs_approval` and the tool runs inside an agent loop. Outside one (MCP, a direct `execute`, tests), the parked result is returned as before. | Plan A7 ("tool-factory.ts turns a parked call into Mastra `suspend()`"); gap map extension point 1. Mastra 1.74: `ToolExecutionContext.agent.suspend/resumeData/suspendPayload` (`@mastra/core/dist/tools/types.d.ts`). |
| 2 | The suspend payload (`ParkedCall`, `@hykr/core/tools`) is `{ kind: 'approval', approvalId, summary, output, context }`: `output` is exactly what the tool returned while parked before (its approval card included); `context` is how to resume the turn (`actingFor`, `tenantId`, `userId`, `channel`, `lang`, `timeZone`, `surfaces`, `screen`, `record`), read from the request context. The canvas page is not kept. | Default: the snapshot is the one durable record of the run, so it carries what a resume needs. |
| 3 | The run's Mastra run id is the turn's run id (the request context's `runId`, the approval's `run_id`, the trace id). Every turn passes it to Mastra (`durableAgent`, decision 5), so one id names the trace, the audit rows, the approval and the snapshot. | Gap map ("key by runId, which approvals.run_id already holds"). |
| 4 | The turn's answer is unchanged. A suspended turn reads as a parked one: each suspended call becomes a tool result carrying its parked `output` (the stream gets a `tool-result` chunk in place of Mastra's `tool-call-suspended`), and the turn ends with the framework's waiting line, in the turn's language and for its surfaces (`parkedLine`, the same words the scripted model said before), then a `finish` chunk (a suspended stream has none). So the thread, `/api/chat/once`'s `toolCalls`, WhatsApp's approval buttons, the voice reply and the app's approval card stay as they were. | Hot-file table: `chat.service.ts` is F5's ("all later gaps use TurnHooks"), so the adaptation is in `@hykr/agents` (`agentFor`), not in the chat service. Mastra ends a suspended stream with no `finish` chunk and no text after the tool. |
| 5 | `agentFor(surfaces)` returns the agent wrapped by `durableAgent`: `generate` and `stream` pass the run id and adapt a suspended run (decision 4). `generate` runs on `stream` + `getFullOutput()`, so every suspended call of the turn is seen (Mastra's `suspendPayload` keeps only the last), and throws a failed run's error as `generate` does. The scorers' data (`returnScorerData`) gets the waiting line as a reply too, and the eval harness runs the wrapped agent, so evals see a parked turn as a chat does. The registered agents (Studio) are not wrapped. | Default. Verified against Mastra 1.74 (two parks in one step suspend both; `resumeStream` with `toolCallId` resumes one and leaves the run suspended on the other). |
| 6 | The model never sees `needs_approval` in a chat turn any more. The framework rule now says: a write that waits for approval pauses the run and the user is told; when the run continues, the tool's result says how it was decided (`approved`, `rejected`, `expired`); say what happened in one line and carry on, or stop when it was rejected or expired. | Default; `framework/agents/src/version.ts`. The agent version hash changes with it. |
| 7 | What the resumed tool answers. `approved`: `{ ok: true, result: { status: 'approved', approval } }` plus the tool's usual present (a command's view). `rejected` and `expired`: `{ ok: true, result: { status, approval } }`. `failed` (approved, but the replay was refused): `{ ok: false, status: 409, error: { error: 'approval_failed', reason } }`, which the model explains like any refusal. `approval` is `{ id, summary, status, resourceType, resourceId, decidedAt }`. The written value of the replay is not stored, so `approved` carries none. | Gap map risk ("resume with the decision result; never re-call the tool"). `approvals.ts` (A5's file) keeps no replay result. |
| 8 | The resumed tool trusts only a decision for its own approval: `resumeData` must parse as `ResumeDecision` and name the approval the call suspended with; anything else (a hand-made resume in Studio) answers `{ ok: false, error: 'not_decided' }`. No write follows from a resume: the replay already ran when the approval was approved. | Default, fail closed. |
| 9 | Trigger. The `resume` feature contributes the subscriber `resume.approvals` on `approval.decided`, for rows with a `run_id` requested by an agent, which sends the stored event to its own queue `agent-resume` (6 tries from 2 s backoff, about a minute; concurrency 4). Decisions on WhatsApp, in the app and the expiry sweeper all store `approval.decided`, so all of them resume. | Plan A7 ("subscriber on approval.decided → agent-resume queue → resume by runId"); F5 decisions (stored events, job id per event and subscriber). Owner question ("decisions over WhatsApp resume runs too?"): yes. |
| 10 | Finding the run: `agents.findSuspension({ runId, approvalId })` reads the run from Mastra's storage by its id (`getWorkflowRunById`), and looks in its suspended steps (one step, or one of several calls run together) for the payload naming the approval; the payload's `__agentId` says which assistant profile resumes it. No stored run waiting for that approval: it never suspended (an MCP or test call), or it was resumed already; the job stops. A run stored but whose reply is not in a thread yet (the turn is still saving) is retried (about a minute of tries) while the approval is younger than 2 minutes. | Default. `listSuspendedRuns` (public) scans every suspended run's snapshot in a date window, and a run that parks a second time keeps its first date; the lookup by id is one row. |
| 11 | Checks before resuming, all fail closed (the run stays suspended, the job logs why): the snapshot's business is the approval's; the person it acts for is the approval's requester (`owner_id` or `requester_contact_id`); that person still belongs to the business (`PrincipalResolver.forActingFor`); the thread holding the run's reply belongs to that person in that business. | Default; tenancy rules. |
| 12 | One resume at a time per run: the job takes a Redis lock on the run id (10 minutes at most, released when it ends) while it finds, resumes and saves. A second decision of the same run is put back on its queue for a second (BullMQ `moveToDelayed`, the inbound processor's pattern), spending no try, then resumes its own call. No database transaction is held while the model runs: Mastra's first use of its storage in a process builds indexes `CONCURRENTLY`, which waits for every open transaction, so an advisory lock held in a transaction (the first version) stalled the worker's first resume. | Gap map risk ("several parked calls in one turn mean several suspensions per run"); found in the WhatsApp approvals e2e test. |
| 13 | A resume is a turn for the turn hooks: `TurnInfo.kind` gains `'resume'`, with the run's id, thread, channel, surfaces, language and the person's original message. `gateTurn` runs first (credits caps, the business's model policy choose the model again), `afterTurn` meters what it used. A refused resume runs no model: the thread gets the refusal's words (`say`, else `run.couldNotContinue`) and the run stays suspended. | Hot-file table (TurnHooks); PRD 1 key result ("Runs that exceed their credit cap: zero"). |
| 14 | The resumed request context is rebuilt from the payload's `context`, today's date in the person's time zone, and the hooks' shape (`turnContext`, `model`, `withoutTools`), with the same run id. The tools' API calls then carry the same agent key, person, business, run and channel as the turn that parked. | Rule 2 (the assistant is a user). |
| 15 | The continuation is one new assistant message in the run's thread, with the run id, its tool calls as parts (as the chat service saves them) and the reply. Mastra counts a resumed run's text, tool results and usage from the run's start; the continuation takes them from the resumed stream alone, so nothing said or shown before the park repeats and no token is metered twice (the step that parked is metered with the resume: the parking turn did not count it). An empty reply gets the framework's line for the decision (`run.approved`, `run.rejected`, `run.expired`, `run.failed`). If the resumed run parks again, it suspends again and the continuation reads as a parked turn (decision 4). A run with two parked calls resumed for one of them says nothing until the other is decided. | Plan A7 ("continuation appended to the thread"); verified against Mastra 1.74 (`resumeStream` totals). |
| 16 | Delivery. WhatsApp: when the run's thread is a WhatsApp one, the continuation goes to the person's contact in the business (the contact itself, or the one linked to the person) from the business's number, rendered like any reply, while the 24-hour window is open; outside it nothing is sent (no template for it) and the thread keeps it. A new park in a continuation is rendered with "approve it in the app", not buttons. App and voice: a stored event `thread.continued` (record type `thread`) goes through the live feature; `liveResources` gets a `thread` check (the thread is the person's); the app's chat runtime reloads its thread when it hears it (`onLiveEvent`), and a resumed call's line says how its request was decided (`ParkedLine`). | Gap map risks ("there is no open HTTP response when a resume happens"; "WhatsApp needs the 24h window or a template"); B15 live. |
| 17 | The snapshot lives in Mastra's `mastra` schema, written and migrated by Mastra. Snapshots are deleted when a run ends. Every pending approval ends (approved, rejected, or expired by A5's sweeper), so every suspended run is resumed once. A run whose resume was refused or failed stays in Mastra's table. | Gap map risk (retention must exceed the approval TTL). |
| 18 | A run resumed after a deploy runs on the current code: today's instructions, tools and model policy (the agent version on its audit rows says so). Mastra's snapshot keeps the messages so far; nothing pins the old version. | Gap map risk ("the resumed run may run under a different agentVersion"). Default: the business's current rules apply to what happens next. |
| 19 | The scripted model: `written()` (`@hykr/agents/script`) says the framework's line for `approved` (unless the result has a value), `rejected` and `expired`, and `decided(outcome)` tells a script how a resumed call was decided. The engine already answers `ok: false` with "I couldn't do that". Shared with the turn adapter: `parkedLine`. | Task ("scripted-model support for resume"). |
| 20 | Sample: the meetings module's close script, once the close is approved, lists the meeting's open to-dos (`list-todos`) and says how many to follow up; rejected or expired, it says nothing changed. | Task ("meetings: a parked close that resumes and continues in the thread"). |
| 21 | `app.thread_messages` gets an index on `run_id` (where not null), for finding a run's reply and thread. | Migration rule (additive only). |

## Assumptions to review

- **Who hears the continuation.** It goes to the person the run acted for, in their thread (and
  on WhatsApp when the run was on WhatsApp). The approver, when someone else, is not told what
  the assistant did next. Should they be?
- **Turns in between.** If the person keeps chatting while a request waits, the resumed run does
  not see those later messages (it continues from where it stopped), and its reply lands after
  them in the thread. Is that acceptable, or should a newer turn cancel the parked run's plan?
- **Rejected means stop.** The model is told to stop the rest of the plan when a step is rejected
  or expired. Should it ask what to do instead?
- **WhatsApp outside 24 hours.** A decision that arrives after the window closed sends nothing on
  WhatsApp (the app shows it). Should there be an approved template for "your request was
  decided, open the app"?
- **Approve twice on WhatsApp.** A person who decides with the button hears the button's answer
  ("Done: …") and then the assistant's continuation. Is the double reply wanted?
- **Refused resumes.** When the business is out of credits at the moment of the decision, the run
  stays suspended and the thread says it could not continue; nothing resumes it later. Should a
  top-up resume paused runs?
- **New code, old run.** A run parked before a deploy continues under the new instructions and
  tools. Is that right for long waits (the irreversible level waits up to 72 hours)?

## API sketch

```ts
// @hykr/core/tools
type RunContext = { actingFor; tenantId?; userId?; channel?; lang?; timeZone?; surfaces?; screen?; record? };
type ParkedCall = { kind: 'approval'; approvalId; summary; output: ToolOutcome; context: RunContext };
const ResumeDecision = z.object({ approvalId, status: 'approved'|'rejected'|'expired'|'failed', reason?, summary?, resourceType?, resourceId?, decidedAt? });
safely(tool, ctx, kit, fn, presentOf)   // suspends on needs_approval inside an agent loop; answers a resume
runContextOf(requestContext): RunContext; isParkedCall(x)

// @hykr/agents
durableAgent(agent): Agent               // runId from the request context; suspended → parked turn
parkedLine(approval, turn): string        // the waiting line (also the scripted model's)
createAgents(...) → { …, agentFor, findSuspension({ runId, approvalId }), resume(s, decision, { requestContext, maxSteps, text }) }
type Suspension = { agent: string; runId; toolCallId; toolName; parked: ParkedCall }
// @hykr/agents/script
written(o, done, turn)  // + approved / rejected / expired lines;  decided(o): status | undefined

// @hykr/api
TurnInfo.kind: 'chat' | 'draft' | 'resume'
features/resume: subscriber 'resume.approvals' → queue 'agent-resume' → ResumeService.resume(event)
liveResources: { type: 'thread' }; stored event 'thread.continued' (resource 'thread')

// @hykr/app
onLiveEvent(listener) (features/live); ChatRuntime reloads its thread on 'thread' events

// @hykr/i18n  messages/runs.ts
run.approved, run.rejected, run.expired, run.failed, run.couldNotContinue
```

## Test plan

- Unit, `@hykr/core` (`durable.test.ts`): `safely` suspends with the parked output and the run
  context, returns the parked result outside an agent loop, answers a resume for its approval
  (approved with the present, rejected, expired, failed as a refusal) without calling the API,
  refuses a resume for another approval or a malformed one.
- Unit, `@hykr/agents` (`durable.test.ts`): a scripted run parks, its stream reads as a parked turn
  (tool result plus waiting line) and its `generate` too, the run id is the request context's;
  `findSuspension` finds it by approval; `resume` continues it with the decision; two parked calls
  in one step resume one at a time. `written` and `decided` for each decision.
- Fixture e2e (`framework/api/test/framework/resume.e2e.test.ts`, fixture feature `resume`):
  an assistant delete parks and the turn answers as before; approving it resumes the run in the
  worker: the thread gets the continuation with the same run id, the follow-on `list-tasks` call is
  audited with that run id, the run is gone from Mastra; rejecting says nothing changed and the
  task stays; expiring through the sweeper resumes with `expired`; another business's person never
  sees the thread or its live event (404 on the thread); a parked call the API made outside a chat
  turn (no snapshot) resumes nothing; a WhatsApp turn's continuation is sent to the same number
  after the button; a resume refused by a turn hook runs no model and says so in the thread.
- Sample e2e (`application/api/test/domain/meetings.e2e.test.ts`): after Ana approves the close,
  her thread gets "Closed Site review. 3 to-dos to follow up" under the run id; a rejected close
  says nothing changed.

## Deferred

- Pausing runs on other waits (a question to the person, a timer, a webhook): A6's triggers and
  workflows can build on `ParkedCall.kind`.
- Push notifications for a continuation when the person is not in the app (A9's channels).
- WhatsApp buttons for a park made by a continuation (it says to approve in the app).
- Resuming a run refused by credits after a top-up.
- Cancelling a parked run's plan when the person starts something else.
- Runs outside a chat thread (A6's agent runs) are found and checked, but only a run whose reply is
  in a thread is resumed; A6 adds its own delivery.
