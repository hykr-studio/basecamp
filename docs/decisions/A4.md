# A4: roles, capabilities, per-record grants, field-level hiding

## Summary

A4 turns F4's role registry into a role model a business can shape, adds per-record grants, and
hides fields by capability on every read path.

- **Roles.** The framework still registers only its five generic roles (`owner`, `admin`, `ops`,
  `staff`, `customer`). An application adds roles and capabilities (`contributes.roles`,
  `capabilities`), and now also overrides what it did not declare: `roleOverrides` relabels a
  role or replaces its capabilities, and `roleDefaults` names the roles the framework hands out
  itself (a business's creator, a WhatsApp contact). Each business can then define its own roles
  from registered capabilities and edit the declared ones (label, capabilities), stored in its
  `roles` settings section.
- **Rows.** An entity's `access` map may name a capability as well as a role, so a role a
  business made reaches rows through the capabilities it holds. A new grant kind, `granted`,
  reaches only the records granted to the person (`app.record_grants`), or the children of such
  records (`via` a column).
- **Fields.** A spec declares `traits.fieldPolicy` (`{ cost: 'orders.cost.read' }`). The
  `field-policy` entity plugin removes the field for anyone without the capability wherever a
  record leaves (`toRead`: API, tools, command results, approvals, history, events), refuses a
  list filter or sort on it, and refuses a write to it.
- **Members.** `features/members` serves the member list, role changes, removal, invitations,
  the business's roles, and record grants, all audited through `runWrite`. The back office has a
  Members screen.

The sample's to-dos module declares a `buyer` role, a `todos.cost.read` capability and a
`cost` field hidden by it; buyers reach only the to-dos granted to them.

## Declaring the PRD role set

The PRD's roles (owner, manager, designer, supervisor, procurement, accounts) are product
configuration. An application declares them in a module (say `team`) and gives rows and fields by
capability; a business then renames or adds roles in its settings:

```ts
// application/domain/src/modules/team/roles.ts
const label = (en: string, hi: string, te: string) => ({ en, hi, te });
export const teamCapabilities = [
  defineCapability({ name: 'projects.read_all', label: label(…) }),   // every project
  defineCapability({ name: 'quotes.cost.read', label: label(…) }),    // cost and margin
];
export const teamRoles = [
  defineRole({ name: 'manager', label: label('Manager', …), capabilities: ['projects.read_all', 'quotes.cost.read', 'members.manage', 'records.grant', 'backoffice.use'] }),
  defineRole({ name: 'designer', label: label(…), capabilities: ['members.read'] }),
  defineRole({ name: 'supervisor', label: label(…), capabilities: ['members.read'] }),
  defineRole({ name: 'procurement', label: label(…), capabilities: ['projects.read_all', 'quotes.cost.read'] }),
  defineRole({ name: 'accounts', label: label(…), capabilities: ['projects.read_all', 'quotes.cost.read'] }),
];
export const team = defineModule({ ...teamSpec, contributes: {
  roles: teamRoles,
  capabilities: teamCapabilities,
  // The framework's owner keeps its name; give it the product's capabilities too.
  roleOverrides: [{ role: 'owner', capabilities: ['projects.read_all', 'quotes.cost.read', 'members.manage', 'members.read', 'records.grant', 'backoffice.use', 'customers.message', 'channels.manage', 'queues.admin'] }],
} });

// the project entity: managers, procurement and accounts see all; designers and supervisors
// only the projects granted to them; a room follows its project
access: {
  read:  { owner: 'tenant', 'projects.read_all': 'tenant', designer: { grant: 'granted' }, supervisor: { grant: 'granted' } },
  write: { owner: 'tenant', manager: 'tenant', designer: { grant: 'granted' } },
}
// rooms: { designer: { grant: 'granted', of: 'project', via: 'projectId' }, … }
// the quote spec: traits: { fieldPolicy: { cost: 'quotes.cost.read', margin: 'quotes.cost.read' } }
```

A studio that wants a "junior designer" defines it in its `roles` settings (through
`POST /api/members/roles`) with the capabilities it should have; a role that should see every
project gets `projects.read_all`.

## Assumptions to review

- **A4 edits a hot file it is not listed for.** The plan lists `define-entity.ts`'s editors as
  F3 → B19 → B12. A4 adds a grant-kind seam there (decision 12): the `grantKinds` registry, ORed
  into the scoped `where`, and asked by `ownership` before an insert. A grant that widens reach
  cannot be a plugin hook, because a plugin's `scope` is ANDed and can only narrow. Without the
  seam there is no `granted` reach and no child create under a granted parent; with it, B7 and B9
  add their grant kinds without editing the file. Accept A4 into the file's editor order
  (F3 → A4 → B19 → B12)? On merge, the integrator records A4 in the `define-entity.ts` row of
  the plan's hot-file table so that B19 and B12 rebase on it knowingly.
- **Who manages roles.** `members.manage` (owner and admin by default) manages every role,
  including giving roles capabilities the manager does not hold. Should a manager only grant
  what they hold themselves?
- **Business roles in settings.** A business's roles are a settings section, cached for 10
  seconds per process. A capability taken away from a role reaches other processes within 10
  seconds (a member's roles themselves are read on every request). Acceptable?
- **Grantable capabilities.** Only `queues.admin` is closed to businesses. Should
  `channels.manage` or others be too?
- **Writing hidden fields.** A field's write capability defaults to its read capability. The
  PRD's "procurement sets cost that designers never see" works by giving procurement the
  capability; is there a role that should write a field it cannot read?
- **Granted rows and owners.** Under `granted` alone, a person cannot create a top-level record.
  Should a designer be able to start a project and be granted it automatically?
- **Invites.** One use, matching email, 7 days, and the joined business becomes the default. Is
  an invite by phone number (WhatsApp) needed before B7's participants?
- **Notification parameters.** A module's template parameters come from the raw row: a module
  must not put a hidden field into a template another role receives. Should the dispatcher
  project the row for each recipient (needs the dispatcher's owner)?

## API sketch

```ts
// @hykr/contracts (roles.ts)
interface CapabilityDef { name; label; roles?; grantable?: boolean }   // grantable: default true
interface RoleOverride { role: string; label?: Labels; capabilities?: readonly string[] }
roleOverrides: HookRegistry<RoleOverride>          // collects 'roleOverrides'
interface RoleDefault { name: 'creator' | 'contact'; roles: readonly string[] }
roleDefaults: HookRegistry<RoleDefault>            // collects 'roleDefaults'
givenRoles(name: 'creator' | 'contact'): string[]  // contributed, else ['owner'] / ['customer']
FrameworkCapabilities.{ readMembers: 'members.read', manageMembers: 'members.manage', grantRecords: 'records.grant' }
capabilitiesOf(roleNames)                          // with application overrides
checkRoles()                                       // + overrides and defaults name real roles

// @hykr/contracts (settings/roles.ts)
TenantSettingsSections.roles = { defined: BusinessRole[]; edits: Record<string, RoleEdit> }
TenantSettingsSections.members = { inviteDays: number }
TenantConfigService.section(tenantId, key)        // @hykr/core: one section, parsed alone if need be
rolesOfBusiness(settings?): RoleView[]             // declared (edited) + the business's own
standingIn(roleNames, settings?): { roles: string[]; capabilities: string[]; unknown: string[] }
capabilityProblem(list, keep?): string | null      // undefined, or not grantable by a business
declaredCapabilities(role); declaredLabel(role); isGrantable(capability)

// @hykr/contracts (framework/field-policy.ts)
EntityTraits.fieldPolicy / CommandTraits.fieldPolicy: Record<field, string | { read: string; write?: string }>
fieldPolicyOf(spec); fieldCapability(rule, op); hiddenFields(policy, held, op?): string[]; withoutFields(row, fields)

// @hykr/contracts (platform/members.ts): Member, RoleView, CapabilityView, Invite, RecordGrant, inputs

// @hykr/policy
interface GrantKinds { own; customer; tenant; granted }  // open
type Grant = keyof GrantKinds
type GrantRule = { grant: Grant; minAssurance?; of?: string; via?: string }
type AccessRule = Grant | GrantRule | readonly (Grant | GrantRule)[]
type RoleAccess = Record<string /* role or capability */, AccessRule>
accessFor(p, access, op): { kind: 'grants'; grants: Grant[]; rules: GrantRule[] } | …
rowAllowed(p, grants, row)                          // other kinds: the query decides

// @hykr/core
interface GrantKind {
  name: string;
  where(p, rule: GrantRule, target: GrantTarget): SQL | undefined;
  creates?(tx, p, rule, input, target): Promise<boolean>;
}
grantKinds: HookRegistry<GrantKind>                // collects 'grantKinds'
EntityPlugin.query?(q: ListQuery, p, target): void // throw to refuse a list request
recordGrantKind, grantsCleanup, holdsGrant (plugins/grants.ts); fieldPolicyPlugin, fieldPolicyProblems (plugins/field-policy.ts)
// @hykr/api (features/members): commandFieldPolicy (read projector), FieldPolicyCheck (at start)

// @hykr/db
recordGrants (app.record_grants), memberInvites (app.member_invites)
ensureDefaultTenant(db, userId, name, roles = givenRoles('creator'))

// HTTP (features/members)
GET    /api/members                       members.read   → Member[]
PATCH  /api/members/:userId {roles}       members.manage → WriteResult
DELETE /api/members/:userId               members.manage
GET    /api/members/roles                 members.read   → { roles: RoleView[], capabilities: CapabilityView[] }
POST   /api/members/roles {name,label,capabilities}      members.manage
PATCH  /api/members/roles/:name {label?,capabilities?}   members.manage (edit, or reset with null)
DELETE /api/members/roles/:name           members.manage (a business role; a declared role's edit)
GET    /api/members/invites               members.manage → Invite[]
POST   /api/members/invites {email,roles} members.manage → WriteResult<{ invite, token }>

POST   /api/members/invites/accept {token}  signed in, matching email
GET    /api/grants?resourceType&resourceId  records.grant + can read the record → RecordGrant[]

```
