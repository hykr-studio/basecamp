# B2: documents (PDF), stored, emailed and sent on WhatsApp

## Summary

An application declares a document once, next to the module whose records it is about:
`defineDocument({ name, label, entity, load, render, fileName, send })`, contributed as
`documents`. `load` reads what the document shows **as the person who asks**, inside the write's
transaction (scoped repositories, records projected for them, so a hidden field never reaches a
PDF). `render` turns that data into a small layout (headings, text, label/value fields, tables
with groups and indents, totals, page header and footer) in the reader's language. The framework
holds no template and no wording.

Asking for a document is a command through `runWrite` (`document.render`, `POST /api/documents`,
tool `render-document`): the data is snapshotted on a new `app.documents` row (version 1, 2, …
per record and document), and a stored event (`document.requested`) sends it to the worker's
`documents.render` queue. The worker lays the pages out with the engine behind the
`DocumentEngine` interface, stores the PDF through the files feature (B1) as a server file held by
the document, and records its size, page count and SHA-256 (`document.rendered`). The engine is
pdfkit with HarfBuzz shaping and the Noto Sans, Noto Sans Devanagari and Noto Sans Telugu fonts
(regular and bold); a fake engine writes a plain-text PDF for tests and CI.

Sending is a second command (`document.send`, `POST /api/documents/:documentId/send`, tool
`send-document`), through `runWrite` too: the assistant's send waits for the person's approval by
default. The worker's `documents.send` queue delivers it by WhatsApp (the document uploaded as
media, in an approved template with a DOCUMENT header, or as a document message inside the
24-hour window) or by email with the PDF attached, in the order the document declares, and records
each send.

A rendered document is reached only through its record, by people who see at least what its
requester saw. The sample's `orders` module ships one: an order as a PDF, in English, Hindi or
Telugu, with its own WhatsApp template and email wording.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | Documents are declared by the application: `defineDocument` (`@hykr/api`), contributed as `documents` (a new `Contributions` key with its registry). The framework ships the mechanism, the layout model, the engines, the fonts, storage and sending; no template, label or wording. | Plan boundary table ("Document templates and wording … `defineDocument`, the render pipeline, fonts, storage, sending"); task. |
| 2 | A definition names its record kind (`entity`: an entity name); a document is always about one record. Its name is namespaced by its owner (`orders.order`), lower case and dotted, unique (the registry refuses a duplicate). At start, each definition's entity must be served, its WhatsApp template (if any) must have a DOCUMENT header and be one of the application's templates, or the start fails. | Default: fail closed at boot, as the files trait does. |
| 3 | **Data is read as the requester, at request time, in the write's transaction.** `load(ctx)` receives the record already read through the entity's scoped repository and projected for the principal (`toRead(row, p)`: entity plugins' `project`, then the read projectors, so any field-hiding plugin applies), plus `ctx.read(def, id)` and `ctx.children(childDef)` that do the same, and the raw `tx` and principal. Its result is stored on the document row (`data`, JSON) and is what the PDF shows. A re-render never reads live rows again: version N shows what was true when it was asked for. | Gap map risk ("If a document re-renders from live rows instead of a frozen version, a re-sent document may show different numbers"); PRD Win 7.1 ("Each revision immutable"); task ("hidden fields stay hidden"). |
| 4 | `render(data, ctx)` returns a `DocumentLayout` (validated with Zod both when asked and in the worker): page size (A4, A5, Letter), margins, title, a header and footer on every page (`{page}` and `{pages}` placeholders), and blocks: `heading`, `text` (bold, muted, aligned), `fields` (label and value, in one or two columns), `table` (weighted column widths, alignment, rows of kind `line`, `group` or `subtotal`, an indent per row, the header repeated on each page), `totals`, `spacer`, `rule`, `pageBreak`. Strings are already in the reader's language: `ctx` gives `label(Labels)`, `money(m)` (`moneyText`) and `date(iso)` in the business's time zone. Engine-neutral, so a second engine (Chromium) can render the same layout. | Gap map ("an engine behind an interface"); plan. Default: declarative layout keeps templates testable without a PDF parser. |
| 5 | Engine: **pdfkit 0.20.2** writes the PDF; **HarfBuzz** (harfbuzzjs 1.6.4) shapes every run: each embedded font's fontkit `layout` is replaced by a HarfBuzz one (F6 decision 22: fontkit's own shaping crashes on common Telugu words). Text is split into runs by script (Devanagari, Telugu, everything else) and each run uses its Noto font; digits, spaces and punctuation stay with the run they are in when its font has them. The framework lays lines out itself (word wrap with the shaped widths, one baseline per line from the tallest font in it), so a line can mix scripts. harfbuzzjs is imported lazily (its WASM loads with a top-level `await`); fonts are parsed once per process. | F6 decisions 21–22 and its notes for B2; PRD Overview ("English, Hindi and Telugu"). |
| 6 | Shaping is verified in tests: conjuncts and reordering in Hindi (क्ष, श्री, कि) and Telugu (శ్రీ, ప్రేమ, కృష్ణ) shape to fewer glyphs than code points, never `.notdef`, and a PDF with all three scripts embeds the three fonts and maps them back to the text (ToUnicode). Pages were also checked by eye while building (rasterised locally, not in CI). | Task ("verify shaping"). |
| 7 | `DOCUMENTS_ENGINE`: `pdf` (default) or `fake`. The fake engine writes a minimal, valid, uncompressed PDF of the layout's text lines (Helvetica, raw UTF-8), fast and searchable, so tests can check what a document shows. Both Vitest configs and CI set `fake`; the unit tests run the real engine directly. Production refuses `fake`. | Task ("fake renderer in CI"); B1's storage-driver pattern. |
| 8 | The PDF is stored with `FilesService.storeBytes` (B1) as a server file, then held by the document (`resource_type 'platform.document'`, field `file`). The files routes never serve it (no entity of that name: 404); `/api/documents/:id` does, after its own reach check, with a short-lived URL from `FilesService.urlFor`. A held file is never swept. | Plan DAG (`B2←B1`); B1 decision 25. A dotted resource type cannot collide with an application entity. |
| 9 | **Who reaches a rendered document.** Same business, always. The record must be reachable by the reader now (the entity's scoped `repo.find`, so access, grants and plugins' scopes apply), an agent needs the entity's `get` exposed, and the reader must see at least what the requester saw: each document keeps the requester's roles and capabilities (`seen_as`); a reader must hold every one of them. A definition that knows which capabilities change what it shows lists them (`capabilities: ['orders.cost.read']`, or `[]` when nothing it shows is restricted); then only those count, roles are ignored. Anything else is 404, never 403. | Task ("hidden fields stay hidden", "another tenant gets 404"); plan A4 row ("fields hidden by capability in every read path … PDFs"). Default fails closed: a staff member never opens a copy an owner rendered unless the definition says it hides nothing. |
| 10 | The assistant renders, reads a document's status and sends; it never gets a download URL (as with files). Its tools: `render-document`, `send-document` (from the command specs) and `get-document`, `list-documents` (`toolContributions`). | B1 decision 6; "the assistant is a user". |
| 11 | Rendering is allowed to anyone who reaches the record (the assistant included). A definition may decide otherwise: `authorize.render(p, record)` returns an `AuthorizeResult` or null for the default. | Default: making a PDF of a record you can read discloses nothing new. |
| 12 | **Sending** names one recipient: `{ self: true }` (the person asking, or the person the assistant acts for, resolved and stored as their `userId` or `contactId`), `{ customerId }`, `{ contactId }`, `{ userId }` (a member of the business) or `{ email }`, each checked in the business (404 otherwise). Sending to yourself is allowed to anyone who reaches the document. Sending to anyone else needs `customers.message` (the capability `notify.send` uses), and the assistant's send waits for the person's approval (`needs_approval`, rule `agent_sends_document`; level and approver are the application's: `authorize.send` replaces the default decision). A document that failed cannot be sent; a pending one can: the send waits for the render and goes when it is ready. | PRD Overview ("2 client/vendor sends wait"), applied as a neutral default; boundary (levels are the application's). |
| 13 | **Channels.** A definition declares how it goes out: `send.whatsapp: { template, params(data, reader) }` and/or `send.email: { subject, body }`, in its order (`send.order`, default WhatsApp then email). The reader's language is the recipient contact's, else the document's. The worker tries them in that order (or only the one asked for): WhatsApp when the recipient has a contact that is reachable, consented to `service` messages and the business has a number, as the template in the reader's language (or English) when approved, else as a document message when the 24-hour window is open; email when there is an address. The first that takes it wins; none: the send fails `unreachable`. | Gap map ("Delivery: an OutboundMessage document kind plus a template DOCUMENT header … attachments in mailer.service.ts"). The dispatcher (`dispatch.processor.ts`) is not this unit's file (hot-file table), so documents send through the same services (consent, template approval, `OutboundService`, `MailerService`) from their own queue. |
| 14 | WhatsApp media: the PDF is uploaded to the Cloud API (`POST /{phone-number-id}/media`, `ChannelAdapter.uploadMedia`) and sent by media id, so no public URL is needed (a local or private bucket works). whaloc accepts both; checked against `whaloc-test`. | Gap map risk ("Sending a PDF on WhatsApp needs either a media upload to Meta or a public HTTPS link"). |
| 15 | Templates get an optional `header: { type: 'document' }` (`defineTemplate`). It is part of the template's content hash only when present, so every existing template keeps its hash. `templates:sync` creates it with a DOCUMENT header; Meta's review wants a sample, which the adapter uploads through the resumable upload API when `WA_APP_ID` is set (a one-page sample PDF). Without it, the template is created without a sample. | Task ("define-template DOCUMENT header"). |
| 16 | `OutboundMessage` gets `{ kind: 'document', to, mediaId \| link, filename, caption? }` (stored as message kind `media`; its caption is the template's body, filled), and the `template` kind gets `header?: { kind: 'document', mediaId \| link, filename }`. The send processor's 24-hour check already holds for every kind but templates. A document's WhatsApp message carries no notification meta: the dispatcher's fallback reads that meta, and a document's later failure shows on its message, not as a fallback to email. | Gap map ("OutboundMessage has no image or document kind"). |
| 17 | Email attachments: `MailerService.send` takes `attachments: { filename, content, contentType }[]` (nodemailer), and the message row records each attachment's name and size, not its bytes. | Gap map ("attachments in mailer.service.ts"). |
| 18 | Tables: `app.documents` (one row per rendered version: the definition, the record, version, language, status `pending`/`ready`/`failed`, the data snapshot, `seen_as`, who asked, the file, size, pages, SHA-256, error) and `app.document_sends` (one row per send: recipient, channel, status `waiting`/`queued`/`sent`/`failed`, the message row, error). Versions are numbered under an advisory lock per record and definition, unique per record. | Default: additive tables in the framework schema (migration rule). The SHA-256 is what B8 binds an acceptance to. |
| 19 | Events: `document.requested` and `document.send_requested` (stored by `runWrite`, relayed to the two queues by subscribers), `document.rendered` and `document.failed` (stored by the worker, as the system principal of the business), `document.sent` and `document.send_failed` (resource type `documentSend`). Their rows carry ids, names, status and version, never the data snapshot, so a later webhook or live feed cannot leak it. What leaves through the API passes the read projectors as resource types `document` and `documentSend`. A send asked for while its document is pending is queued again when the render finishes (its own job id: BullMQ keeps finished jobs, so the first id would add nothing). | Plan F3 (durable outbox); B10/B15 rows ("payloads are field-filtered", "ids only"). |
| 20 | The render job tries three times (backoff); on the last failure the document becomes `failed` with the error's message, and its waiting sends fail with `document_failed`. | Default. |
| 21 | Audit: `document.render` and `document.send` (the commands, through `runWrite`, with the document's id) and the rows they create (`document.create`, `documentSend.create`: recipient, channel, state), `document.rendered`, `document.failed` and `document.sent`/`document.send_failed` (the worker, as `system`). The PDF's file row has its own `file.stored`. | CLAUDE.md rule 1; B1 decision 24. |
| 22 | Code layout: `DocumentsService` (reads, drawing) is exported from `@hykr/api`; `DocumentSender` (WhatsApp and email) is the worker's and not exported, because the channel's services read the configuration when they load and `@hykr/api`'s entry must not. `/api/documents` is reserved for the framework (`reserveRoutes('documents')`). Routes: `POST /api/documents` (render), `POST /api/documents/:documentId/send`, `GET /api/documents?entity=&id=` (a record's documents the caller reaches, newest first), `GET /api/documents/:id` (with its sends and, for people, a URL), `GET /api/documents/kinds?entity=` (the definitions for an entity, with their labels). | CLAUDE.md ("A framework feature with its own `/api/<x>` routes calls `reserveRoutes`"). |
| 23 | Personal data: the export contributor lists the documents a person asked for (metadata, not the snapshot). Erasure does not delete documents: they are business records about a record, kept with it; a send's address stays as evidence. | Default; B18 decides retention. |
| 24 | The app: `useDocuments(entity, id)`, `useRenderDocument()`, `useSendDocument()` and `<RecordDocuments entity id />` (`@hykr/app`): a record's documents with their status, "Make PDF" per definition, open (a fresh URL) and "Send to me". The sample's order screen shows it. | Plan (app parts per feature); PRD Design 7.2 ("Client page tabs: … Documents"). |
| 25 | The sample: `orders.order` (an order's number, title, date, status, its groups and lines with quantity, unit price and amount, tax lines and totals; never cost) in en/hi/te, `capabilities: []` (it shows nothing restricted, so any colleague who reads the order opens any copy), the template `order_document_v1` with a DOCUMENT header, email wording, and scripts: "pdf of order <number>", "send order <number> to me", "email order <number> to <address>". | Task ("the orders module ships the sample PDF template"). |

## Assumptions to review

| Topic | What we chose | Question for the product owner |
|---|---|---|
| Who opens a rendered copy | Readers who see at least what the requester saw (roles and capabilities), unless the definition lists the capabilities that matter | Should a copy someone sent to a customer be visible to every colleague who reads the record, whatever their role? |
| Snapshot | Each render snapshots its data; nothing re-reads live rows | Should a re-sent document be the stored copy (today) or a fresh render? Should the snapshot ever be deleted (retention)? |
| The assistant sending | Waits for the person's approval; sending to oneself does not | Which documents may the assistant send without asking (a receipt to the customer who asked for it)? |
| Recipients | A customer, a contact, a member or any email address (with `customers.message`) | Should sending to an address that is not a customer or member be allowed, or need an owner? |
| Languages | The language asked for, else English; the WhatsApp template in the recipient's language | Should a document default to the customer's language? Is a bilingual document (English + Hindi) needed? |
| Branding | Business name in the header; no logo, colours or signature image | Is a per-business letterhead (logo, colours, signature) needed for v1 (A11 branding)? |
| Fonts | Noto Sans, Devanagari, Telugu, regular and bold, bundled in `@hykr/api` (~2 MB used of 19 MB installed) | Are other scripts (Tamil, Kannada, Bengali) needed? Should fonts move to an optional package? |
| Meta template review | A sample PDF is uploaded when `WA_APP_ID` is set | Will production set the app id, or will document templates be created in WhatsApp Manager? |
| Digital signature, PDF/A | Neither; the SHA-256 is kept for B8's acceptance | Must sent PDFs be digitally signed or archived as PDF/A? |
| Mandated formats | None in the framework; the application lays out its own | Is there a mandated invoice format or e-invoicing (IRN/QR) to support in the application? |

## API sketch

```ts
// @hykr/api
defineDocument<D>({
  name: 'orders.order', label: Labels, entity: 'order',
  capabilities?: readonly string[],           // what changes what it shows; default: all of the requester's
  load(ctx: DocumentLoadContext): Promise<D>,  // ctx: { tx, principal, id, lang, record, row, business, read, children }
  render(data: D, ctx: DocumentRenderContext): DocumentLayout,   // ctx: { lang, label, money, date, business }
  fileName(data: D, lang): string,            // '.pdf' added when missing
  send?: { whatsapp?: { template, params(data, reader) }, email?: { subject(data, reader), body(data, reader) } },
  authorize?: { render?(p, record), send?(p, { document, to }) },   // AuthorizeResult | null
})
documents                                       // the registry (contributes: { documents })
DocumentLayout, DocumentBlock                   // Zod schemas and types
DocumentEngine { kind; render(layout, meta): Promise<{ bytes, pages }> }, DOCUMENT_ENGINE,
createPdfEngine(), createFakeEngine(), documentsConfig()
DocumentsService (get, list, reaches, urlFor), documentsFeature

// @hykr/contracts
RenderDocumentSpec ('document.render', POST /api/documents, tool render-document)
SendDocumentSpec   ('document.send', POST /api/documents/:documentId/send, tool send-document)
DocumentInfo, DocumentSendInfo, DocumentRecipient, DocumentKindInfo, DocumentStatus

// @hykr/channels
OutboundMessage += { kind: 'document', … }; template header; ChannelAdapter.uploadMedia(from, file)
TemplateSpec.header?: { format: 'DOCUMENT' }; WhatsAppConfig.appId (sample upload)

// @hykr/notifications
TemplateDef.header?: { type: 'document' }

// @hykr/api-client
api.documents.render({ document, id, lang? }) / send(documentId, to, channel?) / get(id) / list(entity, id) / kinds(entity)

// @hykr/app
useDocuments, useDocumentKinds, useRenderDocument, useSendDocument, <RecordDocuments entity id />
```

Env: `DOCUMENTS_ENGINE` (`pdf` | `fake`), `WA_APP_ID` (optional).

## Test plan

- `framework/api/test/framework/documents.test.ts` (unit, no boot): the layout schema refuses a
  bad block; script runs (Latin, Devanagari, Telugu, digits and punctuation kept with their run);
  HarfBuzz shaping of Hindi and Telugu conjuncts (fewer glyphs than code points, no `.notdef`);
  the real engine writes a valid PDF (`%PDF-`, `%%EOF`), embeds the three fonts with ToUnicode
  maps, breaks pages on a long table and fills `{page}`/`{pages}`; the fake engine's text; the
  configuration's refusals; `defineDocument`'s checks.
- `framework/api/test/framework/documents.e2e.test.ts` (fixture `features/documents`: a `memos`
  module with a line only owners see (a read projector by capability), a role that only reads,
  and three documents: one without `capabilities`, one naming the capability, one with `[]`):
  - render → pending → ready, the PDF stored, its text, version numbers, SHA-256, `GET` with a URL
    that serves it; the list of a record's documents; kinds;
  - another business: 404 on render, get, send and the URL; left out of the list;
  - a hidden field stays hidden: staff's render does not show it; the owner's copy (which shows
    it) is 404 for staff; a definition with `capabilities: []` is opened by everyone who reads;
  - the assistant renders and reads status without a URL; its send parks and is audited, and runs
    once approved; a refused send is audited as denied;
  - sending: by email with the PDF attached (Mailpit), by WhatsApp as a template with a document
    header after a media upload (stand-in Cloud API), as a document message inside the window,
    fallback to email, `unreachable`; a send before the render finishes waits and goes;
  - a template must have a document header; a failed render.
- `framework/channels` and `framework/notifications` unit tests: `toGraph` for the document kind
  and a template header, `uploadMedia`'s multipart request, `create` with a DOCUMENT header (and
  the sample upload with an app id); `defineTemplate` with a header and an unchanged hash without.
- `application/api/test/domain/order-document.e2e.test.ts`: the order PDF in English and Hindi
  (fake engine: its text; real engine: a valid PDF with fonts), cost never in it, another business
  404, the scripted assistant's "pdf of order …" and "send order … to me" (approval).

## Deferred

- Images in documents (a logo, a signature, photos): the layout has no image block yet; per-business
  branding is A11's.
- A Chromium engine (HTML and CSS templates): the interface allows a second engine.
- Digital signatures and PDF/A.
- Notifications that carry a document (the dispatcher, `dispatch.processor.ts`, is not this unit's
  file): a notification cannot attach a PDF; send it with `document.send` from a subscriber.
- Following a WhatsApp send's later failure (the message row shows it; the send stays `sent`, and
  no fallback to email happens after the fact).
- Right-to-left scripts, other Indic scripts, hyphenation and justified text.
- Deleting documents and their files (retention) and a re-render of a stored snapshot after a
  template change.
