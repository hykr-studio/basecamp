# A6: agents a business makes, with triggers and a run log

## Summary

A business's people make their own agents. An agent is a record (the platform entity `agent`,
`/api/agents`): a name, instructions in plain words, the person it acts for (its owner, the
person who made it), a scope (the assistant's tools it may use), a budget, and triggers: a time
(once), a schedule (recurring), an event, a condition, an inbound message, an @-mention, or a
webhook. When a trigger fires, the `agents` feature puts a run on the `agents.run` queue. In the
worker the run passes the turn hooks like any assistant turn (credits, the model policy), then the
assistant runs with the agent's instructions and what fired it (as data), with only the tools in
its scope. Its tools call the API with a **run token**: the API sees an agent (`agent:<id>`)
acting for the owner, in the owner's business, with the owner's roles and capabilities as they
are now, narrowed by the scope. So an agent never does more than its owner may, and every write
is audited under the run, the agent and its version. A write that waits for approval suspends the
run (A7) and the owner decides it; the run goes on after. Every run is in the run log
(`/api/agent-runs`): what fired it, its status, what it said and did, what it used.

The framework ships the mechanism only. What agents a business is offered ready-made (templates)
is the application's: the sample's meetings module offers "Monday: summarize open to-dos" (a
recurring agent) and "Meeting closed: draft a follow-up" (an event agent). The assistant drafts
an agent from one line ("create an agent to …"): the draft is an approval card, and approving it
creates the agent. The app (`agentsPlugin()`) and the back office (Agents) have the list, the
editor and the run log.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | An agent definition is a **platform entity** (`AgentSpec`, `app.agents`, `/api/agents`), like the business's memory (A8): CRUD, validation, audit, history, approvals, live updates and the app's data hooks come from the spec. Its triggers, scope and budget are JSON fields checked by the spec's schemas and, on every write (and on an approval's replay), by the feature against what the server has (tools, entities, connections, cron). A bad definition is 400 `invalid_agent` with every problem listed. | Plan A6 ("contracts/platform/agent-definition.ts … features/agents"); gap map extension point 1 (a platform entity like pages). |
| 2 | **Who.** `agents.create` (owner and admin by default) makes agents of one's own. `agents.manage` (owner and admin) reads every agent and run log of the business, pauses and resumes them, runs them now and deletes them. Only the owner changes what an agent does (name, instructions, triggers, scope, budget); a manager who is not the owner may change only `status`. The owner is the person who creates it and never changes: another person's instructions never run with the owner's rights (so a manager's Run now takes no note either: decision 20). A customer and a guest have neither capability. An application gives its own roles the capabilities. | PRD 1 §6 ("an agent acts for a named owner and can never exceed that person's permissions"); gap map owner question ("who may create agents"); default, fail closed. |
| 3 | **The assistant drafts, the person approves.** The assistant gets the entity's tools (`create-agent`, `update-agent`, `delete-agent`, `list-agents`, `get-agent`, `run-agent`); its create, update and delete park for the person it acts for (the approval card shows the draft). Approving creates the agent, owned by that person. The scripted model's `agents` set drafts from "create an agent to <job> [every <day> at <time>] [using <tool>, …]". | PRD 1 §6 ("describe a job in one line; the assistant drafts the agent, schedule and scope"); task note ("the assistant drafts the definition for approval"). |
| 4 | **Scope** is a list of the assistant's tool ids (at most 50). The run's model gets only those tools (every other tool is in the turn's `withoutTools`). The agent's own tools (`*-agent`, `list-agents`, `summarize-agents`, `run-agent`) and the canvas tools are never in a scope: an agent never makes or starts agents. Server side, the run token's principal carries what the tools in scope reach (`agent-run.read:<entity>`, `agent-run.write:<operation>`): a generated entity tool reads its entity (a write tool also writes with its operation), a command's tool runs that command. The `agents.scope` write hook refuses any other write (403 `agent_scope`, audited as denied), and the `AgentScopeInterceptor` refuses a GET of an entity's routes (`/api/<plural>…`) outside the scope (403 `agent_scope`) and every request to `/api/agents`, `/api/agent-runs` and `/api/agent-templates`. A contributed tool in scope (`list-comments`, `recall-memory`) reads through its own route, still as the owner; its writes count only when the operation's own tool is in scope. | Gap map owner question ("what does scope mean"); gap map risk ("scope must narrow it"); default, fail closed. |
| 5 | **Identity: a run token.** Each run's tool calls carry `x-agent-run: <token>` and `x-run-id`, never the assistant's key. The token is an HMAC of the run id with `AGENT_API_KEY` (only server processes hold it), so it is never stored and a resumed run (A7) makes the same one. The `agent-run` identity provider checks it, finds the run (running or waiting) and its agent (active), and answers: actor `agent:<agent id>`, acting for the owner, in the run's business (fixed: a header naming another is 403), channel `background`, the run's agent version, and the scope as the identity's `narrowing` (decision 28). PrincipalGuard then resolves the owner's standing as it is now (a person no longer in the business: 403 `not_a_member`). | Plan A6 ("run-token identity acting for its owner (never more than the owner)"); F4 (`AgentIdentityProvider`, "the business, when the credential fixes it (a run token …)"). |
| 6 | **Agent version.** `agent:<id>@<model>#<hash>`, where the hash covers the assistant's own version (its instructions) and the agent's instructions, scope and step limit. It is stored on the run and stamped on every audit row of it. | PRD 1 §7.2 ("agent version = ID + model + prompt hash"). |
| 7 | **The run.** The worker loads the run, checks that the agent is active, the owner still belongs to the business and the budget has room (otherwise the run is `refused` with the reason), gates it as a turn (`TurnInfo.kind: 'agent'`: credits and the model policy decide; a refusal is `refused`), and runs the assistant (text surfaces, the business's time zone, at most the budget's `maxSteps` steps, default 6) on one message: the instructions, a line saying which agent and trigger started it, and what fired it as data (JSON, at most 4000 characters, projected for the owner). It answers in one go (no stream). The reply and its tool calls are kept in the run log and in the agent's thread. | Plan A6; gap map extension points ("a new queue agent-run … calls ChatService (or a new AgentRunService) with the run's principal and a dedicated thread"). |
| 8 | **Threads.** `app.threads` gets `kind` (`chat` by default, `agent`) and `agent_id`. Each agent has one thread, owned by its owner; each run adds its message and the reply (with its run id). A run reads no history: each starts from its own message. The person's current chat thread is only ever a `chat` thread, so runs never land in their conversation. | Task note ("threads.kind"); gap map extension point ("so autonomous runs do not land in the person's conversation"). |
| 9 | **Parked writes.** A write of the run that waits for approval suspends the run (A7); its approval is the owner's to decide (their own assistant's request). The run is `waiting`. When it is decided, A7's resume finds the run in the agent's thread (its owner is the requester), the `agents` turn hook checks the agent again (active, budget) and gives back only the scope's tools, and the run token carries on (the resumed request context keeps `agent`). The stored `thread.continued` event now says how the run went on (`resumed`, `refused`, `failed`); the `agents.continued` subscriber closes the run: `done` (or `waiting` again when another approval of it is pending), with the continuation's reply. | A7 decisions (deferred: "A6 adds its own delivery"); PRD 1 KR ("one agent task runs end to end under approvals"). |
| 10 | **Triggers** (at most 10 per agent), each a row in `app.agent_triggers` kept in step with the definition by the `agents.definitions` write hook, in the write's transaction. An unchanged trigger keeps its row (its id, when it fires next, a condition's records seen, the run log's link to it): the stored spec and the new one are both read through the schema and compared with their keys sorted, since jsonb gives keys back in its own order. So a rename, a pause or a resume fires nothing again; a trigger that changes starts again under a new row: `once { at }`, `recurring { cron, timeZone? }` (five fields, the business's zone by default, at most every 5 minutes), `event { on: [names or prefixes], where? }`, `condition { entity, where, everyMinutes }`, `message { contains? }` (WhatsApp), `mention {}`, `webhook { connectionId, on }`. | PRD 1 §7.1 (the seven trigger kinds); review fix (a key-order comparison recreated every trigger on every write, so a condition fired again after a pause). |
| 11 | **Time triggers.** The `agents.tick` schedule (every 30 seconds, queue `agents.tick`) takes the due `once`, `recurring` and `condition` triggers of its own queue prefix (`FOR UPDATE SKIP LOCKED`), records one run each in the same transaction as it moves the trigger on (`once`: then never again; `recurring`: next time from now, so missed times while the worker was down run once, not many times), queues them after it commits, and evaluates conditions. A paused agent's due triggers move on without a run, so resuming it does not fire what it missed. By the real clock (a test may pass its own `now` for the triggers), it also gives a run queued for 30 seconds without a job a new one, and fails a run that has been `running` for 15 minutes (its worker died). | Gap map extension point ("upsertJobScheduler per definition"); default: one sweeper over a table is restart-safe and testable where one BullMQ scheduler per definition is not. |
| 12 | **Event triggers.** The `agents.events` subscriber reads every stored event (except the agents' own). For each active agent of the event's business with a matching trigger, the record must be one the owner may read now (an entity's scoped read, or a contributed `liveResources` check; anything else is skipped), and `where` (field equals value, on the record as the owner sees it) must hold. The run's data is the event passed through `eventFor` for the owner (fields hidden from them stay hidden). A record that is gone (a delete) is one the owner can no longer read: its event starts nothing. | Gap map extension point (a subscriber like NotifyService); F5 (`eventFor` before anything leaves). |
| 13 | **Loops.** An event made by a run of the same agent never starts it again. A run started by an event (or a mention) of another agent's run is one level deeper; nothing starts deeper than 3. An agent has at most 10 runs queued or running at once; more are skipped (logged). | Gap map risk ("feedback loops … loop guards are needed"). |
| 14 | **Conditions.** `where` is the list grammar of the entity (the same filters as its list tool), with `$now` and `$today` (and `±<n>m/h/d`) for moving times, checked every `everyMinutes` (5 to 1440, default 15) as the owner (their scope, the plugins' list checks). Each record that newly matches starts one run (at most 10 per check); a record that stops matching may start one again later. The entity must be readable in the agent's scope. | Default: a condition is a query that becomes true for a record; polled, because a time passing raises no event. |
| 15 | **Inbound messages.** An inbound hook sees each WhatsApp message the code did not answer itself; each active agent of the business with a `message` trigger (with `contains`: when one of its words is in the text) starts a run with the sender and the text as data. It never takes the message: the assistant answers the person as before. The owner must hold `backoffice.use` (they see customers' conversations), at save and when it fires. | Gap map extension point ("a hook in InboundProcessor"); Meta policy risk (the reply stays the business assistant's). |
| 16 | **@-mentions.** The feature registers the mention kind `agent` (B16): an agent of the comment's business that is active, has a `mention` trigger and whose owner may read the record (and, for a team-only comment, holds `comments.internal`) may be named `@[Name](agent:<id>)`; any other is refused like a person who cannot read it. The `agents.mentions` subscriber starts a run per `comment.mentioned` for an agent, with the comment (excerpt, author, record) as data. | B16 decision 7 ("A6 adds `agent`"). |
| 17 | **Webhooks.** Through B10: the feature adds the connector `agent-webhooks` (Standard Webhooks signing, a generated secret). A person with `integrations.manage` adds a connection; an agent's `webhook` trigger names it and the event types it takes. Each stored inbound event of that connection starts a run per matching agent, with the event as data. An application may let agents take events of its own connector too, by contributing `agentWebhookHandler('<connector>')`. Other connectors' events are unchanged (an event no handler takes is still `ignored`). | Plan A6 ("webhook via B10"); B10 decisions (connector handlers). |
| 18 | **Budget** per agent and period (`day`, `week`, `month` in the business's time zone; default month): at most `runs` runs, `tokens` tokens and `credits` credits (A3's minor units, from the usage events of its runs). At 100% of any of them a run is `refused` (`agent_budget_exhausted`), also a resume. The business's own caps (A3) apply on top, through the credits turn hook. One run may overshoot (usage is known after it). | Plan A6 ("budget via A3"); PRD 1 KR ("runs that exceed their credit cap: zero (auto-pause at 100%)"). |
| 19 | **The run log** is `app.agent_runs`: what fired it (kind and a short description), status (`queued`, `running`, `waiting`, `done`, `failed`, `refused`), why, the reply, the tool calls (as the chat summarizes them), tokens, model, agent version, depth, times. `GET /api/agent-runs?agentId&status&cursor&limit` (newest first) and `GET /api/agent-runs/:id` (with the run's messages) for the owner and holders of `agents.manage`; anyone else, another business included, gets 404. A manager who is not the owner gets an outline (trigger, status, reason, tool names and outcomes, usage): the reply, the messages and what the tools showed are the records as the owner reads them, which the manager may not. It is bookkeeping, written by the feature (like deliveries and the inbox), not through `runWrite`; every write a run makes goes through it. `agent.run.finished` is stored when a run ends (for live updates and subscribers). | Gap A6 ("run log"); CLAUDE.md rule 1 (domain writes only). |
| 20 | **Run now**: the command `agent.run` (`POST /api/agents/:agentId/run`, tool `run-agent`), for the owner or `agents.manage`, of an active agent. It records a queued run and the stored event `agent.run.requested` in its transaction; the `agents.requested` subscriber queues it. Its optional `note` is the run's data, which steers the run; only the owner may give one (anyone else, a manager or a manager's assistant: 403 `agent_note_owner_only`, audited as denied). A manager runs it without one. | Default; the editor's "Run now"; review fix (a manager's note ran with the owner's rights and could read what the manager may not). |
| 21 | **Pausing** (`status: 'paused'`) stops every trigger and refuses runs and resumes of it. Deleting an agent deletes its triggers, run log and thread; the audit trail keeps every write its runs made. | Default; gap map owner question (run-log retention). |
| 22 | **Agent templates** are the application's: `defineAgentTemplate({ key, name, description, instructions, triggers, scope, budget })` (names and descriptions in every language), contributed as `agentTemplates`; `GET /api/agent-templates?lang=` lists them in that language with whether this server can make them, and every tool an agent may be given here (the editor's choices). An agent made from one keeps its key (`template`). The framework ships none. | Task ("agent templates are application content"); plan boundary section. |
| 23 | **Live.** `agent.run.finished` (resource `agent_run`) reaches the owner and holders of `agents.manage` (a `liveResources` check). Agent records' own events are an entity's. | B15. |
| 24 | **Personal data.** Erasing a person deletes the agents they own (with triggers, runs and thread); their export lists their agents and runs (what fired them, status, reply). | F5 decision 25; B18 direction. |
| 25 | **Routes.** `/api/agents` is the entity's (its plural is reserved by the catalog); `/api/agent-runs` and `/api/agent-templates` are reserved with `reserveRoutes`. An agent run's token reaches none of them (403). | CLAUDE.md. |
| 26 | **App and back office.** `agentsPlugin()` (`@hykr/app`): `/agents` (the business's agents for a manager, one's own otherwise, with status and last run), the editor (from a template or blank: name, instructions, triggers, the tools in scope, budget, pause, run now, delete) and the run log with each run's messages. The back office's Agents screen (for holders of `agents.manage` or `agents.create`): the list, the same editor in a desktop layout, and the run log. The UI words are English, as the other framework screens. | Coverage checklist ("Studio-made helpers, run log": desktop Helpers, phone OwnerHelpers); B16 decision 24. |
| 27 | Sample: the meetings module contributes two templates and the scripted model's scripts for their runs: `meetings.weekly-todos` (every Monday 09:00, `list-todos`: "N open to-dos: …") and `meetings.follow-up` (on `meeting.closed`, `list-todos` and `create-note`: a follow-up note listing the meeting's open to-dos). | Task ("Sample demo: meetings"). |
| 28 | **A run's limits are not route scopes.** An identity provider's `scopes` are a scoped credential's route scopes (an MCP token's `<module>:read` and `<module>:write`, A1), which `PrincipalGuard` checks against what each route declares. A run's limits are finer (an entity's reads, an operation's writes) and are enforced by this feature (`AgentScopeHook`, `AgentScopeInterceptor`, the agents' own rules), so the run identity returns them as `narrowing` (a new `AgentIdentity` field): `PrincipalGuard` puts them in the principal's `scopes` (so `isAgentRun` and the checks see them) but never checks them against a route. A run token is therefore not a scoped credential: the routes its tools call need no route scope, and a contributed tool's own route (comments, memory) is still reached as the owner. | Review fix (after A1, every run's call was 403 `out_of_scope`); fail closed: dropping the limits instead would have turned every run check off. |

## Assumptions to review

- **Who makes agents.** Owners and admins (`agents.create`). Should staff make their own (they act
  only with their own rights anyway)?
- **Ownership never moves.** When an owner leaves, their agents' runs are refused until someone
  deletes them. Should a manager be able to take an agent over (as its new owner, after reading
  its instructions)?
- **A manager may pause, run and delete anyone's agent, but not edit it.** Right?
- **Scope is tools.** Not modules or records. Should a scope also narrow to records (one project)?
- **Approval of an agent's writes.** The owner decides what their agent's run asks for (like their
  assistant's). Should a business be able to send agent runs' requests to a named approver?
- **Inbound messages.** An agent sees a customer's WhatsApp message only if its owner holds
  `backoffice.use`, and it never answers the customer itself (the assistant does). Should an
  agent be able to take over a conversation (Meta's policy allows the business's own tasks)?
- **Webhooks.** Agents take events from their own connector (`agent-webhooks`); other connectors
  only when the application opts in. Should every connection be open to agents?
- **Budgets.** Runs, tokens and credits per day, week or month; a run may overshoot once. Is an
  80% alert per agent needed (the business's alerts exist)?
- **Deleting an agent deletes its run log** (the audit trail keeps its writes). Should the log be
  kept for a period instead?
- **Conditions are polled** every 5 to 1440 minutes. Is a 5-minute floor right?
- **What a trigger hands the run.** An event's or a mention's record comes as its owner reads it,
  even when the agent's scope has no tool for that entity (the owner asked for it by naming the
  event). Should the data be cut to what the scope reads?
- **Deleted records.** An event about a record that is gone (`*.deleted`) starts nothing, since the
  owner can no longer read it. Should delete events start agents with the record as it was?
- **Depth 3, 10 runs at once** per agent: are these the right guards?
- **A note on Run now is the owner's only.** A manager runs anyone's agent but cannot add a note
  (403). Should a manager instead be able to send a note that the run gets without the owner's
  rights (for example only as text in the run log, never to the model)?
- **Run limits are not MCP scopes.** A run token reaches every route its owner reaches except
  what the run's own checks close (entity reads and every write outside the scope, the agents'
  routes). Should a run also be limited to routes that declare a scope, as MCP tokens are (which
  would close contributed tools such as comments and memory until their routes declare one)?

## Test plan

- Unit (`@hykr/api`): cron next times and the 5-minute floor, `$now`/`$today` in conditions,
  trigger matching (`event`, `message`), the run token, the prompt (data block, truncation).
- Unit (`@hykr/agents`): the `agents` script set drafts a definition from one line.
- Fixture e2e (`framework/api/test/framework/agents.e2e.test.ts`, fixture feature `agents`):
  - definitions: create needs `agents.create`; a member without it is 403; another member and
    another business get 404; a manager reads every agent and may change only `status`; bad cron,
    unknown tool, an agent tool in scope, a condition on an entity outside the scope: 400;
    the assistant's draft parks and approving it creates the agent, owned by the person;
  - a run now: the run log goes `queued` → `done` with the reply; the run is in the agent's
    thread, not the person's current one; its tool calls are audited as `agent:<id>` acting for
    the owner, channel `background`, under the run id with the agent version;
  - never more than the owner: the run cannot read a record its owner cannot (404); an out-of-scope
    write with the run token is 403 `agent_scope` and audited as denied; an out-of-scope entity
    read is 403; a token for a finished run, or a forged one, is 401; a run whose owner left
    is refused;
  - a parked write: the run is `waiting`, the approval is the owner's; approving resumes it and
    the run is `done` with the continuation; the follow-on write is audited under the same run
    and agent;
  - triggers: recurring and once through `tick(now)`; an event (and not its own run's events, one
    level deeper for another agent's, none for an owner who reads no such records); a condition
    (one run per newly matching record); an @-mention (and a refused mention of an agent whose
    owner cannot read the record); an inbound WhatsApp message (the hook's body, called directly,
    once per message); a signed webhook to an `agent-webhooks` connection;
  - editing keeps unchanged triggers: a condition's trigger row, its hits and the run log's link
    to it survive a pause, a resume and a rename with the whole definition again, and the next
    tick starts nothing; a changed trigger gets a new row (unit: `sameTrigger` across key orders,
    defaults, list order);
  - a manager's Run now with a note is 403 `agent_note_owner_only` (audited, no run); without a
    note it runs; the owner's note works;
  - the run identity carries its limits as `narrowing`, not route `scopes`;
  - budget: a second run in a period with `runs: 1` is refused; a paused agent fires nothing;
  - hidden fields: an event's record is projected for the owner in the run's data;
  - live: `agent.run.finished` reaches the owner, not another member;
  - erasure deletes the person's agents.
- Sample e2e (`application/api/test/domain/agents.e2e.test.ts`): Ana makes both meetings
  templates; Monday's tick runs the summary ("2 open to-dos: …"); closing a meeting runs the
  follow-up, which writes a note on the meeting.

## Deferred

- An 80% alert per agent (the business's credit alerts exist).
- Taking over another person's agent; agents shared across businesses (a platform library, B19).
- Agents that answer a customer directly on WhatsApp.
- Agents on every connector without the application opting in.
- Retention of the run log after the agent is deleted.
- Multi-step workflows (several agents in a chain) beyond event triggers.
