# B20: bulk import

## Summary

Moving a business onto Basecamp means bringing its records from somewhere else: a spreadsheet,
another product's export, an older database. The `imports` feature reads a CSV, JSON or NDJSON
file of one entity's records and writes them **through the write path**, row by row, exactly as
the app's own create and update would: validated against the entity's spec, scoped to the
importer, checked by the entity's rules, plugins, field policy, write hooks, feature flags and
approval levels, and audited. It runs as a long-running job (B11) in the worker, reports
progress, and finishes with counts and an **error report file** (B1) listing every row it could
not write and why, in a form that can be fixed and imported again.

Each row carries its id in the other system (the **key** column). The feature remembers which
record each key became (`app.import_keys`, per business, entity and **source**), so running the
same import again updates the records it made before (or leaves them, `existing: 'skip'`)
instead of making them twice. A column can also name another entity's records by their keys in
the same source (`refs`), so related records (projects, then their tasks) import in turn.

Three ways in:
- `basecamp import <entity> <file> --as <email> [--dry-run]`: the operator's command. It stores
  the file, starts the import as that member of the business, follows the job and writes the
  error report next to the file.
- `POST /api/imports` after uploading the file (`for: { entity: 'import', field: 'file' }`):
  for the apps. `api.imports.start(...)` in `@hykr/api-client`, `useStartImport()` in `@hykr/app`.
- `importFile(context, options)` from `@hykr/api`: the same thing for server code and tests.

A **dry run** does everything a real run does, inside transactions that are rolled back: the
counts and the error report say what a real run would do, and nothing is written.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | One feature, `framework/api/src/features/imports/`, with the tables `app.import_keys` (the external-id map) and `app.import_batches` (a run's checkpoints), in `framework/db/src/schema/imports.ts`. It reserves `/api/imports`. Its contracts are `contracts/src/platform/imports.ts` (capability, options, result, the start command) and the entity trait `imports` in `contracts/src/framework/imports.ts`. | Plan conventions; plan B20 row ("`features/import`"). The feature is named `imports` (plural, like `jobs`, `files`). |
| 2 | **An import is a job** of the framework's kind `imports.records` (`defineJob`, contributed by the feature). Its `submit` does the work in the worker, as whoever started it (`ctx.starter()`), and returns its finished update with the error report as bytes; the job keeps the report as its result file. Progress is reported after each batch. The job is about no record: only its starter (and the business's system principal) reaches it and its report. | Plan B20 row ("a B11 job"); B11 decisions 4, 11 (work done in `submit`, jobs about no record). |
| 3 | **Starting is a write.** `import.start` (`POST /api/imports`) is a command (`expose: 'human'`, no tool) through `runWrite`: validated, idempotent, audited, and it may park (an application's level rule on `import.start` makes imports wait for someone). Its `run` calls `startJob`. The input names the entity, the file and the options (decision 9). | CLAUDE.md rule 1; B11 decision 3 ("starting is a write"). |
| 4 | **Who may import:** a person (no assistant, no contact) holding the capability `imports.run`, which the framework gives `owner` and `admin` (an application re-grants it with `roleOverrides`, a business with its roles settings). The entity must be served, not opted out (`traits.imports: false`), not a child record (`traits.parent`: children are saved through their parent's command), creatable and updatable by people (`expose.create` and `expose.update` not `'internal'`: an import never writes what nobody could write one record at a time), not switched off by a feature flag for the business (404 like its routes), and the person must be allowed to create it (`def.decide(p, 'create')` not `deny`). A `refs` entity must be served and readable. | Fail closed: a bulk write is powerful; the built-in roles are generic (boundary rule). B5 decision 20 (children through the parent). A11 (flags: 404). |
| 5 | **Every row goes through `runWrite`** with the entity's own operation (`entityOp(def, 'create')`, `entityOp(def, 'update', { id })`), so an import can never do what the person could not do one record at a time: their access, the entity's rules (only refusals count inside commands, but these are entity operations: parks count too), plugins (money, field policy, custom fields, shared records), write hooks (files, feature flags), the application's level rules on `<entity>.create` / `.update`, undo windows and audit all apply unchanged. `insertMany` with a batch command (one multi-row audit statement) was not used: it would need the import to repeat runWrite's authorize step for every row, and an application's level rule on `<entity>.create` would not see a batch command. | CLAUDE.md rule 1 ("one write path"); plan B20 row ("through runWrite/insertMany"): runWrite chosen, insertMany rejected for the reason given. |
| 6 | **Batches.** Rows are written in batches of `IMPORTS_BATCH_SIZE` (100): one transaction per batch, one savepoint per row. A row that fails rolls back to its savepoint and is reported; the others in the batch commit together. In-process events of a batch are published after it commits; stored events (the outbox) are written by each row's write as always. | Plan ("writes in batches"); default (one commit per hundred rows instead of one per row). |
| 7 | **Rows that would wait are not parked.** A row whose write would need approval is rolled back and reported `needs_approval` with the rule's reason: an import never files hundreds of approvals, and never writes what would wait. The approval of `import.start` (when an application declares one) does not approve the rows: the rows are written as the starter **without** `approvedBy`, so each is decided on its own. | Fail closed; default. Assumption to review. |
| 8 | **External ids.** Every row needs a key (the `key` column, default `id`): an empty key is `missing_key`, a key seen earlier in the same file is `duplicate_key` (that row is not written). The map row `(tenant, entity, source, external_id) → record_id` is written in the row's savepoint, with the job that last wrote it. It is locked (`FOR UPDATE`) while the row is written, so two imports of one source never make a record twice: the second one's insert of the map row fails and its row is reported `conflict`. A key the map knows: the record is updated with the row's values (`existing: 'update'`, the default), or left alone (`'skip'`, counted `skipped`); a row that would change nothing (or that has only its key) is counted `unchanged` and not written. A mapped record that is gone, or that the importer no longer reaches, is `not_found`: a re-run never brings back a record someone deleted. | Gap ("external-id mapping for idempotent re-runs"); fail closed. |
| 9 | **Options** (`ImportOptions`): `entity`; `file`; `format` (`csv`, `json` (an array of objects), `ndjson`; default from the file's type and name); `key` (default `id`); `source` (lower case, default `default`: keys are unique per business, entity and source); `columns` (file column → field, `null` to leave a column out); `refs` (field → entity: the column holds that entity's keys in the same source, resolved through the map to its record, which the importer must reach, else `unknown_reference`); `existing` (`update` or `skip`); `empty` (`omit` or `null`: what an empty CSV cell means); `dryRun`. | Gap; default. |
| 10 | **Columns.** A column's field is its `columns` mapping or its own name. Columns starting with `_` are ignored (the error report's own columns, decision 13). Any other column that is not a field of the entity's create or update schema fails the import before anything is written (`unknown_columns`, listed): a typo in a header must not drop data silently. The key column needs no field. | Fail closed; default. |
| 11 | **Values.** CSV cells are text. Each is given to the field's schema as it is, or, when the schema refuses the text, as the number, `true`/`false` or JSON it spells; the schema then validates it as the app's create would. An empty cell leaves the field out (`empty: 'omit'`) or sets null where the field takes null (`'null'`). JSON and NDJSON values are used as they are. Values are checked against the create schema (new records) or the update schema (existing ones) before the write, so the report names the field (`_field`) and every problem (`invalid`). | Plan B20 row ("validates against the spec"). |
| 12 | **Create, then update.** A new record is created with the fields of the create schema; fields only the update schema has (a to-do's `done`) are then written by an update of that record, in the same savepoint (two audit rows: create, update). On an existing record only the update schema's fields are compared and written. | Default: faithful migration of state that is not set at creation. |
| 13 | **The error report** lists each row that was not written (and each `needs_approval` row): `_row` (the row's number in the file, from 1 after the header), `_code`, `_field`, `_message`, then the row's own columns as given. CSV in, CSV out; JSON and NDJSON in, NDJSON out. Fixed rows can be imported again from the report as it is (the `_` columns are ignored; the rows already written are found by their keys). Named `<input name>.errors.csv`; at most `IMPORTS_REPORT_ROWS` (10 000) rows, and never larger than the files feature's cap: past either, the report says it was cut (`reportTruncated`). No report when every row was written. | Gap ("error report file"); B1 (`storeBytes`), B11 (result files). |
| 14 | **Error codes** (`ImportErrorCode`): `invalid` (the schema refused a value), `missing_key`, `duplicate_key`, `unknown_reference`, `not_found`, `forbidden` (a rule, access or feature flag refused; `_message` is its reason and `_field` its rule), `needs_approval`, `conflict` (a stale record or a concurrent import), `failed` (anything else, such as a database constraint, said without the database's detail, which could name another business's value). | Default; tenancy (no detail from the database). |
| 15 | **Dry run.** Each batch runs exactly as a real run, then its transaction is rolled back: nothing is stored (records, map rows, checkpoints, events, approvals, undo windows). One thing outlives it: a row refused by a rule is audited as refused, as every refused write is (runWrite writes that row outside the transaction), so a dry run's refusals are on record. | Gap ("--dry-run"); CLAUDE.md rule 1 (pipeline.ts is not this unit's hot file). |
| 16 | **Retries resume.** A job's `submit` may run again (B11 decision 4). Each committed batch stores its counts and problem rows in `app.import_batches` in its own transaction; a retry skips those batches and reuses what they recorded, so the counts and the report cover the whole file once. The checkpoints are deleted when the import finishes. A dry run keeps none (they roll back), so a retried dry run starts over. | B11 decision 4 ("submit must be safe to repeat"). |
| 17 | **Limits** (technical, per deployment): `IMPORTS_MAX_ROWS` (50 000; more fails the job `too_many_rows` before any write), `IMPORTS_BATCH_SIZE` (100), `IMPORTS_REPORT_ROWS` (10 000), `IMPORTS_TIMEOUT_S` (14 400: the job's deadline and its submission's time limit). The file's size is the files feature's `FILES_MAX_BYTES`. A file that does not parse fails the job `unreadable` with the line. | Boundary rule (technical defaults only). |
| 18 | **Audit.** `import.start` (the person, through runWrite), `job.start` and the job's steps (B11), one row per record written (`<entity>.create` / `.update`, as the importer, with the job id as the run id, so a migration's rows can be found together), a `denied` row per refused write, and `import.done` at the end (the importer; resource type `job`, the job's id; after: the counts, the source, the entity, whether it was a dry run). | CLAUDE.md rule 1; task ("parked writes are audited"). |
| 19 | **The upload.** `POST /api/files` takes `for: { entity: 'import', field: 'file' }`: the files feature gains a small registry, `uploadTargets`, of upload targets that are not an entity's field (`{ type, field, accept, maxBytes?, may(p) }`), checked like a field's (type, size, then `may`: here `imports.run`). Such a file stays the uploader's own until it is swept (it is never put on a record); the import's start checks that the starter reaches it (`inputFiles`). An entity named like a target stops the start. The import takes CSV, JSON and NDJSON (`text/csv`, `text/plain`, `application/json`, `application/x-ndjson`). | B1 decision 7 (upload for a target, reached by the uploader); B11 (`inputFiles`). |
| 20 | **The CLI.** `basecamp import <entity> <file>` loads the application's compiled server, opens a Nest application context with the framework and the modules but **no processors and no HTTP** (it never takes another process's queue work), resolves `--as <email or user id>` in `--tenant <id>` (default: their default business) as a person on the `api` channel, stores the file as theirs, runs `import.start` through runWrite, and follows the job until it finishes, printing its progress. The worker runs the job (`basecamp dev`, `basecamp start worker`): the command says so if nothing picks it up. It writes the report to `--report <path>` (default `<file>.errors.csv` or `.ndjson`) and exits 0 when every row was written (or would be), 1 when some were not or the job failed, 2 when the import waits for approval. It refuses `STORAGE_DRIVER=memory` (the worker could not read the file). | Plan B20 row (`basecamp import <entity> <file> [--dry-run]` in framework/cli); CLAUDE.md (the CLI loads `application/api/dist/server.js`). |
| 21 | **The map's data.** `app.import_keys` holds ids only (the other system's and ours) and is the business's: it is not personal data the framework erases. Deleting a record leaves its map row, so a re-run reports `not_found` (decision 8). | Default. Assumption to review. |
| 22 | **The app.** `@hykr/api-client`: `api.imports.upload(bytes, { name, mime })` and `api.imports.start(options)`. `@hykr/app`: `useCanImport()`, `useStartImport()` (upload a picked file, its type from its name, then start) and `<ImportRecords entity />` (pick a CSV or JSON file, optionally a dry run first, then `<JobProgress>` and the counts, with the report among the job's files). The sample's to-dos screen shows it to people with `imports.run`. | Task ("Sample demo: todos: CSV import"). |
| 23 | **Sample.** The to-dos module ships `import/todos.csv` (a small file with a key column `legacy_id`, a done row and a cost) and `application/api/test/domain/todo-import.e2e.test.ts`, through the typed client: a dry run that writes nothing, the import, a re-run (nothing new), a changed row, a fixed error report, the business's custom field as JSON, staff refused, another business 404. | Task. |
| 24 | **Fixture** (`framework/api/test/fixture/src/features/imports/`): a `shelves` module with `shelf`, `item` (an item names its shelf; a `cost` field only `fixture.items.cost` holders read and write; a rule that refuses one title and parks another; a field only the update schema has) and `bin` (opts out: `traits.imports: false`); a business role `fixture_importer` holding `imports.run`, and a level rule that makes its imports wait for holders of `approvals.decide`. Its own migration set. | CLAUDE.md ("framework tests must not depend on the sample domain"). |
| 25 | **A JSON upload on the local drivers.** The files feature's blob route (`PUT /api/files/blob/:token`, the memory and fs drivers) took a body the JSON parser had read only when `req._body` was set, which body-parser 2 no longer sets: every `application/json` upload was refused `wrong_size`. It now takes the bytes the parser kept (`rawBody`), and never reads a stream that has ended. Such a file must still be valid JSON within `JSON_BODY_LIMIT` on those drivers (the parser reads it first); S3 uploads go straight to the bucket. | Found by this unit's tests (B1's route, not a hot file); fail closed. |
| 26 | **Naming.** The files feature's registry of non-entity upload targets is `uploadTargets` (`UploadTarget`), so it is not confused with `FileTarget` in `@hykr/contracts` (the presign's `for`). `basecamp import` prints a refusal's reason and rule (`failureText`). | Default. |

## Assumptions to review

| Topic | What we chose | Question for the product owner |
|---|---|---|
| Who may import | `imports.run`: owners and admins | Should managers (or a dedicated role) import? Should an import ever need the owner's approval by default? |
| Rows that need approval | Reported `needs_approval`, never parked | Should an approved import approve its rows (one approval for the whole file)? |
| Who owns imported records | The importer (the write path's ownership) | Should an import set each record's owner from a column (an email per row)? It needs the entity repository to accept an owner (a hot file today). |
| Deleted records | A re-run does not bring them back (`not_found`) | Should a re-run re-create a record someone deleted? |
| Required key | Every row needs an id from the other system | Is there data with no ids at all (a hand-made spreadsheet)? Should such rows be imported once, with no re-run protection? |
| Empty cells | Leave the field out (`--empty null` to clear) | Should an empty cell clear a field on a re-run by default? |
| Limits | 50 000 rows per file, 100 per batch, 4 hours | Are larger migrations expected (the PRD's D1 move of pros, projects and leads)? |
| The assistant | Cannot start an import (reads its job) | Should the assistant import a file someone sends on WhatsApp, after a dry run and an approval? |
| Map retention | Kept as long as the business | Should the map be dropped once a migration is signed off? |

## API sketch

```ts
// @hykr/contracts
ImportsCapability                   // 'imports.run' (owner, admin)
ImportFormat                        // 'csv' | 'json' | 'ndjson'
ImportOptions                       // { entity, file, format?, key, source, columns?, refs?, existing, empty, dryRun }
ImportResult                        // the job's output: counts, errors by code, reportRows, reportTruncated
ImportErrorCode                     // 'invalid' | 'missing_key' | ... (decision 14)
StartImportSpec                     // import.start, POST /api/imports, output JobInfo
IMPORT_UPLOAD                       // { entity: 'import', field: 'file' }: the upload target
interface EntityTraits { imports?: false }   // opt an entity out

// @hykr/db
importKeys, importBatches           // app.import_keys, app.import_batches

// @hykr/api
ImportJob                           // the job kind 'imports.records'
importFile(context, { entity, file, as, tenant?, ...options }): Promise<ImportOutcome>  // the CLI's work
runImport(app, options): Promise<number>   // `basecamp import`: boots a context, exit code
uploadTargets                         // (files feature) non-entity upload targets
importsConfig()

// HTTP
POST /api/imports                   ImportOptions → WriteResult<JobInfo> (people with imports.run)
POST /api/files  for: { entity: 'import', field: 'file' }

// @hykr/api-client
api.imports.start(options)

// @hykr/app
useStartImport(), <ImportRecords entity />

// CLI
basecamp import <entity> <file> --as <email> [--tenant id] [--dry-run] [--key col] [--source s]
  [--format csv|json|ndjson] [--existing update|skip] [--empty omit|null]
  [--map column=field ...] [--ref field=entity ...] [--report path]
```

## Test plan

- Unit (`framework/api/test/framework/imports.test.ts`, no boot): CSV parsing (quotes,
  escaped quotes, newlines in quotes, CRLF, BOM, blank lines, ragged rows), JSON and NDJSON,
  format detection, value coercion against Zod schemas (numbers, booleans, JSON, unions, empty),
  the report writer (CSV quoting, `_` columns, NDJSON), CLI option parsing.
- Fixture e2e (`framework/api/test/framework/imports.e2e.test.ts`):
  - upload for `import` (type, size, capability); start; the job runs in the worker; records are
    created owned by the importer, audited with the job as their run, `import.done` audited;
  - a re-run creates nothing (`unchanged`), a changed row updates, `existing: 'skip'` skips;
  - refs: items name their shelf by its key; an unknown shelf is `unknown_reference`;
  - errors: invalid values, missing and duplicate keys, a rule's refusal (audited `denied`), a
    hidden field the importer may not write; the report file lists them with the row's columns,
    and importing the fixed report writes them;
  - unknown columns fail the job before anything is written; a file that does not parse fails;
    an entity that opts out is 400 `not_importable`; an unknown entity or `refs` entity is 404;
  - a dry run writes nothing (no records, no map rows), but reports the same counts;
  - a field only the update schema has is written after the create;
  - a row whose write would wait is `needs_approval`, and nothing is parked;
  - another business: 404 for the job, its report and the uploaded file; its keys never match
    ours; an import cannot name another business's file;
  - staff without `imports.run` are refused (audited `denied`), and so is the assistant; the
    fixture's `fixture_importer` role has it, and its import waits for approval (audited
    `needs_approval`) and runs once approved, its rows still decided on their own;
  - `importFile` (the CLI's path) imports a file from disk as a named member, saves the report
    beside it, and says why a staff member is refused (`failureText`).
- Sample e2e (`application/api/test/domain/todo-import.e2e.test.ts`): a dry run, the to-dos CSV
  in, again (nothing new), a changed row, a fixed report, custom fields as JSON, staff refused,
  another business 404.
- By hand (done once): `basecamp import todo todos.csv --as <owner> --key legacy_id --source
  legacy [--dry-run]` against the worktree database with `basecamp start worker` and
  `STORAGE_DRIVER=fs`: it waits and says so with no worker; with one, a dry run, the import and a
  re-run print their counts and save the report (exit 1 while a row is not written); a staff member is refused with its reason.
- CLI unit (`framework/cli/src/import-args.test.ts`): argument parsing and its refusals.

## Deferred

- An owner per row from a column (decision "who owns imported records"), and imported
  `createdAt` dates: both need the entity repository (`define-entity.ts`, a hot file) to accept
  framework-set columns from an import.
- Children (`traits.parent`) through their parent's command; files inside rows (a URL to fetch
  into a file field).
- An assistant tool to start an import, and parking a whole import's rows as one approval.
- Reading and editing the map (`GET /api/imports/keys`), forgetting a source.
- Excel (`.xlsx`) files; column types guessed from a sample; an import screen in the back office.
- Running an import in the CLI's own process when no worker runs.
