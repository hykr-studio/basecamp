# B16: comments and @-mentions

## Summary

People discuss a record where it lives. Any record a person can read takes comments: the
framework's `comments` feature (`framework/api/src/features/comments`) stores them in
`app.comments`, keyed by the record's entity and id, and reaches them only through that record.
Writing goes through `runWrite` as three platform commands (`comment.add`, `comment.edit`,
`comment.remove`), so comments are validated, authorised, parked when a rule says so, and
audited like every other write; reading is `GET /api/comments?entity=&id=`, which answers 404
unless the caller can read the record now.

A comment names people with mention tokens in its text, `@[Name](user:<id>)`. The server reads
the tokens, checks that each person may read the record (and an internal comment's audience),
writes their current name into the token, and stores the list. Each new mention is a durable
`comment.mentioned` event in the outbox: the trigger the agents feature (A6) subscribes to for
@-mentioned agents, and what notifications follow. The framework's own `comment.mention`
notification puts it in the person's in-app inbox; an application adds push or email by
declaring its own notification on the same event.

The in-app inbox is a new delivery channel, `inapp` (`framework/api/src/features/inbox`): any
notification can list it. Items are kept in `channel.inbox_items`, listed and marked read at
`/api/inbox`, and announced on the live stream. In the app, `<Comments entity id />` shows a
record's discussion with an @-picker, and `inboxPlugin()` adds an Inbox screen; the sample's
orders module shows comments on an order and pushes a mention to the person's phone.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | Comments are a framework feature over one table (`app.comments`: tenant, `resource_type`, `resource_id`, author, body, mentions, `internal`, `anchor`, `edited_at`), not an entity. An entity's generic list would list every comment of the business; the record a comment is on decides who reads it, and entity scopes cannot be expressed per polymorphic parent without changing `define-entity.ts` (a hot file this unit does not own). | Plan B16 row ("comments on any readable record"); gap map ("parent must be readable"); hot-file table. |
| 2 | **Which records.** Every served entity's record takes comments unless its spec says `traits: { comments: false }`. The trait's object form adds an approval rule for added comments and an anchor schema (decisions 9 and 10). An unknown entity is 400 `unknown_entity`; comments switched off are refused as `comments_off` (403, audited). | Gap ("on any readable record"); PRD Design 7.1 ("Comments per room and version"). |
| 3 | **Who reads.** Whoever reads the record now: the entity's scoped `repo.find` (role grants and every plugin's scope, as `GET /api/<plural>/:id`). The assistant also needs the entity's `get` exposed to it. A record they cannot read, another business's included, is 404, never 403, and says nothing about its comments. | Plan ("parent must be readable"); CLAUDE.md ("Not yours is a 404"); B1 decision 7 (the same rule for files). |
| 4 | **Who writes.** Anyone who reads the record may add a comment: PRD family access ("Extra participants can view and comment"). The author is a person with an account (`subjectOrThrow`): an agent acting for a person writes as that person, marked `createdBy: 'assistant'`; a WhatsApp contact without an account and a system principal cannot comment. Only the author edits. The author or a holder of `comments.moderate` removes. Both also need to read the record still. | PRD Design 7.1 (Family access); CLAUDE.md ("The assistant is a user"); default: least privilege for edits. |
| 5 | **Internal comments.** A comment marked `internal` is read, written and mentioned only by people holding `comments.internal`, a framework capability given to the built-in team roles (owner, admin, ops, staff). An application gives its own roles the capability (`RoleDef.capabilities`). Nobody without it learns that internal comments exist. | Gap map risk ("internal-only comments versus comments visible to homeowners … leak potential"); default, fail closed. |
| 6 | **Mentions** are tokens in the body, `@[label](kind:id)`, so the text and the list of people never disagree. The server parses them, resolves each (decision 7), rewrites the label to the name it knows (a client cannot make a token read as someone else) and stores `mentions: [{ kind, id, label }]`. At most 20 different targets per comment; the body is at most 4000 characters. Text outside the token grammar (`@ name`, `[x](y)`) stays plain text; a well-formed token of a kind nobody registered refuses the write (decision 7). | Default; gap map ("mentions[]"). |
| 7 | **Who can be mentioned.** Kind `user`: a member of the business who may read the record now (their own principal, built by `PrincipalResolver.forUser`, through the same scoped read) and, for an internal comment, holds `comments.internal`. Anyone else refuses the write as `mention_not_allowed` (403, audited, without saying who), so a notification never carries a comment to someone who cannot open it. Other kinds come from the `mentionKinds` registry (`contributes: { mentionKinds }`): A6 adds `agent`. An unregistered kind refuses the write the same way. | Gap map risk (leaks); plan DAG (`A6←B16`); default, fail closed. |
| 8 | **Events.** `comment.added`, `comment.edited`, `comment.removed` (resource type `comment`, the stored row, `before` on edit and remove) and one `comment.mentioned` per new mention target, all in the write's transaction (the durable outbox). Mentioning yourself raises nothing. An edit raises `comment.mentioned` only for targets the comment did not name before. A `comment.mentioned` row is `{ id (the comment), tenantId, commentId, on: { entity, id }, target: { kind, id, label }, author: { id, name }, internal, excerpt }`, where `excerpt` is the first 200 characters with tokens shown as `@Name`. The names avoid `<x>.created` so no check takes comments for an entity. | Plan ("`comment.mentioned` events (an A6 trigger)"); F3/F5 outbox. |
| 9 | **Approvals.** Two ways, both the application's. Per entity: `traits.comments.approval` is an ordinary `ApprovalRule`, checked with the action `comment`, the input and the record; its object form also gives `by`, `channels`, `minAssurance` and the approval `level` (A5) the park is at. Across the application: `comment.add` is an operation like any other, so A5 level rules see it (`on: ['comment.add']`, with `input.entity` and `input.internal`). Without either, comments run at once. The parked approval names the record (its resource type and id), so a card can link to it. `comment.edit` and `comment.remove` are people only (`expose: 'human'`), so they never park. | PRD Platform 7.1 (sends to someone outside wait; what each level means is the application's); A5 decisions 5, 7 and 13; plan boundary section. |
| 10 | **Anchor.** A comment may carry an `anchor` (a JSON object, at most 2 KB) only when the entity's trait declares `anchor: <zod schema>`, which validates it (a version, a point on a drawing). Without the schema an anchor is 400 `anchor_not_accepted`. The client filters by anchor; the list does not. | PRD Design 7.1 ("Comments per room and version", "Comments on drawing coordinates"); default. |
| 11 | **Audit and history.** Each command's own audit row names the record (`resource_type` = its entity, `resource_id`), so the record's history shows "commented on"; the comment row itself is audited as `comment.create`, `comment.update` and `comment.delete` (resource type `comment`, before and after). A refusal is audited as denied, a park as `needs_approval`. | CLAUDE.md rule 1; F3 audit. |
| 12 | **Reads.** `GET /api/comments?entity&id&cursor&limit`: newest first (keyset on created time and id), 50 a page (at most 100), each with `can: { edit, remove }` for the caller. `GET /api/comments/mentionable?entity&id&q&internal`: up to 10 people of the business whose name starts a word with `q` and who could be mentioned (decision 7), plus what other mention kinds suggest. Both are open to the assistant (tools `list-comments` and `list-mentionable`). | Gap map ("a members endpoint for autocomplete"). |
| 13 | **Live.** Comment events are announced as type `comment` to the streams that may read the comment now (a `liveResources` check: the record, then `internal`); inbox events as type `inbox` to the item's owner only. The app invalidates `['comments']`, `['history']` and `['inbox']` for them. | B15 (A9B15 decision 19, `liveResources`). |
| 14 | **The in-app inbox** is a delivery channel named `inapp` (`features/inbox`), open to any notification: `NotificationChannels.inapp` and `NotificationDef.inapp: { title, body, url?, record? }` (required when listed). It reaches people with an account only (a contact without one: `unavailable`, the next channel). It keeps one item per person and dedupe key (a retry adds nothing), stores the title and body in the person's language, and records an `inbox.added` event for the live stream. | Plan ("an in-app DeliveryChannel"); A9B15 decision 1 (open channel names). |
| 15 | **The inbox API** is people only: `GET /api/inbox?unread&cursor&limit` (newest first, with the unread count) and `POST /api/inbox/read { ids }` or `{ all: true }` (204). Items belong to one person in one business; anyone else's id is ignored. Marking read is channel state, written directly like push tokens (no `runWrite`, no audit). | Default: the inbox is per-person delivery state, not business data. |
| 16 | **The framework's mention notification**, `comment.mention`: on `comment.mentioned` for a `user` target, channel `inapp` only, topic `service`, "<Name> mentioned you" in the reader's language and the excerpt, linking the record. The framework sends nothing outside the app on its own: an application adds push, WhatsApp or email with its own notification on the event (the sample's orders module does push then email). | A9B15 decision 2 ("The framework has no fallback order of its own"); plan boundary section. |
| 17 | **Personal data.** Erasing a person deletes their comments and inbox items (in one business or all), and in other people's comments replaces a token naming them with `@—` and drops them from `mentions`. Their export lists their comments (record, body, when) and inbox items. | F5 decision 25; plan B18 direction; gap map risk ("B18 erasure must include comments"). |
| 18 | **Orphans.** A record deleted through its entity does not delete its comments (there is no foreign key to a polymorphic record): they are unreachable, since reading needs the record. The business's deletion cascades. | Gap map risk; default. |
| 19 | **Assistant.** `add-comment` comes from the command spec; `list-comments` and `list-mentionable` are a tool contribution (`comments`), calling the API as the agent. The scripted model's `comments` set (order 320) handles "comments on <entity> <id>", "comment on <entity> <id>: <text>" and "who can I mention on <entity> <id>". | Task ("add scripted-model scripts for new tools"). |
| 20 | **App.** `<Comments entity id />` (`@hykr/app`): the discussion (oldest at the top, "Show earlier"), names, time, "edited", "Team only" for internal ones, edit and remove where `can` allows, and a composer whose `@` opens the mentionable list and inserts the token when sent. A "Team only" switch shows for holders of `comments.internal`. `inboxPlugin()` adds `/inbox` and its destination; a tap marks the item read and opens its link (`url`, else `hrefFor(record)`); `<InboxBell />` and `useInboxCount()` are there for headers. | Plan ("a Comments component"); F2 plugin slots. |
| 21 | **Sample.** The orders module: `<Comments entity="order">` on the order screen; its level rule `orders.comments` puts a comment on an order that a customer could read at the application's `external` level (the assistant's waits for the person it is for; team-only notes have no level); an `orders.comment-mention` notification pushes a mention on an order, then emails it. The fixture shows the trait's `approval` instead. | Task ("Sample demo: orders comments"); plan boundary ("sample proof"); A5 decision 28. |
| 22 | `/api/comments` and `/api/inbox` are reserved for the framework (`reserveRoutes`), and the tables are the framework's. | CLAUDE.md. |
| 23 | A command route answers a request without a body as an empty one (`commandController` in `@hykr/core`): `DELETE /api/comments/:id` needs no body, as any command whose input is only path params. Before, such a request was 400. | Found while testing; generic and backward compatible. |
| 24 | The scripted model's replies and the app's words (the Comments box, the Inbox screen) are English; the inbox item and the sample's push and email are in the reader's language (`comments.mentioned` in `@hykr/i18n`, the module's own `Labels`). | Default: the app's other framework screens are English today. |

## Assumptions to review

- **Who may comment.** Anyone who can read a record, customers included (PRD family access).
  Should some entities be read-only for comments for customers, or should commenting need write
  access to the record?
- **Internal comments.** Hidden from everyone without `comments.internal` (by default the team
  roles). Is "team only" the right default name and audience? Should internal be the default for
  staff?
- **The @-picker for customers.** A customer who comments on their own record is offered the
  business's people who may read it (names only). Should customers be offered only people already
  in the discussion, or nobody?
- **Mentioning someone who cannot see the record** refuses the comment. Should it instead keep
  the comment and skip that person (and say so)?
- **The assistant's comments.** It may add comments for its person (no approval unless the
  entity's trait asks), but not edit or remove them. Right?
- **Mention notifications.** The framework only fills the in-app inbox; push, WhatsApp and email
  are each application's choice. Should a mention count against credits (A3) when it goes out?
- **Removing.** Removing deletes the comment (the audit keeps its text). Should removed comments
  leave a "removed" line in the discussion instead?
- **Erasure.** Mentions of an erased person become `@—`. Acceptable, or should the token stay
  with a neutral label?
- **Attachments, reactions, threads.** Not built (see Deferred). Which matter for P1 (photos on
  a site comment?)

## API sketch

```ts
// @hykr/contracts
traits: { comments?: false | { approval?: ApprovalRule; anchor?: z.ZodType } }
Comment = { id, on: { entity, id }, body, mentions: Mention[], internal, anchor,
  author: { id, name }, createdBy, editedAt, createdAt, updatedAt, can: { edit, remove } }
Mention = { kind, id, label };  mentionToken(m) → '@[label](kind:id)';  parseMentions(body)
AddCommentSpec    comment.add    POST   /api/comments              tool add-comment
EditCommentSpec   comment.edit   PATCH  /api/comments/:commentId   people only
RemoveCommentSpec comment.remove DELETE /api/comments/:commentId   people only
CommentPage = { items: Comment[], nextCursor };  MentionablePage = { items: Mention[] }
InboxEntry = { id, notification, title, body, url, record: { type, id } | null, readAt, createdAt }
InboxPage = { items, nextCursor, unread };  MarkInboxRead = { ids } | { all: true }
CommentCapabilities.internal ('comments.internal'), CommentCapabilities.moderate ('comments.moderate')
commentsPolicyOf(spec); mentionTokens / mentionRefs / rewriteMentions / plainComment / commentExcerpt

// HTTP
GET  /api/comments?entity=order&id=<id>&cursor=&limit=     → CommentPage (404 unless readable)
GET  /api/comments/mentionable?entity&id&q&internal          → MentionablePage
GET  /api/inbox?unread=true&cursor=&limit=                   → InboxPage (people only)
POST /api/inbox/read { ids } | { all: true }                 → 204

// @hykr/notifications
interface NotificationChannels { inapp: true }
NotificationDef.inapp?: { title(row, reader), body(row, reader), url?(row), record?(row) }
CommentMentionNotification ('comment.mention', on comment.mentioned, channels ['inapp'])

// @hykr/api
interface MentionKind { kind; resolve(a): Promise<Map<id, label>>; suggest?(a): Promise<{ id, label }[]> }
mentionKinds (contributes: { mentionKinds }). The services stay inside the package: @hykr/api's
entry loads nothing that opens the database.
// features: commentsFeature (comment commands, GET /api/comments, tools list-comments and
//   list-mentionable, liveResources: comment, erasure and export), inboxFeature (channel inapp,
//   /api/inbox, liveResources: inbox, erasure and export)

// @hykr/api-client
api.comments.list({ entity, id, cursor?, limit? }) / .mentionable(...) / .add(...) / .edit(id, body) / .remove(id)
api.inbox.list({ unread?, cursor? }) / .read(ids) / .readAll()

// @hykr/app
<Comments entity id />, useComments(entity, id), useCommentActions, useMentionable,
inboxPlugin(), <InboxScreen />, <InboxBell />, useInbox(), useInboxCount(), useMarkRead()
bodyParts, mentionQuery, pickMention, composeBody   // the composer's pure parts
```

## Test plan

- `framework/notifications/src/notifications.test.ts`: `inapp` without content throws.
- `framework/api/test/framework/comments.e2e.test.ts` (fixture: tasks take comments with an
  approval rule for the assistant and an anchor schema; visits say `comments: false`):
  - add, list (newest first, cursor), edit (author only), remove (author or `comments.moderate`);
  - another business: list, add, edit and remove are 404; own-rows staff on Ana's task: 404;
  - an internal comment is invisible to a customer and a role without `comments.internal`, who
    cannot write one or be mentioned in one;
  - mentions: labels rewritten, the mentioned person's inbox gets one item (once), the
    `comment.mentioned` event is stored with the documented row, a subscriber receives it; a
    mention of someone outside the business or without read access refuses the write (audited
    denied, nothing stored); an edit notifies only new targets; self-mention notifies nobody;
  - the assistant: lists through the tool route, its comment parks (`needs_approval`, audited),
    approving it adds the comment; edit and remove are 403 for it;
  - `comments: false` and an unknown entity; an anchor that fails the schema, and one on an
    entity without one;
  - audit rows name the record; history of the task shows `comment.add`;
  - live: a comment event reaches the record's readers only; the inbox event its owner only;
  - inbox: people only, mark read and read all, another person's ids ignored, unread count;
  - erasure removes the person's comments and items and rewrites tokens naming them.
- `framework/app/src/features/live/keys.test.ts`: comment and inbox keys.
  `framework/app/src/features/comments/body.test.ts`: drawing mentions, the @-picker's word,
  composing tokens, and the contracts' token grammar.
- `application/api/test/domain/order-comments.e2e.test.ts`: a mention on an order lands in the
  inbox with a link to the order and, with no phone, in email (Mailpit); someone who cannot read
  the order cannot be named; the assistant's comment parks, a team-only one does not; the
  order's history shows it.
- `framework/api/test/framework/delivery.e2e.test.ts`: the erasure and export lists now include
  `comments` and `inbox`.

## Deferred

- Attachments on comments (B1 file fields), reactions, replies in threads, and editing history
  beyond the audit trail.
- Comments from WhatsApp contacts without an account, and replying to a mention from WhatsApp.
- A server-side filter by anchor.
- An unread badge on the Inbox destination (the shell's nav item has no badge slot; `AppShell.tsx`
  is not this unit's file). `<InboxBell />` shows the count where an application puts it.
- Agents as mention targets (A6 registers the `agent` kind).
