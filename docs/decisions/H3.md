# H3: MCP tool hints and flag gating, credits metering and cap holes

## Summary

A fix group from the completeness and security review of A1 (MCP), A3 (credits), A8 (memory)
and A11 (feature flags). Five holes:

1. **MCP tools carry hints.** `<module>_read` says it only reads; `<module>_write` says it
   changes things, and whether it can delete or do something that cannot be undone. Outside
   clients use these to decide when to ask the person first (PRD "tool layer: flagged read-only
   or consequential").
2. **Feature flags gate MCP tools.** A token's tool list (and the actions inside each
   `<module>_write`) leaves out what its business switched off, failing closed, as the
   assistant's turn already does (A11).
3. **Embeddings and the guardrail are metered.** Memory recall, the memory indexer and the
   prompt-injection guardrail record the tokens they use under the business, priced like any
   model's tokens, with the model as the variant. Embedding stops while the business is paused.
4. **A run stops at 100%.** An agent's tool call (the assistant's key, an agent run's token, an
   MCP token) is refused with 402 while its business is paused, and the assistant's run then ends
   with the paused sentence instead of carrying on. A turn that crosses the cap in the middle
   stops there.
5. **A purchase settles from a connector, only in its own business.** `settlePurchase` now needs
   the business (and the provider) the confirmation comes from, so a webhook received on one
   business's connection can never top up another's wallet. The fixture has a provider whose
   B10 connector's verified webhook settles purchases, tested end to end.

## Assumptions to review

- **Writes are "open world".** Every `<module>_write` says `openWorldHint: true`, because a
  write can notify people outside the business or fire a webhook. Should a module say it never
  reaches outside (a closed write), so clients ask less?
- **Destructive is declared, not inferred.** Only deletes, HTTP `DELETE` commands and actions
  the application marks `destructive` make a write tool destructive. A command that cancels or
  sends without the mark is not. Should a parked level (the application's "irreversible") also
  count?
- **Every agent request is refused when paused**, reads included, for the assistant, agent runs
  and MCP clients. Should reads stay open (they cost a tool call each)?
- **A token limit pauses the assistant's tool calls**, not an MCP client's (it spends none of
  our tokens). The credits budget pauses both.
- **A customer crossing the cap mid-turn** hears the paused sentence once; the handoff happens on
  their next message. Should the turn hook's `after` open the handoff at once?
- **Embeddings are priced as tokens** (`tokens.<embedding model>` or the generic `tokens` price,
  else the model's own price). Should embeddings have a meter of their own?
- **The indexer waits a minute** before it looks at a paused business again. Its pending rows are
  embedded once the business has credits.
- **Settling needs the provider's name.** A provider whose webhook does not carry our purchase
  id has to look it up by its own reference first; there is no lookup by provider reference yet.

## Test plan

- `framework/api/test/framework/mcp.test.ts` (unit): read tools are read-only and
  non-destructive; a write tool with a delete, a `DELETE` command or a `destructive` command or
  transition is destructive, one without is not; a switched-off module, entity, command or named
  tool leaves the tool list or the write actions.
- `framework/api/test/framework/mcp.e2e.test.ts`: the listed tools carry their annotations over
  MCP; a business with a flag off gets no tools of a gated module and no gated write action, and
  gets them back when it switches the flag on; another business is unaffected; settings that do
  not parse hide every gated tool.
- `framework/agents` unit tests: `EndWhenPaused` ends a run whose tool is refused 402
  `credits_paused` with the paused sentence and runs nothing else; any other refusal is left to
  the model; `meteredModel` reports a generate's and a stream's usage to the sink with the
  turn's business and run, and nothing without a business.
- `framework/api/test/framework/credits.e2e.test.ts`:
  - a turn records its recall's embedding tokens (variant the embedding model, priced);
  - a turn that crosses the cap mid-run (`render-report` then `create-task`) ends with the paused
    sentence, its second call refused 402 and no task made; the next turn is refused at the gate;
  - while paused, the assistant's and an agent run's direct calls are 402 `credits_paused`;
    an operator's `run` override lets them through; the voice relay's session report is not
    refused;
  - the guardrail's usage reported through the slot is recorded for the business;
  - a purchase through `fixture-gateway` is settled by its connector's signed webhook once
    (a repeated webhook and a second event change nothing), a bad signature is 401, and a
    webhook on another business's connection naming this purchase fails and moves nothing.
- `framework/api/test/framework/memory.e2e.test.ts`: the indexer and the recall API record their
  embedding tokens; a turn that calls `recall-memory` records two uses (the message, keyed to the
  run, and the tool's query, unkeyed); two recalls in one run both count; a paused business's
  recall API is 402 and its pending rows stay pending until it has credits again.

## Fix round 1

- **The recall tool was not metered inside a turn** (review). Every recall embedding was keyed
  `memory.recall:<run>`, and `usage_events` keeps one row per (business, meter, ref), so the
  tool's embedding (same run as the recall before the turn) and every further recall in a run
  were dropped. Now only the recall before a turn has a ref (`EmbedUse.ref`); the API and the
  tool pass none (decision 9).

## Integration with S4

S4 (merged first) metered and capped embeddings on its own meter, `embedding_tokens`
(`docs/decisions/S4.md`). The merge keeps S4's meter and checks and takes H3's keys, so decisions
9 and 11 now read as follows:

- Embeddings are `embedding_tokens` uses (variant the embedding model), not `tokens`, checked
  with `embeddingRefusal` and recorded with `recordEmbedding` (`features/memory/usage.ts`), priced
  by `embedding_tokens.<model>`, `embedding_tokens`, then the model's own input price. `tokens`
  keeps a turn's and the guardrail's calls (decisions 10 and 12).
- Recall before a turn has the ref `memory.recall:<run>` (`EmbedOptions.ref`), so it counts once per
  run; the recall API and tool pass none and carry the caller's run id (`p.runId`); the indexer's
  use is keyed `memory.index:<claim>` (one per business and batch).
- A refused recall throws S4's `UsageRefused`, answered 402 `credits_paused` (`creditsPaused`). The
  indexer leaves a refused business out for S4's 5 s (`PAUSED_RECHECK_MS`), not a minute;
  `MemoryIndexer.wake(tenantId)` looks again at once.

S2 (also merged first) stores an event whose id the signature does not cover under the hash of
its body. The fixture gateway therefore signs `<timestamp>.<id>.<body>` (`x-gateway-timestamp`,
`signedIds: true`), as real gateways do, so decision 14's repeated webhook and second notice keep
their own ids.
