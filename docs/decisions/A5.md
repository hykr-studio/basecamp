# A5: approval levels on the payload, named approvers, level-1 undo

## Summary

The closed tier union (`0 | 1 | 2 | 3`) is gone. The application declares its own approval levels
(`defineApprovalLevel({ name, rank, label, policy })`, contributed as `approvalLevels`). Each level
has a policy: whether it parks, an undo window, who decides, where and how surely, and how long it
waits. A decision names a level by name. The framework only compares ranks (the highest wins) and
keys undo on `undoMs`. Without levels, everything works as before.

Which actions sit at which level is declared by the application too: level rules
(`defineLevelRule({ name, on, decide })`, contributed as `levelRules`) see the action, its
validated input, the loaded row and the business's settings. Thresholds and named approvers per
amount band are per-business settings (the `approvals` settings section). Approvers are chosen by
capability (`approvals.decide`, `marketing.approve`), never by role name. Nobody decides a request
they made unless the policy sends it back to them on purpose (the person deciding their own
assistant's request). Pending approvals expire on a schedule. A write that runs with an undo window
can be undone by the person it was for, through `POST /api/undo/:id`, until the window closes: the
change is reversed through the write path and its held events are withdrawn. The app shows the
level and amount on approval cards, hides the decision from someone who may not make it, and has an
`/approvals/:id` deep link.

The sample application declares the four levels of its product brief (read, internal write that can
be undone, a send to someone outside the business, and money or irreversible actions decided by a
named person in the app, signed in) and maps its to-do writes and `notify.send` onto them.

## Assumptions to review

- **Level 2 for a person's own send.** The sample's `external` level parks only when an assistant or
  a background job sends; a person sending themselves goes ahead (they are the human the PRD asks
  for). Should a person's own send to someone outside also wait, and for whom?
- **Who loosens.** A business may switch off parking only for levels the application marks
  `tenantMayLoosen` (the sample: `external`). Should owners be able to loosen any level?
- **No threshold set.** `overThreshold` counts a missing threshold as exceeded, so a new business
  parks every amount until it sets one. Should a missing threshold mean "never parks" instead?
- **Named approver who asked.** When the band's named approver is the requester, the request goes to
  holders of `approvals.decide` other than them. Should it go to the next band up, or to the owner?
- **Self-approval everywhere.** An owner alone in a business can no longer approve their own
  marketing send. Is a single-person business allowed to approve its own requests?
- **Undo window length.** The sample's internal level gives 10 seconds. What should the product's
  window be, and should it differ per channel (WhatsApp replies are slower)?
- **Undo of a delete.** Rows removed by cascade with the deleted row are not put back. Should an
  entity with children refuse undo instead?
- **Approval view for the requester.** The requester can open their own request read-only (deep
  link). Should they also see a list of everything they are waiting on?
- **Sends in an undoable write.** A command that writes a notification (`app.outbox`) in a write with
  an undo window still sends at once. Should the framework hold those back too?

## API sketch

```ts
// @hykr/contracts
const Approver = z.object({ by?: 'requester' | { capability } | { userId } | { band }, channels?, minAssurance? })
AuthorizeResult = { decision, rule, reason, level?: string, approver?: Approver, amount?: Money, undoMs?: number }
type ApproverRule = { by?; channels?; minAssurance?; level? }           // spec/command `approval`
interface ApprovalLevelPolicy {
  parks?: boolean | ((p: Principal) => boolean); undoMs?: number; approver?: Approver;
  expiresInMs?: number; tenantMayLoosen?: boolean;
}
defineApprovalLevel({ name, rank, label, policy? }); approvalLevels; levelOf(name); checkApprovalLevels()
ApprovalCapabilities.decide   // 'approvals.decide' (owner, ops)
ApprovalCapabilities.marketing // 'marketing.approve' (owner, admin)
// settings section 'approvals'
{ levels: Record<level, { parks?, undoMs?, expiresInMs? }>, thresholds: Record<key, Money>,
  bands: Record<key, { upTo?: Money; approver: { userId } | { capability } }[]> }
approvalThreshold(settings, key); overThreshold(settings, key, amount); bandApprover(settings, key, amount)
Approval += { level: { name, rank?, label? } | null, amount: Money | null, canDecide, decider }
WriteResult done += { undo?: { id, until } }

atLevel(level, rule, reason?, details?)       // an allow that names a level
defineLevelRule({ name, on: ['todo.*'], decide: ({ p, op, kind, input, row, settings }) => … })
levelRules                                     // contribution key 'levelRules'

// @hykr/notifications
type Recipient = … | { capability: string; except?: string[] }

// @hykr/api-client
api.undo(id)

// @hykr/app
ApprovalScreen, ApprovalsScreen, useUndo()
```

## Test plan

- Unit (`@hykr/contracts`, `@hykr/core`): level definitions and rank checks; settings parsing,
  thresholds and bands (currency mismatch, no threshold); `strongerDecision` by rank; `atLevel`;
  applying a level's policy with a business's override (loosen allowed or not, tighten).
- Fixture e2e (`framework/api/test/framework/approval-levels.e2e.test.ts`, fixture feature
  `features/approval-levels/`): a level rule parks a payment above the business's threshold and runs
  one below it; deciders by capability; the requester sees it read-only and gets 403 `own_request`;
  a named approver per amount band decides alone (others 404); a named approver who asked falls back
  to the capability; app-only and signed-in levels refuse WhatsApp-assured deciders; the business
  loosens a loosenable level and cannot loosen another; per-level expiry and the sweeper (status,
  audit, event); a replay whose level rose fails; another business gets 404 for the approval and the
  undo; hidden fields stay hidden on the approval card; parks are audited with the level.
- Undo e2e (same file): a level-1 create, update and delete are undone; events are withdrawn; the
  window, a second undo, a change since and another person are refused.
- Existing tests updated: `write-path` (capability approver instead of a role), `wa-approvals`
  (deep links), core `seams` and `decisions` unit tests (levels instead of tiers).
- Sample: `application/api` to-do test checks the level-1 undo and the level on a parked delete.

## Deferred

- Multi-step levels (two approvers). The policy has one decider per request.
- Delegation and escalation when a named approver is away, beyond the capability fallback.
- Push and email for approval requests (A9's delivery channels); WhatsApp only, as before.
- Holding back `app.outbox` sends inside an undo window.
- A requester's list of their own pending requests.
- Tenant-defined roles (A4) will need `Recipient { capability }` expansion to read the business's
  own role table.
