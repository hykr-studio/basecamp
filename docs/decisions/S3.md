# S3: bounded SLA lists, reach in SQL, clocks kept from whoever cannot read the record

## Summary

`GET /api/sla` used to page with OFFSET through every timer of the business in the asked status
and run one scoped `find` per distinct record until it had `limit` readable ones, with no cap on
the pages scanned. A member who reaches none of the records (staff with `own`, a customer, a
participant) made it walk the whole table: measured as staff with `?status=breached&limit=1`,
500 timers took 138 ms, 5,000 took 1.1 s and 20,000 took 4.5 s per request, each answering
nothing. Ended timers stay in the table, so the cost only grew. Neither `GET /api/sla` nor
`GET /api/sla/:plural/:id` applied the assistant rule the other record-attached features use
(`p.actor.kind === 'agent' && spec.expose.get !== 'all'`), so the assistant saw clocks (ids,
states, due dates) on entities whose records are hidden from it.

Now reach is SQL. For each entity with a state machine the caller may see clocks of, one branch
keeps the timers whose record is in the caller's list (`exists (select 1 from <table> where id =
resource_id and <the entity's list WHERE for p>)`, the WHERE read with B14's `listWhere`), each
branch is ordered and cut in Postgres, and the branches are merged there (`union all`). Pages
are keyset pages on `(dueAt, id)`, exact to the microsecond, with a `nextCursor`. A request costs
at most three queries plus one per entity type on the page, however many timers the business
has. The assistant sees no clock on an entity whose `get` is not exposed to it (left out of the
list, 404 for one record's), nobody sees clocks of an `internal` entity, and a reader who cannot
see a record's state field does not see its clocks (they carry the state).

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | A timer is listed exactly when its record is in the caller's list of its entity. For each entity type, its branch is `resource_type = <name> and exists (select 1 from <table> where <table>.id = sla_timers.resource_id and <W>)`, where `<W>` is `listWhere(def, p, { filters: [] })`: the WHERE of the repository's own list query for p (business, grants, every plugin's scope), recorded, not rewritten. Ids are text on both sides (`id()`, `resource_id`), so the join uses either index. | Task note (S3 fix); B14 `listWhere`. |
| 2 | Only entities with a state machine (`traits.states`) get a branch: the `sla` write hook starts clocks only for them. A timer of any other or unknown type is never listed (as before). | B6B4 decision 11; fail closed. |
| 3 | The branches are combined with `union all`, each `order by due_at, id limit n+1`, and the merged rows ordered and cut in Postgres. Each branch is a semi-join the planner can start from either side: from the entity's rows when the reader reaches few (staff with `own`: a nested loop into `sla_timers_resource_idx`), from the due index when it reaches many. All ordering is Postgres's, so the cursor and the order agree under any collation. | Default: measured (decision 9). |
| 4 | Keyset pagination on `(dueAt, id)`. The cursor is opaque (base64url JSON of the last row's due time as UTC text with microseconds, from Postgres, and its id); the next page is `due_at >= d and (due_at > d or id > i)`. Not a JavaScript `Date`: it keeps milliseconds only, and a due time set in SQL has microseconds, so a page would repeat its last row. A cursor that does not parse is 400 `bad_cursor`. | Task note ("paginate by keyset (dueAt, id) instead of OFFSET"). |
| 5 | `GET /api/sla` answers a page, `{ items, nextCursor }` (`SlaPage`), and takes `cursor`. Breaking: `api.sla.list` returns the page, `useSlaList` returns the page, `<OverdueList>` reads `items`. `GET /api/sla/:plural/:id` still answers the record's timers as a list. | Default: the shape of entity lists (`Page`); plan ("break freely"). |
| 6 | The assistant (`actor.kind === 'agent'`) sees clocks only of entities whose `expose.get` is `'all'`: other types get no branch in the list, and `GET /api/sla/:plural/:id` is 404 for them (the record looks missing, as in files, comments, jobs and documents). | Task note; the same rule as files, comments, jobs, documents, calls, calendar. |
| 7 | An entity whose `expose.get` is `'internal'` has no GET route for anyone, so its clocks are not served either: no branch, and 404 for one record's. | Default, fail closed: a clock is as readable as its record. |
| 8 | A clock carries its record's state (`state`, and `sla` names the state it runs in). A reader who cannot see the state field does not see the record's clocks. When the spec's field policy hides the field from the reader, the type gets no branch (decided before any SQL). When a projection hides it per record (a read projector, a plugin's `project`), the page's records are read once through `toRead` and the clocks of those whose projection lacks the field are dropped; the page can then hold fewer than `limit` items, and `nextCursor` still follows the last timer scanned. For one record, its clocks are `[]`. | Task rule ("hidden fields stay hidden"); default, fail closed. |
| 9 | Measured on this machine with 20,030 breached timers in one business on 2,016 records, as a staff member reaching 2 of them: the old loop's queries alone (raw `pg`, without the framework around them) took 1.5 s, 201 OFFSET pages and 2,010 finds; the pushed-down branch takes 1 ms (0.2 ms in Postgres: a nested loop from the staff's 2 records into `sla_timers_resource_idx`), and the CASE-per-row form it replaced in the design 8 ms (a hashed subplan over the due index). The e2e test seeds 20,000 breaches on 2,000 records staff cannot read and requires staff's empty answer in under 1 s (the probe measured 4.5 s through the API before). | Task note (the probe's numbers). |
| 10 | No new index: `sla_timers_status_idx (tenant_id, status, due_at)` serves the owner's plan and `sla_timers_resource_idx (tenant_id, resource_type, resource_id)` the low-reach plan. No migration. | Default: additive changes only, none needed. |
| 11 | A shared entity (`defineSharedEntity`) lists in two queries when the deployment has a platform business, so `listWhere` cannot read one WHERE for it and throws. Such a type gets no branch (logged once per type), its records' clocks stay readable through `GET /api/sla/:plural/:id`. A business's timers are only ever on its own rows (the platform's are in the platform business), so nothing else would be listed. No shared entity has a state machine today. | Default, fail closed. |
| 12 | `limit` stays 1 to 100 (default 50); `status`, `open` and `resourceType` keep their meaning and are applied in every branch before the limit. A `resourceType` that names no entity with states, or one the caller may not see clocks of, answers an empty page. | B6B4 decision 17. |
| 13 | The reading lives in `@hykr/core` (`states/sla-read.ts`: `listSlaTimers`, `recordSlaTimers`, `clocksShown`), so the controller stays a thin route and the rule is unit-tested without a database. | Default. |

## Assumptions to review

- The list answer changed from an array to `{ items, nextCursor }`. Question: should the Today
  view page further than its first `limit`, or is the first page always enough there?
- Clocks of an `internal` entity are no longer shown to people either. Question: is there a case
  where people should see a clock on a record they cannot open?
- A reader who cannot see the state field sees none of the record's clocks, rather than clocks
  with the state blanked. Question: should such a reader see that a deadline was missed without
  the state it was missed in?
- A page can hold fewer than `limit` clocks when a projection hides some records' state. Question:
  acceptable for the Today view, which shows the first page only?

## API sketch

```
GET /api/sla?status=breached&open=true&resourceType=order&limit=50&cursor=<opaque>
  → 200 { items: SlaTimer[], nextCursor: string | null }
  → 400 { error: 'bad_cursor' }                       a cursor that does not parse
GET /api/sla/:plural/:id
  → 200 SlaTimer[]                                     [] when the state field is hidden from p
  → 404                                                not readable, not served, or the assistant
                                                       on an entity whose get it is not exposed to

@hykr/contracts  SlaQuery (+ cursor), SlaPage, SlaListInput
@hykr/core       listSlaTimers(conn, p, q) → SlaPage
                 recordSlaTimers(conn, p, def, id) → SlaTimer[]
                 clocksShown(def, p) → boolean        (expose, internal, declared field policy)
@hykr/api-client api.sla.list(q) → SlaPage
@hykr/app        useSlaList(q) → UseQueryResult<SlaPage>
```

## Test plan

- Unit (`framework/core/src/states/sla-read.test.ts`): `clocksShown` for a person and the
  assistant on `all`, `human` and `internal` entities, and a state field hidden by a declared
  field policy (with and without the capability); the cursor round trip and its refusals.
- Fixture e2e (`framework/api/test/framework/sla.e2e.test.ts`, the existing file):
  - the existing cases, on the page shape;
  - keyset pages: the owner walks `limit=2` pages through breaches with equal due times and due
    times a microsecond apart, and gets every one exactly once, in `(dueAt, id)` order, the same
    as one large page;
  - a cursor that does not parse is 400 `bad_cursor`;
  - 20,000 breaches on 2,000 records staff cannot read: staff's list is empty, in under 1 s, and
    staff's own breach due after all of them is listed first;
  - the assistant acting for the owner lists ticket clocks but none of a `privateTicket`'s
    (`expose.get: 'human'`), gets 404 for one private ticket's clocks, and the owner sees them;
  - a ticket whose projection hides its status from staff (fixture projector, `[sealed]` titles)
    has its clocks dropped from staff's list and `[]` for its record, while the owner sees them;
  - another business: empty list, 404 for a record's clocks (existing).
- Sample e2e (`application/api/test/domain/orders.e2e.test.ts`): unchanged; reads one record's
  clocks.

## Deferred

- A total count on `GET /api/sla` (it would cost the scan the page avoids; a summary is the
  place for counts).
- Shared entities with a state machine in a deployment with a platform business (decision 11).
- An infinite list in `<OverdueList>`: it shows the first page.
