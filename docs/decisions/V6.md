# V6: retries make one record, events reach only what existed, and one bad event stops nothing

## Summary

Fixes from the live validation (`VALIDATION.md`, unit V6), three root causes:

- **A retry wrote twice.** The integrations routes (B10) never passed the `idempotency-key` to
  `runWrite`, so a retried endpoint or connection create made a second row with a second secret
  (C9-1). Passing the key was not enough: the op's input carries what the server made for that
  request (a fresh id, a sealed secret, a token's hash), so the same body hashed differently
  each time, and the secret was added to the answer outside the write. The same holds for the
  calendar routes (B17) and, where no `runWrite` is involved at all, for a file's upload and
  discard (B1), a job's cancel (B11) and a back-office reply to a customer (which sent the
  WhatsApp message twice). Now a request is recognised by what its caller sent,
  a repeat says it is one, and each route answers its first answer again: an endpoint's or
  connection's secret is read back from its sealed row, never stored in `app.idempotency`.
- **An event reached a subscriber made after it.** A stored event is relayed when it is due
  (an undo window holds it, a stopped worker delays it), and an agent's event trigger or a
  webhook endpoint made in between got it (C6-1, L15). Now an agent's event and mention triggers
  and a webhook endpoint see only what happened after they were saved.
- **One bad stored event stopped every business's events.** The outbox feed turned its batch of
  100 rows into envelopes in one go, so one row the envelope schema refuses failed the batch on
  every tick, for every business on that queue prefix (F5's deferred poison row, L8). Now such a
  row is marked failed with the reason and left out of later batches, and the rest go on; a
  subscriber whose `when` throws fails only that event.

The egress lead (L9) did not hold for webhooks: the guard already refuses a name that resolves
inside when the socket connects. It held for a job's result URL (`jobs/fetch.ts`), which looked
the name up and then let `fetch` look it up again; that fetch now connects only to the
addresses it checked.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | `WriteCtx.requestBody?: unknown`: what the caller sent, when the op's input also carries values the server made for this request (a fresh id, a sealed secret, a token's hash). The idempotency hash is then `[op.name, op.args, requestBody]` instead of the parsed input, so the same body with the same key is the same request, and a different body is a 409. Without it, nothing changes. | Validation C9-1 (verifier: "hash the user's body rather than the sealed input"); B12 decisions 7 and 8. |
| 2 | `WriteOutcome.repeat?: true` on a stored reply (before the transaction, or after the advisory lock). A caller that adds something to the answer after the write (a secret shown once, a retry now, a clean-up) knows not to do it again. | Default (a repeat was indistinguishable from a first run). |
| 3 | `findRepeat(db, ctx, op, request)` (`@hykr/core`): the stored outcome of a repeat before any work, by the same hash and table as `runWrite`, or undefined; a key used for another request is a 409. For routes that do work before their write that must not run twice (a Google code exchange, minting a secret). | Default; CLAUDE.md design rule 1. |
| 4 | Integrations: every write route passes the key. Endpoint create, rotate, connection create and connection update with credentials pass the parsed body as `requestBody` (credentials in it tagged, decision 15). On a repeat, endpoint create and rotate answer the endpoint's secret, unsealed from its row; connection create answers generated credentials from its row when the first request generated them. Only while the record is as the repeated write left it (the stored reply's `updatedAt` equals the row's): after a later rotation, new credentials or any other change, the repeat answers the stored reply alone, since the row may hold what someone else wrote. Before unsealing, the caller must still pass what the write asks (`integrations.manage`, and every capability the endpoint reads with): a stored answer is the caller's, but their roles may have changed (403 otherwise). A rotate repeated does not rotate again, so the secret before it keeps its day of overlap. A delivery retry repeated does not try again. Nothing secret is written to `app.idempotency`: the stored reply is the write's result, which never held it. | Validation C9-1 (verifier's option A); B10 decisions 8 and 18 (a connection never reads back its credentials); review of V6 (a repeat after another admin's PATCH answered their credentials). |
| 5 | Calendar: every write route passes the key. `complete` looks for a repeat before it takes the sign-in state and exchanges Google's one-time code, and a repeat does not clean the old account up again. A repeated feed create answers the same feed without its URL: only the token's hash is stored, so the URL is shown once, as invites are. | Lead L7; B17. |
| 6 | Files and jobs write without `runWrite` (B1, B11); their key is honoured with the same table (`findRepeat` and `saveReply`). A repeated presign answers the same pending file with a new upload URL for the time it has left (the stored reply holds the file's id, not the signed URL), or 409 `upload_expired` once that time ran out, as `confirm` does. A repeated discard answers 204. A repeated cancel answers the job as it is now, instead of 409 `already_finished`. Without a key, nothing changes. Concurrent duplicates take no lock here (runWrite's advisory lock is inside its transaction). | Lead L7; B12 decision 7 for runWrite only. |
| 7 | An agent's event and mention triggers see only what happened at or after the trigger was saved: `event.occurredAt` is compared with `agent_triggers.created_at`. A changed trigger is a new row (A6 `syncTriggers`), so it starts again too. Every trigger has a row, so a mention of an agent whose mention trigger has none (out of step) starts nothing, as an event trigger without a row cannot. Message and webhook triggers are not cut off: they run when the message or webhook arrives (a webhook's handler retries for seconds), and the only time to compare with, the inbound row's `received_at`, is Postgres's clock, so a webhook sent right after the trigger was saved could be skipped. Condition triggers look at records as they are, by design. | Validation C6-1 (verifier's fix sketch); A6 decision 12; lead L15 (the `matchesEvent` sites: agents.service, triggers.ts, deliveries.service, the connector handler registry, which is code, not something a business saves). |
| 8 | A webhook endpoint gets deliveries only for events that happened at or after it was created. | Lead L15. |
| 9 | Both cut-offs compare the app's clocks: `agent_triggers.created_at` and `integration_endpoints.created_at` are written from the app's clock on insert (the `now` `syncTriggers` already has; `new Date()` in the endpoint op), as `occurred_at` is, instead of Postgres `now()`, which is the transaction's start and, in development, a container's clock. | Default; validation C6-1 ("avoid comparing the JS clock with Postgres now()"). |
| 10 | `app.domain_events` gains `failed_at` and `error`. The outbox feed turns each row into an envelope on its own; a row the envelope refuses is marked failed (with the schema's message) and logged, and is never returned again. The pending index leaves failed rows out. | Task (F5 known gap, L8): "keep it visible, for example marked failed with the reason". |
| 11 | The relay routes each event on its own. An event a subscriber's `when` throws on, or that fails the envelope, is failed (the feed's optional `failed`), not relayed; the other events of the batch are relayed and marked. A queue that refuses a job (Redis down) stops the feed's tick: what was relayed is marked, the rest stays pending for the next tick. `EventFeed.failed` is optional, so a feed without it keeps working (its bad event is logged and returned again). | Default: a deterministic failure is the event's; a transient one is the tick's. |
| 12 | Failed rows are deleted with relayed and withdrawn ones by the `events.relayed` retention target, since each holds a copy of its record. An operator can relay one again by clearing `failed_at` (guide 5.10). | DPDP default (no copy kept past its period). |
| 12a | The back-office reply (`POST /api/backoffice/handoffs/:id/reply`) honours the key the same way: a repeat sends nothing and answers `{ sent }` as the first did. | Same class as C9-1 (a retried send went out twice). |
| 13 | A job's result URL is fetched with a connect-time check: `fetchResult` resolves the name once, at connect, through a lookup that refuses any address that is not public, and connects only to what it returned. The separate lookup before the fetch is gone. | Lead L9; B11's result-URL rule. |
| 14 | Schema: two nullable columns on `app.domain_events` and the pending index's predicate. No migration is committed: **the integrator generates the framework's (`pnpm --filter @hykr/db generate`) when merging**, before CI runs on a fresh database; `runtime.e2e`, `integrations-retries.e2e` and the feed's `failed_at` filter need it. | Plan migration rule; review of V6. |
| 15 | A connection's credentials in a create or update body are recognised on a retry by an HMAC-SHA256 under a key derived (HKDF) from `SECRETS_KEY` (`secretTag`, integrations `settings.ts`), not by a plain SHA-256: `app.idempotency.request_hash` then holds nothing a low-entropy secret could be guessed from offline. The route tags its body; `runWrite`'s hash is unchanged. A changed `SECRETS_KEY` between a request and its retry makes the retry a 409. | Review of V6 (was an assumption). |

## The class: write routes and the idempotency-key

The write routes in `framework/` that never read the key (the review added voice, the WhatsApp
link, the job callback and inbound webhooks):

| Route | Before | Now |
|---|---|---|
| `integrations` (9 writes) | Key dropped: a second endpoint or connection, a second rotation | Honoured (decision 4) |
| `calendar` complete, disconnect, feeds create and revoke | Key dropped; complete's code used up first | Honoured (decision 5) |
| `files` presign, discard | No `runWrite`: a second pending file; a repeat discard 404 | Honoured (decision 6) |
| `files` confirm, transcribe | A repeat returns the ready file, or the stored words | Unchanged: no second effect one after another (concurrent transcription in Deferred) |
| `jobs` cancel | A repeat 409 `already_finished` | Honoured (decision 6) |
| back-office reply | A second WhatsApp message | Honoured (decision 12a) |
| back-office take, return, consent, draft | Take and return are state moves (a repeat is refused or a no-op); a draft writes nothing | Unchanged |
| chat turns, new threads, WhatsApp link codes | A second turn, thread or code | Deferred (section 14) |
| `voice` session, end | A second room token and `voice.session.start` audit row (no worker or minutes until someone joins); end is a state move | Deferred (section 14) |
| WhatsApp link `verify`, `number`, `DELETE` | A used code, a number claimed again, an unlink of nothing | Deferred (section 14, with the link code) |
| `jobs` callback | Signed by the service and deduped by its delivery (`dedupe`); a finished job ignores later updates (B11) | Unchanged: not a caller's retry |
| inbound webhooks (`/webhooks/:connector/:id`) | Stored once per connection and the sender's id (B10) | Unchanged |
| inbox read, push register and forget, the blob PUT | Idempotent by nature (a flag, an upsert, the same bytes) | Unchanged |
| undo, approval decide (`@hykr/core`) | A repeat is 409 (too late, already decided): nothing twice | Unchanged |
| invites, party invitations by email, share links | Documented exceptions (A4, B7, B9) | Unchanged |

## Leads

- **L7 (other routes ignore the key): held**, for calendar feeds, file presign and discard, and
  job cancel; each now has a test that failed before. A sequential repeated transcribe did not
  hold: it returns the stored words (`files.service.ts`, `transcript !== null`), and files
  record no usage rows; only concurrent ones run twice (Deferred).
- **L8 (one poison event stalls every business): held.** `runtime.e2e` inserts a row with
  `channel = 'bogus'` and one a subscriber's `when` throws on; before the fix another business's
  event never arrived. Now both rows are failed with their reasons and the other event arrives.
  Same class: `OutboxRelay` (`app.outbox`, sends) runs its batch in one transaction and read
  `payload.row`; a JSON `null` payload would throw and stop every send under the `bull` prefix.
  It now reads a missing payload as empty, so that row fails in its own dispatch job. No test:
  only the `bull` prefix takes a payload without `queues`, and tests must not use it; writers
  (`queueNotification`, `send-template`) always store an object.
- **L9 (a name that resolves inside): did not hold for webhooks**, held for job results. The
  egress guard checks addresses in the socket's own look-up (`egress.ts` `guardedLookup`), which
  `egress.test.ts` ("refuses a public-looking name that resolves inside, at connect time")
  already proves with an injected resolver; deliveries go through `safeRequest`. No live DNS
  (nip.io) was used. `jobs/fetch.ts` looked up, then let `fetch` resolve again: a new unit test
  (`jobs-fetch.test.ts`) makes the first look-up answer public while the name resolves to
  127.0.0.1 when connecting. Before the fix the fetch went past the check and failed with the
  network's error instead of a refusal; now it is refused and a local server sees no connection.
- **L15 (an event older than its subscriber): held** for webhook endpoints (test in
  `integrations-retries.e2e`); mention triggers are fixed with event triggers; message, webhook
  and condition triggers are left as decision 7 says.

## Assumptions to review

- **Any change hides the secret from a repeat.** A repeat answers a secret only while the
  record's `updatedAt` is the one the repeated write left, so a label change or a pause since
  also answers without it (fail closed; the creator can rotate). A fingerprint of the sealed
  value would tell credentials apart from other changes, at the cost of keeping it with the
  stored reply and stripping it from answers.
- **A paused agent.** Events that happen while an agent is paused still start runs when it is
  active again before they are relayed; the cut-off is the trigger's creation, not its last
  resume. Should a resume start a new cut-off?
- **An endpoint's changed events.** An endpoint that adds a pattern, or is made active again,
  gets the events relayed after that change, even ones that happened a few seconds before it.
- **Files, cancel and calendar `complete` take no lock.** Two presigns with one key at the same
  moment can both make a pending file (the second's expires unused). Two completes with one key
  at the same moment make one connection and one code exchange, but the second answers 400
  `calendar_sign_in_invalid` instead of the first answer (section 14). Is that worth a lock?
- **A parked create repeated has no secret.** The first answer of a parked endpoint create
  carried its secret; a repeat finds no endpoint yet and answers without it. Rotate after the
  approval if the first answer was lost.
- **A filter that throws withholds the event from everyone.** An event a subscriber's `when`
  throws on is failed for every subscriber (notifications, webhooks, resumes), not only that one.
  Should the others still get it?
- **Write hooks see the caller's body.** `ctx.requestBody` (a connection's credentials,
  Google's one-time code) reaches every write hook's `decide` and `afterRun` with the rest of
  the context. None stores the context: `auditCtx` and parking pick named fields.
- **A failed event is not retried.** A row the envelope refuses stays failed until someone
  clears `failed_at`. Nothing tells the business; the worker's log does.

## API sketch

```ts
// @hykr/core
interface WriteCtx { /* … */ requestBody?: unknown }
interface WriteOutcome { result: WriteResult; events: object[]; repeat?: true }
findRepeat(db, ctx, op, request?): Promise<WriteOutcome | undefined>   // 409 for another request
saveReply(db, ctx, op, request, response): Promise<void>               // for writes outside runWrite

// @hykr/api
interface EventFeed { /* … */ failed?(items: { id: string; error: string }[], a: { prefix }, ctx) }
// app.domain_events: failed_at timestamptz, error text
```

## Test plan

- `integrations-retries.e2e` (new): one key twice gives one endpoint and the same secret (also
  two at the same moment), and no secret is kept in `app.idempotency`; a repeat by someone who no
  longer manages integrations is 403 without the secret; the same key with another
  body is 409; a change repeated is one change; a connection with generated credentials, once,
  same credentials; a rotate repeated rotates once; an endpoint made after an event happened
  gets no delivery for it, and gets one for the next. After review: a connection given new
  credentials by another admin answers a repeat of its create without any credentials; an
  endpoint rotated since answers a repeat of its create, or of the earlier rotate, without a
  secret; a connection with credentials given is recognised on a retry (and 409 with other
  credentials) while its stored `request_hash` is not the plain SHA-256 of the body.
- `handoff.e2e`: a back-office reply repeated with its key is sent and audited once.
- `calendar.e2e`: a feed created twice with one key is one feed, the URL only the first time;
  a sign-in completed twice with one key is one connection and one code exchange.
- `files.e2e`: a presign with one key twice is one pending file; a discard repeated is 204; a
  presign repeated after its upload expired is 409 `upload_expired` (after review).
- `jobs.e2e`: a cancel repeated with its key answers 200.
- `agents.e2e`: a stored event that happened before the agent was made starts no run; a later
  one does; a mention of an agent with no saved mention trigger starts no run (after review).
- `runtime.e2e`: a stored event the envelope refuses is marked failed with its reason, and
  another business's event still reaches its subscriber; a subscriber whose `when` throws fails
  that event only.
- `jobs-fetch.test.ts` (new, unit): a result URL whose name resolves inside at connect time is
  refused, with no connection made. Both resolvers are mocked (`node:dns/promises` answers a
  public address to `checkResultUrl`, `node:dns` `lookup` answers 127.0.0.1 when the socket
  connects), and the test checks the connect-time look-up was the one asked.

Fixes without a test of their own: the mention-trigger cut-off by time (the same check as the
event trigger's; its missing-row case has one), the failed rows in the `events.relayed` retention, the `OutboxRelay` payload guard,
and the result fetch's handling of a body cut off mid-way.

Each test above failed on the code before its fix, except the two calendar tests, which were
written after the shared fix was built (before it, a repeated feed create hashed a fresh id and
token hash, so it was a 409, and a repeated complete found its sign-in used up, a 400).

## Deferred

- Files and jobs still write without `runWrite` (B1, B11): moving them onto it is its own unit.
- A transcription asked for twice at the same moment still runs speech to text twice (a retry
  after it finished returns the stored words).
- Chat turns, new threads, voice sessions and the WhatsApp link's routes ignore the key
  (section 14).
- No lock for concurrent repeats of a file presign or discard, a job cancel, a back-office reply
  or a calendar `complete` (section 14).
- A screen or notice for failed stored events (section 14).
