# B6 + B4: state machines and SLAs, versioned and frozen records

## Summary

B6 gives an entity a declared state machine. Its spec's `states` trait lists the states, the
initial one, the transitions (from, to, who may, guards, required fields, the approval each one
needs and its approval level) and the SLAs that run while a record sits in a state. The `states` plugin
keeps the state field honest on every write: a record starts in the initial state, plain CRUD
never moves it, and a command moves it only along a declared transition. A transition runs
through `runWrite` like every write (`<entity>.transition`, from `POST /api/transitions/...`,
the assistant's `transition-<plural>` tool, or the `transition()` helper inside a command), so
it is validated, authorized, parked when its approval says so, audited, and stores an event per
transition with the row before and after. SLA timers start when a record enters a state and stop
when it leaves, in the write's own transaction (a durable table, not Redis). A sweeper in the
worker marks breaches, stores a breach event (`<entity>.sla.breached`) that names the
capabilities whose holders the application's notification tells, and runs the escalation's transition as
the system principal. Business hours come from the business's settings.

B4 gives an entity a version. The `versioned` trait adds a version counter bumped on every
write; a write against an old version answers 409 (`stale`), whether the client sent the version
it read or the write path loaded it. A parked write pins the versions it loaded: approving it
after the record moved on fails instead of applying it to a newer version. `frozenWhen` freezes
a record (and its children) in the states the application names, apart from its state field.
Revisions (v1, v2, v3) are records of their own in one series: `reviseWithChildren` copies a
record and its whole tree of children as the next revision, and the application freezes the old
one. The history endpoint lists a record's revisions; the approval card shows which version a
request is for.

The sample's `orders` module proves both: an order moves draft → submitted → approved →
fulfilled (or cancelled), with two SLAs on `submitted` (owners are told after 24 business hours;
after a week it expires, by the server itself), a level-3 approval on the assistant's `approve`,
and `order.revise` that turns a submitted (or expired) order into v2 (a draft) and freezes v1 as
superseded. An approved order is the contract: frozen, never revised. The fixture's `tickets`
module proves every mechanism on neutral data.

## Assumptions to review

- **Workflows are code.** States and transitions are declared by modules; a business can rename
  nothing and add no stage. The PRD's pipeline board has "studio-configurable stages": should a
  business be able to add stages (stored per tenant) on top of a module's machine?
- **SLA durations per business.** A business can override an SLA's duration or switch it off in
  its `sla` settings (once settings can be edited, A11). Is that the right granularity, or should
  a business define new SLAs?
- **No working week by default.** Without `businessHours.week`, business-hours SLAs count every
  hour (they fire sooner, never later). Should the framework assume a working week instead?
- **Holidays are dates.** Half days and per-branch calendars are not supported. Needed?
- **Breach after the fact.** A breach found when the record leaves the state (the sweeper ran
  late) is recorded but neither notified nor escalated. Should it still notify?
- **Escalation by the system.** An escalation transition runs as the system principal, which
  cannot park. A transition whose approval would park for the system is refused and recorded on
  the timer. Should escalations be allowed to ask a person instead?
- **Readers who cannot write.** A transition is tried in a savepoint before anything parks, so a
  reader who cannot write gets 404 instead of a request someone else would approve. Is a
  "request a change" flow for read-only participants wanted (B7 participants)?
- **Revisions are copies.** v2 is a new record with its own id, and v1 stays readable, frozen. Is
  one record with snapshots preferred for some kinds of document?
- **Revision numbers.** A revision's number is `<number>-v<n>` in the sample. Is another form
  wanted, and should a revision ever take a new series number?
- **What freezes.** A frozen record keeps its state field movable (an approved order can still be
  fulfilled) and `editableWhenFrozen` fields. Can an owner re-open an accepted (approved) order,
  with audit, or is cancelling and starting again the only way?
- **Who sees versions.** Everyone who may read a revision sees it in the versions list. Should a
  customer see only the revision sent to them?
- **Approval pins.** A parked write fails on approval when the record's version changed at all,
  even for an unrelated field. Should only changes to the fields the request touches count?
- **Expired orders.** In the sample, an order nobody decided in a week expires and can then only
  be revised (or left). Should expiry instead hand it back to draft, or cancel it?
- **Who approves.** The sample's `approve` needs `orders.approve` (owners and admins); a person
  who holds it may approve an order they submitted themselves. Should approving your own order be
  refused (A5's self-approval rule)?
