# H5: the orders module's acceptance state and its supplier connector

## Summary

Two gaps the completeness review found in the sample `orders` module, both closed in the module
(no framework change):

- **An accepted order has a state of its own (B8).** `ORDER_STATES` gains `accepted` and a
  system transition `accept` (`approved` → `accepted`). `OrderAcceptance` names it, so a
  customer's acceptance moves the order in the accepting transaction, and the order stays frozen.
  The plan's smoke flow (submit → approve → PDF → share link → OTP acceptance → frozen v1) now
  ends in a state of its own: lists, totals by status and fulfilment tell an accepted order from
  one that is only approved.
- **The integration bus in the sample (B10).** Accepting an order *places* it: the acceptance's
  `accepted` hook stores the event `order.placed`, whose record carries the order's groups and
  lines. A business sends it to its supplier and its books with webhook endpoints; the module's
  read projector `costHidden` takes each line's cost out unless the endpoint was given
  `orders.cost.read`. The supplier reports back through the module's own connector,
  `orders-supplier` (HMAC-signed body, one connection per supplier party): its `order.fulfilled`
  event fulfils the order as the business's system principal, through `runWrite`, and only for an
  accepted order that this connection's party supplies.

## Assumptions to review

- **Placed when accepted.** An order is sent to outside systems (`order.placed`) when its
  customer accepts it, not when the business approves it, and an order with no customer is never
  placed. Should approving an order without a customer place it too?
- **Fulfilling without acceptance.** People may still fulfil (or cancel) an approved order that
  was never accepted in the app. Should fulfilment wait for acceptance?
- **A supplier reports only on accepted orders.** The supplier's `order.fulfilled` is refused for
  an order that is only approved. Is that right, or may a supplier report on any order it is on?
- **One connection per supplier.** A connection names one party, and the business types the
  shared secret. Should the server make the secret (and the supplier be chosen separately)?
- **Fulfilled is the only report.** A supplier's acknowledgement and dispatch (PRD Build, vendor
  portal) have no state yet; only `order.fulfilled` moves an order. Which supplier events should
  the orders module take, and what should each do?
- **Whole order in the event.** `order.placed` carries every line (up to 1000 nodes) in one
  stored event and one delivery. Is a size limit or a summary needed for very large orders?

## API sketch

```ts
// contracts/order.ts
transitions: [ …, { name: 'accept', from: 'approved', to: 'accepted', expose: 'system' } ]
frozenWhen: { status: ['submitted', 'approved', 'accepted', 'fulfilled', …] }

// server/acceptance.ts
export const OrderAcceptance = defineAcceptance<OrderDocumentData>({
  name: 'orders.order', document: 'orders.order', by: 'customer', channels: ['whatsapp', 'email'],
  transition: 'accept',
  when: (row) => row.status === 'approved' ? null : row.status === 'accepted'
    ? { rule: 'order_accepted', … } : { rule: 'order_not_approved', … },
  accepted: async ({ tx, row }) => ({ events: [await orderPlaced(tx, row)] }),
});

// server/connector.ts
export const SupplierConnector = defineConnector<{ secret: string; partyId: string }>({
  name: 'orders-supplier', credentials, publicFields: ['partyId'],
  inbound: { verify: x-supplier-signature, parse: { id: x-supplier-event, type, data } },
});
export const SupplierFulfilled = defineConnectorHandler({
  name: 'orders.supplier-fulfilled', connector: 'orders-supplier', on: ['order.fulfilled'],
  handle: (event, ctx) => /* party supplies it, it is accepted */ ctx.write(transitionOp(Order, { id, transition: 'fulfil' }), {}),
});
// index.ts: contributes: { connectors: [SupplierConnector], connectorHandlers: [SupplierFulfilled] }
```

```
POST /api/integrations/endpoints   { url, events: ['order.placed'], capabilities?: ['orders.cost.read'] }
POST /api/integrations/connections { connector: 'orders-supplier', credentials: { secret, partyId } }
POST /webhooks/orders-supplier/<connection>   x-supplier-signature: sha256=<hex>, x-supplier-event: <id>
     { "type": "order.fulfilled", "data": { "orderId": "<uuid>" } }
```

## Test plan

- `application/api/test/domain/order-acceptance.e2e.test.ts`: the owner asking for `accept` is
  `system_only`; the customer's code moves the order to `accepted` (one version on from the
  PDF's; the evidence keeps the PDF's), frozen (save `record_frozen`, no revise); the write
  stored `order.accept` and `order.placed`, and the history shows the order's update from
  `approved` to `accepted` by the customer who accepted; the same PDF is `already_accepted`, and
  a new PDF of the accepted order is `order_accepted`; the assistant cannot fulfil it
  (`humans_only`); the owner may still cancel it.
- `application/api/test/domain/share.e2e.test.ts`: the guest accepts through the link and the
  order is `accepted`, one version on, and frozen (the owner's save is `record_frozen`); the link
  shows it accepted, and its PDF is `already_accepted`.
- `application/api/test/domain/order-webhooks.e2e.test.ts` (a local receiver,
  `INTEGRATIONS_ALLOWED_HOSTS=127.0.0.1`):
  - outbound: accepting an order sends `order.placed` to the business's endpoints, signed
    (verified with `verifyWebhook`); the endpoint without `orders.cost.read` gets every line
    without `cost` (and no internal column), the one given it gets each line's cost; nothing is
    placed before the acceptance; the delivery log keeps what each endpoint got; another
    business reaches no delivery and its `*` endpoint gets nothing of it;
  - inbound: the connector is listed (public `partyId`, no `generate`); a connection without a
    party or with a short secret is 400, and the secret is never shown back; a forged, missing or
    body-tampered signature is 401 and a signed request without an event id 400, all storing
    nothing; a signed `order.fulfilled` for an order this supplier is not on (also another
    business's) fails `not_supplier` and changes nothing; one for an approved, unaccepted order
    it supplies fails `order_not_accepted`; data that does not parse fails
    `supplier_event_invalid`; one for the accepted order fulfils it, audited as the system
    (`integrations.orders-supplier`, channel `background`, run id the inbound event), and a
    redelivery is stored once; a later report on the fulfilled order changes nothing; another
    business reaches neither the connection nor its log (404).
- `application/domain` views test: `order.card` and `order.list` say the accepted state in each
  language.
