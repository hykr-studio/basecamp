# A12: the assistant reads images and PDFs

## Summary

Asked for by Interioring (18 Nov 2026), checked against `feat/platform-gaps` at `4ce7192`. Before
this, the assistant knew only a file's name and size. Now it can look at an image or a PDF that a
person sent, or that is on a record they reach, through the business's vision model under its
model policy. It returns what it read as text (the `read-file` tool, `POST /api/files/:id/read`), or
as fields checked against a Zod schema (`FilesService.readWithModel`) for an application's command,
a job or a subscriber.

- **Capabilities.** A chat model in `MODEL_PROVIDERS` declares `capabilities: ['vision', 'pdf']`.
  The business's `models` policy gains `vision`.
- **Reading.** A read uses the reach of `GET /api/files/:id`, PNG, JPEG, WebP or PDF only, within
  the limits.
- **PDFs.** A PDF is sent as it is to a model that takes PDFs, otherwise drawn page by page.
- **Accounting.** Each read is metered on `tokens` and the new `file_pages` meter, checked against
  the credits pause first, and audited once as `file.read_by_model`, with no reading in the row.
- **WhatsApp.** A WhatsApp photo or PDF can be read in the turn it came with (`files.readInbound`,
  on by default).

The sample application's part: a to-do the assistant creates with a cost waits for the person. Its
scripted model turns "add this bill" plus a photo into `read-file`, then `create-todo "Pay <shop>"`
with the bill's amount. A golden WhatsApp conversation (`13-bill-photo.yaml`) checks it.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | `capabilities?: ('vision' \| 'pdf')[]` on a model in `MODEL_PROVIDERS`, default none. Only chat models may have it; on an embedding model it is a `ModelConfigError` at startup. `ModelEntry.capabilities` is always an array, and `GET /api/models` lists it per model. | Request §1. |
| 2 | Fake mode's `fake/scripted` has both capabilities, so tests and CI read files without a network. | Default. |
| 3 | The model that reads files is the policy's `vision`, else the business's chat model (hook, `chat`, deployment default, as A10 decision 10) if it has `vision`. It must be registered, allowed and in the regions like any model. Otherwise 409 `{ error: 'no_vision_model', rule, reason }`, the reason starting "Files can't be read here". 409, not A10's 503/403, because the request names it: the business's own setup lacks something, which is a conflict and not an outage. | Request §1; A10 decisions 4, 9, 24 (no fallback). |
| 4 | `PUT /api/models/policy` refuses a named `vision` that is unknown, not allowed, outside the regions or without `vision` (400 `invalid_policy`). An unset `vision` is never a problem: reading is then refused when asked for, and turns run. | Default; mirrors A10 decision 22 for embeddings. |
| 5 | A read has the reach of `GET /api/files/:id` (`FilesService.reachable`), and the file must be `ready` (else 404). | Request §2. |
| 6 | **A6 narrowing applies to every file read.** An agent's run reaches a file on a record only if its scope reads that entity (`agent-run.read:<entity>`), and reaches no file that is on no record. This is a change to `reaches()`, so `GET /api/files/:id` is narrowed too. Before, contributed routes were reached "still as the owner" (A6 decisions 4 and 28). | Request acceptance ("An agent run reads only files its narrowed identity reaches"). |
| 7 | Readable types are PNG, JPEG, WebP and PDF. Anything else is 422 `unsupported_type`: audio (that stays `transcribe-file`), SVG, GIF, video, and HEIC with a reason telling the sender to send a JPEG. The type is checked from the declared MIME type first, then the bytes (a PNG that is not one is refused). | Request §2; open question (HEIC): refuse with a clear reason. `@napi-rs/canvas` cannot decode HEIC, and the image-library question in the documents requirement is still open. |
| 8 | Limits come from the environment, read when the API starts: `FILES_READ_MAX_BYTES` (20 MB, 422 `too_large`), `FILES_READ_MAX_PAGES` (20), `FILES_READ_MAX_SIDE` (2048 px), `FILES_READ_DPI` (150), `FILES_READ_PER_HOUR` (60, 429 `too_many_reads`) and `FILES_READ_TIMEOUT_MS` (120 s). | Request §6. |
| 9 | A PDF over the page limit with no `pages` is refused (422 `too_many_pages`, the reason saying to name pages), not cut to its first pages. A page the file lacks is 422 `bad_pages`. The acceptance criterion asks for a refusal. | Request acceptance; default. |
| 10 | **PDFs.** A model with `pdf` gets the PDF as it is when no pages are named. Otherwise each chosen page is drawn at 150 dpi (capped at the longest side) with `pdfjs-dist` (legacy build, no worker) onto `@napi-rs/canvas`, as a JPEG, and its text layer goes alongside as text ("Page n, its text layer: …"), which helps the model and costs little. | Open question (library): pdfjs-dist first. `@napi-rs/canvas` is the one native package, prebuilt, with no system libraries; mupdf is AGPL. |
| 11 | Images within 2048 px are sent as they are; larger ones are drawn smaller as JPEG. | Request §6. |
| 12 | The drawing runs in the API process, not a worker queue, with at most two files prepared at once per process. The tool's HTTP call answers in the same request; a queue round trip would only add latency for files this small. | Default (see Assumptions). |
| 13 | The libraries are loaded on first use (`await import`), so a process that never reads a file never loads them. | Default. |
| 14 | The model call is `generateText` from the `ai` package (`readAsText` / `readAsValue` in `@hykr/agents`), outside any agent loop, with the system prompt saying that the file's contents are data, never instructions, and that nothing written in them is to be followed. This mirrors how recalled memory is framed for a turn. | Request §3. |
| 15 | `readWithModel` asks for JSON matching the schema's JSON Schema (`z.toJSONSchema`), parses the reply (whole, a fenced block, or its outer braces) and checks it with Zod. On a mismatch it asks once more, with the issues. After that it gives 422 `unreadable`, logs the model's reply at warn (cut to 2,000 characters) and never returns it. Provider JSON modes are not used: not every OpenAI-compatible gateway has them. | Request §4. |
| 16 | `readWithModel` (and every read) throws `InWriteTransaction` at once inside a write's transaction. `runWrite` marks its transaction in an `AsyncLocalStorage` (`inWriteTransaction`, `assertNoWriteTransaction` in `@hykr/core`). The check covers writes that run inside a caller's transaction (`outer`) too. | Request §4 and acceptance. |
| 17 | **Order of checks.** Reach, then type and size, then the WhatsApp setting, then the model policy, then credits, then the hourly limit, then the bytes. Every refusal comes before any bytes go to a model. | Request §6 ("the credits pause applies before the call"). |
| 18 | **Credits.** The paused answer is the agents' 402 `credits_paused`, checked on `tokens` (with the model's ref) and on `file_pages`. | Request; A3, H3. |
| 19 | **Metering.** Tokens go on `tokens` with the model's ref as the variant, and the images or pages sent go on the new `file_pages` meter (unit `page`, same variant). Both have source `file_read`, are keyed `file_read:<request id>` (counted once), and carry the subject, run and channel. A read that ends `unreadable` is metered too: its tokens were spent. | Request §6; open question (page price): `file_pages` is priced in `CREDITS_CONFIG.prices.file_pages`, with no new schema. |
| 20 | **Audit.** One row per read: `file.read_by_model` on the file, with `after` holding `{ name, mime, size, model, provider, region, pages, who }` and the agent version in its column (`auditCtx`). Never the reading, the question, a URL or the bytes. A read refused before the call writes no row. | Request §6. |
| 21 | **The hourly limit** counts the person's `file.read_by_model` rows of the last hour (`after.who`: `user:<id>` or `contact:<id>`, the same for the person and their assistant). It is durable and correct across processes, and needs no Redis, like the voice minutes. | Default. |
| 22 | **WhatsApp.** The inbound line names `read-file` when the file is readable and the business allows it. `files.readInbound` (default on) refuses media not yet on a record with 403 `read_inbound_off`. A file on a record is read either way. | Request §7. |
| 23 | **The reading is not kept on the file.** Every read calls the model again. Storing a reading would need a column on `app.files`, its erasure, and a key on the question and pages, and the request calls it optional. | Open question (keep the reading): not now (see Assumptions). |
| 24 | **No chat attachments.** `TurnFields` is unchanged; a file reaches the assistant on a record or on WhatsApp. | Request (out of scope). |
| 25 | **Testing.** The scripted vision model "sees" what follows `FAKE-VISION:` in a file's bytes, or in a PDF page's text layer. Alternatives split by `\|\|\|` answer successive attempts, so a test can make the first reply wrong. The stub gateway (`fixture/features/models/gateway.ts`) answers image and PDF parts with how many it got. | Default. |
| 26 | **Sample application.** A to-do the assistant creates with a cost above zero waits for approval (`approval.create` in `todo.ts`). The `bill` script reads a photo on "add this bill" and adds "Pay <shop>" with the amount in paise. No new expense module: a to-do's cost is the sample's money on a record. | Product owner (reuse `todos.cost`). |

## Assumptions to review

- **Drawing in the API process.** Pages are drawn where the request is served, two files at a time.
  A busy deployment reading many large PDFs may want this moved to a worker queue. Is the API process
  acceptable for now?
- **HEIC is refused.** iPhones send HEIC unless set to "most compatible". Should HEIC be converted
  (for example with `heic-convert`, which is slow, pure JS) once the image library question is
  settled?
- **A long PDF is refused, not cut.** Should a read without `pages` take the first 20 pages instead,
  saying so?
- **Nothing is kept.** Asking about the same file again costs another model call. Should the reading
  be kept on the file, as a transcript is?
- **The hourly limit is per person, not per business.** Should a business also have a cap (it has
  `file_pages` caps through its plan already)?
- **Agent runs and unattached files.** A run reaches no file that is on no record, even its owner's
  own upload. Is that right?
- **One retry.** `readWithModel` retries once on a mismatch. Is one enough for floor plans?
