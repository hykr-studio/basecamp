# S2: an inbound event is keyed by what its sender signed

## Summary

A fix found by the security review of B10. `hmacConnector` verified an HMAC over the raw body
only, but took the event's id from a header (`idHeader`) that nothing signs. The server stores
each inbound event once per connection and event id, so whoever saw one genuine request (sender
logs, a proxy, a TLS-terminating middlebox) could post the same body and signature again under a
fresh id, as often as they liked. Each copy was stored as a new event and every handler ran
again: a purchase credited twice, a call placed twice, an order made twice. No timestamp was
checked either, so a captured request never went stale.

The fix has two layers:

- **The server never keys an event by an id nobody signed.** A connector declares whether the
  ids it reads are signed (`inbound.signedIds`). The default is false. Then the server stores
  each event under a hash of the signed body (`sha256:<hex>`, with the event's place for a
  batch), so the same signed request is one event whatever id travels with it. The id the
  sender gave is still kept, as `senderId`, for the log and for calling the sender back. It is
  never a key.
- **`hmacConnector` can sign the id and a timestamp.** `signedContent(req, { id, timestamp })`
  says what the sender signs, `timestampHeader` and `toleranceSec` (300 s by default) refuse a
  stale request, and `signedIds: true` says the id is covered. Its default stays the raw body
  with no timestamp, and then its ids are unsigned.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | `ConnectorInbound.signedIds?: boolean`. True means changing an event's id breaks the request's proof: the id is in the signed content, or read from the signed body. The default is **false**, so a connector whose author never thought about it is keyed safely. | Task ("have a connector declare whether its event id is authenticated"); plan rule: fail closed. |
| 2 | `InboundService.receive`, for a connector without `signedIds`, stores each event under `bodyKey(rawBody)`: `sha256:<hex of the raw body>`, or `sha256:<hex>:<n>` for the n-th event of a request that carries several. The unique index stays on (connection, `external_id`), so the same signed request is stored once, whatever id it carries. The check is in the server, not only in `hmacConnector`, so a hand-written `defineConnector` gets it too. | Task ("in InboundService.receive fall back to a body-hash key when it is not"). |
| 3 | The id the sender gave is kept in a new nullable column, `integration_inbound.sender_id`, when it is not the key. It is shown in the inbound log (`senderId`) and given to handlers (`InboundEventRecord.senderId`), documented as unverified: for logs and calls back to the sender, never a key. `externalId` is now documented as the key the event is stored under. | Default: support staff and handlers still need the sender's own reference; additive column (plan migration rule). |
| 4 | Combining the body hash with the unsigned id was rejected: an attacker changes the id, so the key changes, and a replay is a new event again. | Task's alternative ("optionally combined with the header"), considered and refused. |
| 5 | The cost of keying by the body: a sender that does not sign its ids and sends two different events with byte-identical bodies has the second dropped as a redelivery. A batch sender whose retry regroups events (a different body) stores events of the first batch again. Both are fixed by signing the ids (`signedContent` and `signedIds`), or by reading the ids from the body (`events` or `eventId` with `signedIds: true`). Logged as an assumption. | Default: a dropped duplicate-looking event is safer than a handler run twice. |
| 6 | `hmacConnector` options: `signedContent?(req, { id, timestamp }): string \| Buffer` (what the sender signs; default the raw body), `timestampHeader?`, `timestampUnit?: 's' \| 'ms'` (default seconds), `toleranceSec?` (default `DEFAULT_TOLERANCE_SEC`, 300, either way), `signedIds?`. With a `timestampHeader`, `verify` refuses a request without the header, with a value that is not a whole number, or one further than `toleranceSec` from now. With `signedIds` and an `idHeader`, a request without the id header is refused. A `signedContent` that throws refuses the request. | Task ("fold the id (and a timestamp) into the signed content with an option such as `signedContent(req)` plus `timestampHeader` and `toleranceSec`"); Standard Webhooks' 5-minute tolerance (B10 decision 3). |
| 7 | `hmacConnector`'s `signedIds` defaults to true only when the id is its own hash of the body (no `idHeader`, `eventId` or `events`). Otherwise it defaults to false. | Default: the only case the connector can prove on its own. |
| 8 | `hmacConnector` refuses, when it is defined, a `timestampHeader` without `signedContent` (a timestamp outside the signature proves nothing), and `signedIds: true` with an `idHeader` but no `signedContent`, `eventId` or `events` (a header outside a body-only signature cannot be signed). A `toleranceSec` that is not a positive whole number is refused too. | Default: catch the obvious misconfiguration when the app is built, not after a replay. |
| 9 | `defineConnector` refuses an inbound side that is `bodyless` without `signedIds`. With no body there is nothing else to key by, so the author must say that the ids are as trustworthy as the request. The `connectors` registry runs `defineConnector`'s checks on every connector, so a plain object literal is checked too. | Default: fail closed when the app starts. |
| 10 | `standard-webhooks` sets `signedIds: true`: its `webhook-id` is in the signed content `<id>.<timestamp>.<body>`. | B10 decision 3. |
| 11 | `google-calendar` sets `signedIds: true`. Google signs nothing: the channel token is a bearer secret, and whoever has seen one notice can send any notice, so the id is as trustworthy as the rest of the request. Its handler only reads the calendar again, so a forged or repeated notice changes nothing. Logged as an assumption. | B17; default (no stronger proof exists for Google's push channels). |
| 12 | `bodyKey(rawBody, index?)` is exported from `@hykr/connectors`. `hmacConnector`'s own fallback id (no id header) uses it, so its ids read `sha256:<hex>` instead of a bare hex digest, and the server's key and the connector's id are the same string. | Default: one key format. |
| 13 | The fixture keeps `fixture-sender` as the unsafe shape (body-only signature, id header), now keyed by its body. It adds `fixture-signed`, which signs `<timestamp>.<id>.<body>` with `x-fixture-timestamp` and `x-fixture-event`, to show signed ids. `fixture-phone` (B17's calls) is body-only and now keyed by its body, with no change to its test. | Task ("an integrations e2e test that replays with a fresh id header"). |
| 14 | No sample-application change: the sample registers no connector of its own. | Task note ("Sample demo: as needed"). |
| 15 | Schema: one nullable column, `app.integration_inbound.sender_id`. Additive. No migration is committed (the integrator generates it). | Plan migration rule. |

## Assumptions to review

- **Identical bodies.** For a sender whose ids are unsigned, two events with byte-identical
  bodies are one event. Senders usually put an id or a time in the body, so this should not
  happen. Is there a sender the product needs that sends identical bodies for distinct events
  and cannot sign its ids?
- **No timestamp, no expiry.** A sender that signs no timestamp can still have one captured
  request posted again later. It is dropped while its stored row exists, and inbound rows are
  kept until their connection is deleted. If a retention period for inbound rows is added (B18),
  a replay after that period would run again. Should inbound keys be kept longer than the event
  data, or should connectors without a timestamp be refused?
- **Bearer-token senders.** Google Calendar's push notices prove themselves with a token only, so
  anyone who sees one can forge others. Its handler is naturally idempotent. Should a connector
  of that kind be limited to handlers that only read the sender again?
- **Tolerance.** 300 seconds either way, as Standard Webhooks. Should a business be able to change
  it for a sender with a skewed clock?

## API sketch

```ts
// @hykr/connectors
interface ConnectorInbound<C> {
  bodyless?: boolean;
  /** The ids parse returns are covered by verify's proof. Default false: keyed by bodyKey. */
  signedIds?: boolean;
  verify(req, credentials, now?): boolean;
  parse(req, credentials): readonly InboundEvent[];
  challenge?(req, credentials): string | null;
}
bodyKey(rawBody: Buffer, index?: number): string          // 'sha256:<hex>' or 'sha256:<hex>:<n>'

hmacConnector({
  name, label, description?, header, prefix?, algorithm?, encoding?,
  signedContent?(req, parts: { id?: string; timestamp?: string }): string | Buffer,
  idHeader?, timestampHeader?, timestampUnit?: 's' | 'ms', toleranceSec?,
  signedIds?, eventId?(req), eventType?(req), events?(req),
}): Connector<{ secret: string }>

// e.g. a sender that signs "<timestamp>.<id>.<body>"
hmacConnector({
  name: 'their-system', label, header: 'x-signature', prefix: 'sha256=',
  idHeader: 'x-event-id', timestampHeader: 'x-timestamp', signedIds: true,
  signedContent: (req, { id, timestamp }) => `${timestamp}.${id}.${req.rawBody}`,
});

// @hykr/api
interface InboundEventRecord {
  externalId: string;        // the key it is stored under: the signed id, or bodyKey(...)
  senderId: string | null;   // the id the sender gave when it is not the key: unverified
  ...
}
// GET /api/integrations/connections/:id/inbound rows gain senderId
```

## Test plan

- `framework/connectors/src/connectors.test.ts`:
  - `bodyKey`'s format, single and indexed;
  - `defineConnector` refuses `bodyless` without `signedIds`;
  - `standardWebhooks` and `googleCalendarConnector` declare `signedIds`;
  - `hmacConnector` with an id header and a body-only signature: `signedIds` false, the
    header's id is parsed, and a fresh id header still verifies (which is why the server keys by
    the body);
  - with no id: `signedIds` true and the id is `bodyKey`;
  - `signedContent` with a timestamp and an id: a fresh request verifies; a changed id, a stale
    timestamp (either way), a missing timestamp, a non-numeric one or a missing id is refused; a
    millisecond timestamp with `timestampUnit: 'ms'`; a `signedContent` that throws refuses;
  - the definition checks (`timestampHeader` without `signedContent`, `signedIds` with a bare id
    header, a bad `toleranceSec`).
- `framework/api/test/framework/integrations.e2e.test.ts`:
  - the review's scenario: one genuine `fixture-sender` request with `x-fixture-event: ev-1`,
    then the same body and signature with `ev-attacker-2` and `ev-attacker-3`, then `ev-1`
    again. One event is stored (keyed `sha256:<hex>`, `senderId` `ev-1`) and
    `fixture.sender-done` runs once;
  - `fixture-signed`: a genuine request is stored under its own id; the same signature with a
    fresh id is 401; a genuine redelivery (same id, signed again with a new timestamp) is
    stored 0 times; a different signed id with the same body is a new event; a stale timestamp
    and a missing one are 401;
  - the log shows `senderId`, and another business gets 404 for it.

## Deferred

- A retention period for inbound rows (B18) must keep their keys at least as long as a replay
  of a sender without a timestamp should be refused. No inbound retention exists yet.
- Senders whose signature header carries the timestamp too (`t=…,v1=…`) need their own
  `defineConnector`; `hmacConnector` reads one signature header and one timestamp header.
