# V3: erasure reaches invitations, file names, calendar labels and the assistant's stored runs

## Summary

A fix unit from the live validation of `feat/platform-gaps` (`docs/decisions/VALIDATION.md`, row 3;
defects C8-2, C8-3 and C8-4), plus the critic's lead that audit redaction is shallow. After a
person was erased, three kinds of copies kept their personal data:

- **File names (C8-2).** The `files` contributor marked the person's files erased but returned no
  `erased` set, so the `file.*` audit rows (`file.upload`, `file.confirm`, `file.attach`,
  `file.received`, ...) kept `after.name`. The same held for files erased with a declared record
  (`eraseFilesOn`, erasure and retention): `redactCopies` only redacted rows of the record's own
  type.
- **Email (C8-3).** Nothing erased the business's invitations (`app.member_invites`) or their audit
  rows (`invite.create` / `invite.update` carry the email), and the owner still listed them under
  invitations. The calendar contributor deleted the calendar's inbound connection but not the
  label of its audit row (`Google Calendar: <email>`).
- **Chat words (C8-4).** The erasure deleted the person's run spans but not Mastra's stored score
  results (`mastra.mastra_scorers`, keyed by the run) or the scorers' own traces (their spans name
  the run only in `metadataRaw.targetTraceId`). Retention of `assistant.traces` missed both.

The shared root cause is that `redactCopies` matched only rows of the same resource type and id,
and took fields out at the top level only. Contributors that return erased sets (unit V8 adds the
comments, parties, shares, memory, jobs, inbox, agents and push sets) need a mechanism that finds
every copy the server keeps, so V8 only has to return sets.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | **Copies are found by the record's id at any depth.** A JSON copy loses a set's fields from every object in it whose `id` is one of the set's ids, at any depth: a reply `{ invite: { id, email }, token }`, a notification `{ rows: [...] }`, an order's `lines[]`. Rows of the record itself (`resource_type` and `resource_id` are the record) also lose them at the top, as before. | Task ("deep enough for nested command inputs"); validation C8-3 (the kept reply of `invites.create`). |
| 2 | **Approvals about the record, and every copy of them, are redacted.** An approval is about the record when its resource is the record, or when its input names the record (decision 3). It loses its summary and the fields in its input. Its copies lose the same: audit rows of `resource_type 'approval'` (the whole approval row, `payload.input` and `summary`), `approval.*` stored events (the row, with its summary), approval notifications in the outbox, the parked reply (`response.approval.input`), and the park's own audit row (`after.summary`, found by the approval's resource and `after.approvalId`). Before, only the approval row itself was redacted, and only when its resource was the record. | Task ("record-level rows"); critic lead (a comment's commands park on the record the comment is on). |
| 3 | **A command's input names a record by `id` or by `<type>Id`** (`commentId`, `inviteId`). An object in an approval's input that names an erased id by one of those keys loses the set's fields (`{ commentId, body }` loses `body`). `ErasedRecords.refs` (optional) lists other keys for a set. Only command inputs are matched by reference: a record that merely references an erased id (a to-do's `noteId`) keeps its own fields wherever it is copied. | Task; default (precise matching, no over-redaction of other records). |
| 4 | **The walker is plain TypeScript** (`scrubCopy`, `scrubInput`, exported from `redact.ts` and unit-tested). Candidate rows are selected per table in one statement per set (by resource for audit and events, which are indexed; by the ids found at `$.**.id` for the outbox, messages and replies, as before scoped to the business), changed in memory, and written back in one statement per table (`jsonb_to_recordset`). Only rows that changed are written and counted. A set is handled in slices of 1000 ids, so a retention rule's thousands of records never overflow a statement's parameters. | Default; same pattern as `redactFilings`; retention calls it with large sets. |
| 5 | **Derived files' copies go too.** `eraseFilesOn` returns the ids it erased, and `redactCopies` redacts them as a `file` set (`fileCopies(ids)`: `name` and `transcript`). The `files` contributor returns the same set. A `file` set is a no-op for the file, memory and feature steps: no entity is named `file`, no file is on a `file`, and no feature keeps a `file` copy. | Validation C8-2 (verifier's sketch 1 and 2); B1 decision 21 ("cleared at once"). |
| 6 | **Invitations are erased.** A members erasure contributor (`invites`, a person only) deletes the business's invitations addressed to the person's email or accepted by them, and returns them as an `invite` set (`email`), deleted. It runs with the other contributors, before the account's email is replaced. The register gains `members.invites` (delete), and the person's export lists them (`invites`). | Validation C8-3 (verifier's sketch); H4 decision 3 (calendar invites, the same reasoning). |
| 7 | **The calendar's inbound connection is an erased record** (`integration_connection`, `label` and `public`, deleted), so the `integration_connection.create` audit row loses its label. The label keeps naming the account as before. | Validation C8-3. |
| 8 | **Mastra's score results and scorer traces go with the runs.** `eraseMastra` first collects the scorer traces of the person's runs (`mastra_score_events.scoreTraceId` of the runs, and spans whose `metadataRaw.targetTraceId` is a run), then deletes span and log events of those traces with the rest, and deletes `mastra.mastra_scorers` rows whose `runId` or `traceId` is a run. `expireTraces` also expires `mastra.mastra_scorers` by `createdAtZ`. | Validation C8-4 (verifier's sketch); B18 decision 15. |
| 9 | **The same class in the framework's own part of an erasure.** `eraseFramework` and `deleteContacts` also return what they delete or blank as erased sets: the person's saved pages (`page`: `name`, `spec`, deleted), their customer records (`customer`: `displayName`, blanked) and their contacts (`contact`: `address`, `displayName`, and a consent's `note`, deleted). Before, a saved page's name stayed in its `page.create` audit row. | Task ("fix the class, not one site"); found by the member test. |

## Assumptions to review

- Over-redaction in approval inputs: an input that names an erased record by `<type>Id` loses the
  set's field names from that object, even when a field of the same name belongs to the record
  the approval is on (`{ noteId, title }` on a to-do loses `title` when the note is erased).
  Approval inputs are copies of what someone asked for; erring towards taking out is the safer
  side.
- An approval whose input names an erased customer record or contact (`customerId`,
  `contactId`: a message to them, the erasure filing about them) is about it, so it loses its
  summary in every copy, pending ones included. The summary is the approval card's line; the
  action, the requester and the ids stay.
- Scorer rows are found by run only, not by `requestContext.userId`: `requestContext` is a JSON
  string inside jsonb (encoded twice), and matching it would scan the whole deployment's scores on
  every erasure. Every turn of the person has a run in their thread messages or in audit.
- An invitation accepted by the person but addressed to another email (it cannot be: acceptance
  checks the email) is matched by `accepted_by` too.

## API sketch

```ts
// hooks.ts (additive)
export interface ErasedRecords {
  type: string;
  ids: readonly string[];
  fields: readonly string[];
  deleted?: boolean;
  /** Keys a command's input names these records by, besides `id` and `<type>Id`. */
  refs?: readonly string[];
}

// features/privacy/redact.ts
export interface CopyTarget {
  type: string;
  ids: ReadonlySet<string>;
  fields: readonly string[];
  refs: readonly string[];
  /** Approvals about these records: their copies lose summary and input fields. */
  approvals: ReadonlySet<string>;
}
/** A JSON copy without the target's fields (top: the copy is the record). Same value if unchanged. */
export function scrubCopy(v: unknown, t: CopyTarget, top?: boolean): unknown;
/** A command's input: also objects that name an id by a `refs` key. */
export function scrubInput(v: unknown, t: CopyTarget, top: boolean): unknown;
export function redactCopies(tx, tenantId, sets): Promise<Redacted>; // unchanged signature

// features/files/privacy.ts
export const fileCopies = (ids: readonly string[]): ErasedRecords;
export async function eraseFilesOn(tx, a): Promise<string[]>; // the ids it erased

// features/members/privacy.ts
export const invitesErasure: ErasureContributor; export const invitesExport: ExportContributor;
export const membersParts: PersonalDataPart[]; // members.invites
```

## Sites and leads

Every erasure path that deletes or blanks something with copies now returns it as a set:
`filesErasure` and `eraseFilesOn` (files, C8-2), `invitesErasure` (new, C8-3), the calendar's
inbound connection (C8-3), `eraseFramework` (pages, customer records) and `deleteContacts`
(contacts), besides the declared records, calls, calendars and integrations that did already.
The other features' contributors (comments, parties, shares, memory, jobs, inbox, agents, push)
are unit V8's.

- Lead "redaction is shallow" (critic, V8-L0): held. Shown by the seeded copies of the `copies`
  block failing on the old code (an `approval.approved` audit row, an approval naming the card by
  `cardId`, its park row, a nested reply, a nested notification, a file's audit row).
- Lead "a kept `invites.create` reply holds the email" (verifier, C8-3): does not hold for
  create, which takes no idempotency key (`members.controller.ts`, "No idempotency key"). A keyed
  `invites.revoke` keeps the invitation as its reply; the member test sends one with a key, and
  no reply holds the email after the erasure.
- The critic's `comment.remove` row on the record (`resource_type` of the record): a command's
  own audit row holds only `after.touched` (types, ids and changes, `pipeline.ts`), so it carries
  no personal data. Its approval and park are covered by decision 2.

## Deferred

- The approval of a parked **create** names no record (its `resource_id` is null and the record
  does not exist yet). Once approved, nothing links the approval to the record it made, so the
  record's erasure does not reach the approval's input. The requester's own pending approvals
  are deleted with them (B18); a decided one of someone else's request keeps its input.
- Park rows of an approval whose resource is another record keep their summary unless the
  approval itself is found (decision 2); a summary that names a record without its id stays.
  The framework's member writes never park (their `authorize` allows or denies), but an
  application's level rule could park `invites.create`: its approval (`Invite <email>`, the email
  in its input) names no invitation yet, as above.
- Mastra writes a turn's spans and scores after the turn, in batches. An erasure that commits in
  the seconds after the person's last turn can run before they land, and they stay (seen in the
  fixture: Cy's turn's run spans, erased about three seconds later, outlive it). The
  `assistant.traces` retention target removes them in time. A second pass after the erasure (a
  delayed job) would close it.
- The contributors of the other framework features return their erased sets in unit V8.
