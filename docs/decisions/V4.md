# V4: money refuses a currency that does not exist

## Summary

A fix found by the live validation (`VALIDATION.md`, defect 4, C3-1). A record's currency was
checked for its format only: any three capital letters passed. `POST /api/orders/save` with
`currency: 'ABC'` wrote order ORD/2026/0002 with a total of `{ minor: 100, currency: 'ABC' }`
(Intl's default of two decimals was assumed), and spent a series number. A plain create of any
entity with the `money` trait did the same (a brief in `QZX`). Only the `money` settings checked
a code against the currencies the runtime knows, and B3B5 says the opposite of what happened: a
currency is an ISO 4217 code (#1), the plugin's rules fail closed (#3), and decimals become
minor units only with the currency's own exponent (#9).

The list of currencies is ISO 4217 data that Intl carries, not a business value, so the check
lives in the framework, in one function every write and every boot check uses:

- **`knownCurrency(code)`** (`@hykr/i18n`, next to `currencyExponent`): a currency Intl lists, or
  `XXX` (no currency). It is built on first use, so loading the package never fails. Where the
  runtime cannot list its currencies (Hermes on a device), any three capital letters pass: the
  server, which can, refuses the rest.
- **Writes refuse an unknown currency.** The `money` plugin refuses a create whose currency is
  unknown (403 `money_invalid`, `"ABC" is not a currency`), on a plain create and on a command's
  repository write alike. `toMinor` and `resolveMoneyInput` throw a `RangeError` for it, so a
  command that resolves its amounts in `authorize` (the sample's order save) refuses there, before
  a number is taken; one that writes in `run` is rolled back with its number.
- **Reads stay lenient.** `CurrencyCode`, `Money`, `isMoney`, `fromMinor`, `currencyExponent`
  and `moneyText` still take any three capital letters, so a row stored before this fix with a
  made-up code still reads, lists, sums and formats. A change to such a row that names no amount
  (a title, a transition) still goes through; a new amount in it is refused.
- **The deployment's configuration** is checked the same way at start: `DEFAULT_CURRENCY`,
  `CREDITS_CONFIG.currency` and a model's `price.currency` in `MODEL_PROVIDERS`.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | `knownCurrency(code)` lives in `@hykr/i18n` (`money.ts`): the set of `Intl.supportedValuesOf('currency')` plus `XXX`, built lazily on first call. The settings checks (`section-checks.ts`) use it instead of their own set. | Validation (verifier fix sketch 1); default: one list, in the leaf package that already asks Intl about currencies. |
| 2 | Where `Intl.supportedValuesOf` is missing or throws (Hermes), `knownCurrency` falls back to the format check (`/^[A-Z]{3}$/`). The app never refuses a currency the server would take; the server, on Node, is the one that enforces. | Validation (verifier fix sketch 1); default: isomorphic packages must load on the device. |
| 3 | `XXX` is known (ISO 4217's "no currency": a business that set none counts in it, B3B5 #4). Other X codes count only if Intl lists them (`XDR`, `XAF`, … yes; `XTS`, `XAU` no), as the settings check already did. | B3B5 #4; section-checks.ts (unchanged meaning). |
| 4 | The refusal is the existing rule `money_invalid`, reason `"ABC" is not a currency` (the settings' own wording). No new rule code: the validation's expected outcome names `money_invalid`, and guide 5.13 already lists it. | Validation (expected: "403 money_invalid or currency_required"); default: no new contract. |
| 5 | The `money` plugin checks the code only on a **create**, the one write that stores a record's currency (an update never writes it, and changing it is `currency_fixed`). An update's new amounts are refused through `resolveMoneyInput` (decision 6). So a row already stored with a bad code can still be renamed, cancelled or moved through its states. | Task ("keep reading rows already stored with a bad code possible"); default. |
| 6 | `toMinor(decimal, currency)` and `resolveMoneyInput(input, currency)` throw `RangeError('"ABC" is not a currency')` for an unknown code, for both input shapes (a `{ minor }` amount never looked up an exponent, so it needed its own check). Callers that already turn a `RangeError` into `money_invalid` (the plugin, the sample's `price()`, the app's `parseCredits`) need no change. | Validation (verifier fix sketch 3). |
| 7 | `CurrencyCode`, `Money`, `fromMinor`, `currencyExponent`, `moneyText` and `spokenMoney` stay format-only: they are the read side. Tightening them would make a stored row with a bad code fail to parse or format. | Task ("formatting stays lenient"); validation (verifier fix sketch 3). |
| 8 | `KnownCurrencyCode` (`@hykr/contracts`): `CurrencyCode` refined with `knownCurrency`, for inputs and configuration that should refuse at parse. The format message stays the regex's; only a well-formed unknown code gets `"ABC" is not a currency`. | Validation (verifier fix sketch 4). |
| 9 | The deployment's codes are checked at start with the same function: `DEFAULT_CURRENCY` (`assertConfig`, and `setDefaultCurrency`), `CREDITS_CONFIG.currency` and `ModelPrice.currency` (`MODEL_PROVIDERS`) use `KnownCurrencyCode`. A price in a made-up currency was priced with a guessed exponent. | Task step 3 (fix the class); default. |
| 10 | The sample needs no change: its order save resolves prices in `authorize` (refused there, before `nextNumber`), a save with no priced line is refused by the plugin inside `run` and rolled back with its number, and a brief is a plain create. Its schemas keep `CurrencyCode`. | Default: the framework holds the rule, so every application gets it without code. |
| 11 | Lead V4-L17 (money sums in summaries) did not hold: a business with INR and JPY orders gets one bucket per currency in `totals` and in `groups`, each `{ minor, currency }`; a staff member without `orders.cost.read` cannot sum line costs (`cost` is not a summary measure of `orderItems`: 400). Kept as a test. | Lead V4-L17; checked by test (see Test plan). |

Sites of the class (a currency checked for its format where a real one is needed), all fixed:

| Site | Before | Now |
|---|---|---|
| `framework/core/src/plugins/money.ts` `moneyCurrency` (CRUD `decide` and command `toValues`) | regex | `knownCurrency` on create |
| `framework/contracts/src/framework/money.ts` `toMinor`, `resolveMoneyInput` | regex (exponent guessed) | `RangeError` |
| `framework/api/src/config.ts` `DEFAULT_CURRENCY` | regex | `knownCurrency` |
| `framework/core/src/money/tenant-money.ts` `setDefaultCurrency` | `CurrencyCode` | `KnownCurrencyCode` |
| `framework/api/src/features/credits/config.ts` `CREDITS_CONFIG.currency` | `CurrencyCode` | `KnownCurrencyCode` |
| `framework/contracts/src/settings/models.ts` `ModelPrice.currency` | `CurrencyCode` | `KnownCurrencyCode` |
| `framework/api/src/features/settings/section-checks.ts` | its own set | `knownCurrency` from `@hykr/i18n` |

Read-side sites left lenient on purpose: `CurrencyCode` in read schemas (`Money`, the sample's
`order.ts` and `brief.ts`), `isMoney`, `exceeds` / `overThreshold` (`approvals.ts`, a comparison),
`ApprovalPreview.tsx` (`/^[A-Z]{3}$/`, telling an amount apart from other values), the summary and
share response shapes (`z.string()`).

## Assumptions to review

- **A deployment that names a made-up currency stops at start.** `DEFAULT_CURRENCY=ABC`, a
  `CREDITS_CONFIG` or a `MODEL_PROVIDERS` price in one now refuses to boot, where it used to start
  and guess two decimals. ISO 4217's testing code `XTS` is refused too (Intl does not list it).
- **Intl's list is the list.** A currency the runtime's ICU does not know yet (a new ISO code
  before Node ships it) is refused until Node is updated. Is that acceptable, or should a
  deployment be able to add codes?
- **Rows already stored with a bad code** (written before this fix) are read as before and can be
  changed except for their amounts. Nothing repairs them; a business would cancel and re-create
  such a record.
- **On a device**, the app checks the format only (Hermes has no `Intl.supportedValuesOf`), so a
  made-up code typed in the app is refused by the server, not by the form.

## API sketch

```ts
import { knownCurrency } from '@hykr/i18n';
knownCurrency('JPY'); // true
knownCurrency('XXX'); // true: no currency
knownCurrency('ABC'); // false (true on a runtime that cannot list currencies)

import { KnownCurrencyCode, resolveMoneyInput, toMinor } from '@hykr/contracts';
KnownCurrencyCode.parse('ABC'); // ZodError: "ABC" is not a currency
toMinor('1.00', 'ABC'); // RangeError: "ABC" is not a currency
resolveMoneyInput({ minor: 1 }, 'ABC'); // RangeError
fromMinor(100, 'ABC'); // '1.00': the read side stays lenient

// POST /api/baskets { title, currency: 'ABC', total: '1.00' }
// 403 { error: 'forbidden', rule: 'money_invalid', reason: '"ABC" is not a currency' }
```

## Test plan

- `framework/i18n/src/money.test.ts`: `knownCurrency` knows EUR, JPY, BHD and XXX, refuses ABC,
  XTS and `eur`; `currencyExponent` still answers for an unknown code; without
  `Intl.supportedValuesOf` it falls back to the format.
- `framework/core/src/money/money.test.ts`: `toMinor('1.00', 'ABC')`, `resolveMoneyInput('1',
  'ABC')` and `resolveMoneyInput({ minor: 1 }, 'ABC')` throw a `RangeError`; `fromMinor(100,
  'ABC')` still reads; `KnownCurrencyCode` refuses ABC with the settings' wording and one issue
  for `eur`.
- `framework/api/test/framework/money.e2e.test.ts` (fixture baskets):
  - a plain create in `ABC` (with an amount, and with none) is 403 `money_invalid`, audited as
    denied, and writes nothing;
  - a command save in `ABC` with no priced line (the plugin refuses inside `run`) is 403
    `money_invalid` and gives its number back (the next save's number follows the one before);
  - a basket stored in `ABC` before the fix (seeded by SQL) still reads, lists and sums, takes a
    title change, and refuses a new amount;
  - `DEFAULT_CURRENCY=ABC` stops `assertConfig`; `JPY` and `XXX` start.
- `framework/api/test/framework/credits.test.ts`: `CREDITS_CONFIG` with `currency: 'ABC'` is a
  `CreditsConfigError`; the model price test's other currency is `USD` (it was `XTS`).
- `framework/agents/src/models/models.test.ts`: a model price in `ABC` is a `ModelConfigError`.
- `application/api/test/domain/orders.e2e.test.ts`:
  - C3-1: a save in `ABC` (priced, and with no line) is 403 `money_invalid`, no order is written,
    and the next save's number follows the one before; a brief in `QZX` is 403 `money_invalid`;
  - lead V4-L17: in a business with INR and JPY orders, `sum=total` has one bucket per currency in
    `totals` and in `groups`, each `{ minor, currency }`; staff cannot sum `orderItems` cost.

## Deferred

- Repairing rows already stored with an unknown currency (decision 5): nothing finds or fixes
  them. A deployment that ran before this fix can find them with
  `select ... where currency not in (...)` per money table.
- A deployment's own list of extra currency codes (assumption 2).
