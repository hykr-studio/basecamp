# W1: push notifications in a web browser

## Summary

People who work in a browser now get push notifications. Web Push (VAPID, RFC 8291, a service
worker) is a delivery channel, `webpush`, beside Expo's `push`. Its rules are the dispatcher's
rules: fallback order, quiet hours, sends held for an undo window, dedupe, words read as the
recipient may read them, erasure and export. It closes A9B15's deferral ("Web push (VAPID) for
people working in a browser") and A9B15 decision 6.

**Server.** The push feature (`framework/api/src/features/push`) gains these parts:

- `WebPushService` and `WebPushChannel`;
- the table `channel.web_push_subscriptions` (one row per browser per business, with the
  browser's keys sealed);
- `GET /api/push/web/key`;
- the settings `WEB_PUSH_PUBLIC_KEY`, `WEB_PUSH_PRIVATE_KEY` and `WEB_PUSH_SUBJECT`, checked at start;
- `basecamp webpush keys`.

A browser registers with the existing `POST /api/push/tokens` and forgets with
`POST /api/push/tokens/forget`.

**Sends.** Every send is encrypted for its browser with that browser's own keys and signed with
the deployment's VAPID key. It goes out under the egress guard. `push` becomes a shorthand: it
tries the person's phones, then their browsers.

**App.** `pushPlugin()` handles the web (`framework/app/src/features/push/web.ts`):

- It registers `/push-sw.js` after sign-in.
- It asks for permission only when the person clicks "Turn on notifications".
- A notification's click opens its link.
- Sign-out forgets the browser.

`@hykr/app` ships the service worker and an Expo config plugin (`app.plugin.js`). The config plugin
writes the service worker and a web manifest into the app's `public/` folder.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | **A separate channel, and `push` as a shorthand.** `webpush` is its own registered `DeliveryChannel`, so a chain can order phones and browsers. `push` tries the person's phones (Expo), then, when no phone took it, their browsers. When a notification lists both, `push` means phones only, so nothing is sent twice. Existing chains, the framework's `approval.request` among them, reach browsers with no change. | Request, open question 1 (suggested answer), confirmed by the owner in this unit. |
| 2 | **The same words.** `webpush` uses the notification's `push` content (`{ title, body, url? }`). `defineNotification` refuses `webpush` in `channels` without it. The payload is exactly `{ title, body, url, notification }`, built from `req.row`, the record as the recipient may read it (H1). A field hidden from the recipient by field policy is not in their push. Lock-screen care is the same as for a phone: the author decides. | Request ("its existing push content… so declarations don't change"); H1 decisions 1 and 2; A9B15 decision 12. |
| 3 | **Combining the outcomes.** `push` returns the phones' outcome when it was `sent`, or when browsers are unavailable. It returns the browsers' outcome when they sent, or when the person has no phone. When both failed, it fails for good only if both failed for good; otherwise it is retried (both, again). A phone's send that fails later, through its receipt, goes to the chain's next channel, not to the browsers. | Default. Receipts arrive a minute later; the browser fallback is decided at send time. |
| 4 | **Keys and settings.** `WEB_PUSH_PUBLIC_KEY` (a P-256 point, base64url), `WEB_PUSH_PRIVATE_KEY` (32 bytes, base64url) and `WEB_PUSH_SUBJECT` (`mailto:` or `https:`). `assertConfig` refuses a partial set, a private key that is not P-256, a public key that is not the private key's, and any other subject. None set means web push is off. `basecamp webpush keys` prints a new pair, without loading the application. The feature reads the settings when used, as push's are. | Request (section 1). |
| 5 | **Off is unavailable.** Without the keys, or without `SECRETS_KEY`, `webpush` answers `unavailable`: the next channel is tried at once. `GET /api/push/web/key` answers `{ publicKey: null }` (the app then shows nothing), and registering a browser answers 503 `webpush_unavailable`. | Request ("as push does without Expo"); integrations' `requireSecretBox` pattern. |
| 6 | **Subscriptions.** `channel.web_push_subscriptions` has the columns `id`, `tenant_id`, `user_id`, `endpoint` (unique per business), `p256dh`, `auth`, `user_agent`, `created_at` and `last_seen_at`. There is one row per browser per business. A subscription held by anyone else, in any business, is removed first, as tokens are (A9B15 decision 4). `user_agent` keeps only the browser's name and system ("Chrome on macOS"). | Request (section 2); A9B15 decisions 3 and 4. |
| 7 | **Sealed keys.** The browser's `p256dh` and `auth` are sealed with the deployment's secret box (`SECRETS_KEY`). The associated data is `webpush:<tenant>:<endpoint>`, so a value copied to another row does not open. A subscription whose keys no longer open (a changed `SECRETS_KEY` without the previous key) is dropped at its next send. | Request ("sealed with SECRETS_KEY"); integrations' secret box (B19). |
| 8 | **Which endpoints.** An endpoint must be https, on the standard port, without credentials, on a known push service or one of its subdomains: `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `push.services.mozilla.com`, `web.push.apple.com`, `notify.windows.com`. Anything else is 400 `bad_endpoint`. `WEB_PUSH_ALLOWED_HOSTS` adds hosts, over http too (a stand-in push service in development and tests), as `INTEGRATIONS_ALLOWED_HOSTS` does. The endpoint is checked again before each send, and the request goes through `safeRequest` (public addresses only, no redirects, a timeout from `WEB_PUSH_TIMEOUT_MS`, 10 s by default). | Request ("checked against a list… the egress guard applies"); the egress guard (B19). |
| 9 | **Sending.** For each of the person's browsers in the business, `web-push`'s `generateRequestDetails` builds the request: aes128gcm (RFC 8291), VAPID, `TTL` 24 hours. `Urgency` is `high` for a notification with an `approval` and for `approval.request`, and `normal` otherwise. The request is posted with `safeRequest`. `web-push` is pinned at 3.6.7: 4.0.0 is less than two weeks old. | Request ("TTL of 24 hours", "Urgency is high for approvals"). |
| 10 | **Outcomes.** A 201, 202 or 200 from any browser means `sent`. A 404 or 410 deletes that subscription. A 429, a 5xx or a network error is a failure for now: the dispatcher retries (3 tries, F5 decision 22), then the next channel. Any other answer (400, 403, 413) is final for that browser. No browser means `unavailable`. | Request (section 3). |
| 11 | **The log.** Each browser's send is a row in `channel.push_tickets` with `platform: 'web'`. The row's status is `ok` or `error`, decided when it is made. Web Push has no receipts, so the receipt poll skips these rows (`platform is null` only). The ticket's `token` is the subscription's id, never its endpoint, which is the address a push goes to. | Request ("in push_tickets… with platform: 'web'"). |
| 12 | **Unchanged rules.** Quiet hours, held sends, dedupe and retries come from the dispatcher, before and around any channel. An undone write's event is withdrawn, so nothing is sent. | Request; F5, A5 (undo windows). |
| 13 | **Personal data.** Erasing a person deletes their subscriptions (with their devices and push log). Their export adds `pushBrowsers`: the browser, the endpoint masked to its host and at most six characters of its id, never more than half, and the dates. The device list masks the same way. | Request; A9B15 decision 14; V7 (masks). |
| 14 | **The service worker.** `@hykr/app/push-sw.js` shows a push with `showNotification(title, { body, tag: notification, icon, badge, data: { url } })`. A payload that is not ours shows nothing. On a click it keeps a `url` only when it is an app path (`/…`, not `//…`, as `appPathOf` requires). It focuses an open tab of the app's origin and posts it `{ type: 'hykr.push.open', url }`, which the app routes in place; otherwise it opens a window on the link. There is no caching and no offline page. | Request (section 4); out of scope ("no offline cache"). |
| 15 | **Where it lives in an Expo web build.** `@hykr/app` ships an Expo config plugin (`app.plugin.js`; `"plugins": ["@hykr/app"]`). Each time Expo reads the config (`expo start`, `expo export`, a build), it writes three files: `public/push-sw.js`, `public/manifest.webmanifest` (`name`, `short_name`, `start_url`, `display: standalone`, the app's `icon` with its size) and `public/pwa-icon.png`. The web build serves `public/` at the root. If it cannot write them, it throws, and that is the build-time check. The files are generated and git-ignored. The app adds the `<link rel="manifest">` at run time, because the web output stays `single` with no HTML template. | Request, open question 2 (suggested answer); checked with `expo export -p web` (SDK 57). |
| 16 | **When to ask.** The app never asks on load. After sign-in it registers the service worker. If the person allowed notifications before (and did not turn them off here), it subscribes and registers the browser again, silently. Otherwise `usePushStatus()` is `off`, and a dismissible strip ("Turn on notifications", "Not now") and `<PushToggle />` in the person's card offer a button. The browser's prompt follows that click. `blocked` says where to allow them, and `unsupported` draws nothing. | Request, open question 3. Browsers block a prompt that no gesture led to. |
| 17 | **Turning off, signing out, switching.** "Turn off" unsubscribes, forgets the browser on the server, and remembers in the browser's storage to stay off at the next sign-in. Sign-out (`onSignOut`, while the session still holds) unsubscribes and forgets. Forget needs no session either (A9B15 decision 5). A switch of business registers the browser again in the new one. | A9B15 decisions 5 and 15; F2 sign-out order. |
| 18 | **Origins.** A subscription belongs to the origin it was made on. A person on two of a business's domains has two subscriptions, and both get the notification. | Request ("Custom domains"). |
| 19 | **No "not opened" fallback.** A web push that is never opened is not retried on the next channel, as for phones. | Request, open question 4; A9B15 (deferred). |
| 20 | **The sample.** Its orders notifications (`order.decision-overdue`, `orders.comment-mention`) list `['webpush', 'push', 'email']`: accounts staff work at a desk. The to-do reminder keeps `['push', 'whatsapp', 'email']`, which now reaches a browser through the shorthand. `app.json` lists `"@hykr/app"`, and the person's card shows the control. | Request (Interioring's use; acceptance "lists webpush in its chains"). |

## Assumptions to review

- **`push` reaching browsers.** Any application's `push` now reaches a person's browsers when no
  phone takes it. Is that welcome everywhere, or should some notifications (a reminder meant for
  the field) stay on phones? Listing `webpush` anywhere in the chain makes `push` phones-only.
- **Phones and browsers together.** A person with a phone gets the phone's push and not the
  browser's. Should a desk worker get both at once?
- **The push service list.** It names FCM, Mozilla, Apple and WNS. A browser on another push
  service cannot register. Should the list be a deployment setting?
- **Urgency.** Only approvals are `high`. Should a business's own messages to a person (a client's
  reply) be high too?
- **The strip.** It shows on every signed-in page in a browser until the person turns
  notifications on or says "Not now". Should it wait for a moment that needs it (the first approval
  request)?
- **Expired subscriptions.** A browser's `expirationTime` is not used. The push service's 404 or
  410 is what removes it.

## API sketch

```ts
// @hykr/contracts
PushPlatform = z.enum(['ios', 'android', 'web'])
RegisterPushToken = { token, platform: 'ios' | 'android' } | { platform: 'web', subscription: { endpoint, keys: { p256dh, auth } } }
ForgetPushToken = { token } | { endpoint }
PushDevice = { id, platform, token /* masked */, browser?, createdAt, lastSeenAt }
WebPushKey = { publicKey: string | null }

// HTTP
GET  /api/push/web/key          -> { publicKey }        (anyone)
POST /api/push/tokens           { platform: 'web', subscription } -> 201 PushDevice | 400 bad_endpoint | 503
POST /api/push/tokens/forget    { endpoint } -> 204     (no session)

// @hykr/notifications
interface NotificationChannels { webpush: true }  // uses NotificationDef.push

// @hykr/app
pushPlugin()                      // web: service worker, Banner, onSignOut
usePushStatus(): 'on' | 'off' | 'blocked' | 'unsupported' | undefined
enableWebPush(), disableWebPush(), <PushBanner />, <PushToggle />
// app.json: "plugins": ["@hykr/app", …]  ->  public/push-sw.js, manifest.webmanifest, pwa-icon.png

// CLI
basecamp webpush keys
```

## Test plan

- **`framework/api/test/framework/webpush.e2e.test.ts`.** A stand-in push service on localhost
  (`WEB_PUSH_ALLOWED_HOSTS`). It answers 201, 410 or 429 by endpoint. Test browsers are P-256 key
  pairs, and the payload is decrypted with `http_ece`. The fixture is chores, with a due date
  hidden from staff and an undo window. Cases:
  - the public key;
  - registering, with sealed keys and the browser's name;
  - `bad_endpoint` for an unknown host, http, a look-alike host and credentials;
  - a subscription moving to a new person;
  - forget without a session;
  - two browsers reached once each, encrypted, with the hidden date absent;
  - the owner reading the date;
  - no browser: email at once;
  - a 410 forgetting a browser, with the next send skipping it;
  - every browser gone: email;
  - a 429 tried three times, then email;
  - no VAPID settings: email at once, a null key and a 503;
  - the `push` shorthand reaching a browser;
  - an approval request urgent in the decider's browser;
  - quiet hours moving it;
  - an undone write sending nothing while one not undone sends;
  - erasure and export.
- **`framework/api/test/framework/webpush.test.ts`.** The settings checks, the endpoint list,
  the masks and the browser's name.
- **`framework/app/src/features/push/service-worker.test.ts`.** The service worker in a sandbox:
  what it shows, foreign or bad payloads, links that leave the app, focusing a tab or opening one.
  The config plugin's files and its refusal.
- **Other unit tests.** `framework/notifications`: `webpush` needs push content.
  `framework/cli`: the key pair.
  `application/domain`: the orders chains.
- **Manual, in Chrome, Firefox and Safari** (not run in this unit's environment):
  - permission is asked only after a click;
  - a push shows its title and body;
  - a click opens or focuses the app on the record;
  - sign-out stops pushes to that browser.

## Deferred

- Sending through FCM or APNs directly (developer guide section 14 keeps it).
- Rich notifications (images, action buttons) and offline pages.
- Retrying a push not seen within a time on the next channel.
