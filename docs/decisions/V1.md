# V1: untrusted keys and query strings cannot harm the process

## Summary

A fix found by the live validation of `feat/platform-gaps` (`VALIDATION.md`, cluster C10). It
predates the branch: `main` has the same code.

- **C10-1 (critical).** `nestBrackets` (`@hykr/contracts`, the step that turns `a[b]=c` query keys
  into `{ a: { b: c } }` for every list, summary and the custom-field filter check) wrote into a
  plain `{}`. `?__proto__[x]=1` therefore wrote `x` onto `Object.prototype` for the whole process.
  Zod's strict objects then refused every list, summary, settings parse and sign-up of every
  business with `unrecognized_keys ['x']` until a restart. One signed-in person could do it, and
  anyone can sign up.
- **C10-2 (low).** A list cursor is base64url JSON the client sends back. `decodeCursor` checked
  only its sort signature. A tampered value that does not fit the sort column's type (`"not-a-date"`,
  an object, a missing `v`) reached Postgres or a `TypeError` and answered 500.

The fix builds the nested query object without a prototype and never nests under a name that
reaches one. It checks every cursor value against the column it sorts by before any SQL is built.
It also probes the other places where a key or a value someone sends picks or builds an object.

## Decisions

| # | Decision | Source |
|---|----------|--------|
| 1 | `nestBrackets` builds its result and each nested object with `Object.create(null)` and tests keys with `Object.hasOwn`. A key whose outer name is `__proto__`, `constructor` or `prototype` stays flat (`'__proto__[x]'`): no schema knows that key, so the strict list and summary schemas answer that request alone with a 400 `unrecognized_keys`, whatever Zod does with inherited names. | Validation (verifier's fix sketch) |
| 2 | One fix covers each caller of `nestBrackets`: `listQuerySchema` (every entity list and shared list), `summaryQuerySchema` (every `/summary`) and the settings gate interceptor's custom-field filter check, which parses the list query before the validation pipe does. Each is probed by a test. | Validation, lead V1-L1 |
| 3 | The other merges keyed by what a client sends skip the same three names, as `mergePatch` already does: the custom-field values merge (`mergeCustom`, `mergeCustomSql`) and the wording merge (`UpdateWording`). A body key `__proto__` is dropped, never stored, and never changes an object's prototype. | Lead V1-L1 |
| 4 | A cursor is checked in two steps. `decodeCursor` requires an object with a string `s`, an array `v` with one value per sort key and a string `id` of at most 200 characters, before it reads `s`. `after()` checks each value against its sort key. Anything else is 400 `bad_cursor`, the code a cursor that does not parse already got. | Validation (verifier's fix sketch), default |
| 5 | Each sort key carries `check(value)`. It accepts exactly what `keep` and `encodeCursor` emit for that column type. A date column takes a real `YYYY-MM-DD`. A Date-mode date or timestamp column takes the ISO string `toISOString` writes. A string-mode timestamp takes Postgres's own text form. Integer columns take a safe integer, other number columns a finite number, numeric columns also a numeric string, boolean columns a boolean, and text, uuid and enum columns a string (a uuid column a uuid). The far value a nullable sort emits passes. A contributed field type's `order` may return its own `check` (geo does: `null` or a point with finite `lat` and `lng`). | Validation (verifier's fix sketch) |
| 6 | As a backstop, when a cursor was sent, a Postgres data exception (SQLSTATE class 22: a value out of range, an enum value it does not have) from the keyset query answers 400 `bad_cursor` too. One helper is used at both list sites (`define-entity.ts`, `plugins/shared.ts`). Without a cursor the error stays a 500, because it is then a bug, not a client's input. | Advisor, validation |
| 7 | `farValue` gains the `PgTimestampString` case. `sortExpr` already sorted that type's nulls as a far timestamp, but its cursor kept the number `1e15`, which Postgres cannot compare with a timestamp. | Default (found while writing the checks) |
| 8 | An import's error report writes its cells with the export's one rule (`cellText` in `export/csv.ts`): a cell that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading `'`. | Lead V1-L18 |
| 9 | Routes that look something up by a route parameter must answer 404, never 500, for `__proto__`, `constructor` and `toString`. Each lead route is probed by a test. | Lead V1-L1 |
| 10 | Routes that read their own query strings are fuzzed with `limit=-1`, `limit=1e9`, `before=not-a-date`, `cursor=garbage`, a cursor of the wrong types and a repeated key. The bar is no 5xx and never another business's rows. A route that clamps a bad `limit` and answers 200 keeps doing so. | Lead V1-L14, advisor |

## Assumptions to review

- Refusing `constructor[x]` and `prototype[x]` as unknown keys means no list field may be named
  `constructor` or `prototype` and filtered with an operator. No spec does, and such a name would
  be odd for a field.
- The report's `'` prefix: whether a report fixed in a spreadsheet and imported again still reads
  as the file meant is recorded under Test plan, with what the test found.
- The cursor backstop (decision 6) maps every class 22 error from a list query with a cursor to
  `bad_cursor`, including one a filter value caused. Filter values are checked by the list schema
  first, so such a filter error would be a bug either way. It is then reported as the cursor's.

## API sketch

```ts
// @hykr/contracts: unchanged signature; the result and its nested objects have no prototype.
nestBrackets({ 'dueOn[gte]': '2026-01-01', '__proto__[x]': '1' });
// → { dueOn: { gte: '2026-01-01' }, '__proto__[x]': '1' }   (null-prototype objects)

// @hykr/core: a contributed list field type may check the values its cursor kept.
listFieldSql.register({
  name: 'geo',
  where: geoWhere,
  order: (sort) => ({ expr, at, check: (v) => v === null || isPoint(v) }),
});

// A list or a summary request: a cursor that does not fit → 400
// { error: 'bad_cursor', message: 'This cursor is not valid' }
```

## Test plan

- Contracts unit tests (`list.test.ts`): after `nestBrackets` on `__proto__[x]`, `constructor[x]`
  and `prototype[x]`, `Object.prototype` has no own keys. The flat key is kept, and the list and
  summary query schemas refuse it. Null-prototype nested objects still pass every filter kind
  (operators, `in` lists, `custom[...]`). Each test cleans `Object.prototype` in `finally`.
- Core unit tests (`list-grammar.test.ts`): a cursor round trip for each sortable column type
  (date in both modes, timestamp in both modes, integer, bigint, numeric, double, text, uuid, enum,
  boolean, nullable far values). Every tampered shape and value is refused with 400 `bad_cursor`,
  and the `PgTimestampString` far value.
- Framework e2e (`untrusted-keys.e2e.test.ts`, the settings fixture's gadgets: custom fields, a
  summary, shared): one business's `?__proto__[x]=1` on a list, on a summary, and with a custom
  filter; `constructor[x]=1`, `__proto__=1`. Each answers 400. After each one `Object.prototype`
  is still clean, another business's list answers 200, its write 201, and a sign-up succeeds.
  Body keys `__proto__` and `constructor` in custom values, wording and settings sections (bodies
  built with `JSON.parse`, so the key is really sent): 400 or dropped, never stored (checked on
  the column's text). Route parameters `__proto__`, `constructor` and `toString`: 404. Cursor
  tampering on lists: 400 `bad_cursor`. Feature query strings fuzzed: never 5xx.
- `geo.e2e`, `pages.e2e`, `summary.e2e`, `imports.e2e` and a paginated sample e2e run again,
  because they cover nested operator objects and genuine cursors.

## Deferred

- Process-wide hardening such as Node's `--disable-proto=delete` or freezing `Object.prototype`
  in `startApi`. It would turn a future gadget into a no-op, but it changes how every dependency
  runs and needs its own check.
