# V1: untrusted keys and query strings cannot harm the process

## Summary

A fix found by the live validation of `feat/platform-gaps` (`VALIDATION.md`, cluster C10). It
predates the branch: `main` has the same code.

- **C10-1 (critical).** `nestBrackets` (`@hykr/contracts`, the step that turns `a[b]=c` query keys
  into `{ a: { b: c } }` for every list, summary and the custom-field filter check) wrote into a
  plain `{}`. `?__proto__[x]=1` therefore wrote `x` onto `Object.prototype` for the whole process.
  Zod's strict objects then refused every list, summary, settings parse and sign-up of every
  business with `unrecognized_keys ['x']` until a restart. One signed-in person could do it, and
  anyone can sign up.
- **C10-2 (low).** A list cursor is base64url JSON the client sends back. `decodeCursor` checked
  only its sort signature. A tampered value that does not fit the sort column's type (`"not-a-date"`,
  an object, a missing `v`) reached Postgres or a `TypeError` and answered 500.

The fix builds the nested query object without a prototype and never nests under a name that
reaches one. It checks every cursor value against the column it sorts by before any SQL is built.
It also probes the other places where a key or a value someone sends picks or builds an object.

## Decisions

| # | Decision | Source |
|---|----------|--------|
| 1 | `nestBrackets` builds its result and each nested object with `Object.create(null)` and tests keys with `Object.hasOwn`. A key whose outer name is one every plain object has (`__proto__`, `constructor`, `toString`, any `Object.prototype` name, and `prototype`; decision 3) stays flat (`'__proto__[x]'`): no schema knows that key, so the strict list and summary schemas answer that request alone with a 400 `unrecognized_keys`, whatever Zod does with inherited names. | Validation (verifier's fix sketch) |
| 2 | One fix covers each caller of `nestBrackets`: `listQuerySchema` (every entity list and shared list), `summaryQuerySchema` (every `/summary`) and the settings gate interceptor's custom-field filter check, which parses the list query before the validation pipe does. Each is probed by a test. | Validation, lead V1-L1 |
| 3 | One notion of "a name every object has" (`isPrototypeKey` in `@hykr/contracts`: `Object.prototype`'s own names and `prototype`), used wherever a key someone sends is written into or read from a plain object: `nestBrackets`; the custom-field values merge (`mergeCustom`, `mergeCustomSql`) and the wording merge (`UpdateWording`), which skip such a key; a custom field's key, which may not be one (`constructor` passed the camelCase rule, and a required field of that name read `Object` from every record's values, so the required check never failed); a wording phrase key, which is looked up as the catalog's own key (`{"phrases":{"constructor":…}}` was a 500). `mergePatch` keeps its own three-name guard. | Lead V1-L1, tests |
| 4 | A cursor is checked in two steps. `decodeCursor` requires an object with a string `s`, an array `v` and a string `id` of at most 200 characters before it reads `s`, then one value per sort key. `after()` checks each value against its sort key, and the id against the id column (any string for the framework's text ids, a uuid for a uuid column). Anything else is 400 `bad_cursor`, the code a cursor that does not parse already got. | Validation (verifier's fix sketch), default |
| 5 | Each sort key carries `check(value)`. It accepts exactly what `keep` and `encodeCursor` emit for that column type. A date column takes a real `YYYY-MM-DD`. A Date-mode date or timestamp column takes the ISO string `toISOString` writes. A string-mode timestamp takes Postgres's own text form. Integer columns take a safe integer, other number columns a finite number, numeric columns also a numeric string, boolean columns a boolean, and text, uuid and enum columns a string (a uuid column a uuid). The far value a nullable sort emits passes. A contributed field type's `order` may return its own `check` (geo does: `null` or a point with finite `lat` and `lng`). | Validation (verifier's fix sketch) |
| 6 | As a backstop, when a cursor was sent, a Postgres data exception (SQLSTATE class 22: a value out of range, an enum value it does not have) from the keyset query answers 400 `bad_cursor` too. One helper is used at both list sites (`define-entity.ts`, `plugins/shared.ts`). Without a cursor the error stays a 500, because it is then a bug, not a client's input. | Advisor, validation |
| 7 | `farValue` gains the `PgTimestampString` case. `sortExpr` already sorted that type's nulls as a far timestamp, but its cursor kept the number `1e15`, which Postgres cannot compare with a timestamp. | Default (found while writing the checks) |
| 8 | An import's error report writes its cells with the export's one rule (`formulaSafe` in `export/csv.ts`, which `cellText` uses): text that starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading `'`. An import reads that escape back off a CSV cell and a header cell (`formulaSafeRead`), because the report exists to be fixed and imported again: without it `-5`, `+91 98765 43210` or `@someone` would come back with the `'`. | Lead V1-L18, test |
| 9 | Routes that look something up by a route parameter must answer 404, never 500, for `__proto__`, `constructor` and `toString`. Each lead route is probed by a test. | Lead V1-L1 |
| 10 | Routes that read their own query strings are fuzzed with `limit=-1`, `limit=1e9`, `before=not-a-date`, `cursor=garbage`, a cursor of the wrong types, prototype names and repeated keys, each bare and after the parameters the route needs. The bar is no 5xx. A route that clamps a bad `limit` and answers 200 keeps doing so. Two failed. `GET /api/files?ids=a&ids=b` called `split` on an array (500); a repeated `ids` is now read as a list. `before=99999` (or `-100000-01-01T00:00:00Z`) on the credits ledger, the member's and the operator's, is a valid JavaScript `Date` that Postgres cannot store (500); `storableInstant` (`infra/instant.ts`) reads only years 1 to 9999, and the integrations delivery log's `before`, which parses the same way, uses it too. | Lead V1-L14, advisor |

## Assumptions to review

- Refusing `constructor[x]`, `toString[x]` and the like as unknown keys means no list field may
  be named after an `Object.prototype` name (or `prototype`) and filtered with an operator. No
  spec does, and such a name would be odd for a field.
- Reading the `'` escape back on import (decision 8) changes what a CSV import reads: a cell
  `'=x`, `'-5` or `'@x` now reads `=x`, `-5`, `@x`. That is what a spreadsheet means by a leading
  `'`, and it makes an export and an error report import as given. A file that meant the `'`
  literally loses it.
- The cursor backstop (decision 6) maps every class 22 error from a list query with a cursor to
  `bad_cursor`, including one a filter value caused. The list schema does not catch every such
  value: a NUL character in a filter passed it, and with a genuine cursor answered `bad_cursor`
  (without one, a 500). Corrected in V10: a NUL is now refused at the request edge (400
  `nul_character`), before any list query, so what reaches the backstop is the cursor's.

## API sketch

```ts
// @hykr/contracts: unchanged signature; the result and its nested objects have no prototype.
nestBrackets({ 'dueOn[gte]': '2026-01-01', '__proto__[x]': '1' });
// → { dueOn: { gte: '2026-01-01' }, '__proto__[x]': '1' }   (null-prototype objects)

// @hykr/core: a contributed list field type may check the values its cursor kept.
listFieldSql.register({
  name: 'geo',
  where: geoWhere,
  order: (sort) => ({ expr, at, check: (v) => v === null || isPoint(v) }),
});

// A list or a summary request: a cursor that does not fit → 400
// { error: 'bad_cursor', message: 'This cursor is not valid' }
```

## Test plan

- Unit tests of the query string (`framework/core/src/query/query-string.test.ts`; contracts has
  no test runner): after `nestBrackets` on `__proto__[x]`, `constructor[x]` and `prototype[x]`,
  `Object.prototype` has no own keys. The flat key is kept, and the list and
  summary query schemas refuse it. Null-prototype nested objects still pass every filter kind
  (operators, `in` lists, `custom[...]`). Each test cleans `Object.prototype` in `finally`.
- Core unit tests (`list-grammar.test.ts`): a cursor round trip for each sortable column type
  (date in both modes, timestamp in both modes, integer, bigint, numeric, double, text, uuid, enum,
  boolean, nullable far values). Every tampered shape and value is refused with 400 `bad_cursor`,
  and the `PgTimestampString` far value.
- Framework e2e (`untrusted-keys.e2e.test.ts`, the settings fixture's gadgets: custom fields, a
  summary, shared; and the base fixture's tasks): one business's `?__proto__[x]=1` on a list, on
  a summary, and with a custom filter; `constructor[x]=1`, `__proto__=1`. Each answers 400. After each one `Object.prototype`
  is still clean, another business's list answers 200, its write 201, and a sign-up succeeds.
  Body keys `__proto__`, `constructor` and `toString` in custom values, wording, branding,
  settings sections and feature flags (bodies built with `JSON.parse`, so the key is really
  sent): 4xx or dropped, never stored (checked on the column's text). A custom field key
  `constructor`: 400. Route parameters `__proto__`, `constructor`, `toString`: 4xx, never 500. Cursor
  tampering on lists: 400 `bad_cursor`. Feature query strings fuzzed: never 5xx.
- Import report unit tests (`imports.test.ts`): risky cells get the `'`, and the report imports
  again as given.
- `geo.e2e`, `pages.e2e`, `summary.e2e`, `share.e2e`, `offline.e2e`, `sla.e2e`, `settings.e2e` and
  the full framework and sample suites run again, because they cover nested operator objects and
  genuine cursors.

## What the leads came to

- **V1-L1 held, in part.** List, summary and the gate interceptor's custom filter: fixed by
  `nestBrackets` (the e2e test answered 400 for each, and `Object.prototype` stayed clean, before
  and after another business's list, write and a sign-up). Body keys: `__proto__` never reached a
  merge, because Zod 4.6 drops it from records and objects (checked: 200 or 400, nothing stored).
  Two same-class gadgets did hold and are fixed (decision 3): the wording phrase `constructor` (500)
  and a custom field key `constructor` (accepted, and a required one never enforced). Route
  parameters `__proto__`, `constructor`, `toString` and `hasOwnProperty` on settings sections,
  member roles, `/webhooks`, `/api/sla/:plural`, transitions and `PUT /api/features/:key` all
  answered 4xx already: they look things up with `find`, a `Map` or a registry (`get`), never a
  plain object. Other lookups checked by reading: role names (`standingIn`, a `Map`), import
  columns (`Object.hasOwn`, a `Set`), `?lang=` (always through `isLang`, a `Map`).
- **V1-L14 held twice:** `/api/files?ids=a&ids=b` and a far-off `before` on the credits ledger
  (decision 10). Every other fuzzed route, signed in, as an operator and with no session (the
  calendar's OAuth callback, the WhatsApp webhook's `hub.*`, a share link), answered 4xx, a
  redirect or a page for every variant, and no answer carried the other business's id. The
  integrations delivery and inbound logs answer 404 before reading the query for an endpoint the
  test does not have; they were checked by reading instead: `limit` is clamped, `status` is a
  text column compared as a bound parameter, and `before` now goes through `storableInstant`.
  *Correction (V10):* this claimed too much. The fuzz sent only `cursor=garbage` and wrong-typed
  cursors: a far-off time or a NUL id in the inbox's, comments' and agent runs' keyset cursors
  still answered 500, as did a NUL in any text, and V1-L14 names agent runs. V10 fixed both and
  added them to the fuzz, and tests the delivery log's `before` on an endpoint of its own.
- **V1-L18 held** (decision 8).

## Deferred

- Process-wide hardening such as Node's `--disable-proto=delete` or freezing `Object.prototype`
  in `startApi`. It would turn a future gadget into a no-op, but it changes how every dependency
  runs and needs its own check (developer guide section 14).
- Seen while writing the checks, not changed: a `PgTimestamp` sort keeps the row's time as a
  JavaScript `Date` (milliseconds), while `defaultNow()` stores microseconds. Two rows within one
  millisecond can repeat or be skipped across a page boundary when a list sorts by such a column.
  S3 avoided this for SLA timers by keeping Postgres's own text. In developer guide section 14
  since V10 ("Paging within one millisecond").
