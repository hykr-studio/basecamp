# B19: the platform-operator tier

## Summary

A tier above the businesses, for the people who run a deployment (the platform's operators):

- **Operators** (`app.platform_operators`): named, signed-in people, each with operator
  capabilities (`platform.tenants`, `platform.support`, …). Never a header, never a role in a
  business. The first one is added from the command line (`basecamp operator add <email>`).
- **Support access** (`app.platform_support_grants`): an operator asks to work in one business, for
  a reason, with named roles and capabilities, read-only unless asked otherwise. A person of that
  business holding `support.consent` consents (or declines); the access then lasts the minutes
  consented, can be revoked at any time, and every request made under it is logged
  (`app.platform_support_log`) and every write audited with `on_behalf_of = support:<grant>`.
- **Tenant provisioning**: `POST /api/platform/tenants` makes a business for an existing account,
  which becomes its owner (the creator's roles), audited in the new business and announced with a
  stored `tenant.provisioned` event. Operators also switch platform-managed feature flags.
- **A routing hook for inbound requests**: `defineInboundRouter({ name, route, deliver })`
  contributed as `inboundRouters`. The framework asks the application's routers which business
  takes a request (a WhatsApp message to the platform's business, or any server code calling
  `PlatformRoutingService.route`), then runs the router's `deliver` as the system principal in that
  business, once per request, logged in `app.platform_routed`. There are no routing rules in the
  framework.
- **Platform-scoped shared records**: an operator holding `platform.shared` works in the platform's
  business (`PLATFORM_TENANT_ID`, A11) without being a member, with the capability `shared.publish`;
  the `platform-scope` entity plugin keeps a shared entity's rows there written only at platform
  scope (an operator, or server code).
- **A usage report across businesses** (`GET /api/platform/usage`): what each business used of
  each meter and the credits in and out of its wallet, from A3's `usage_events` and
  `credit_ledger`. No plans or prices.
- **The system principal can create rows** (`define-entity.ts`): owned by the business's default
  owner, for the customer it names, so a routed request (or any background job) can make a record.
- **Bull Board** is for operators holding `platform.queues`; the business capability `queues.admin`
  is gone. A3's credits operator routes take a signed-in operator holding `platform.credits` instead
  of `OPERATOR_API_KEY`, which is gone.
- **The back office** gets an operator mode (businesses, support access, usage, routing, operators)
  and a Support access screen for a business's people.

## Assumptions to review

- **Who operators are.** Named people with capabilities, added from the command line first. Should
  operators have roles (support desk, finance, admin) instead of capability lists?
- **Consent, not free access.** Operators never read a business's data without its consent
  (decision 9). Is there a case for break-glass access without consent (a legal request, an
  outage), audited and announced afterwards?
- **Who consents.** `support.consent` is the owner's by default. Should admins consent too, or
  should a consent need two people?
- **Default limits.** Read-only by default, 8 hours at most, a request expires after 72 hours. Are
  these the right defaults for the pilot?
- **Withheld capabilities.** Support never holds capabilities that change who reaches the business,
  or exports all of its data (decision 10). Should data export be allowed with consent?
- **Provisioning needs an account.** Operators provision a business for someone who signed up
  (decision 15). Should operators invite an owner by email before they have an account?
- **Who publishes shared rows.** By default the platform business's members still publish them,
  as in A11; an entity opts into operators only (decision 18). Should operators-only be the
  default for every shared entity?
- **Routing content.** The routing log keeps what happened to a request, not what it said. Should
  the platform keep unrouted requests (for an operator to assign by hand)?
- **Usage report.** Credits as recorded, no money prices. Is a CSV export or a per-day breakdown
  needed?
- **Bull Board in production.** It stays off in production even for operators. Should operators
  have it there?

## API sketch

```ts
// An application's router (no rules in the framework): which business takes a request, and what
// that business does with it.
import { defineInboundRouter } from '@hykr/api';
export const ByCode = defineInboundRouter({
  name: 'by-code',
  route: async (req, ctx) => ({ tenantId: await lookUp(ctx.db, req.text) }), // or null
  deliver: async (req, target) => {
    const who = await target.contact();               // the sender, as the business's customer
    const made = await target.write(entityOp(TaskDef, 'create', null), { title: req.text },
      { customerId: who?.customerId });
    return { resourceType: 'task', resourceId: made.id };
  },
});
defineServer({ ..., contributes: { inboundRouters: [ByCode] } });

// A shared entity operators maintain.
access: { read: { ...BUSINESS.read, 'shared.publish': 'tenant' },
          write: { ...BUSINESS.write, 'shared.publish': 'tenant' } }
```

## Deferred

- Impersonation (acting as one of the business's people) and break-glass access without consent.
- Inviting a business's owner who has no account; seeding a business made at sign-up (only an
  operator's provisioning announces `tenant.provisioned`).
- Routing rules of any kind (the application's), keeping unrouted requests, and an operator's
  manual assignment of one.
- Suspending or deleting a business, plans and prices, invoices.
- Bull Board in production.
- `repo.where` on the entity repository (B13B14's deferral) and bulk inserts for plain entities
  (B3B5's): `define-entity.ts` is B12's next.
- Reads under support access other than over HTTP (none exist today) are not logged, nor a
  request refused before PrincipalGuard knows it is support's (no session, an unknown business).
- Labelling support and operator rows in the history screen, and `on_behalf_of` on stored
  events (subscribers see the operator as the actor).
- A notification to the business when support is requested: the events `support.requested`,
  `support.consented`, `support.declined` and `support.ended` are stored; an application words
  a notification on them.
