# B11: long-running jobs

## Summary

Some work takes minutes and runs elsewhere: a render on a GPU worker, a plan read by a vision
model, a nesting optimiser, a large export or import. The `jobs` feature runs such work as a
**job**: a row in `app.jobs` that moves from `queued` to `running` to `succeeded`, `failed` or
`cancelled`, with a progress percentage and a message on the way, and result files at the end.

An application (or a framework feature) declares each kind of job once with `defineJob`:
its input schema, the record it is about, how long it may take, and the functions that talk
to the outside service:
- `submit` hands the work over and returns the service's id (or does the work itself, for work
  that runs in the worker);
- `poll` asks the service how it is going (the polling fallback);
- `callback` reads what the service posts back;
- `cancel` asks the service to stop;
- `complete` writes the result back onto the business's records.

A job starts inside a write: a command's `run` calls `startJob(tx, p, def, input)`. The job
row and its `job.queued` event then exist exactly when the write commits, and the write keeps
its approvals (an assistant's start can park), audit and idempotency. The worker submits each
queued job. The service then reports back in one of two ways:
- it posts signed updates to `POST /api/jobs/:id/callback` (HMAC-SHA256 with a per-job secret,
  a timestamp, each update stored once);
- the worker polls it.

Every state change and progress step is stored as an event (`job.running`, `job.progress`,
`job.succeeded` …) in the durable outbox, for subscribers, webhooks and live updates. Result
files are stored through the files feature (B1) and kept on the job. Whoever reaches the job
reaches them: anyone who can read the record it is about, or, for a job about no record, the
person it was started for. Everyone else gets 404.

People and the assistant read jobs with `GET /api/jobs/:id` and `GET /api/jobs`, and the
assistant's tools `get-job` and `list-jobs`. People cancel with `POST /api/jobs/:id/cancel`. The
app gets `useJob`, `useJobs`, `useCancelJob` and `<JobProgress>`; a job's events also reach
the live stream (B15) of whoever reaches the job. The fixture's `drawings` module shows a
callback job and a polled job against a stand-in external service.

## Decisions

| # | Decision | Source |
|---|---|---|
| 1 | One feature, `framework/api/src/features/jobs/`, with the tables `app.jobs` and `app.job_updates` (`framework/db/src/schema/jobs.ts`). It reserves `/api/jobs`. `job` is the resource type of its audit rows, its events (`job.*`) and its read projections. An application entity named `job` stops the start, and so does a module table named `jobs`, as with B1's `files`. | Plan B11 row ("`features/jobs`: `defineJob`, a jobs table …"); B1 decision 27 (precedent). |
| 2 | `defineJob({ name, description, input, output?, about?, inputFiles?, timeoutMs, submit, poll?, pollEveryMs?, callback?, cancel?, download?, complete?, submitAttempts?, maxFiles? })` returns a checked `JobDef`. Contribute it as `jobs` (a new `Contributions` key, registry `jobDefs`), from a module (`defineModule({ contributes })`), the application or a feature. The rules for the name are the same as for queues (`<owner>.<what>`). A duplicate name stops the start. | Plan ("defineJob"); F5 registry pattern. |
| 3 | **Starting is a write.** `startJob(tx, p, def, input, { requestId })` is called from a command's `run` (or from any server code that holds a transaction). It validates the input, checks that the `about` record is reachable by `p` (the entity's scoped repo, so another business's record is 404) and that every file in `inputFiles(input)` is reachable by `p` (403 `file_unavailable` otherwise). Then, in that transaction, it inserts the job, writes an audit row `job.start` and stores the `job.queued` event. A rolled-back write leaves no job. There is no generic `POST /api/jobs`. Who may start a job, whether the assistant may, and whether it waits for an approval are the application's command's `expose`, `authorize` and `approval`. | CLAUDE.md rule 1 (one write path); boundary rule (who may spend on outside compute is business policy); gap map owner question ("Who pays for the external compute"). |
| 4 | **Submitting.** A framework subscriber (`jobs.submit`, on `job.queued`) adds a `jobs.submit` queue job. The processor takes a lease on the queued row (`lease_until`, so two workers never submit one job twice), then calls `def.submit(ctx)` outside any transaction. `ctx` holds the job (`id`, `tenantId`, `kind`, `input`, `attempt`), `callback: { url, secret, header }` (null when the kind takes no callbacks), `signal` (aborts at the deadline), `fileUrl(id)` and `fileBytes(id)` for the declared input files, `progress(percent, message?)`, `starter()` (whoever started it, refreshed through `PrincipalResolver.refresh` as an approval's replay is: still in the business, today's roles; the job's system principal when the server started it; the snapshot is kept on the job and never shown), `db`, and `get(token)` for Nest providers. `submit` returns `{ externalId?, update?, files? }`. The job becomes `running` and `job.running` is stored; an `update` it returns is applied at once, so work that runs in the worker (an export, an import) returns its finished update, with the files it made as bytes (`files`), which are stored at once and named on the stored update under a key only the runner writes (a callback's unknown keys are dropped). A throw is retried with exponential backoff (`submitAttempts`, default 3; `submitBackoffMs`, default 5 s, doubling) and then fails the job with `submit_failed`. An `update` that does not parse fails it with `bad_update`. | Gap map extension points ("A polling fallback via upsertJobScheduler"; "Worker-only processing"); default. |
| 5 | **Callback authentication.** `POST /api/jobs/:id/callback`, with no session and no throttle (as the WhatsApp webhook). Each job has its own secret, `HMAC-SHA256(JOBS_SECRET, "basecamp.jobs.callback.<id>")`, which is handed to `submit` and never stored or shown. `JOBS_SECRET` is derived from `BETTER_AUTH_SECRET` when it is unset. By default the service signs each post as `x-job-signature: t=<unix seconds>,v1=<hex HMAC-SHA256(secret, "<t>.<raw body>")>`: the signature is compared in constant time, and `t` must be within `JOBS_CALLBACK_TOLERANCE_S` (300 s) of now. A kind can give its own `callback.verify({ rawBody, headers }, { secret, job })` for a provider's own scheme. A bad or missing signature, or a stale one, is 401. An unknown job, or a kind with `callback: false`, is 404. `signJobCallback` and `verifyJobCallback` are exported for services and tests. | Plan ("an HMAC-signed callback"); gap map risks ("Callback endpoints are anonymous by nature. They need per-job secrets and replay protection"). |
| 6 | **Store once.** A verified post is parsed into a `JobUpdate` (the framework's format by default, or the kind's `callback.parse(body, headers)`). It is stored in `app.job_updates` under a dedupe key, unique per job: `sha256(raw body)` by default, or the kind's `callback.dedupe(...)`, such as a provider's delivery id. A repeat answers 200 `{ received: true, duplicate: true }` and is not applied again. A new one is queued (`jobs.apply`, job id `apply--<update id>`) and answered 202. An update for a finished job is stored and answered 200 `{ received: true, finished: true }`, and changes nothing. The worker's tick queues again any update not applied within a minute (a crash between storing and queueing). A body that does not parse is 400. | Gap map ("store the callback once, as inbound_events does"); WhatsApp webhook pattern (verify → store once → queue). |
| 7 | **Polling.** A kind with `poll` is polled by the worker every `pollEveryMs` (default 30 s) after its last update, once it has an external id. A callback pushes the next poll back, so polling is only a fallback when both exist. The `jobs.tick` schedule (every 10 s) leases due rows (`FOR UPDATE SKIP LOCKED`) and calls `poll(ctx)`. A `JobUpdate` it returns is stored (source `poll`) and applied; `null` means no news. A poll that throws is logged and tried again at the next interval. | Plan ("a polling fallback"); gap map ("for providers without callbacks"). |
| 8 | **Applying an update**, under a row lock: |  |
|   | - `running` with `progress` (0–100, kept as a whole number) and/or `message` (up to 500 characters). Progress only goes up: a lower value is ignored, so updates that arrive late or out of order change nothing. A `job.progress` event is stored only when the whole percentage rises or the message changes. Progress updates are not audited; `app.job_updates` is their log. |  |
|   | - `succeeded` with `output` and `files`. `output` must parse with the kind's `output` schema, or the job fails with `bad_output`. Files arrive as `{ name, mime, data }` (base64) or `{ name, mime, url }`. A URL is fetched by the kind's `download` (for a provider that needs credentials) or by the framework's guarded fetch (decision 10). Each file is stored by `FilesService.storeBytes` as a server file, at most `maxFiles` (default 20) and each within `FILES_MAX_BYTES`. The files are then attached to the job (`resource_type 'job'`, field `results`) in the transaction that marks it succeeded. A file that cannot be fetched or stored fails the apply, which is retried 3 times and then fails the job with `result_unavailable`. |  |
|   | - `failed` with `{ code?, message }`, or `cancelled`. |  |
|   | A finished job never changes again: the first finishing update wins. | Plan ("progress events", "result files through B1"); default (monotonic progress). |
| 9 | **Deadlines.** Every kind declares `timeoutMs`; the framework sets no default, because how long a job may take is the kind's business. The tick fails unfinished jobs past their deadline with `timed_out` and asks the service to stop (`cancel`, best effort, on the `jobs.cancel` queue). | Boundary rule (durations are declared, not framework constants); fail closed. |
| 10 | **Fetching result URLs.** The default download takes `https` URLs only. It resolves the host first and refuses loopback, private, link-local and unique-local addresses. It follows no redirects, stops at the size cap, and gives up after 60 s. `JOBS_ALLOW_PRIVATE_URLS=1` lifts the address check and allows `http`, for development against local services; production refuses to start with it. A kind whose files need credentials gives `download`. | Default, fail closed (SSRF); B10's shared SSRF guard is not merged, so this one is local to the feature (Deferred). |
| 11 | **Who reaches a job.** Always within the same business (the query is tenant-scoped). For a job about a record: anyone who reaches that record through the entity's scoped repo (its access, grants and plugins); an agent also needs the entity's `get` exposed to it. For a job about no record: only the person, or contact, it was started for (the assistant acting for them included). A system principal of the business reaches every job. Anything else is 404. The starter does not keep a separate right to an about-record job: losing the record loses the job. | Task ("another tenant gets 404"); B1 decision 7 (reach through the owning record). |
| 12 | **What a reader sees.** A job leaves the server as `JobInfo`: `id`, `kind`, `status`, `progress`, `message`, `about`, `input`, `output`, `error`, `files` (ids), `createdAt`, `updatedAt`, `submittedAt`, `finishedAt`, `deadlineAt`. It then passes the read projectors as resource type `job`, so an application can hide fields from some readers, such as an output's cost. The external id, the lease, the attempts and the callback secret never leave the server. Events store the same `JobInfo` as their row, so `eventFor(event, p)` projects them in the same way. | Task ("hidden fields stay hidden"); F3 decision 19. |
| 13 | **Result files** are reached through their job. The files feature gains a small registry, `fileHolders`: a resource type that is not an entity and keeps files (the jobs feature registers `job`). `FilesService.reaches` asks the holder when the type is no entity. The holder answers yes only when the reader reaches the job and the job, as projected for them, still lists the file. So `GET /api/files/:id`, `?ids=` and `<FileThumbs>` work for results, and a hidden field hides its files, as B1 decision 7 does. A result file cannot be put on a record (B1's attach hook refuses a file on another holder). `complete` gets `copyFile(id)`, which stores a copy as a server file that a system write can attach. | B1 decisions 7, 10 and 25; default (one owner per file). |
| 14 | **Writing results back.** `complete(ctx)` runs after the success commits, in the worker, through the framework's subscriber `jobs.complete` on `job.succeeded`. It runs at least once, up to 5 times with backoff. `ctx.principal` is `systemPrincipal({ tenantId, job: <kind>, runId: <job id> })`. `ctx.write(op, input)` is `runWrite` as that principal, with the idempotency key `job:<id>:<n>` (the n-th write of the hook), so a retried hook's earlier writes return their first result instead of writing again. The job records `completion` (`pending`, `done` or `failed`) and the last error. A completion that fails does not change the job's status. | F4 `systemPrincipal`; F5 subscribers (durable, retried); CLAUDE.md rule 1. |
| 15 | **Cancelling** is for people (`HumanOnlyGuard`): `POST /api/jobs/:id/cancel`. It needs reach, and either being the person the job was started for or being allowed to update the about record (`def.decide(p, 'update', row, {})` not `deny`). A finished job is 409 `already_finished`. Cancelling is audited (`job.cancel`) and stores `job.cancelled`. The service is then asked to stop through the `jobs.cancel` queue, best effort and retried. The assistant cannot cancel; it reads jobs. | Default: least privilege for agents (B1 decision 6). |
| 16 | **Audit.** `job.start` (the starter, in the write's transaction), `job.submit`, `job.succeeded`, `job.failed`, `job.cancel` (a person), `job.cancelled` (the service said so) and `job.timeout` rows, resource type `job`. Background steps are audited as actor `system`, with the kind as the actor id, channel `background` and the job id as the run id. Progress is not audited. | B1 decision 24 (infrastructure rows audited by their feature). |
| 17 | **Events** (`app.domain_events`, through `recordEvents` in the change's transaction): `job.queued`, `job.running`, `job.progress`, `job.succeeded`, `job.failed`, `job.cancelled`. The resource type is `job` and the row is the `JobInfo`. Live updates (B15), webhooks (B10), agent triggers (A6) and resumes (A7) subscribe to these. Nothing in B11 notifies a person. | Plan ("progress events"); F3/F5 outbox. |
| 18 | **Personal data.** "Delete my data" erases the jobs about no record that were started for the subject: their input, output, message and error are cleared, their result files are erased (the files sweeper deletes the objects), and unfinished ones are cancelled with `erased`. Jobs about a record are the business's and stay. The export lists every job started for the subject. | F5 decision 25; B1 decision 21. |
| 19 | **The assistant** gets `get-job` (one job's status, progress, message, error and result file ids) and `list-jobs` (`entity` and `id` for a record's jobs, `status`; without a record, the jobs started for the person). Both call the HTTP API as the agent, so the reach rules above apply. Scripted-model set `jobs` (order 310): "how is job <id>" and "which jobs are running". | Task ("add scripted-model scripts for new tools"). |
| 20 | **App.** `@hykr/api-client`: `api.jobs.get(id)`, `api.jobs.list(q)`, `api.jobs.cancel(id)`. `@hykr/app`: `useJob(id)` (every 2 s until it finishes), `useJobs({ entity, id })`, `useCancelJob()`, and `<JobProgress job onCancel? />` (status, bar, message, error and result files through `<FileThumbs>`). The polling stays when the live plugin is installed (decision 23): the hooks cannot tell whether a stream is open, and a missed event must not leave a job stuck on screen. | Gap map ("Progress to the UI: … a react-query poll"); default (works without B15's plugin). |
| 21 | **Configuration** (read when called, like B1's): `JOBS_SECRET` (at least 32 characters when set), `JOBS_PUBLIC_URL` (the API's address that callbacks are posted to; default `BETTER_AUTH_URL`), `JOBS_CALLBACK_TOLERANCE_S` (300), `JOBS_ALLOW_PRIVATE_URLS` (off). The tick (10 s), the poll interval default (30 s), the submit timeout and the retry counts are technical defaults; each kind can override its own. | Default; no business values in the framework. |
| 22 | **The fixture** (`framework/api/test/fixture/src/features/jobs/`): a `drawings` module with an entity `drawing` (a title, a preview image field and a page count) and two kinds. `fixture.render` is about a drawing: callbacks, inline and URL result files fetched with its own `download`, `cancel`, and a `complete` that puts a copy of the first result on the drawing's preview and its page count on the drawing. `fixture.convert` is about no record and is polled only. `fixture.export` has no service: `submit` does the work as its starter and returns its file as bytes. The commands `drawing.render` (the assistant's start waits for approval), `drawing.convert` and `drawing.export` start them. A read projector hides `output.cost` from staff. A stand-in external service in the test records submissions, posts signed callbacks and answers polls. | Task ("Sample demo: fixture with a stubbed external service"); plan ("B11 and B19 are shown in fixture tests"). |
| 23 | **Live updates** (B15, merged after this unit started). The jobs feature contributes a `liveResources` check for the type `job`: a stream hears of a job's event only when its person reaches the job now (`JobRunner.reachable`, the same check as `GET /api/jobs/:id`). Like every live event, it carries the name, type and id only, never the message, input or output. The app's `liveKeysFor` maps a `job` event to the `['jobs']` query key, so `useJob` and `useJobs` refetch on it. | B15 (A9B15 decisions: non-entity types register a `liveResources` check); task ("hidden fields stay hidden"). |

## Assumptions to review

| Topic | What we chose | Question for the product owner |
|---|---|---|
| Who may start a job | The application's own command decides (role, capability, approval); the framework only checks reach | Should outside compute (renders, plan reading) need an approval, or a credit check (A3), before it starts? |
| Results onto records | Results stay on the job; `complete` copies what a record should show | Should a result ever change records with no one reviewing it first? |
| Who sees a job | Whoever reads its record; the starter for jobs about no record | Should owners and admins see every job of the business (an operations view)? |
| Cancelling | People only; the starter or someone who may edit the record | May the assistant cancel a job it started? |
| Deadlines | Declared per kind; the framework has no default | What are the expected durations (the PRD: Blender stills 2–14 minutes, plan reading 99–258 seconds)? |
| Notifications | None; events exist | Should the person be told when a job finishes (push, WhatsApp, in-app)? On which channel? |
| Erasure | Jobs about no record are erased; jobs about a record stay | Is a job's input (a floor plan, a brief) personal data of the person who started it? |
| Retention | Jobs and their result files are kept until erased | How long should finished jobs and their results be kept? |
| Callback scheme | Our own signature header by default; per-kind `verify` for a provider's | Which providers (render farm, vision model) are planned, and how do they sign webhooks? |

## API sketch

```ts
// @hykr/contracts
JobStatus            // 'queued' | 'running' | 'succeeded' | 'failed' | 'cancelled'
JobInfo              // what a reader sees (decision 12)
JobUpdate            // { status: 'running', progress?, message? }
                     // | { status: 'succeeded', output?, files?: JobResultFile[], message? }
                     // | { status: 'failed', error: { code?, message } } | { status: 'cancelled', message? }
JobResultFile        // { name, mime, data?: base64, url? } (exactly one of data and url)
ListJobsQuery        // { entity?, id?, kind?, status?, limit? }

// @hykr/db
jobs, jobUpdates     // app.jobs, app.job_updates

// @hykr/api
defineJob<I, O>(def): JobDef<I, O>;  jobDefs (registry, contributes: { jobs })
startJob(tx, p, def, input, { requestId? }): Promise<JobInfo>
JobRunner            // Nest provider: get, list, cancel, receive, apply, tick, complete
signJobCallback(secret, rawBody, t?) / verifyJobCallback(secret, rawBody, header, now?)
jobsConfig()
fileHolders          // (files feature) { type, reaches({ p, resourceId, field, fileId, db }) }

// HTTP
GET  /api/jobs?entity=&id=&kind=&status=&limit=   { items: JobInfo[] }
GET  /api/jobs/:id                                 JobInfo
POST /api/jobs/:id/cancel                          JobInfo (people only)
POST /api/jobs/:id/callback                        202 { received } | 200 duplicate/finished | 401 | 404

// @hykr/api-client
api.jobs.get(id), api.jobs.list(q), api.jobs.cancel(id)

// @hykr/app
useJob(id), useJobs(q), useCancelJob(), <JobProgress job onCancel? />
```

## Test plan

- `framework/api/test/framework/jobs.test.ts` (unit, no boot): signing and verifying (good,
  tampered body, wrong secret, stale and future timestamps, malformed header), the per-job
  secret, `defineJob`'s refusals, `JobUpdate` parsing, and the URL guard (http, loopback,
  private, link-local, IPv6, allowed with `JOBS_ALLOW_PRIVATE_URLS`).
- `framework/api/test/framework/jobs.e2e.test.ts`, against the fixture's `drawings` module and a
  stand-in external service:
  - work done in the worker (`fixture.export`): progress, read as its starter (another business's
    export counts none of ours), its file kept on the job; a callback cannot name stored files;
  - a person starts a render: queued, audited, `job.queued` stored; submitted with a callback
    URL and secret; the service's signed progress posts move it on (event per step, late and lower
    progress ignored); success with an inline and a URL file: files stored, kept on the job,
    served to a colleague; `complete` puts a copy on the drawing's preview, as the system;
  - callbacks: a bad signature, a stale timestamp, another job's secret (401); an unknown job
    (404); a repeat (duplicate, applied once); after the job finished (changes nothing);
  - another business: 404 on get, cancel and the job's files, absent from lists, and its record
    cannot be named in a start (404);
  - a field hidden from staff: `output.cost` is hidden in get, list and the event as projected
    for staff;
  - the assistant's start is parked and audited; once approved, the job runs; the assistant
    reads the job through `get-job` and `list-jobs`, and cannot cancel;
  - polling: the convert job has no callback (its callback is 404), is polled to success by
    the tick, and only its starter reaches it;
  - deadline: a job past its deadline is failed `timed_out` and the service is asked to stop;
  - cancel by the starter: cancelled, audited, the service is told; again: 409;
  - submit failures retry and then fail the job `submit_failed`; a result URL to a loopback
    address with the default download fails the job `result_unavailable`; bad output fails it
    `bad_output`;
  - live updates: the starter and a colleague who reads the drawing hear a render's events, as
    ids only; a colleague hears nothing of a job about no record started for someone else, and
    another business hears nothing;
  - "delete my data" erases a personal job's input and its files; export lists jobs.
- Unchanged and green: the existing framework suites (`files.e2e` included).

## Deferred

- A generic start route (`POST /api/jobs`) and a generic start tool: each application starts its
  kinds through its own commands.
- Notifying the person when a job finishes, and parking an assistant run until a job finishes
  (A7 can subscribe to `job.succeeded`).
- Stopping the 2 s poll while a live stream is open (decision 20).
- A shared SSRF guard and HMAC helpers in `@hykr/connectors` (B10): the feature keeps its own for
  now.
- Retention of finished jobs and their files (B18), and an operations view of every job of a
  business.
- Moving a result file onto a record without copying it (B1 keeps one owner per file).
- Telling the service to stop when "delete my data" cancels a job.
- Metering outside compute per business (A3).
